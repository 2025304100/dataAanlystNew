## 1. 文档概述

### 1.1 目的

本文档是"机会中心、标的研究、组合交易改造"的**详细开发计划**。每个工作包都分解为可执行的子任务，包含：

- 具体的代码改动描述
- 涉及的文件路径和修改方式
- 数据库迁移脚本要点
- API 接口规格
- 前端组件拆分方案
- 测试用例清单
- 验收标准

### 1.2 当前项目技术栈

| 层级 | 技术 | 说明 |
|------|------|------|
| 前端 | React 18 + TypeScript + Ant Design 5 + ECharts 5 | Vite 5 构建，Vitest 测试 |
| 后端 | FastAPI + SQLAlchemy ORM | 统一路由 `/api/v1`，支持 SQLite/MySQL 热切换 |
| 因子仓库 | DuckDB | 本地列式分析 |
| 数据源 | AkShare + 通达信 | 多源回退链 |
| 异步任务 | 应用内持久化任务 + 后台 worker | 心跳、取消、进度 |
| 定时任务 | 应用内跨平台调度器 | 每日/每周/间隔/启停/编辑/运行历史 |

### 1.3 改造约束

1. 数据库迁移只允许增量加表、加字段、加索引和回填，**不删除现有业务数据**
2. 第一阶段不改变自动交易和组合回测的实际数据来源，只增加新页面和关联状态
3. 新链路完成回填与验证后，再逐步切换自动交易和组合回测
4. 旧接口至少保留一个兼容周期，前端迁移完成前不得直接删除
5. 所有状态流转必须经过后端服务和事务
6. 历史订单、成交、回测、规则版本和收益曲线不可因重构被覆盖
7. 当前 `core` 观察池、现有组合、持仓和模拟交易记录必须无损保留
8. 新表和查询必须同时兼容 SQLite 与 MySQL

### 4.2 详细子任务

#### 4.2.1 新增功能开关配置

**文件**：`app/core/config.py`

在 `Settings` 类中新增：

# 功能开关（默认关闭）
opportunity_center_enabled: bool = False
portfolio_members_enabled: bool = False
auto_trade_member_source_enabled: bool = False
portfolio_backtest_member_source_enabled: bool = False
```

支持通过环境变量覆盖：
- `OPPORTUNITY_CENTER_ENABLED=true`
- `PORTFOLIO_MEMBERS_ENABLED=true`
- `AUTO_TRADE_MEMBER_SOURCE_ENABLED=false`
- `PORTFOLIO_BACKTEST_MEMBER_SOURCE_ENABLED=false`

**操作步骤**：
1. 在 `app/core/config.py` 的 `Settings` 类中添加 4 个布尔字段
2. 设置默认值：新页面开关可在开发环境通过环境变量开启，自动交易和回测新来源默认关闭
3. 在 `app/api/router.py` 中新增 `GET /api/v1/system/feature-flags` 端点，返回当前开关状态

#### 4.2.2 建立 Alembic 迁移

**文件**：`alembic/versions/<new_revision>_wp0_baseline.py`

**操作步骤**：
1. 运行 `alembic revision -m "wp0_baseline"` 创建新迁移
2. 在新迁移中不做表结构变更，仅记录当前 schema 版本
3. 确保 `alembic upgrade head` 和 `alembic downgrade -1` 可正常执行

#### 4.2.3 扩展 init_db.py 兼容迁移

**文件**：`app/db/init_db.py`

**操作步骤**：
1. 新增 `_ensure_wp0_baseline()` 函数，函数体为空（仅作为版本标记）
2. 在 `init_db()` 中调用此函数，确保后续 WP 的列升级可在此版本之上执行
3. 确保 SQLite 新库/旧库升级、MySQL 旧库升级均可正常启动

#### 4.2.4 旧 URL 兼容映射

**文件**：`frontend/src/App.tsx`

**操作步骤**：
1. 在 `activeTab` 切换逻辑中增加兼容映射：
   - `activeTab="investment"` → 跳转到新的标的研究路由（WP5 完成后）
   - `activeTab="portfolio"` → 保持兼容，显示名称改为"组合交易"
2. 在 `AppContext` 中增加 `featureFlags` 状态，从 `/api/v1/system/feature-flags` 加载
3. 根据 `opportunityCenterEnabled` 控制"机会中心"标签是否显示

    async def fetch(
        self,
        interface_key: str,          # 接口标识，如 "akshare_stock_daily"
        request_params: dict,         # 请求参数
        freshness_requirement: timedelta,  # 新鲜度要求

**处理流程**：

```
1. L1 进程缓存查询（秒/分钟级 TTL）
   ↓ miss
2. L2 业务数据库查询（检查新鲜度）
   ↓ miss 或 过期
3. L3 DuckDB/快照查询
   ↓ miss 或 过期
4. 检查接口熔断状态
   ↓ 未熔断
5. 单飞去重（相同 interface_key + params 同时只允许一个真实请求）
   ↓
6. 按 SourceChain 尝试主源 → 备用源
   ↓
7. 幂等 UPSERT 入库
   ↓
8. 返回统一结果
```

def run_fast_scan(db, scope: str, min_score: float, 
                  indicator_plan_id: int = None,
                  portfolio_id: int = None) -> dict:
    """
    快速扫描：从 ready 快照读取，5 分钟内完成
    """
    # 阶段1: 快照与数据健康预检（10s）

    if not snapshot:
        raise AppError("DISCOVERY_SNAPSHOT_NOT_READY", ...)
    
    # 阶段2: SQL 粗筛（30s）
    # 在 snapshot_items 上完成分数阈值、资产类型、阶段、动作、可信度过滤
    # 按 priority_score 降序取 Top 300
    top_candidates = _coarse_filter(db, snapshot.id, min_score, limit=300)

        候选/观察项直接加入组合
        事务内操作：
        1. 创建 portfolio_member（WP4 后生效）
        2. 更新源对象状态（candidate → "portfolio" / observation → "promoted"）
        3. 创建 transition_event
        4. 提交事务
        """
    
    def exclude_candidate(
        self, db, candidate_id: int, reason: str = None
    ) -> TransitionResult:
        """排除候选"""
    
    def restore_candidate(
        self, db, candidate_id: int
    ) -> TransitionResult:
        """恢复候选"""
    
    def expire_candidates(
        self, db, candidate_ids: list[int]
    ) -> TransitionResult:
        """批量过期候选"""
    
    def archive_member_to_observation(
        self, db, member_id: int, watchlist_id: int
    ) -> TransitionResult:
        """组合成员归档后回到观察状态"""
```

**关键约束**：
- 单事务写入业务对象和关联状态
- 幂等键防止双击、重试或网络超时产生重复关系
- 来源快照和操作者类型（`user`、`system`、`migration`）
- 明确的旧状态、新状态、原因和时间
- 失败回滚，不允许出现半状态

def _get_buy_candidates_from_members(db, portfolio_id, limit=10):
    """从有效 auto 成员中获取买入候选"""
    members = db.query(PortfolioMember).filter(
        PortfolioMember.portfolio_id == portfolio_id,
        PortfolioMember.status == "active",
        PortfolioMember.execution_mode == "auto",
        PortfolioMember.effective_from <= today,
        or_(
            PortfolioMember.effective_to.is_(None),
            PortfolioMember.effective_to >= today
        )
    ).all()
    
    candidates = []
    for member in members:
        # 跳过已有持仓的成员
        existing_position = db.query(Position).filter(
            Position.portfolio_id == portfolio_id,
            Position.symbol_id == member.symbol_id
        ).first()
        if existing_position:
            continue
        
        # 查最新 Score
        score = _latest_score_for_symbol(db, member.symbol_id)
        if not score or score.action not in ("open", "buy_dip"):
            continue
        
        # 数据健康检查
        if not _check_data_health(db, member.symbol_id):
            continue
        
        # 组合风控检查
        budget = compute_position_budget(db, portfolio_id, member.symbol_id)
        if not budget.can_open:
            continue
        
        candidates.append({
            "member": member,
            "score": score,
            "budget": budget
        })
    
    return candidates[:limit]

#### 12.2.4 双轨安全切换

**切换流程**：

```
1. AUTO_TRADE_MEMBER_SOURCE_ENABLED=false
   → 旧来源实际执行，新来源仅 Dry Run 对比
   
2. 连续至少 5 个交易日或 3 次有效运行
   → 保存旧/新买卖集合差异
   → 对每个差异给出原因：成员缺失、状态暂停、信号不同、数据过期、风控阻断
   
3. 差异经人工确认后
   → 先对一个非默认测试组合开启新来源
   
4. 逐组合切换
   → 开关关闭可立即回退旧来源
   
5. 旧来源至少保留一个发布周期
```

#### 12.2.5 安全门禁

1. 数据是否过期或缺失（fail-closed，禁止买入）
2. 组合与成员是否启用
3. 公式版本是否有效
4. 可用现金、现金保留和目标仓位
5. 单股、行业、资产类型和总仓位上限
6. 最大持仓数
7. A 股 T+1、整手、涨跌停和停牌规则
8. 重复信号和幂等订单键（client_order_key）

def _get_members_for_date(db, portfolio_id, trade_date):
    """按交易日读取当时有效成员"""
    members = db.query(PortfolioMember).filter(
        PortfolioMember.portfolio_id == portfolio_id,
        PortfolioMember.effective_from <= trade_date,
        or_(
            PortfolioMember.effective_to.is_(None),
            PortfolioMember.effective_to >= trade_date

#### 16.2.3 Outbox 与异步发送

**流程**：

```
业务事件/AlertEvent
→ 匹配推送策略
→ 同事务写 notification_outbox
→ 后台 dispatcher
→ 渠道适配器
→ delivery 记录
```

**发送规则**：
- `event_key + channel_id` 唯一，防止任务重试造成重复推送
- 超时和临时错误使用指数退避
- 鉴权失败或配置失效直接暂停该渠道
- 一个渠道失败不影响其他已选渠道
- dispatcher 重启后继续处理未完成 Outbox

**安全与隐私约束**：

1. **内容脱敏**：消息只包含必要标的、状态和跳转 ID，不推送数据库连接、Token、完整策略配置或技术堆栈
2. **模板转义**：所有模板变量做转义，防止 Markdown/Webhook 注入
3. **内容超限处理**：第三方内容长度超限时自动摘要，并在站内保留完整详情
4. **手动重发**：用户可对失败记录手动重发，但继续使用同一业务事件审计链（`event_key` 不变）
5. **OneBot 风险说明**：个人 QQ 没有适用于所有账号的稳定官方直推接口，第一版不写死非官方服务。系统提供 OneBot/兼容 Webhook 适配器，由用户自行配置
6. **站内消息默认**：站内消息不需要第三方配置，默认可选
7. **渠道状态生命周期**：`unconfigured` → `configured`（已配置）→ `tested`（测试成功）→ `active`（已启用）；测试失败或鉴权失效时回到 `configured`

## 22. 回滚边界（原文档第15.4章）

**允许（安全操作）**：
- 关闭 WP0 功能开关，新页面回到旧入口
- 功能开关关闭后，N+1 次请求内恢复旧逻辑
- 迁移脚本可重复执行，不会因重复执行导致数据重复或丢失
- 旧表的现有列不会被删除，即使在迁移脚本中新增了列

**禁止（危险操作）**：
- 在迁移脚本中删除旧列、重建现有业务表或改写历史记录 ID
- 在迁移脚本中回填默认值覆盖用户的真实业务数据
- 迁移失败时进入半迁移状态（必须通过事务回滚全部写入）
- 在功能开关关闭期间调用新接口的写操作

**分阶段双轨运行 6 个步骤**（原文档第15.2章）：

```
步骤 1: 新来源仅 Dry Run（可读，不写入）

步骤 3: 连续验证 N 个交易日/运行无差异
步骤 4: 对差异生成解释报告
步骤 5: 逐组合/逐功能切换新来源
步骤 6: 旧来源保留至少一个发布周期后移除
```
