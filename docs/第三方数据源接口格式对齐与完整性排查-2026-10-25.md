# 第三方数据源接口：格式对齐与数据完整性排查报告（2026-10-25）

> 起因：接口管理页（第三方接口状态）中东财三个接口失败/高失败率，用户发现"有些数据源有些接口会缺数据，导致导入脏数据"。
> 本文回答两个问题：**①三源（东财/新浪/腾讯）的格式能保证对齐统一吗？②数据完整性有保障吗？**
> 排查方式：代码走读（三个方向并行）+ 验证库 `gpfx_validation`（MySQL 5.7.26）只读实测。
> 实测脚本：`tmp/audit_kline_quality.py`、`tmp/audit_kline_quality_2.py`、`tmp/audit_kline_quality_3.py`（均只读）。
> 与《验证环境自动接管四红点排查与修复-2026-10-25》的 H2/H3/H4/H5 相互印证。

---

## 一、结论摘要（TL;DR）

| 问题 | 回答 |
|---|---|
| **格式对齐能保证吗？** | **主路径能，例外通道不能。** 股票日K三源已通过"共享归一化 + 单位契约 + 跨源守卫"统一（`cn-stock-shares-v1`）；但**指数路径完全没进这套体系**（三套独立归一化、腾讯 amount 语义错位、无契约），且**存量旧数据中成交量"手/股"混存已实测坐实（universe 2026 年 50.7 万行 + daily_bars 2026 年 59.7 万行）**。 |
| **数据完整性能保证吗？** | **不能。** 写入前的行级校验很硬（脏 OHLC 进不来，实测 2024-11 之后零脏 OHLC），但"**空结果/缺交易日**"被当成合法结果：空帧标 `is_synced=1`、`empty` 计入成功计数、无交易日历完整性对账、覆盖率台账只记不补、所有修复通道都是手动。实测 **1713 个标的自 10-19 起静默停更且全部被标"已同步"**，上证指数 000001 停更 2.5 个月。 |
| **脏数据的真实来源** | 不是"校验放过了坏值"，而是 **①单位换算漏洞期写入的存量行无人纠错**（增量同步起点=`latest_bar+1`，修复后旧行不会被重写）＋ **②源缺数时的静默缺失**（不报错、不记缺口、不自动补）。 |

## 三、格式对齐现状

### 3.1 股票日K：已统一，残留 3 处细节差异

三源归一化后统一为 `trade_date / OHLC / volume(股) / amount(CNY) / turnover(百分点)`，由共享函数 `standard_history_frame`（`app/services/market_data_sources/sources/_normalize.py:36-56`）＋ 单位契约 `cn-stock-shares-v1`（写入时 `history_source_tag` 校验，`market_history_contract.py:104-123`）＋ 跨源守卫（`history_source_guard.py:10-31`，禁止 B 源覆盖 A 源已存行）保证。单位换算：东财成交量手→股 ×100（`_normalize.py:82`），腾讯按代码族 688=股/其余=手经契约换算（`market_history_contract.py:80-101`），新浪原生股免转换。复权：生产强制 qfq（`market_history_contract.py:136-141`）。

残留差异（低危）：
1. **新浪 qfq 价格唯一做 round(2)**（`sina_history.py` 严格解析器），东财/腾讯不舍入——同一标的两源相邻日的价差可能引入 ±0.005 噪声；
2. **腾讯行的 amount/turnover 恒为 NULL**（`_normalize.py:180-181`，契约明确禁止用量×价估算）——同表内不同日期行的字段完整度依来源而异，实测 129 行（universe）+98 行（daily_bars）；
3. **空帧契约不一致**：东财空帧不挂 history_contract（`_normalize.py:61-62`），新浪/腾讯空帧挂（`_normalize.py:125,160`）。

### 3.2 指数日K：完全没进统一体系（本次最重要发现之一）

`app/services/index_data.py` 用三套**独立**的轻量归一化（`_normalize_eastmoney_frame:120-143`、`_normalize_sina_frame:146-158`、`_normalize_tencent_frame:161-173`），**无共享契约、无单位换算、无 dropna、无复权概念**，直接写 `index_prices`：

- **腾讯 `stock_zh_index_daily_tx` 的第六列名为 amount、实为成交量**，被原样写入 `IndexPrice.amount`（`index_data.py:161-173` + 写入 `:387-399`），与东财 amount=成交额（元）**同列不同义**；
- 新浪无 amount 列 → 写 NULL；腾讯无 volume 列 → 写 NULL。
- 实测 `index_prices`：sina 12127 行中 12120 行 amount 为 NULL；仅有的东财行 amount≈4.0e11（成交额量级）。目前腾讯行 0 行是运气好，一旦腾讯备源生效，`amount` 列将混入成交量量级的值，**任何按 amount 画图/算指标的代码都会被污染**。

### 3.3 ETF 日K：对齐良好，校验最严

东财（手→份额 ×100，契约 `cn-etf-shares-v1`）与腾讯（原生份额，不做 ×100）量纲一致；腾讯 ETF 有**双请求核验**（qfq 与 raw 同时下载、日期与量额必须完全一致，`tencent_history.py` ETF 分支）＋**写前衔接校验**（≥3 个重叠交易日、价格容差 0.0005、量 50 份、额 0.01 元，不符整批拒写 `ETF_QFQ_BASIS_UNVERIFIED`，`etf_sync_validation.py:24-86`）。新浪 ETF 透传无换算、无契约，但被"生产强制 qfq"挡在生产写入之外（`AS:160-161`）。实测库内 ETF 行（baostock 1277、em 3、tx 3）全部干净。

### 3.4 两条无契约透传路径（当前被挡住，属隐患）

新浪 ETF（`normalize_cn_etf_sina_history`，仅不复权）与 TDX（volume 不推断股/手、价格 /100、无复权）：若经 `external_data_gateway.py:447` 等调用方显式传 `adjust=""`，会流出无契约标签的帧（`history_source_tag` 契约缺失时返回裸 `"akshare"`，`market_history_contract.py:110-112`）——**存量 `source='akshare'` 行就是这么来的**。

## 四、完整性现状

### 4.1 写入侧的硬校验（有效，实测验证）

- DailyBar/universe 写前**整批校验**：OHLC 有限且>0、`low<=min(open,close)<=max<=high`、volume/amount/turnover≥0 有限，任一违反整批拒绝（`market_data.py:408-421`、`universe_sync.py:588-598`）；
- 指数：批量预校验"缺日期/越界/OHLC 边界"整批抛（`index_data.py:322-336`），但**实际写库循环逐行 try/except 跳过坏行**（`:403-408`）→ 存在部分写入可能；
- upsert＋唯一约束＋每 symbol 单事务：实测两表 `(symbol, trade_date)` **重复行 0**。

### 4.2 缺口如何静默产生（5 个漏洞，均有代码位置）

| # | 漏洞 | 位置 | 后果 |
|---|---|---|---|
| V1 | **空帧直接标 `is_synced=1`**（注释："可能是退市/停牌"），增量同步此后按 `last_bar_date` 判"已最新" | `universe_sync.py:699-704, 822-833` | 源临时缺数被永久视为已同步，不再有任何告警 |
| V2 | **`status=="empty"` 计入 ok_count 并 commit**，不记 failed batch、不升级告警 | `market_data_sync_task.py:201-203` | "源返回空而非抛错"静默通过 |
| V3 | **日K写入无交易日历完整性校验、无行数下限**（唯一下限是 ETF 备源 ≥3 重叠日） | 全局 | 源少给几天就少写几天，不产生缺口记录 |
| V4 | **覆盖率台账只记"确认点"，不触发补数**；全部修复通道（backfill/range-repair/field-repair/gap-repair）均为手动 API | `sync_coverage.py:1-6`、`universe_sync_task.py:1395-1457` 等 | 无任何自动缺口检测调度（`scheduled_tasks.py` 仅三条日更同步） |
| V5 | **增量同步起点=`latest_bar+1`**，对"行已存在但字段 NULL"无效；range-repair 不能按标的过滤 | `universe_sync.py:657`（H4） | 换手率等缺失字段永远无法自动回补 |

### 4.3 接口失败的处理：不产生脏写，但产生"静默缺失"

- 调用失败：任务 rollback、failed_count+1、记 errors_json（`market_data_sync_task.py:205-226`），**不会**清空或覆盖已有数据，也不会标已同步——这部分是安全的；
- 但 `universe_symbols.sync_failed>=5` 熔断后该标的被**直接跳过**（`universe_sync.py:669-670, 775-780`，实测 41 个标的熔断中），且没有任何面板提示"这些标的已停止同步"；
- registry 的 `record_call_result` 只累加统计（`akshare_registry.py:667-727`），**连续 125 次失败也不会自动停用或降权**；`enabled` 唯一写入口是人工 PUT（`akshare_apis.py:588-627`）；
- "探测"只验证**结果非空**（`akshare_apis.py:462-466`），不校验列名/行数/dtype——探测通过 ≠ 格式正确。

## 六、其他发现

### 6.1 `sync_write_policy.py` 名不副实
它不拦截任何写入，只是"只补缺不改值"助手（`sync_write_policy.py:16-37`）。真正的写入拦截在 `history_source_guard.py`、`etf_sync_validation.py` 和 data_quality 的隔离机制——但**质量门/隔离（`data_quality.py:322-505`）未被接入日更链路，仅测试调用**；生产在用的只有事后快照（`capture_field_quality_snapshots`，失败也只 warning）。

### 6.2 质量快照不覆盖日K完整性
`capture_field_quality_snapshots` 只统计字段 NULL 覆盖率，**没有"每标的期望交易日 vs 实有行"的对账**；`source_field_integrity.py` 有 `source_behind_calendar` 告警但只是只读报告、不拦不补。

### 6.3 截图错误成因
- `index_zh_a_hist` 的 `ValueError: I/O operation on ...`：`quiet_akshare_output`（`akshare_utils.py:13-18`）用进程级全局的 stdout/stderr 重定向且**非线程安全**，批量探测（前端 3 并发 × 8 worker 线程池）与同步任务线程并存时，一个线程退出上下文关闭 sink，另一线程仍向其写 → closed I/O；叠加 akshare 默认无 timeout 的历史问题（已用 timeout+Connection:close 缓解，`akshare_utils.py:60-68`）。
- 129 调 125 失败仍继续：计数按调用链记（链内最多 3 次 HTTP 重试），每 symbol 独立循环、失败只 failed_count+1 继续下一个（`index_prices_sync_task.py:179-188`），且这些路径**绕过网关熔断器**（熔断只护 gateway L4）。

## 七、修复建议（按优先级）

### P0（脏数据存量 + 静默停更，建议本周）
1. **存量手单位行修复**：以 `ABS(amount/(volume*close)-1)>10` 圈出候选行（universe 约 50 万行、daily_bars 约 60 万行，需排除送转导致的 2-20 倍正常偏离），用 range-repair 定向重拉；**前提是给 range-repair 加 `symbol_ids` 过滤参数**（今日文档 §3.1-2 已提出）。
2. **空帧不标已同步**：`universe_sync.py:699-704` 空帧时不再置 `is_synced=1`（或置 2=空结果待复核），并在数据健康面板暴露"停更标的数"；`market_data_sync_task.py:201-203` 的 empty 单独计数告警。
3. **每日指数同步覆盖全部基准指数**：`scheduled_tasks.py:112` payload 改为列表（至少 000001/000300/000905/399006/399001/000016/000688），`index_data_task.py` 支持 symbols 列表（手动入口已支持，`index_prices_sync_task.py:64-97`）。

### P1（防再犯）
4. **日K交易日历对账任务**：新增每日调度——按 trade_calendar 对每标的比对"应有多少行/实有多少行"，缺口入表并自动触发 backfill（复用 `get_external_data_gaps` 的思路，`external_data_sync_task.py:568-651`）。
5. **增量同步补 NULL 字段**：对"近 N 日内 turnover_rate/amount IS NULL 且行已存在"的标的做补偿性重拉（对应 H4/建议 2）。
6. **回退源字段级降级保护**：upsert 时低质量源缺失字段保留原值（MySQL `COALESCE(VALUES(x), x)` 配合 source 标签判断）（对应 H5/建议 3）。
7. **接口连续失败自动处置**：registry 统计已有（total_failures），加"连续 N 次失败→临时停用+告警"，并把 `quiet_akshare_output` 改为线程本地重定向或加锁（修 closed I/O）。
8. **指数写入并入统一契约**：腾讯指数 amount 改入 volume（或加 `index-shares-v1` 契约），三套归一化收敛到共享 `standard_history_frame`；存量 `index_prices` 的腾讯语义行需甄别清理。

### P2（观测加固）
9. 探测增加 schema 校验（列集合 + 行数下限 + dtype），探测通过才允许启用；
10. 把 `data_quality.py` 的质量门/隔离接入日更链路（HEAVY 时阻断发布评分而非只记快照）；
11. `sync_coverage` 台账增加"缺口视图"（有确认点≠无缺口），供前端数据覆盖诊断直接消费。

## 附：本次实测口径

- 快照时间：2026-10-25 15:30（库内最新交易日 2026-10-23）；
- "疑似手×100"判定：`amount/(volume*close) ∈ [20,200]`；正常 VWAP/close 偏离受涨跌停约束（≤±20%/±30%），20 倍以上只能由单位或复权解释；送转导致的复权偏离集中在 2-20 档（2016-2017 年实测 11.3 万行），修复时需按"是否有后续除权事件"二次过滤；
- 审计脚本均为只读（`SET TRANSACTION READ ONLY` + 一致性快照），可随时重跑复现。
