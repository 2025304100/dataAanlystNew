## 5. 缺陷明细与修复证据

### P1（功能缺陷 · 高）锁过期不回收导致 Step4 提交被永久禁用

- **现象**：资源确认弹窗「确认提交」disabled；`GET /factor-mining/locks/status` 显示 `miningDomain.busy=true`，owner 为 08:34 创建的已死任务，心跳超时 >12h。
- **根因**：`expire_stale_locks` 只挂在 task_runner patrol 链路，普通运行路径从不触发；worker 重启/崩溃后 `task_locks` 行成为永久"僵尸锁"，前端 `domainBusy` 永久判 true。
- **修复**：[factor_mining.py](file:///d:/ai_project/dataAanlystNew/app/api/routes/factor_mining.py) `GET /locks/status` 先执行 `mining_lock.expire_stale_locks(db)`（幂等、best-effort），前端每次打开资源弹窗即自愈。
- **证据**：修复前走查 4.4/5.1 FAIL；修复后 21/21；`locks/status` 返回 busy=false；task_lock 并发单测 21/21。
- **回归保护**：用例 TC14 对应该行为。

### P2（质量缺陷 · 中）PoolFilterPanel React key 警告

- **现象**：控制台 `Each child in a list should have a unique "key" prop … Check the render method of PoolFilterPanel`。
- **根因**：`catFields.map` 对数值字段返回的 `rangeControl(f)` 未带 key。
- **修复**：[PoolFilterPanel.tsx](file:///d:/ai_project/dataAanlystNew/frontend/src/components/factors/mining/wizard/step1/PoolFilterPanel.tsx) 以 `<Fragment key={f.field}>` 包裹。
- **证据**：控制台 key 警告清零；前端挖掘域单测 156/156；tsc exit 0。

### P3（环境观测）preview 曾慢至 19.5s

- **现象**：首轮走查时 preview 接口测量 19.5s（前端 20s 超时边缘）→ 防抖预览与生成物料出现连锁超时。
- **处置**：服务重启后实测 0.5s（热后 0.2s）；独立 Profile 证明各装载步骤（universe 0.04s / valuation 0.01s / liquidity 0.02s / financials 0.03s）均正常，非代码缺陷，属当时进程内资源竞争/缓存状态；无代码修改。

### P3（功能缺陷 · 高，贯通阻断）Step3 字段目录错误 → worker 崩溃

- **现象**：每次提交 run 均在启动后 ~20s `Worker crashed: eval.worker.crashed`；首代即失败。
- **根因**：MiningShell 用候选池 `filter-fields`（`avg_amount/board` 等筛选字段）充当 Step3 挖掘字段目录；用户勾选后 `selected_fields=["avg_amount"]`，经典模板 25 个全部因字段依赖不满足跳过（实测 candidates=0）→ `_run_real_stages` 抛「初始种群无有效候选」→ worker crash。
- **修复**：
  1. 后端新增 `GET /factor-mining/fields`（DSL 注册字段，来源 `factor_compiler.FIELD_CATALOG`，分组行情/估值/财报/资金流/事件）—— [factor_mining.py](file:///d:/ai_project/dataAanlystNew/app/api/routes/factor_mining.py)；
  2. 前端 [MiningShell.tsx](file:///d:/ai_project/dataAanlystNew/frontend/src/components/factors/mining/MiningShell.tsx) 改用该接口；
  3. [task_runner.py](file:///d:/ai_project/dataAanlystNew/app/services/factors/mining/task_runner.py) 经典层为空不再直接阻断，由 AI/随机探索层补位（设计 §6.3），三来源为空才失败并给出明确指引。
- **证据**：修复后浏览器 Step3 展示 21 个 DSL 字段（open/close/pe_ttm… 分组正确）；提交 run 进入真实评估（此前 100% crash）；API 冒烟 2 次 succeeded。

### P4（功能缺陷 · 高，贯通阻断）worker 运行中 MySQL 连接丢失（2006 / InterfaceError）

- **现象**：进化中途 `eval.db.mysql_gone_away_2006` 或 `pymysql.InterfaceError(0,'')`（Packet sequence wrong）→ worker crash。
- **根因**：`load_run` 开启隐式事务后连接被 worker 长持有；随后的目标计算/首代评估为分钟级纯 DuckDB 计算，期间 MySQL 连接空闲被 `wait_timeout=120s` 断开（2006）；多线程（心跳 pump）下长持有连接还会触发协议乱序（InterfaceError）。
- **修复**（[task_runner.py](file:///d:/ai_project/dataAanlystNew/app/services/factors/mining/task_runner.py) + [manager.py](file:///d:/ai_project/dataAanlystNew/app/db/manager.py)）：`load_run` 后立即 rollback 归还连接；每代持久化后 commit；操作级 2006/InterfaceError 重连重试（含 rollback 容错重建 session）；`pool_recycle` 60s→30s。
- **证据**：修复后首代评估跨过 120s+ 空闲仍持久化成功（trials 真实落库）；API 冒烟连续 2 次 succeeded。

### P5（性能问题 · 中，未修复）GA 评估过慢

- **实测**：UI 最小种群 50 个体/代，单代评估 **17 ~ 30+ 分钟**（1407 只 × 397 交易日短样本），5 代完整运行约 1.5h+；两次带 UI 全流程 run 均在首代未完成时被测试取消。
- **影响**：浏览器端「结果页 live 出数」无法在合理时间内等到 run 结束（fullcycle F12~F14 受此限制）。
- **建议**：按设计 §6.11 落地 G2 子表达式缓存的跨 run 复用、target 计算去重、G1 并行（M3 依据探针），或将首期 UI 提供「快速试验（种群 50/代数 10）」之外的更小验证档。

### P6（产品限位 · 中，部分修复）结果页会话性

- **现象**：Step5 结果区仅在**同一会话内** run 完成后展示；刷新页面后 `runState` 丢失，结果不可回溯；`converged`（提前停止）此前不触发候选拉取。
- **修复**：[MiningShell.tsx](file:///d:/ai_project/dataAanlystNew/frontend/src/components/factors/mining/MiningShell.tsx) `converged` 同样拉取候选并展示（§8.3.5 提前停止保留结果）。
