## 2. 数据库事务故障及修复

复现链路：工作线程读取标的后持有数据库连接，外部请求或退避等待期间连接可能失效。接口调用统计会捕获并吞掉SQL异常，但原Session仍保留失效事务；随后即使已收到有效行情，写入也会报`Can't reconnect until invalid transaction is rolled back`，导致该股票被计为失败。

新增真实MySQL故障用例，先在旧实现上复现同样错误并得到failed任务；修复后保留同一条已获取行情，恢复事务后写入成功，后续股票继续处理，未额外抓取同一行情。

最终实现：

1. 仅异步回填工作线程为每只股票的独立事务显式启用恢复。该边界已先提交分区状态，回滚不会撤销其他业务调用者的未提交改动；普通服务调用默认不开启自动回滚。
2. 有效行情取得后暂存于内存。遇到连接失效类SQL异常或失效事务，先完成回滚，再用同一份行情重试写入，最多恢复一次。
3. 回滚自身异常时再完成一次逻辑回滚，不直接清空整个Session的对象。故障注入证明，直接重置Session会使后续股票/分区对象脱离会话，产生新的失败。
4. 第二次数据库写入仍断连时明确失败，不无限恢复；其他股票继续执行。公开重试接口只补失败/未完成分区，不重复抓取已经成功的股票。
5. 任务结果增加`database_recoveries`计数，可审计本次实际发生的恢复。原缺口填充、已有值保留、唯一键和真实日期口径不变。

接口统计仍是尽力记录。断连时其统计写入可能随事务回滚；本轮保证该情况不会丢弃已经获得的有效行情，不将统计计数包装为完整网络请求审计。

## 3. 重试和退避策略

历史资金流适配器统一负责重试，外层通用调用器不再额外套一轮重试。原有接口启用检查及配置延迟继续生效，并在每次重试及实际请求前重新检查接口是否已被停用。

| 规则 | 最终行为 |
|---|---|
| 健康请求节奏 | 保持默认15秒最小间隔，不增加正常场景请求频率 |
| 重试轮数 | 默认3轮，包含首次；配置范围1～5 |
| 临时HTTP故障 | 408、429、500、502、503、504可重试 |
| 网络故障 | 连接错误、连接/读取超时及分块传输错误可重试 |
| 永久错误 | 400/401/403/404等不做无效重试 |
| 数据校验失败 | 错标的、缺字段、重复日期、非有限值、供应商失败码直接拒绝，不靠重试伪造成功 |
| 本地退避 | 连接拒绝和临时HTTP故障默认15秒起、指数增长、最高60秒，增加默认0～10%正向抖动；客户端超时已消耗的I/O等待计入原请求节奏，不额外再叠加冷却 |
| `Retry-After` | 支持秒数及HTTP日期；服务器要求的等待不受本地60秒上限截短 |
| 重试调度预算 | 默认75秒；等待和安排下一次请求受预算约束，预算不足明确失败，不提前突破服务器等待要求 |
| 请求超时 | 连接/读取上限原为5/15秒，剩余预算较小时相应收紧 |
| 多线程等待 | 唤醒后重新检查共享冷却时间，避免使用过期的预约时刻提前请求 |

保留已有的首次HTTPS连接失败后HTTP回退行为，因此3轮逻辑尝试不等于绝对最多3次物理HTTP请求；首次协议回退可多一次物理请求。本轮未增加新数据源。

75秒是适配器的等待与重试调度预算。外层用户配置延迟、数据库处理和底层网络实现仍影响整项任务的实际耗时，不能将其解释为全任务的硬超时承诺。

| 参数 | 默认值 |
|---|---|
| `CAPITAL_FLOW_REQUEST_INTERVAL_SECONDS` | 15 |
| `CAPITAL_FLOW_MAX_ATTEMPTS` | 3 |
| `CAPITAL_FLOW_BACKOFF_BASE_SECONDS` | 15 |
| `CAPITAL_FLOW_BACKOFF_MAX_SECONDS` | 60 |
| `CAPITAL_FLOW_RETRY_JITTER_RATIO` | 0.1 |
| `CAPITAL_FLOW_RETRY_BUDGET_SECONDS` | 75 |

以上默认值属于首轮受控策略，尚未经过真实供应商的长期校准。已有显式环境参数仍按其配置使用。
