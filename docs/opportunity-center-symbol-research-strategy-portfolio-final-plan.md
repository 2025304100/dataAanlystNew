## 当前项目功能基线

### 0.1 当前技术与运行底座

| 层级 | 当前实现 | 改造原则 |
| --- | --- | --- |
| 前端 | React + TypeScript + Ant Design + ECharts，主入口为 `frontend/src/App.tsx` | 延续现有框架和样式体系，不重建 UI 工程 |
| 后端 | FastAPI，统一路由注册在 `app/api/router.py` | 新接口沿用 `/api/v1` 和现有依赖注入方式 |
| 业务库 | SQLAlchemy，支持 SQLite 与 MySQL 热切换；当前工作区配置选择 MySQL | 不改变数据库选择机制；迁移必须同时兼容 SQLite/MySQL |
| 因子仓库 | 本地 DuckDB，路径和启停由因子运行配置管理 | 不重写因子仓库；任务取消后必须释放连接与文件锁 |
| 异步任务 | `async_tasks` 持久化任务记录 + 后台 worker + 轮询进度 | 复用任务状态、心跳、取消和错误明细能力 |
| 定时任务 | 应用内跨平台调度器，支持每日、每周、间隔、启停、编辑、立即执行和运行历史 | 继续作为 Windows/Linux 的统一入口，不另做独立 crontab 产品逻辑 |
| 行情源 | AKShare 与通达信等数据源链，包含接口探测、优先级和降级策略 | 保留多源回退；机会/交易页面只消费统一行情，不直接调用第三方接口 |
| 测试 | 后端白盒/黑盒/E2E，前端 Vitest 组件测试 | 每个任务包必须补对应回归测试，不能只靠页面点测 |

当前工作区 `config/db_config.json` 选择 MySQL 仅代表本机运行配置，不能写死到业务代码、测试或迁移脚本中，也不能在文档或日志中传播数据库凭据。

### 0.2 当前一级导航与真实职责

当前 `frontend/src/App.tsx` 实际注册了 7 个一级入口：

| 当前入口 | 当前真实职责 | 当前问题 | 目标去向 |
| --- | --- | --- | --- |
| 今日决策 | 汇总市场、机会、风险、仓位、数据健康和因子运行状态 | 基本符合定位，但跳转仍指向旧入口 | 保留，改为统一待办和上下文跳转 |
| 投资中心 | 单标的搜索、研究、计划、风险、提醒和单股回测 | 职责过载，并维护本地收藏/提醒状态 | 从一级导航移除，收敛为共享“标的研究”能力 |
| 目前观察池 | 实际是“组合工作台 + 组合交易”，不是单纯观察池 | 名称严重误导，观察名单、持仓和模拟账户混在同一心智中 | 重命名并收口为“组合交易” |
| 机会挖掘 | 扫描任务、结果分池、过滤方案、候选晋升 | 已经接近目标候选池，但“发现结果”和“正式候选”语义混杂 | 成为“机会中心”的候选池与扫描记录底座 |
| 宏观数据 | 宏观快照、市场评分、雷达、历史指标 | 与机会和组合的联动不够直接 | 保留为市场环境能力，并向决策/组合提供上下文 |
| 行情消息 | 市场事件采集、筛选、重要性和情绪展示 | 与标的、组合、告警的关联入口不完整 | 保留，增强上下文跳转 |
| 设置 | 规则、数据、任务、告警、模型、接口、数据库和 AI 配置 | 功能多但基本合理 | 保留，按“业务设置/数据运维/系统设置”分组即可 |

当前页面关系可以概括为：

```text
今日决策
  ├─ 跳机会挖掘
  ├─ 跳投资中心
  └─ 跳行情消息

投资中心
  └─ 单标的研究 + 本地收藏 + 本地提醒 + 交易计划 + 单股回测

目前观察池
  ├─ 组合工作台：候选、观察名单、持仓、风控、数据管理
  └─ 组合交易：模拟账户、手动下单、自动交易、组合回测、绩效

机会挖掘
  └─ 扫描任务 + 结果池 + 候选晋升 + 加入观察池
```

这正是本次改造要解决的主要偏差：功能本身不少，但产品对象和入口名称没有对齐。

#### 0.3.2 投资中心

主代码入口：`frontend/src/components/InvestmentCenter.tsx`；共享详情弹窗为 `frontend/src/components/DetailModal.tsx`。

当前已实现：

- 股票/ETF 搜索、快捷标的、搜索历史和收藏管理。
- 日线/周线 K 线、MA10/MA20、MACD、RSI、图表缩放和点击取价。
- `DetailModal` 已实现趋势线、水平线、撤销和清空，绘图数据保存在浏览器本地；但内联 `InvestmentCenter` K 线尚未接入同一绘图 Hook。
- 因子解释、模型 ID、因子贡献和数据截止时间。
- 本地止损/目标/RSI/MACD 提醒计算及阈值设置。
- 风险仪表盘和本地风险参数。
- 交易计划刷新、参数覆盖、情景分析、分批计划和未来买入计划。
- 单标的事件驱动回测、规则模板、交易成本、结果详情和结果应用到组合。
- 移动端与桌面端两套布局。

当前状态与限制：

- `ic_search_history`、`ic_favorites`、`ic_risk_settings`、`ic_alert_settings` 等保存在 `localStorage`，不是后端业务真相。
- 收藏与后端 `watchlists/watchlist_items` 重复，重启浏览器、换设备或清缓存后可能不一致。
- 页面内价格提醒只是即时前端计算，不等于告警中心的持久化规则和事件。
- 组件接近 2000 行，继续直接堆功能会增加回归风险。
- 趋势线能力在详情弹窗可用，但投资中心内联页尚未统一；多标的对比尚未形成正式功能。

本次处理：保留研究与单股回测能力，迁出收藏、正式告警、组合风控和交易执行；最终抽成可携带来源上下文的标的研究页/抽屉。

#### 0.3.3 当前“目前观察池”中的组合工作台

代码入口：`frontend/src/components/PortfolioWorkbench.tsx`，组合 CRUD 与切换入口在 `frontend/src/App.tsx`。

当前已实现：

- 新建、编辑、删除、切换组合；支持模拟账户/手工账户、默认组合、币种和自动交易开关。
- 今日可执行机会、观察队列和消息摘要。
- 标的总数、观察池、候选池、组合使用率等指标卡。
- 账户摘要、持仓表和手工录入/修改/删除持仓。
- 总资金、单标的/股票/ETF/行业上限、单笔最大亏损和最大持仓数等组合规则。
- 组合暴露与仓位分配信息。
- 候选列表和最新评分列表。
- 数据库备份、恢复和数据导出入口。

当前状态与限制：

- 页面名叫“目前观察池”，实际数据对象是 `Portfolio`，容易把观察名单理解成有资金的组合。
- “观察队列”主要从工作台聚合结果推导，不是一个具有完整生命周期的观察对象。
- 可以直接维护 `positions`，但不存在独立的“组合成员”层。

本次处理：组合账户、规则、持仓、数据管理能力全部复用；页面重命名为“组合交易”，机会/观察名单迁出。

#### 0.3.4 当前组合交易子页

代码入口：`frontend/src/components/Trading.tsx`，并组合以下面板：

- `PortfolioPerformancePanel.tsx`
- `AutoTradePanel.tsx`
- `PortfolioBacktestPanel.tsx`

当前已实现：

- 模拟账户权益、现金、市值、已实现/未实现盈亏和投入比例。
- 手动模拟买卖、快捷数量、预计成本/剩余现金、当前持仓和成交历史。
- 自动交易 Dry Run 预览、实际执行、买卖计划、风控阻断原因和错误隔离。
- 整体组合回测，自动推导标的和规则并展示收益、最大回撤、Sharpe 等摘要。
- 组合每日净值快照、收益曲线、沪深 300 等基准曲线、最大回撤、Sharpe、胜率、盈亏比、交易数和平均持有天数。

底层成交已复用统一成本和市场规则，包含佣金、最低佣金、印花税、滑点、A 股手数、T+1 和涨跌停校验。

当前状态与限制：

- 自动交易卖出来源是当前持仓，买入来源是该组合最新一次成功扫描中的 `executable` 结果，最终动作主要取最新 `Score.action`。
- 组合整体回测的标的集合也是“当前持仓 + 最新扫描可执行结果”，无法稳定复现历史成员变化。
- 自动交易只有“关闭/开启 + Dry Run/执行”，尚未形成成员级手动、待确认、全自动三种模式。
- `SimOrder` 只有备注字段，没有结构化保存候选、观察记录、信号、规则版本和执行模式来源。
- 绩效依赖每日 `portfolio_equity_snapshots` 累积，历史未生成的日期不能凭空还原为真实模拟账户净值。

本次处理：保留执行、成本、市场规则、回测和绩效引擎；只替换标的来源、补齐归因字段和成员级执行策略。

#### 0.3.5 机会挖掘

代码入口：`frontend/src/components/Discovery.tsx`；后端入口为 `app/api/routes/discovery.py` 和 `app/services/discovery_tasks.py`。

当前已实现：

- A 股、ETF 等范围选择，评分阈值、批大小、延迟、并发、预警天数、有效天数和消息开关。
- 扫描任务启动、暂停、恢复、取消、重试、刷新、进度和错误详情。
- 可执行、关注、超限、排除等结果分池与数据可信度/新鲜度展示。
- 自定义指标条件、AND/OR 逻辑、保存/加载/删除筛选方案。
- 结果行刷新、冻结、创建复盘、运行单股回测和加入观察池。
- `discovery_candidates` 的手动晋升、取消晋升和批量晋升。
- 评分配置快照、维度强项、阶段、动作、有效期和原因标签展示。

当前状态与限制：

- 扫描结果、可执行结果、`discovery_candidates.is_promoted` 三种概念同时出现，用户难以理解“候选池”究竟是哪一层。
- 加入观察池只写入简单名单，来源扫描、入池理由和入池评分没有持久化到观察项。
- 缺少正式的已排除生命周期和统一跨页面状态。

本次处理：以现有 Discovery 为候选池和扫描记录底座，不改扫描算法；统一候选生命周期和晋升服务。

### 0.4 当前后端数据资产与复用结论

| 领域 | 当前表/模型 | 已承载能力 | 本次结论 |
| --- | --- | --- | --- |
| 标的主数据 | `symbols`、`universe_symbols` | 业务标的与全市场标的隔离 | 不重写，所有新对象引用统一标的 ID |
| 行情 | `daily_bars`、`universe_daily_bars`、`index_prices` | 研究/回测行情、全市场同步、绩效基准 | 不重写 |
| 评分 | `scores`、`scoring_configs` | Quality/Timing/维度评分、动作、配置快照 | 不重写，继续作为信号输入 |
| 因子 | `factors`、`factor_values`、DuckDB 原始/因子表、模型版本和权重快照 | 四维因子、Ridge、影子/正式模式和解释 | 不重写 |
| 机会扫描 | `discovery_tasks`、`discovery_candidates`、`scan_runs`、`scan_results` | 任务、候选快照、组合约束后的结果 | 复用并补统一生命周期/来源字段 |
| 观察名单 | `watchlists`、`watchlist_items` | 名单、标的、备注、加入时间 | 扩展观察上下文；不另建第二套观察池真相 |
| 组合 | `portfolios`、`portfolio_rules`、`positions` | 模拟/手工账户、资金与风控、当前持仓 | 复用；新增 `portfolio_members` |
| 模拟成交 | `cash_ledger`、`sim_orders`、`sim_trades` | 现金、订单、成交、已实现盈亏 | 复用执行器；补结构化来源归因 |
| 回测 | `backtest_runs`、`backtest_trades`、`backtest_rule_templates` | 单/多标的事件驱动回测、模板、结果历史 | 复用；补成员和版本快照 |
| 绩效 | `portfolio_equity_snapshots` | 每日净值、回撤、Sharpe、基准比较 | 复用，禁止伪造上线前净值 |
| 规则与计划 | `signal_rules`、`trade_setups`、`trade_signals` | 规则预览、交易计划、分批计划和信号 | 复用并建立版本/订单关联 |
| 告警 | `alert_rules`、`alert_events` | 持久化规则和事件 | 作为正式提醒唯一真相 |
| 任务 | `async_tasks`、`scheduled_tasks`、`scheduled_task_runs` | 进度、心跳、取消、调度和审计 | 不重写 |
| 复盘 | `journal_entries` | 组合/标的复盘记录 | 复用并关联交易或回测上下文 |

当前明确不存在的关键模型是 `portfolio_members`。这不是命名问题，而是自动交易、组合回测和成员生命周期无法稳定复现的根因。

### 0.5 当前数据与因子能力

项目已经实现或接入了以下数据/因子能力，不应在本次产品重构中重复开发：

- 估值与基本面：PE/PB/股息率、财报快照、ROE 及同比衍生能力。
- 资金面：个股资金流、龙虎榜机构买卖、北向/市场资金数据。
- 情绪面：东方财富人气榜、换手率与成交量价数据。
- 尾盘代理：分钟数据可用时计算尾盘金额占比、活跃比和尾盘收益；没有 Level-2 时明确作为代理指标。
- 宏观与流动性：中美 10 年期收益率、两融变化、全市场成交额变化、成交额 Z-Score 和涨跌家数比例。
- 动态模型：未来收益标签、滚动 Ridge、权重快照、影子模式、正式模式和手工回退。
- 数据健康：接口状态、覆盖率、新鲜度、缺失项、降级来源和定向修复。

本次改造只消费这些能力的最新有效结果和快照，不改变其计算公式或训练流程。

### 0.6 当前调度与自动化能力

当前应用内调度器已支持并默认配置以下任务类型：

- 全市场增量同步。
- 人气榜快照。
- 尾盘代理快照。
- 龙虎榜机构同步。
- 财报同步。
- 宏观更新。
- 因子流水线（增量/全量）。
- 机会挖掘。
- 组合净值快照。
- 指数日线同步。
- 组合自动交易。

用户可以在设置中查看全部定时任务、启停、编辑、删除和手动立即执行，也可以查看对应运行记录。因此后续机会中心/组合交易只需注册或调整任务载荷，不需要再开发 Linux crontab 或 Windows Task Scheduler 的独立管理界面。

### 0.7 当前回测与执行引擎边界

项目目前同时存在两类回测能力：

| 引擎 | 当前用途 | 结论 |
| --- | --- | --- |
| 事件驱动引擎 `app/services/backtest.py` | 正式单股/多股/组合回测；支持条件树、自定义指标、信号时点、成本和逐笔交易明细 | 继续作为精确成交和产品结果的权威引擎 |
| VectorBT `app/services/vectorbt_backtest.py` | 基于项目行情/评分快速构造横截面信号并进行向量化验证 | 作为研究和交叉验证引擎，不替代正式事件驱动成交规则 |

VectorBT 已有专用服务和测试，但当前主 UI 的正式结果仍以事件驱动引擎为准。交接时不得再把“增加 VectorBT”列为从零待办；真正待办是决定在研究页或回测中心如何暴露引擎选择和差异说明。

### 0.9 当前项目改造的七个真实缺口

后续参与者应围绕以下七项实施，而不是重新建设量化底座：

1. 导航和命名没有体现真实业务对象。
2. 观察池信息过少，且投资中心另有一套本地收藏。
3. 缺少持久化组合成员，成员、持仓和候选被错误混用。
4. 候选、观察、成员、持仓之间没有统一流转服务和审计。
5. 自动交易与组合回测依赖“最新扫描结果”，历史可复现性不足。
6. 订单、成交和回测缺少完整信号/规则/来源归因。
7. 大型前端组件和跨页面状态重复，增加测试遗漏风险。

## 1. 最终结论

本次优化不再继续扩充当前通用观察池弹窗，也不再把更多交易功能堆进投资中心。最终产品结构确定为：

```text
今日决策
  -> 回答今天需要处理什么

机会中心
  -> 候选池
  -> 观察池
  -> 已排除
  -> 扫描记录

标的研究（公共详情能力，不作为一级业务中心）
  -> 从候选、观察、组合、告警和回测上下文进入

组合交易
  -> 独立模拟账户
  -> 组合成员
  -> 手动/确认/自动模拟交易
  -> 单股与组合回测
  -> 绩效与复盘
```

核心业务流固定为：

```text
数据同步
-> 因子与评分
-> 机会扫描
-> 候选池
-> 观察池
-> 策略组合
-> 模拟持仓/自动交易
-> 绩效统计
-> 复盘改进
```

任何页面和数据结构都必须服务于这条主链路，禁止形成孤立功能。

## 2. 当前问题诊断

### 2.1 投资中心职责过载

当前投资中心同时承担股票搜索、K 线、技术指标、因子解释、收藏、价格提醒、风险参数、交易计划、分批建仓和单股回测。它既像研究工具，又像观察池，又像交易模块，导致用户无法判断应该在哪里完成一项任务。

### 2.2 候选池语义不统一

当前候选主要由机会挖掘和最新扫描产生，但界面同时存在“系统候选”“可执行候选”和“手动晋升候选”等语义。用户难以判断候选是系统自动生成、手动保留，还是已经准备进入交易。

### 2.3 观察池只是通用名单

当前观察池底层是 `watchlists/watchlist_items`，主要记录名单、标的、备注和加入时间。它缺少加入来源、加入原因、加入时评分、当前信号和目标组合等关键上下文，因此看起来像没有明确用途的收藏夹。

### 2.4 模拟交易能力已经存在但入口分散

项目已有独立组合、现金流水、持仓、模拟订单、模拟成交、自动交易、单股回测、组合回测和绩效指标等底座，但这些能力没有围绕“策略组合模拟账户”形成一个统一入口。

### 2.5 重复功能造成状态不一致

投资中心本地收藏与后端观察池重复；投资中心风险设置与组合风控重复；单股回测与组合回测入口分散；价格提醒与告警中心没有统一状态。继续分别扩展会产生多套数据和多种解释。

## 3. 最终信息架构

### 3.1 一级导航

建议最终一级导航保持六项以内：

1. 今日决策
2. 机会中心
3. 组合交易
4. 市场环境
5. 消息与告警
6. 设置

原“投资中心”从一级导航移除。其核心研究能力改造成公共“标的研究页”，由其他模块携带上下文进入。

### 3.2 机会中心页签

机会中心包含：

- 候选池：系统自动发现的短期机会。
- 观察池：用户主动保留并持续跟踪的标的。
- 已排除：用户明确忽略或系统规则禁止的标的。
- 扫描记录：查看候选由哪次任务、哪套评分配置产生。

候选池和观察池共享筛选器、标的详情和数据健康能力，但生命周期和操作权限不同。

### 3.3 组合交易页签

组合交易包含：

- 账户总览
- 组合成员
- 当前持仓
- 订单与成交
- 策略规则
- 回测中心
- 绩效与复盘

每个组合就是一个独立模拟账户，拥有独立资金、现金、成员、持仓、规则、订单、回测和收益曲线。

## 4. 四类核心对象的职责边界

### 4.1 候选池

定位：系统自动产生、具有有效期的机会集合。

来源：

- 全市场或指定范围的数据同步。
- Quality Score、Timing Score 和因子模型评分。
- 机会扫描的阈值、维度过滤和组合风险过滤。
- `ScanResult(result_type="executable")` 及对应候选快照。

候选池展示：

- 标的、市场和资产类型。
- 来源扫描任务与生成时间。
- 有效期和剩余有效天数。
- Quality、Timing、Priority Score。
- 当前阶段、建议动作和入选原因。
- 数据日期、可信度和缺失字段。
- 是否已查看、已观察、已加入组合、已排除或已过期。

候选池操作：

- 查看标的研究。
- 运行单股回测。
- 加入观察池。
- 直接加入策略组合。
- 排除或恢复。
- 批量晋升、批量排除和过期清理。

候选状态统一为：`new -> reviewed -> watched -> portfolio -> excluded/expired`。

### 4.2 观察池

定位：用户主动保留、尚未进入正式资金管理的持续跟踪集合。

观察池不产生现金、持仓和组合收益，也不直接执行自动交易。

观察池展示：

- 加入来源、加入原因和加入时间。
- 加入时评分与当前评分变化。
- 当前信号：等待、接近买点、条件满足、信号失效。
- 价格变化、数据新鲜度和可信度。
- 最近单股回测摘要。
- 所属标签、优先级和用户备注。
- 是否已加入策略组合及所属组合。

观察池操作：

- 更新当前标的数据。
- 查看评分与信号变化。
- 创建价格、评分或公式告警。
- 运行单股回测。
- 加入指定策略组合。
- 移出观察池。

观察分类使用标签，不再鼓励创建大量独立名单。推荐标签包括：重点关注、等待回踩、等待财报、ETF 备选、长线观察。

### 4.3 标的研究

定位：所有模块共享的单标的研究能力，不拥有独立业务数据。

保留功能：

- 股票/ETF 搜索和搜索历史。
- K 线、均线、MACD、RSI、BOLL 等技术分析。
- 基本面、资金、情绪、宏观和因子解释。
- 历史评分变化。
- 单股回测和买卖点展示。
- 当前关联状态：候选、观察、组合成员、持仓、告警。

迁出功能：

- 本地收藏迁移为观察池。
- 正式价格/公式提醒归告警中心。
- 组合风险参数归组合规则。
- 分批建仓、模拟下单和资金管理归组合交易。
- 组合整体回测归组合交易。

标的研究必须携带来源上下文：候选来源、观察记录、组合 ID、告警 ID 或回测运行 ID。

### 4.4 策略组合模拟账户

定位：正式进行模拟资金管理、程序交易和组合绩效评估的对象。

每个组合拥有：

- 独立初始资金、可用现金和现金保留比例。
- 独立成员、持仓、订单、成交和现金流水。
- 独立买卖规则、仓位规则和风控规则。
- 独立手动、确认和自动执行开关。
- 独立单股回测、组合回测和绩效历史。

组合成员不等于持仓。加入组合只建立成员关系，只有手动下单或规则触发后才形成持仓。

## 5. 关联关系与联动规则

### 5.1 统一标的身份

候选、观察、组合成员、持仓、订单和回测都引用同一个 `Symbol.id`，禁止复制标的主数据、行情或评分。

共享能力统一读取：

- 行情：`DailyBar`。
- 评分：`Score`。
- 因子：因子仓库和解释接口。
- 公式：版本化公式/规则。
- 回测：统一事件驱动引擎。
- 模拟成交：统一订单执行器和市场规则。

### 5.2 操作联动

| 用户或系统动作 | 必须产生的联动 |
| --- | --- |
| 扫描完成 | 更新候选池并保存扫描、评分和参数快照 |
| 候选加入观察池 | 候选标记已晋升，观察记录保存候选来源 |
| 观察标的加入组合 | 创建组合成员并显示目标模拟账户 |
| 公式触发 | 更新观察状态并创建告警事件 |
| 手动或自动下单 | 更新订单、成交、现金、持仓和权益快照 |
| 单股回测完成 | 候选、观察、组合成员均可查看同一结果 |
| 组合回测完成 | 归档到该模拟账户的回测历史 |
| 规则调整 | 生成新版本，历史订单和回测继续引用旧版本 |
| 数据过期 | 禁止自动下单，并提示修复数据 |

### 5.3 跨页面状态展示

- 候选池显示：是否观察、所属组合、是否持仓。
- 观察池显示：来源候选、所属组合、最新回测和最近订单。
- 组合成员显示：来源观察记录、执行模式、规则和最近信号。
- 告警点击后打开对应标的或组合上下文。
- 回测结果可返回对应候选、观察记录或策略组合。

## 6. 数据模型优化

### 6.1 候选记录

复用现有 `discovery_candidates`、`ScanRun` 和 `ScanResult`，补齐或统一以下字段语义：

- `source_task_id`：来源挖掘任务。
- `scan_run_id`：来源扫描运行。
- `score_id/score_snapshot_json`：入选时评分快照。
- `reason_snapshot_json`：入选与过滤原因。
- `status`：候选生命周期状态。
- `reviewed_at/promoted_at/excluded_at/expires_at`。
- `target_portfolio_id`：直接进入组合时的目标组合。

候选有效期基于生成时的 `warning_days/valid_days`，不使用当前配置反向覆盖历史候选。

### 6.2 观察记录

保留现有 `watchlists/watchlist_items`，第一阶段在 `watchlist_items` 补充：

- `source_type`：discovery、search、detail、manual。
- `source_ref_id`：候选、扫描或其他来源 ID。
- `added_reason`。
- `added_score_snapshot_json`。
- `latest_signal`。
- `priority_level`。
- `tags_json`。
- `target_portfolio_id`。
- `status`：active、promoted、invalid、removed。

默认只保留一个主观察池。多个业务语义使用标签表达，排除名单单独管理。

### 6.3 组合成员

新增持久化 `portfolio_members`，解决当前组合回测依赖“当前持仓＋最新扫描候选”的不稳定问题。建议字段：

- `portfolio_id`、`symbol_id`。
- `source_watchlist_item_id/source_candidate_id`。
- `execution_mode`：manual、confirm、auto。
- `status`：active、paused、removed。
- `target_weight/max_weight`。
- `buy_rule_version_id/sell_rule_version_id`。
- `rule_override_json`。
- `manual_lock_until`。
- `effective_from/effective_to`。
- `created_at/updated_at`。

同一组合内 `(portfolio_id, symbol_id)` 唯一。历史有效期必须保留，用于无未来数据偏差的组合回测。

### 6.4 订单与成交追踪

在模拟订单和成交中补充：

- `execution_source`：manual、confirm、auto、risk、backtest。
- `portfolio_member_id`。
- `signal_id/signal_date`。
- `rule_version_id`。
- `client_order_key`：防止同一信号重复下单。
- `rejection_code/rejection_detail`。

手动订单、自动订单和回测订单必须可分别统计，不允许只靠备注文本判断来源。

### 6.5 回测快照

每次回测必须冻结：

- 组合成员及其有效日期。
- 每个成员的执行模式。
- 买卖公式版本。
- 仓位、风险、费用和成交配置。
- 数据截止日期、评分模式和模型运行 ID。
- 软件与回测引擎版本。

修改当前规则不得改变历史回测解释。

## 7. 手动、确认与自动交易

### 7.1 三种执行模式

- `manual`：系统只提供研究与信号，用户手动模拟下单。
- `confirm`：系统生成待确认订单，用户确认后成交。
- `auto`：满足规则后程序自动模拟下单。

普通用户默认使用 `confirm`，完成一段时间验证后再启用 `auto`。

### 7.2 冲突优先级

为避免手动操作被程序立即反向交易，执行优先级确定为：

1. 手动锁定。
2. 组合级风险强制减仓/清仓。
3. 自动卖出规则。
4. 自动买入规则。
5. 普通信号建议。

### 7.3 自动交易保护

自动交易必须检查：

- 数据是否过期或缺失。
- 组合与成员是否启用。
- 公式版本是否有效。
- 可用现金、现金保留和目标仓位。
- 单股、行业、资产类型和总仓位上限。
- 最大持仓数。
- A 股 T+1、整手、涨跌停和停牌规则。
- 重复信号和幂等订单键。
- 组合最大回撤、连续亏损和熔断状态。

首次启用自动交易必须先执行 `dry_run`，展示拟买入、拟卖出、被阻止原因和预计资金变化。

## 8. 回测体系

### 8.1 单股回测

单股回测从候选、观察或组合成员进入，默认自动带入该标的当前规则。输出：

- 买卖信号与实际成交点。
- 总收益、年化收益和最大回撤。
- 夏普、Calmar、Sortino。
- 胜率、盈亏比、Profit Factor。
- 交易次数、持仓天数、费用和滑点。
- 规则未触发与不可成交原因。

### 8.2 组合整体回测

组合回测使用一个共享资金账户逐日撮合，不能把多个单股回测收益简单相加。必须模拟：

- 多标的同时触发时的资金竞争和排序。
- 最大持仓数、目标权重和现金不足。
- 卖出回款后的资金再使用。
- 调仓频率和最小调仓阈值。
- 组合风险熔断和恢复。

完整组合回测前提：全部有效成员均为 `auto` 且规则有效。若存在 manual/confirm 成员，默认禁止完整回测，并提供“仅回测自动成员”选项及排除清单。

### 8.3 回测与模拟账户隔离

历史回测不得直接污染当前模拟账户。回测结果应用到组合时必须：

- 创建独立演示账户，或
- 明确清空后重放，并要求二次确认。

默认行为是保存回测结果和参数，不向当前账户写入订单。

## 9. 绩效与复盘

每个模拟组合独立统计：

- 总收益率、年化收益率。
- 最大回撤及回撤持续时间。
- 夏普、Calmar、Sortino。
- 胜率、盈亏比、Profit Factor。
- 交易次数、换手率、资金利用率。
- 费用、滑点和不可成交次数。
- 最长连续盈利/亏损。
- 当前仓位和历史暴露曲线。

进一步拆分：

- 手动交易收益。
- 确认后执行收益。
- 自动交易收益。
- 风控强制交易影响。
- 单标的、行业和资产类型收益贡献。
- 相对沪深 300、全 A 或指定 ETF 的基准与超额收益。

模拟账户实际绩效与回测绩效分开展示，并提供偏差解释。

## 10. 页面结构

### 10.1 机会中心

候选池默认视图只回答：系统今天发现了什么。

固定列：标的、评分、阶段、动作、入选原因、有效期、数据状态、关联状态和下一步操作。

观察池默认视图只回答：我关注的标的里谁接近交易条件。

固定列：标的、加入原因、评分变化、最新信号、价格变化、数据状态、目标组合和下一步操作。

扫描参数收进“运行扫描”抽屉，不长期占用列表主区域。

### 10.2 标的研究

标的研究页顶部展示来源面包屑，例如：

```text
机会中心 / 候选池 / 600519 贵州茅台
组合交易 / 趋势成长组合 / 600519 贵州茅台
告警中心 / 评分跌破 / 600519 贵州茅台
```

页面固定区域：结论摘要、K 线、因子解释、评分历史、单股回测和关联状态。组合相关操作仅在携带组合上下文时出现。

### 10.3 组合交易

每个策略组合固定七个页签：

1. 账户总览。
2. 组合成员。
3. 当前持仓。
4. 订单与成交。
5. 策略规则。
6. 回测中心。
7. 绩效与复盘。

账户首页只展示总资产、现金、持仓市值、今日/累计盈亏、当前回撤、自动交易状态、待处理订单和权益曲线。

### 10.4 今日决策

今日决策不重复维护业务数据，只聚合：

- 数据是否可用于决策。
- 当前持仓风险。
- 候选池今日重点。
- 观察池接近买点标的。
- 自动/待确认订单。
- 组合资金与风险状态。

点击任何卡片都跳转到对应业务页面和上下文。

## 12. 分阶段实施路线

### Phase 1：信息架构收敛

目标：先让用户知道每个页面做什么，不改变核心交易数据。

- 新建一级“机会中心”。
- 将现有机会挖掘结果接入候选池页签。
- 将通用观察池弹窗改成正式观察池页签。
- 将投资中心改名为标的研究并移出一级导航。
- 将本地收藏按钮改为加入观察池。
- 建立候选、观察、组合和持仓的关联状态展示。

交付：可导航的新信息架构、无数据丢失迁移、基础页面回归测试。

### Phase 2：来源追踪与组合成员

- 补充候选和观察来源字段。
- 新增 `portfolio_members`。
- 实现候选到观察、观察到组合的统一服务。
- 增加 manual/confirm/auto 标签。
- 补充去重、状态同步和审计记录。

交付：完整来源链路和持久化组合成员。

### Phase 3：规则与模拟交易统一

- 组合和成员绑定版本化买卖规则。
- 订单记录执行来源、信号和规则版本。
- 增加待确认订单和手动锁定。
- 自动交易只遍历有效 auto 成员。
- 增加数据过期、回撤熔断和幂等保护。

交付：手动、确认、自动三模式模拟交易闭环。

### Phase 4：回测与绩效

- 单股回测自动加载成员规则。
- 组合回测改用有效成员历史，不再使用最新扫描临时集合。
- 保存成员、规则、数据和模型快照。
- 增加基准、归因、Calmar、Sortino、换手和资金利用率。
- 分拆手动与自动交易收益。

交付：可信、可追溯的单股与组合回测及绩效中心。

### Phase 5：自动化与复盘

- 观察信号与组合风险接入告警中心。
- 定时执行数据更新、评分、候选刷新和自动模拟交易。
- 今日决策聚合待处理事项。
- 回测与模拟表现差异进入复盘。

交付：每日无人值守准备、明确人工确认点和完整复盘链路。

## 13. 改动范围与重构约束

### 13.1 总体约束

本方案属于“业务信息架构与交易链路重构”，不是全项目技术重写。实施时必须遵守：

1. 优先复用现有模型、服务和接口，不重写已经验证稳定的底座。
2. 数据库迁移只允许增量加表、加字段、加索引和回填，不删除现有业务数据。
3. 第一阶段不改变自动交易和组合回测的实际数据来源，只增加新页面和关联状态。
4. 新链路完成回填与验证后，再逐步切换自动交易和组合回测。
5. 旧接口至少保留一个兼容周期，前端完成迁移前不得直接删除。
6. 所有状态流转必须经过后端服务和事务，前端不能自行拼接多次写操作。
7. 历史订单、成交、回测、规则版本和收益曲线不可因重构被覆盖。
8. 当前 `core` 观察池、现有组合、持仓和模拟交易记录必须无损保留。

### 13.5 新增功能范围

本方案允许新增：

### 13.6 明确不在本次重构范围

本轮不处理：

- 真实券商账户和实盘自动下单。
- Level-2、逐笔、毫秒级或日内 T+0。

- 云端密钥托管和复杂权限系统。

## 15. 兼容迁移与回滚约束

### 15.1 数据库迁移原则

- 所有迁移脚本必须可重复执行并具备字段存在检查。
- 新表和新字段先允许为空，完成回填后再增加严格约束。
- 对 `portfolio_members`、订单幂等键和来源关联增加必要索引。
- 不在同一版本中同时执行“新结构上线”和“旧字段删除”。
- 迁移前记录各表行数、关键账户余额和持仓汇总，迁移后自动比对。

### 15.2 分阶段双轨运行

切换顺序：

1. 新页面只读现有数据，不改变自动交易行为。
2. 新流转服务写入新关联字段，同时保留旧接口返回。
3. `portfolio_members` 完成回填后，自动交易先执行 dry-run 双轨对比。
4. 新旧逻辑连续多个交易日产生一致计划后，切换自动交易读取源。
5. 组合回测完成历史成员验证后，再切换到成员有效期模型。
6. 旧入口只在确认无调用后隐藏，暂不删除底层接口。

### 15.3 功能开关

建议增加：

- `OPPORTUNITY_CENTER_ENABLED`。
- `PORTFOLIO_MEMBERS_ENABLED`。
- `AUTO_TRADE_MEMBER_SOURCE_ENABLED`。
- `PORTFOLIO_BACKTEST_MEMBER_SOURCE_ENABLED`。

功能开关用于分阶段启用和快速回滚，不得形成长期两套业务逻辑。

### 15.4 回滚边界

发生问题时允许：

- 恢复旧导航和旧观察弹窗。
- 自动交易重新读取原扫描候选逻辑。
- 组合回测重新使用旧入口。
- 暂停新流转服务并保留已写入关联数据。

回滚时禁止：

- 删除已经生成的组合成员。
- 回退或重算历史订单、成交和现金流水。
- 覆盖历史回测快照。
- 用旧状态覆盖用户在新页面做出的明确操作。

### 15.5 切换验收门槛

自动交易切换前必须满足：

- 所有启用自动交易的组合均有有效成员。
- 成员执行模式和规则版本完整。
- dry-run 与旧计划的差异已解释。
- 数据健康门禁生效。
- 幂等订单测试通过。
- 取消任务、后端重启和异常恢复测试通过。

组合回测切换前必须满足：

- 成员有效日期完成回填。
- 同一规则在单股和组合回测中成交语义一致。
- 组合共享资金、仓位和费用约束生效。
- 历史结果可追溯到完整快照。

## 16. 验收标准

### 16.1 信息架构

- 一级导航不再同时出现投资中心、机会挖掘和职责不明的观察池入口。
- 候选池、观察池和组合交易的页面说明与操作完全不同。
- 任意标的都可从来源页面打开统一标的研究。

### 16.2 关联完整性

- 候选可以追溯到任务、扫描、评分和配置版本。
- 观察记录可以追溯到候选或手动来源。
- 组合成员可以追溯到观察/候选来源。
- 订单可以追溯到成员、信号和规则版本。
- 回测可以追溯到成员、公式、模型和数据截止日期。

### 16.3 功能闭环

- 扫描结果能进入候选池。
- 候选能加入观察池并同步状态。
- 观察标的能加入指定组合但不自动形成持仓。
- 组合成员可手动、确认或自动模拟交易。
- 单股和组合回测使用正确规则。
- 模拟成交能更新账户绩效和复盘记录。

### 16.4 安全与可信度

- 数据过期时禁止自动下单。
- 同一信号不会重复下单。
- 手动锁定不会被普通自动规则覆盖。
- 回测不默认写入活动模拟账户。
- 历史规则和回测不会被当前配置覆盖。
- 组合回测不使用今天的成员列表回测过去。

### 16.5 易用性

- 普通用户能在十分钟内完成：查看候选、加入观察、加入组合、运行单股回测和生成待确认订单。
- 每个页面都明确显示“当前状态、为什么、下一步”。
- 技术参数默认折叠，错误信息提供影响范围和修复动作。

## 17. 明确不做的事项

- 不接入真实券商自动下单。
- 不做毫秒级、逐笔或日内 T+0 交易。
- 不把候选评分直接解释为必然买卖命令。
- 不让观察池承担现金、持仓和收益管理。
- 不允许页面各自保存一套收藏、规则、评分或回测结果。
- 不为了页面迁移删除现有组合、订单、回测或 `core` 观察数据。

## 18. 风险与控制

| 风险 | 控制方案 |
| --- | --- |
| 页面重组导致用户找不到旧功能 | 保留兼容路由、迁移提示和来源面包屑 |
| 观察和组合状态不同步 | 所有流转通过统一后端服务和事务完成 |
| 自动交易与手动操作冲突 | execution_mode、手动锁定和优先级规则 |
| 回测与自动交易逻辑漂移 | 共享公式、费用、市场规则和执行器 |
| 历史成员偏差 | portfolio_members 有效日期和回测快照 |
| 重复信号重复下单 | client_order_key 唯一约束和幂等检查 |
| 数据不完整仍自动交易 | 数据健康门禁和 fail-closed |
| 旧观察数据无来源 | 明确标记 legacy，不伪造历史 |

## 19. 最终产品边界总结

```text
今日决策：今天做什么
机会中心：关注什么
标的研究：为什么关注
组合交易：怎么买、怎么卖
回测绩效：规则是否有效
告警复盘：发生了什么、如何改进
```

候选池和观察池是流程节点，标的研究是共享能力，策略组合是资金与交易主体。所有功能围绕同一条数据和决策链路工作，不再形成孤立页面或重复状态。

## 20. 推荐启动顺序

正式实施时按以下顺序开始：

1. 先完成 Phase 1 导航与页面收敛。
2. 同步建立候选、观察和组合关联状态的只读展示。
3. 再实施 `portfolio_members` 和统一流转服务。
4. 最后切换自动交易和组合回测的数据来源。

在关联模型完成前，不应直接删除旧入口或把自动交易切换到新的池结构。

## 21. 工程交接总览

### 21.1 交接目标

## 29. WP6：自动交易成员化与安全切换

### 29.1 新执行逻辑

自动交易的买入候选改为：

```text
active PortfolioMember
  AND execution_mode = auto
  AND 当前无持仓
  AND 最新有效信号允许买入
  AND 数据健康通过
  AND 组合风控通过
```

卖出侧必须覆盖所有当前持仓，即使成员被暂停或归档，也不能因成员状态而漏掉止损/退出信号。

`confirm` 模式只生成待确认订单计划；`manual` 模式只提示信号，不自动创建订单。

### 29.2 订单归因与幂等

扩展 `SimOrder`：

- `member_id`
- `source_type/source_id`
- `signal_id` 或信号快照
- `rule_version_id`
- `execution_mode`
- `client_order_key` 唯一索引
- `decision_snapshot_json`

唯一键建议包含组合、成员、信号日期、方向和规则版本，确保调度重跑不会重复下单。

### 29.3 双跑切换

1. `AUTO_TRADE_MEMBER_SOURCE_ENABLED=false`：旧来源实际执行，新来源仅 Dry Run。
2. 连续至少 5 个交易日或 3 次有效运行，保存旧/新买卖集合差异。
3. 对每个差异给出原因：成员缺失、状态暂停、信号不同、数据过期、风控阻断。
4. 差异经人工确认后，先对一个非默认测试组合开启新来源。
5. 再逐组合切换；开关关闭可立即回退旧来源。
6. 旧来源至少保留一个发布周期，不同步删除。

### 29.4 安全门禁

- K 线、评分或规则版本过期时 fail-closed，禁止买入。
- 卖出风控不得因一般数据缺失静默跳过，应生成高优先级告警。
- 自动交易任务取消时必须停止后续组合和后续订单。
- 每笔失败独立记录，不回滚已合法成交的其他标的，但必须形成任务错误摘要。

### 29.5 验收

- 自动模式、确认模式、手动模式结果互不混淆。
- 同一任务重复执行不会重复下单。
- 关闭新来源开关后恢复当前 `Score.action + latest executable scan` 逻辑。
- 所有新订单可追溯到成员、信号、规则和数据截止时间。

## 37. WP-P：挖掘性能、结果时效与 5 分钟扫描 SLA

### 37.1 当前实现与真实性能基线

当前挖掘已经具备以下优化，并非完全从零开始：

- 从 `universe_symbols/universe_daily_bars` 读取基础数据，评分阶段不必逐标的访问 AKShare。
- `use_cached_bars_first` 和 `refresh_universe` 支持缓存模式与同步模式。
- 批量预载 K 线和现有 Score，避免主要查询路径的 N+1。
- 当 Score 创建时间不早于标的最后同步时间时复用已有评分。
- 进度每 20 个标的提交一次，支持暂停、恢复、取消和断点记录。
- `warning_days/valid_days` 控制扫描结果告警与过期。
- 应用启动和定期任务会删除超过 `valid_days` 且未冻结的 `ScanResult`。

但当前机制仍存在三个性能问题：

1. 缓存扫描仍逐个遍历全市场标的，并为任务维护大体量 ID JSON 和进度状态。
2. A 股全量会预载约 5,500 × 80 根 K 线，之后逐标的检查/计算评分。
3. `run_scan` 会为同一标的分别写 quality、timing、executable 结果，写入量可能接近全市场标的数的 2～3 倍。

2026-07-19 对当前任务历史的只读实测：

| 范围与模式 | 标的数 | 完成耗时 | 是否满足 5 分钟 |
| --- | ---: | ---: | --- |
| A 股，缓存优先、不刷新 | 5,525 | 1,588 秒 | 否 |
| ETF，缓存优先、不刷新 | 1,596 | 213 秒 | 是 |
| ETF，缓存优先、不刷新 | 1,600 | 273 秒 | 是，余量很小 |
| A 股，包含远程刷新 | 5,530 | 12,657 秒 | 否 |
| ETF，包含远程刷新 | 1,596 | 5,122 秒 | 否 |

因此不能承诺“免费接口实时刷新 + 全市场重算 + 消息更新 + 扫描”合计 5 分钟。可以并且应该保证的是：**在已有最近可用数据快照的前提下，用户发起的全市场机会扫描 5 分钟内完成。**

### 37.2 SLA 定义

正式 SLA：

- 范围：A 股约 5,500 只或 ETF 约 1,600 只。
- 前提：存在状态为 `ready` 的最近评分快照。
- 快速扫描 P50：不超过 60 秒。
- 快速扫描 P95：不超过 300 秒。
- 相同快照与相同参数的重复扫描：不超过 10 秒。
- 无可用快照：10 秒内明确返回“数据准备未完成”，同时给出上一快照或启动准备任务，禁止进度条无期限停住。
- 快照过期但仍可用：使用最近成功快照完成扫描，并明确显示数据日期、延迟天数和降级原因。
- 5 分钟不包含远程行情同步、财报同步、因子全量重算或 Ridge 训练；这些属于计划任务的数据准备阶段。

用户看到的“扫描完成”必须同时显示：

- 数据截止日期。
- 快照生成时间。
- 是否使用缓存。
- 评分配置版本和模型版本。
- 扫描耗时。
- 复用结果数、增量重算数和最终候选数。

### 37.3 数据准备与用户扫描分离

流程调整为：

```text
后台数据准备（可超过 5 分钟）
行情增量同步
  -> 外部因子/宏观更新
  -> 因子与评分增量计算
  -> 生成 ready 评分快照

用户快速扫描（必须小于 5 分钟）
读取 ready 快照
  -> SQL 粗筛和排序
  -> Top-K 高级指标过滤
  -> 组合约束过滤
  -> 保存小规模候选结果
```

默认点击“开始挖掘”执行快速扫描，不再隐式触发第三方网络同步。数据准备直接复用设置中已经存在的“全市场基础数据”“历史数据初始化”和“定时任务”能力，不新增第二套采集服务：

- `UniverseDataPanel.tsx` 继续负责初始化、智能同步、增量同步、区间修复和历史回补。
- `HistoryInitSection.tsx` 继续负责按预设或指定范围补齐历史数据。
- `ScheduledTaskManager.tsx` 继续负责基础数据增量同步、因子流水线和快照物化的定时编排与手动执行。
- 机会中心只显示最近数据准备任务、快照日期和健康状态，并提供“前往基础数据”“运行现有增量同步”“数据就绪后自动扫描”三个联动入口。

“运行现有增量同步”调用已有 universe/market-data 任务接口，不在 Discovery 内复制抓取代码。选择“数据就绪后自动扫描”时，系统只建立任务依赖：基础数据任务成功后生成评分快照，再触发快速扫描；该整条准备链不受 5 分钟 SLA 约束，最终快速扫描阶段仍必须在 5 分钟内完成。

### 37.4 评分快照模型

建议新增两个模型。

`discovery_score_snapshots`：

- `id`、`scope`、`trade_date`。
- `status`：`building`、`ready`、`failed`、`superseded`。
- `scoring_config_id/version`。
- `weight_mode/factor_model_run_id`。
- `data_cutoff_at`、`generated_at`。
- `symbol_count`、`coverage_pct`、`dirty_symbol_count`。
- `source_task_id`、`build_duration_seconds`。
- `error_summary_json`。

`discovery_score_snapshot_items`：

- `snapshot_id`、`universe_symbol_id`、`symbol_id`。
- Quality、Timing、Priority 和维度分数。
- `stage`、`action`、`data_credibility`。
- 必要的原因和数据健康摘要。

关键索引：

- `(scope, status, trade_date, generated_at)`。
- `(snapshot_id, priority_score)`。
- `(snapshot_id, action, stage, priority_score)`。
- `(snapshot_id, universe_symbol_id)` 唯一约束。

评分配置、模型和数据截止信息保存在 manifest，不在每个 item 重复存大段配置 JSON。快照生成完成后一次性把状态从 `building` 切为 `ready`；扫描永远不读取半成品。

### 37.5 增量失效规则

只有以下标的进入 dirty 集合：

- `universe_symbols.last_synced_at` 晚于当前快照对应 Score 的创建时间。
- 最新 `last_bar_date` 发生变化。
- 财报、资金、人气、龙虎榜或尾盘数据在快照之后更新。
- 定向数据修复成功。

以下变化会触发新版本全量快照，但在新快照 ready 前继续提供旧快照：

- 激活新的评分配置版本。
- 切换手工/影子/Ridge 权重模式。
- 激活新的因子模型。
- 修改影响全市场的宏观权重或基础公式。

同一 scope、同一配置版本同时只允许一个快照构建任务。多个用户扫描复用同一个 ready 快照，不能各自启动全量评分。

### 37.6 两阶段过滤

为保证自定义公式不拖慢全市场扫描，过滤分两阶段：

1. SQL 粗筛：在快照表上完成分数阈值、资产类型、阶段、动作、可信度和排序，保留 Top 300。
2. 高级筛选：只对 Top 300 批量加载 K 线，向量化计算最多 5 个自定义指标。

组合风控只对高级筛选后的最终集合执行。消息分数读取最近缓存，不在用户扫描中同步抓取新闻。

需要对全市场逐只计算复杂自定义公式时，系统应将其定义为“预计算指标”，由后台快照任务物化，不能放在交互扫描路径中。

### 37.7 相同参数结果复用

建立扫描缓存键：

```text
snapshot_id
+ scope
+ min_score
+ filter_hash
+ indicator_plan_version
+ portfolio_id
+ portfolio_rule_version
```

缓存键完全相同时直接返回已有结果，不重复写 `ScanResult`。只有参数或底层快照改变才创建新结果集。

第一版继续兼容 `ScanRun/ScanResult`，但只物化用户实际需要展示的候选：

- Quality Top 300。
- Timing Top 300。
- 最终 executable 候选。
- 总数和分布统计写入 `ScanRun` 摘要，不为 5,500 只标的各写三类结果。

长期可将三类排名合并为一条候选快照记录的多个 rank 字段，进一步减少写放大。

### 37.8 分层保留与清理

`valid_days` 只控制候选结果时效，不能删除底层行情、Score 或 ready 快照：

| 数据层 | 建议保留 | 清理规则 |
| --- | --- | --- |
| 当前候选展示 | 默认 5 天，3 天预警 | 过期后从活动候选隐藏 |
| 未晋升 `ScanResult` | 7 天且每 scope 至少保留最近 3 次 | 到期物理删除 |
| 未晋升 `DiscoveryCandidate` | 7 天 | 到期物理删除，避免当前表持续增长 |
| 已晋升/已观察/已入组合快照 | 长期保留 | 迁入正式对象后按业务审计保留 |
| 评分快照 items | 最近 20 个交易日/每 scope | 只由后台清理，不受候选 `valid_days` 影响 |
| `ScanRun` 摘要 | 180 天 | 删除大明细后保留参数、数量、耗时和错误摘要 |
| 日 K 与基础因子 | 按模型/回测所需窗口长期保留 | 禁止随候选过期删除 |
| Score 历史 | 至少 250 个交易日 | 支持模型、回测和历史解释 |

候选晋升为观察项或组合成员时，必须把入选评分和来源复制为正式快照；之后原临时候选可以按 TTL 清理。

当前 `cleanup_expired_discovery_results` 只清理非冻结 `ScanResult`，没有完整覆盖 `DiscoveryCandidate`、快照和运行明细。WP-P 应把它扩展为分层清理服务，同时保留启动清理、周期清理和手动清理入口。

### 37.9 5 分钟阶段预算

| 阶段 | 最大预算 |
| --- | ---: |
| 快照与数据健康预检 | 10 秒 |
| SQL 粗筛、排序和 Top-K | 30 秒 |
| 高级指标批量计算 | 90 秒 |
| 组合约束过滤 | 60 秒 |
| 候选快照与摘要写入 | 60 秒 |
| 收尾、审计和前端返回 | 30 秒 |
| 合计 | 280 秒 |
| 预留 | 20 秒 |

没有高级指标或组合过滤时，目标应在 60 秒内完成，而不是把 300 秒全部用满。

### 37.10 可观测性

为 `DiscoveryTaskRecord` 或任务结果补充：

- `snapshot_id`、`snapshot_hit`。
- `stage_durations_json`。
- `dirty_symbol_count`、`reused_score_count`、`rescored_count`。
- `coarse_match_count`、`advanced_match_count`、`result_rows_written`。
- `cache_key`、`cache_hit`。
- `degraded_reason`。
- 峰值内存和关键 SQL 耗时日志。

前端进度条按真实阶段显示，不再用“正在评分第 N 只”掩盖长时间数据库预载或网络刷新。超过阶段预算时显示具体慢在哪一步，并允许取消。

### 37.11 性能验收

必须在与当前规模相当的数据上验收：

- A 股 5,500 只，ETF 1,600 只。
- ready 快照命中时，快速扫描 P95 ≤ 300 秒。
- 相同快照/参数二次扫描 ≤ 10 秒。
- 快速扫描路径发起任何第三方 HTTP 请求即测试失败。
- 扫描主要数据库查询数量为固定量级，不随标的数形成 N+1。
- 自定义指标只处理 Top 300，超过限制时明确拒绝或转后台预计算。
- 单次运行写入结果数受 Top-K 限制，不再接近 `3 × 全市场标的数`。
- 扫描期间峰值内存建议不超过 300 MB。
- 旧新逻辑双跑至少 5 个交易日，使用相同快照时 Top 50 结果应一致；差异必须能追溯到过滤或排序规则。
- 快照缺失、构建失败、数据过期和数据库慢查询均能在 10 秒内给出明确状态，而不是无限等待。

建议新增：

- `tests/test_whitebox_discovery_snapshot.py`
- `tests/test_whitebox_discovery_incremental.py`
- `tests/test_whitebox_discovery_result_retention.py`
- `tests/test_whitebox_discovery_fast_scan.py`
- `tests/performance/test_discovery_5500_sla.py`，标记为 `slow`，在发布环境运行。

### 37.12 推荐实施顺序

1. 先增加阶段耗时、复用数和写入数监控，固定真实性能基线。
2. 增加快照 manifest/items 和必要复合索引。
3. 复用设置中的基础数据采集与定时任务，把评分物化接到现有同步任务成功后的后台任务链。
4. 新增只读快速扫描路径，保持旧路径可切换。
5. 加入 Top-K 高级过滤和相同参数缓存。
6. 扩展分层清理，确保过期候选不拖累查询，但底层快照仍可复用。
7. 对 A 股/ETF 做旧新双跑和 5 分钟 SLA 测试。
8. 达标后把快速扫描设为默认，旧“同步后扫描”保留为显式维护操作。

这套方案能够同时满足两个目标：候选结果按几天自动过期，避免页面和业务表不断膨胀；底层评分快照继续复用，避免候选一清理就重新扫描和重算全市场。

## 38. WP-S：接口风控、本地缓存与程序稳定性

### 38.1 当前能力与缺口

当前已经具备：

- `akshare_registry.py` 的接口登记、探测和标准/保守/自定义防风控策略。
- 随机延迟、重试次数和部分接口并发限制。
- A 股日 K 的东财→新浪→腾讯→本地通达信降级链。
- ETF 日 K 的东财→新浪降级链。
- 全市场基础数据、业务行情、外部因子和 DuckDB 因子仓库的本地存储。
- 异步任务心跳、取消、恢复、错误记录和任务中心。
- 部分任务错误已经区分摘要与技术详情。

仍需解决：

- 不同服务各自决定何时请求第三方，缓存命中规则不统一。
- 同一接口/参数可能被多个任务同时调用，缺少跨任务单飞去重。
- 接口持续 403/429/超时后仍可能反复尝试，缺统一熔断状态。
- 本地已有可用数据时，部分流程仍可能为了“最新”而阻塞等待网络。
- 异常有时直接把 HTTP、数据库或 Python 文本展示给普通用户。
- 任务超时、worker 退出或数据库锁未释放时，页面可能长期停在运行中。

### 38.2 统一外部数据网关

新增 `app/services/external_data_gateway.py`，所有 AKShare/网页抓取类请求逐步通过统一网关执行。业务服务只声明：

```text
interface_key
request_params
freshness_requirement
allow_stale
preferred_sources
task_context
```

网关统一完成：

1. 查询本地业务表/DuckDB 是否已有满足新鲜度的数据。
2. 命中则直接返回，并记录 `cache_hit` 和数据截止日期。
3. 缓存稍旧但仍可用时采用 stale-while-revalidate：先返回旧数据，再后台刷新。
4. 必须联网时检查接口熔断、频率预算和同参数在途任务。
5. 按接口策略加入随机延迟、指数退避和有限重试。
6. 主源失败时按现有 SourceChain 尝试备用源。
7. 标准化字段、校验契约后幂等 UPSERT 入库。
8. 返回统一的来源、缓存、降级和错误元数据。

网关不替换现有 AKShare Registry 和 SourceChain，而是把它们作为接口策略与数据源适配层继续复用。

### 38.3 缓存优先级

| 层级 | 内容 | 使用规则 |
| --- | --- | --- |
| L1 进程缓存 | 接口健康、短期探测结果、小型元数据 | 秒/分钟级 TTL，进程重启可丢失 |
| L2 业务数据库 | 标的、K 线、估值、财报、资金、情绪、宏观和消息 | 用户功能默认先查这里 |
| L3 DuckDB/快照 | 因子原始数据、因子值、评分快照和挖掘快照 | 批量计算、模型和全市场扫描优先读取 |
| L4 第三方接口 | AKShare、网页接口、AI 和推送平台 | 最后手段或显式刷新时使用 |

不同数据使用不同新鲜度，不能统一按“今天没有就重抓”：

- 日 K：交易日收盘后更新一次，盘中允许使用最近完整交易日。
- 财报：按报告期和公告时间增量同步，不按天全量抓取。
- 人气榜、资金和尾盘：按计划任务更新时间判断。
- 宏观：按指标发布频率判断。
- 接口探测失败结果：短期负缓存，避免设置页重复点击造成风控。

负缓存只能缓存明确的 403/429/不可达状态，不能把字段契约错误或程序 Bug 当作“接口暂时不可用”长期隐藏。

### 38.4 单飞、限流与熔断

- 相同 `interface_key + normalized_params` 同时只能有一个真实网络请求，其余调用等待同一结果或读取旧缓存。
- 每个主机、接口和任务类型分别设置并发上限，不能只设全局线程数。
- 429/403、连接重置和连续超时采用指数退避并叠加随机抖动。
- 达到失败阈值后进入 `open` 熔断状态，暂停真实请求并自动尝试备用源/旧缓存。
- 冷却后只允许一个 half-open 探测请求；成功才恢复。
- 手动“探测接口”也使用独立低频预算，不能绕过生产限流。
- 调度时间错峰，避免 16:00 后所有接口和任务同时启动。

建议增加 `external_endpoint_runtime`：

- `interface_key/source_key`。
- `state`：`closed`、`open`、`half_open`。
- `consecutive_failures`、`last_success_at`、`last_failure_at`。
- `cooldown_until`、`last_error_code`。
- `request_count/cache_hit_count/fallback_count`。

### 38.5 本地入库稳定性

- 所有外部数据先完成字段契约和日期范围校验，再进入业务表。
- UPSERT 唯一键必须由业务主键、日期和来源组成，重复任务不产生重复数据。
- 大批量写入按块提交，失败块可重试；禁止整批在内存无限增长。
- 快照采用临时批次→校验→原子切换 ready，不能让用户读到半批数据。
- 网络请求前释放长期数据库事务，网络结束后重新建立短事务。
- DuckDB 连接使用上下文管理器和单写锁；取消、失败和进程退出都必须 finally 释放。
- 数据源降级后保存真实 `source`，不能假装来自主接口。

### 38.6 任务防卡死

所有长任务统一遵守：

- `queued/running/paused/cancelled/done/failed/interrupted` 明确状态机。
- 每个阶段有预算时间、心跳时间和最后进度时间。
- worker 异常退出后由巡检标记 `interrupted`，不能永远显示 running。
- 超过阶段预算先进入 `stalled` 提示，显示当前步骤、已完成量和建议操作。
- 取消必须停止后续批次、关闭线程池、释放数据库/DuckDB 连接和文件锁。
- 任务重启从已提交批次恢复，不重复抓取已成功数据。
- 前端轮询有最大间隔、断线恢复和终态停止，不因一次网络错误丢失任务。

### 38.7 统一用户错误协议

后端业务错误统一提供以下字段：

| 字段 | 示例与用途 |
| --- | --- |
| `error_code` | `DISCOVERY_SNAPSHOT_NOT_READY`，供前后端稳定映射 |
| `user_message` | A股评分快照还没有准备完成，当前不能开始快速扫描 |
| `impact` | 不会产生新候选，已有候选和观察池不受影响 |
| `retryable` | 是否可以重试 |
| `completed` | 基础标的已同步 5530 只，评分尚未完成 |
| `next_actions` | 查看评分任务、使用上一快照扫描等可执行动作 |
| `technical_details` | 折叠展示的维护信息 |
| `correlation_id` | 日志关联 ID |

展示规则：

- 普通用户默认只看“发生了什么、影响什么、下一步做什么”。
- 技术堆栈、HTTP 响应和 SQL 错误折叠在“技术详情”，可复制给维护者。
- 同一错误码在所有页面使用一致中文文案。
- 禁止只显示 `Request failed`、`HTTP 500`、`NoneType`、数据库锁或第三方原始 HTML。
- 所有错误都带关联 ID，后台日志不得包含 API Key、Webhook、SMTP 密码或完整用户数据。

### 38.8 稳定性验收

- 本地存在合格数据时，扫描、回测、研究和评分不得发起第三方请求。
- 相同参数 20 个并发调用只产生一个真实网络请求。
- 接口连续失败后进入熔断，页面继续使用缓存或明确降级，不反复卡住。
- 强制取消因子、同步和挖掘任务后，DuckDB/数据库连接与文件锁均可再次获取。
- worker 被强制终止后，任务在巡检窗口内进入 interrupted，不再永久 running。
- 随机注入超时、429、空字段、数据库断连和响应格式变化时，用户都能看到可理解错误和下一步。

## 39. 前置条件引导与流程防误入

### 39.1 统一就绪状态

新增 `GET /api/v1/system/capabilities` 或等价聚合接口，为每项功能返回：

- `status`：`ready`、`degraded`、`blocked`。
- `reason_code/user_message`。
- `prerequisites` 及每项当前状态。
- `recommended_actions`。
- `data_cutoff_at`。

需要覆盖：

- 基础数据采集是否完成、覆盖率是否足够。
- 行情是否新鲜。
- 评分配置是否存在且已激活。
- 选用 Ridge 时因子仓库和活动模型是否 ready。
- 机会扫描快照是否 ready。
- 组合操作前是否已有组合、成员、规则和模拟账户。
- 自动交易前是否模拟账户、已开启、数据健康和规则均通过。
- AI 前是否已配置、测试成功并启用。
- 外部消息渠道前是否已配置、测试成功并启用。

### 39.2 页面门禁

页面可以浏览，但不满足条件的操作不能直接进入失败分支：

- 按钮显示禁用原因，不使用无解释的灰色按钮。
- 同时提供“去完成前置条件”入口。
- 能自动修复的条件提供一键动作，但执行前说明影响。
- 条件变为 ready 后自动刷新当前页面，不要求用户猜测是否需要重启。
- degraded 状态允许安全的只读/缓存操作，但明确数据日期和限制。

### 39.3 首次使用引导

普通用户首次使用按以下向导推进：

```text
1. 连接数据库
2. 初始化全市场基础数据
3. 检查数据覆盖与新鲜度
4. 选择并激活评分配置
5. 生成首个 ready 评分快照
6. 执行机会扫描
7. 建立观察池和模拟组合
8. 可选配置 AI 与外部消息渠道
```

完成项、可跳过项和阻断项使用不同状态。用户从深链接进入后续页面时，系统仍应显示相同前置条件卡片，不能绕过向导后只看到报错。

### 39.4 典型门禁示例

| 用户动作 | 前置条件 | 不满足时处理 |
| --- | --- | --- |
| 快速扫描 | ready 评分快照 | 使用上一快照或前往任务中心 |
| Ridge 评分 | DuckDB ready + 活动模型 | 回退手工权重或运行因子流水线 |
| 加入组合 | 至少一个组合 | 打开新建组合弹窗 |
| 自动交易 | 模拟账户 + 成员 + 规则 + 新鲜数据 | 显示缺失项，不创建订单 |
| 组合回测 | 有效成员与历史数据覆盖 | 推荐历史回补范围 |
| 使用 AI | AI 配置已测试 | 前往 AI 配置并测试 |
| 选择外部推送 | 渠道已配置并验证 | 禁止勾选，提供配置/测试入口 |

### 39.5 引导验收

- 新用户不阅读文档也能按向导完成第一次扫描。
- 任意后续操作被阻断时，用户能在当前页面完成或跳转处理前置条件。
- 门禁由后端能力状态决定，不能只靠前端隐藏按钮。
- 门禁变化、任务恢复和外部渠道验证都有自动刷新和明确成功状态。

## 40. WP-AI：从公式雏形到可落地的量化助手

### 40.1 当前能力与限制

当前 AI 已实现：

- 配置持久化到 `config/ai_config.json`，原子写入、重启保留和 API Key 脱敏展示。
- OpenAI 兼容、Anthropic Messages、Ollama 和自定义接口路径。
- Bearer、x-api-key、api-key、自定义 Header 和无鉴权模式。
- 连接测试、模型列表获取、超时、温度、最大 Token 和自定义 Header。
- 公式编辑器中的多轮对话、公式提取、插入和后端公式白名单校验。

当前 AI 本质仍是“公式编辑器助手”：

- 没有全局入口和页面上下文。
- 不能解释当前候选、数据健康、任务失败、组合和回测。
- 没有结构化工具调用、操作预览、确认和审计。
- 会话没有持久化，也不能回看 AI 依据了哪些数据日期和版本。
- 单一配置没有主备模型、健康状态和降级策略。

### 40.2 产品定位

AI 定位为“系统使用与量化研究副驾驶”，不是自动荐股或自动交易代理。它负责：

- 解释系统数据、评分、候选、风险和回测。
- 把技术错误翻译为普通用户能执行的步骤。
- 帮助生成公式、筛选条件、告警规则和复盘草稿。
- 引导用户完成缺失的前置条件。
- 对将要发生的业务操作生成预览。

AI 不得：

- 绕过数据健康、组合风控和功能门禁。
- 直接执行自动买卖或修改资金、持仓、规则。
- 在没有数据日期和依据时给出确定性买卖结论。
- 把第三方消息正文中的指令当成系统指令。

### 40.3 第一批落地场景

| 场景 | 用户问题 | AI 输出 |
| --- | --- | --- |
| 系统引导 | 为什么不能扫描？ | 缺失条件、影响和可点击修复步骤 |
| 数据诊断 | 这只股票数据可靠吗？ | 数据日期、来源、缺失项、降级情况和修复入口 |
| 候选解释 | 为什么进入候选池？ | 评分贡献、风险、有效期和来源扫描 |
| 公式助手 | 帮我写回踩均线且放量的条件 | 合法公式、字段说明、预览和插入按钮 |
| 观察助手 | 这些观察项今天有什么变化？ | 分数/价格/信号变化摘要，不自动下单 |
| 组合复盘 | 今天组合为什么亏？ | 成员贡献、风险事件、成本和待复盘事项 |
| 回测解释 | 为什么没有交易？ | 数据覆盖、条件阻断、规则与建议检查项 |
| 告警草稿 | 给这个组合建数据过期提醒 | 可编辑规则草稿，用户确认后保存 |
| 任务诊断 | 因子任务为什么停住？ | 当前阶段、耗时、心跳、错误摘要和安全操作 |

第一版优先完成系统引导、数据诊断、候选解释、公式助手和任务诊断，因为这些直接降低普通用户使用门槛。组合复盘和交易相关草稿在成员归因完成后接入。

### 40.4 上下文包

AI 不能自行查询任意数据库或调用第三方接口。后端按页面构造受控上下文包：

- 当前用户问题和页面来源。
- 标的、候选、观察、组合或任务 ID。
- 数据截止日期、来源、可信度和缺失项。
- 评分配置、模型版本和因子贡献。
- 当前能力门禁和允许的下一步动作。
- 与问题相关的少量行情、回测或绩效摘要。

上下文包必须限制大小、去除 API Key/Webhook/邮箱密码，并把新闻和第三方文本标记为“不可信数据内容”。AI 回复要附“数据截至、模型/规则版本和依据对象”，让用户能回到原页面核对。

### 40.5 工具与操作安全

第一阶段只开放只读工具：

- `get_capabilities`
- `get_data_health`
- `get_task_status`
- `get_symbol_research`
- `get_candidate_explanation`
- `get_portfolio_summary`
- `get_backtest_explanation`

第二阶段开放草稿工具：

- 生成自定义指标草稿。
- 生成筛选方案草稿。
- 生成告警规则草稿。
- 生成观察备注/标签草稿。
- 生成复盘草稿。
- 生成模拟订单草稿。

所有有副作用的操作使用三步流程：

```text
AI 建议
-> 系统规则校验和变更预览
-> 用户明确确认后由普通业务 API 执行
```

AI 本身没有绕过确认调用写接口的权限。模拟订单即使由 AI 起草，也必须重新经过现金、手数、T+1、涨跌停、数据健康和组合风控校验；自动交易永远由策略规则和调度器负责，不由对话直接触发。

### 40.6 结构化输出与审计

AI 响应统一包含：

- `answer`：普通语言说明。
- `evidence`：内部数据对象、日期和版本。
- `warnings`：数据陈旧、样本不足或模型限制。
- `suggested_actions`：允许的下一步。
- `draft`：可选的公式、规则或复盘草稿。

建议新增：

- `ai_sessions`：会话标题、来源页面、提供商和模型。
- `ai_messages`：角色、内容、上下文摘要、Token 与耗时。
- `ai_action_audits`：建议动作、预览、用户确认和最终结果。

会话保留期可配置，用户可以删除。审计记录只保存必要上下文摘要，不重复存完整 K 线和敏感配置。

### 40.7 提供商与降级

- 把当前单一 `ai_config.json` 兼容迁移为多个 AI Profile，支持主用和备用。
- 每个 Profile 保存提供商、地址、模型、鉴权、超时、用途和启停状态。
- 主模型超时/限流时可切备用模型或本地 Ollama；切换必须在回复中显示。
- AI 失败不能阻塞扫描、回测、告警和交易等核心功能。
- 对相同解释请求可按数据版本短期缓存，减少费用和接口风控。
- 限制单次上下文、最大输出、每日请求量和并发。

当前 API Key 虽然脱敏并限制配置文件权限，但配置仍是文件持久化。AI 与消息渠道应共用统一 Secret Store：优先环境变量/系统凭据或主密钥加密存储；日志、API 响应和导出文件永不返回明文。

### 40.8 前端入口

- 全局助手：每个主要页面可打开，自动携带当前上下文。
- 页面动作：候选、标的研究、任务、组合和回测提供“让 AI 解释”。
- 设置 → AI 助手：Profile 管理、连接测试、模型发现、主备优先级、用量和健康状态。
- 结果以解释卡、证据列表和操作草稿展示，不只显示聊天气泡。
- AI 未配置时显示用途和配置入口，不进入请求失败。

### 40.9 AI 验收

- AI 能正确解释至少五类当前对象：数据健康、任务、候选、标的和回测。
- 每个回答包含数据日期和依据对象；缺数据时明确说不知道。
- AI 生成的公式必须通过现有公式校验后才能插入。
- AI 建议的写操作不确认时不产生任何数据库变化。
- AI 无法连接、超时、限流或返回格式异常时，用户看到可理解错误且核心功能正常。
- 任何 AI 请求和日志均不出现数据库密码、AI Key、Webhook、SMTP 密码或完整 Secret。

## 41. WP-MSG：统一消息管理与多渠道推送

### 41.1 当前能力与缺口

当前已有：

- `alert_rules/alert_events` 告警规则、事件、冷却、确认和恢复状态。
- 站内告警中心和未确认计数。
- 任务失败、数据过期、评分跌破等事件来源。
- `WXPUSHER_ENABLED/ENDPOINT/APP_TOKEN/UID` 环境配置占位。

当前没有：

- 实际统一消息发送服务和发送队列。
- WxPusher 发送器、钉钉、QQ/机器人和邮件适配器。
- 设置中的渠道配置、测试、消息来源选择和路由策略。
- 每次发送的成功、失败、重试和第三方响应审计。
- 多渠道去重、摘要、免打扰和故障隔离。

因此不能把当前 WxPusher 环境变量描述为“微信推送已经实现”；它只是配置基础。

### 41.2 区分消息来源和推送渠道

消息来源回答“发生了什么”，推送渠道回答“发到哪里”。两者必须分开多选。

消息来源建议分组：

| 来源分组 | 事件示例 |
| --- | --- |
| 系统运行 | 系统启动、服务异常、备份结果、数据库迁移 |
| 数据与接口 | 数据过期、同步完成/失败、接口熔断/恢复、快照就绪 |
| 因子与模型 | 因子任务完成/失败、模型激活、模型回退、覆盖不足 |
| 机会与观察 | 新候选、候选即将过期、观察信号满足/失效、评分大幅变化 |
| 组合与交易 | 待确认订单、模拟成交、自动交易阻断、止损/退出信号 |
| 绩效与复盘 | 每日组合摘要、回撤预警、周报和待复盘事项 |

推送渠道：

- 站内消息/系统平台广播。
- 微信 WxPusher。
- 钉钉机器人 Webhook。
- QQ 机器人/OneBot 或用户提供的兼容 Webhook。
- 邮件 SMTP。
- 通用 Webhook，供后续企业微信、飞书或自有服务接入。

个人 QQ 没有适用于所有账号的稳定官方直推接口，第一版不写死非官方服务。系统提供 OneBot/兼容 Webhook 适配器，由用户自行配置可用机器人地址和 Token，并明确显示可用性风险。

### 41.3 设置中的消息管理

在设置新增“消息管理”，包含四个页签：

1. 渠道配置。
2. 推送策略。
3. 消息模板。
4. 发送记录。

渠道状态：

```text
未配置 -> 已配置待测试 -> 测试成功 -> 已启用
                         \-> 测试失败
```

只有“测试成功 + 已启用”的第三方渠道才能在推送策略中勾选。未满足时选项禁用，并提供“去配置”“立即测试”入口。站内消息不需要第三方配置，默认可选。

每条推送策略包含：

- 策略名称和启停。
- 一个或多个消息来源/事件类型。
- 最低严重级别。
- 一个或多个推送渠道。
- 适用标的、观察池或组合范围。
- 即时发送或定时摘要。
- 冷却、去重和免打扰时间。
- 使用的消息模板。

示例：

```text
策略：高风险即时提醒
来源：任务失败 + 数据严重过期 + 自动交易阻断
渠道：站内消息 + 微信 + 邮件
级别：error

策略：每日机会摘要
来源：新候选 + 观察信号满足
渠道：站内消息 + 钉钉
发送：每个交易日 17:30 汇总
```

### 41.4 渠道配置字段

| 渠道 | 必要配置 |
| --- | --- |
| 站内消息 | 无，系统默认渠道 |
| WxPusher | Endpoint、AppToken、UID/Topic ID |
| 钉钉机器人 | Webhook、签名 Secret、关键词（如启用） |
| QQ/OneBot | Webhook、Access Token、目标群/用户 ID、消息类型 |
| 邮件 | SMTP 主机、端口、TLS/SSL、用户名、密码/授权码、发件人、收件人 |
| 通用 Webhook | URL、HTTP 方法、鉴权 Header、请求模板、超时 |

敏感字段只返回“已配置”状态和掩码。渠道导出、备份和日志不得包含明文 Secret。

### 41.5 数据模型

建议新增：

`notification_channels`：

- `id/name/channel_type`。
- `enabled/status`。
- `config_encrypted_json` 或 Secret Store 引用。
- `verified_at/last_test_at/last_error_code`。
- `created_at/updated_at`。

`notification_policies`：

- `id/name/enabled`。
- `source_types_json/min_severity`。
- `scope_type/scope_ids_json`。
- `delivery_mode`：`immediate`、`digest`。
- `digest_schedule/quiet_hours_json`。
- `cooldown_minutes/dedup_window_minutes`。
- `template_id`。

`notification_policy_channels`：

- `policy_id/channel_id` 唯一关系。

`notification_outbox`：

- `event_key` 唯一幂等键。
- `source_type/source_id`。
- `channel_id/policy_id`。
- `payload_json/status/attempt_count/next_retry_at`。
- `created_at/sent_at`。

`notification_deliveries`：

- 每次发送尝试、耗时、状态码、脱敏响应摘要和错误码。

`notification_templates`：

- 标题、正文、Markdown/纯文本格式、变量定义和版本。

现有 `AlertEvent` 继续作为正式告警事实，不把每个第三方发送结果塞进 `data_json`。消息系统可以消费 AlertEvent，也可以消费任务完成、成交等非告警事件。

### 41.6 Outbox 与异步发送

业务事务只负责写业务事件和 Outbox，不直接等待第三方平台：

```text
业务事件/AlertEvent
-> 匹配推送策略
-> 同事务写 notification_outbox
-> 后台 dispatcher
-> 渠道适配器
-> delivery 记录
```

这样即使微信、钉钉或邮件不可用，告警和交易记录仍能正常落库。

发送规则：

- `event_key + channel_id` 唯一，防止任务重试造成重复推送。
- 超时和临时错误使用指数退避，达到上限进入 dead-letter。
- 鉴权失败或配置失效直接暂停该渠道并产生站内系统告警。
- 一个渠道失败不影响其他已选渠道。
- dispatcher 重启后继续处理未完成 Outbox。
- 用户可对失败记录手动重发，但继续使用同一业务事件审计链。

### 41.7 渠道适配器

统一接口：

```text
validate_config
send_test
send_message
normalize_error
mask_config
```

建议文件：

- `app/services/notifications/base.py`
- `app/services/notifications/in_app.py`
- `app/services/notifications/wxpusher.py`
- `app/services/notifications/dingtalk.py`
- `app/services/notifications/onebot.py`
- `app/services/notifications/email.py`
- `app/services/notifications/webhook.py`
- `app/services/notifications/dispatcher.py`

适配器统一使用有限超时、重试和熔断，不允许第三方 SDK 建立无法取消的永久线程。

### 41.8 防打扰与隐私

- 相同来源、标的、规则和状态在去重窗口内只发送一次。
- 高频 info/warn 可合并成摘要；error 默认即时发送。
- 支持交易日、工作日和免打扰时间；最高风险是否绕过免打扰由用户明确设置。
- 消息只包含必要标的、状态和跳转 ID，不推送数据库连接、Token、完整策略配置或技术堆栈。
- 第三方内容长度超限时自动摘要，并保留站内完整详情。
- 所有模板变量做转义，防止 Markdown/Webhook 注入。

### 41.9 推荐实施顺序

1. 建立统一事件、Channel、Policy、Outbox 和 Delivery 模型。
2. 先接站内消息，验证来源→策略→发送记录闭环。
3. 实现 WxPusher 和邮件，覆盖个人使用的主要场景。
4. 实现钉钉机器人和通用 Webhook。
5. 实现 OneBot/QQ 兼容适配器，并明确第三方服务依赖。
6. 增加摘要、免打扰、模板和失败重发。
7. 将任务、数据健康、候选、观察、交易和绩效事件逐步接入。

第一版至少交付站内、WxPusher、钉钉、QQ/OneBot、邮件五类渠道的配置和测试入口；如果某个平台缺少可用配置，系统仍可正常使用其他渠道。

### 41.10 消息管理验收

- 用户可同时选择多个消息来源和多个渠道。
- 未配置或测试失败的第三方渠道不能被策略选中，并明确提示如何处理。
- 测试消息能显示第三方响应、耗时和失败原因。
- 同一业务事件重放不会向同一渠道重复发送。
- 任一外部平台超时/限流/鉴权失败时，站内消息和其他渠道仍正常。
- 服务重启后未发送 Outbox 可继续处理。
- 用户可以查看每条消息来自哪个业务事件、匹配哪个策略、发往哪些渠道及各自结果。
- API、日志、导出和前端状态中均不出现完整 Token、Webhook 签名 Secret 或 SMTP 密码。

## 42. 横向能力的发布门槛

机会中心、标的研究和组合交易改造正式切换前，除原业务验收外，还必须满足：

1. WP-S：核心页面本地命中优先，接口失败可降级，任务不会永久卡住。
2. 前置条件：用户不能在条件缺失时误入下游，只能安全浏览或按引导修复。
3. WP-P：ready 快照下 A 股/ETF 快速扫描 P95 不超过 5 分钟。
4. WP-AI：至少完成系统引导、数据诊断、候选解释、公式和任务诊断；AI 不直接写业务状态。
5. WP-MSG：站内与已配置外部渠道具备策略、Outbox、重试和发送审计。

推荐整体实施顺序调整为：

```text
WP0 基线与开关
-> WP-S 稳定性、错误和前置条件
-> WP-P 快照与快速扫描
-> WP1/WP2 机会中心与观察池
-> WP-MSG 统一消息管理
-> WP3/WP4/WP5 流转、成员与标的研究
-> WP-AI 上下文助手
-> WP6/WP7/WP8 交易、回测与归因
-> WP9 清理旧入口
```

AI 和外部消息属于增强能力，故障时必须降级而不能拖垮量化核心；稳定性、前置条件和本地缓存属于强制底座，未完成前不得用新增页面掩盖旧流程的卡顿和错误。
