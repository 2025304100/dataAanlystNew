> 任务卡：T38（PH7，G1 并行决策与实施）

> 需求文档 §6.1.6（性能 G2/G1）
> 任务卡约束：`not_do = 不在无探针数据支撑时盲目实现并行`；

---

## 一、结论（先给答案）

**本期不做 G1 并行实现**，`app/services/factors/mining/parallel.py` **暂不落地**。

理由一句话：设计文档 §7.4 明确要求「**M3 依据探针数据定位瓶颈后再决定 G1 并行哪一段，
否则『压测后决定』无从谈起**」，而当前**真实库中探针数据为 0 行**——没有任何一代
挖掘真正跑完过，无法定位瓶颈、无法估算加速比。在无数据支撑下实现并行，
既违反任务卡 `not_do`，也会把一个高风险的并发模型引入一条尚未跑通的主链路。

这**不等于否定 G1**：离线实测显示（见 §三）中/大数据量下「计算 / 传输」比达
**16~23 倍**，G1 在技术上**是划算的**。缺的只是真实负载数据。
一旦 §五 的触发条件满足，按 §六 的实施方案即可落地。

## 二、决策依据一：探针数据现状（决定性事实）

### 2.1 数据查询结果

| 项 | 结果 |
|----|------|
| 表 `factor_mining_generations` | **存在**（结构已建） |
| 行数 | **0** |
| 去重 `run_id` | **0** |

即：**挖掘主链路从未真实跑完一代**，`probe_*` 六段耗时与三项缓存指标全部无样本。

### 2.2 为什么是 0 行（根因，不是数据丢了）

`app/api/routes/factor_mining.py` 共 22 条路由，其中**仅 3 条已实现**
（`locks/status`、`candidates/{id}/submit`、`candidates/batch-review`），
其余全部 `raise NotImplementedError`：

- 批次创建 `POST /factor-mining/runs` —— **未实现（M5）**
- 批次列表 / 详情 / 取消 / 暂停 / 恢复 / 停止 / 放弃 —— **未实现（M5/M7）**
- 代际汇总 `GET /runs/{id}/generations` —— **未实现（M7）**
- 候选列表、血缘、AI 预览、评估相关 —— **未实现（M7~M13）**

探针埋点本身**已实现且正确**（`performance_probe.GenerationProbe` →
`to_generation_fields()` → 写 `factor_mining_generations`），
缺的是**调用它的那条主链路**。因此：不是"没埋点"，而是"没跑过"。

### 2.3 这直接卡住了 G1 的哪一步

G1 的决策链条是：`探针数据 → 定位瓶颈段 → 选择并行粒度 → 估算加速比 → 实施`。
当前链条在**第 1 环就断了**：

| 决策所需输入 | 当前状态 |
|---|---|
| 单代总耗时 `evaluation_duration_ms` | 未知（无样本） |
| 六段耗时分布（data_load / ast_eval / subexpr_compute / factor_assemble / metric_calc / db_write） | 未知 |
| G2 命中率 `probe_g2_hit_rate`、`subexpr_total/unique` | 未知 |
| 种群规模 × 单因子评估耗时的乘积（并行总量） | 未知 |

没有这些，「并行哪一段」「几个进程」「能快多少」全是猜测。

## 三、决策依据二：可离线实测的风险项（补充证据）

探针拿不到，但 G1 的**三大风险项中有一项可以离线实测**——Windows `spawn` 开销。
本机实测（32 核，脚本见 §七，可复现）：

### 3.1 进程启动开销

| 测量项 | 实测值 |
|---|---|
| 冷启动 spawn + init + 一次任务 | **1199.8 ms** |
| 其中子进程 `import numpy + pandas` | **772.0 ms**（占 64%） |
| 建池（2 进程）+ 20 次轻量任务，单次摊薄 | 23.8 ms |
| **池已就绪后，边际单次往返** | **0.19 ms** |

解读：固定成本约 **1.2 秒/新进程**（主要是 import），但**池复用后边际往返
仅 0.19 ms**——只要满足「进程池复用 + 任务数足够多」，启动开销可以被摊薄。
这与开发文档 §3.13 的「进程池复用」要求一致，也说明**启动成本不是 G1 的否决项**。

### 3.2 数据传输 vs 计算（决定并行是否划算）

`spawn` 走 pickle，父→子传面板的往返成本与收益对比（2 进程池，20 次均值）：

| 量级 | 形状 | 大小 | 传输往返 | 20 pass 向量化计算（净增） | 计算 / 传输 |
|---|---|---|---|---|---|
| 小（周频/少量标的） | (60, 50) | 0.02 MB | 0.21 ms | 0.26 ms | **1.2×** |
| 中（日线 5 年 × 500） | (250, 500) | 0.95 MB | 2.42 ms | 39.26 ms | **16.2×** |
| 大（长周期全市场） | (1000, 3000) | 22.89 MB | 33.98 ms | 773.91 ms | **22.8×** |

判据：**单任务纯计算 > 传输往返 × 进程数** 才划算。

- 中、大两种量级下计算/传输达 **16~23×**，即使 6 进程（传输成本 ×6）仍有明显净收益；
- 小量级下计算≈传输（1.2×），**并行反而更慢**——此时应走共享内存或不做。

**结论：G1 在技术上具备可行性，且中/大数据量下收益明确。**
这进一步说明：**否掉本期 G1 的原因是"没有真实负载数据"，不是"并行不划算"。**

## 四、为什么最终是「不做」而不是「做」

对照设计 §7.4 与任务卡约束，G1 落地需要同时满足下列判据：

| # | 判据 | 当前 | 是否满足 |
|---|------|------|---------|
| 1 | 有 ≥1 个完整挖掘 run 的探针数据 | 0 行 | ❌ |
| 2 | 能定位瓶颈段（六段耗时分布已知） | 未知 | ❌ |
| 3 | 单代总耗时已知，可估算加速比 | 未知 | ❌ |
| 4 | G2 命中率已知（命中率高则 subexpr 段已无并行价值） | 未知 | ❌ |
| 5 | 主链路本身可跑通（有可并行的真实负载） | 未打通（M5/M7 未实现） | ❌ |
| 6 | 中/大数据量下并行净收益为正 | **16~23×（已实测）** | ✅ |

**6 条判据仅满足 1 条** —— 满足的是"理论可行性"，缺的是"工程必要性"。
在此状态下实现并行会同时踩三个坑：

1. **无法验证**：没有可跑的真实一代，无法证明并行正确、也无法证明它更快；
2. **风险叠加**：开发 §3.13 已识别三项风险——项目无 `ProcessPool` 先例
   （全部为 `ThreadPoolExecutor`，且仅用于 akshare I/O 超时兜底）、
   Windows 无 `fork`（spawn 每子进程重 import）、
   `multiprocessing.shared_memory` 在 Windows 有 `resource_tracker` 泄漏坑。
   在一个尚未跑通的单进程链路上同时引入这三项，故障定位成本极高；
3. **可能白做**：若后续探针显示瓶颈在 `db_write`（受 DuckDB 单写锁约束，
   并行不但无益反而加剧锁竞争），则整个 G1 方向需要推翻重来。

## 五、重开 G1 的触发条件（量化门槛）

满足**全部**下列条件时，重开 T38 的实施部分：

1. **主链路打通**：`POST /factor-mining/runs` 等批次/代际接口已实现，
   能完整跑完一个挖掘任务（含 ≥3 代进化）；
2. **探针数据到位**：`factor_mining_generations` 中**至少 1 个 run、≥3 代**数据；
3. **瓶颈可定位**：六段耗时分布清晰，且**可并行段**
   （`ast_eval` + `subexpr_compute` + `metric_calc`）**合计占比 ≥ 60%**；
4. **并行有净收益**：单代可并行段耗时 > （实测传输往返 + 调度开销）× 目标进程数；
5. **瓶颈不在写侧**：若 `db_write` 或 G2 缓存命中率已使瓶颈消失
   （如 `probe_g2_hit_rate` 长期 > 80%，子表达式几乎全部命中缓存），
   则**先优化缓存而非并行**。

不满足时维持「不做」——这是合格且更省成本的决策。

## 六、数据到位后的实施方案（已固化，按图施工）

> 本节为 `parallel.py` 的设计蓝图；结论为「不做」时该文件不落地，
> 避免无数据支撑的实现（任务卡 `not_do`）。

**并行粒度（二选一，按探针结果定）**

| 粒度 | 适用场景 | 传输特征 |
|---|---|---|
| 因子级并行 | 种群大、单因子评估独立 | 每任务一份面板 → 走共享内存 |
| 子表达式级并行 | `subexpr_compute` 占比高且 G2 命中率低 | 子表达式粒度小、数量多 |

**进程策略（开发 §3.13）**

- 进程数 `min(6, cpu - 2)`（本机 32 核 → **6**），并按内存自适应：
  `<2GB` 串行 / `<4GB` 2 / `<8GB` 4；
- **进程池复用**（实测边际往返 0.19 ms，池复用是摊薄 1.2 秒启动成本的关键）；
- **主进程汇总写入**，子进程不写共享存储（规避 DuckDB 单写锁）；
- 贪心负载均衡（大面板优先派发，减少尾部等待）。

**风险规避**

| 风险 | 规避方案 |
|---|---|
| 无 `ProcessPool` 先例 | 单引入、单开关，默认关闭；串行路径保持不变作为回退 |
| Windows 无 `fork` | 强制 `spawn`；子进程入口函数保持**模块级可 pickle**，不在闭包/局部函数里派发 |
| `shared_memory` `resource_tracker` 泄漏 | **优先不用** `shared_memory`；中/大数据量实测传输仅 2.4~34 ms，直接 pickle 传参已足够。若确需共享内存，必须显式 `close()` + `unlink()` 并加 `try/finally` |
| 子进程重 import 慢（772 ms） | 长生命周期进程池，避免每代重建 |

**验收口径**：同种子下并行与串行的 ICIR/适应度结果**逐个体一致**（差异 < 1e-9），
且单代墙钟耗时下降 ≥ 30%。
