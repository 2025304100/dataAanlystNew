> 评审对象：行情/数据覆盖率相关功能域（行情统计看板、外部数据字段覆盖、系统数据健康、sync_coverage 覆盖率台账）。
> 评审方式：代码走读 + 验证库实测结论复用（`docs/第三方数据源接口格式对齐与完整性排查-2026-10-25.md`、`docs/行情统计看板口径优化与回归-2026-10-25.md`）。

## 1. 现状价值评审（客观基线）

### 1.1 功能盘点：四套覆盖率口径并存

| # | 载体 | 口径 | 能力 | 代码位置 |
|---|---|---|---|---|
| ① | 行情统计看板（UniverseHealthDashboard，内嵌于行情数据面板） | 按 scope（cn/us × stock/etf）**实际日线记录**聚合：登记数/有行情数/无行情数/上市日期登记/缓存差异/最近完整交易日（本地 trade_calendar 判定） | 只读展示 + 缺失样本（SLY、301583）+ 刷新统计 | `app/services/universe_health.py:37`、`frontend/src/components/UniverseHealthDashboard.tsx:93-104` |
| ② | 外部数据字段覆盖（ExternalDataSync + 数据检查页 CoverageDiagnostics） | 字段级：nonnull_rows 占比、当天覆盖、连续天数、availability、能否用于因子评价；质量快照只统计字段 NULL 覆盖率 | 展示 + 触发同步 + **缺口检测/修复（唯一现成的"覆盖率→治理动作"闭环）** | `DataCenter.tsx:33,214-217`、`app/services/external_data_sync_task.py:568-651`、`app/api/routes/external_data.py:226` |
| ③ | 系统数据健康（DataDiagnosticPanel） | 全局 covered_symbols / coverage_pct / 7 天 stale；单标的按 1m/1q/1y/3y 的 K线与评分覆盖率（**自然日×5/7 近似交易日，口径粗糙**） | 单标的诊断 + 触发修复（bars/scores/both） | `app/api/routes/system.py:138,352`、`DataDiagnosticPanel.tsx:24-26,233-235` |
| ④ | 覆盖率台账（DataSyncCoverage） | 只记"确认点"（dataset×symbol×trade_date×fields_json×completed），**不触发补数**；汇总仅 dataset 级 earliest/latest/点数 | 无用户界面，仅内部记录 + 兼容读 | `app/services/sync_coverage.py:1-6,145` |

另有相邻但不属本域的：因子值覆盖率（`app/services/factors/readiness.py:56-57`，检查 coverage_zero/below_threshold）、组合巡检对账覆盖率（`portfolio_inspection_coverage.py`，账户口径）——与行情覆盖率不共用服务，本次不动。

### 1.2 原始目标、使用场景、用户与频次

- **原始目标**：回答"我的行情/外部数据齐不齐"，支撑三个下游——每日评分（决策台）、因子计算、回测（回测读旧表 daily_bars）。
- **真实用户**：平台单人运营者（自用量化验证环境 gpfx_validation，MySQL 5.7.26）。无多角色，"责任人分派/工单推送"没有天然收件人。
- **使用频次**：同步调度每日自动跑（`scheduled_tasks.py` 三条日更）；看板本身**低频**——集中在验收、排查、出报告时打开（近两周的使用均由数据异常排查触发，而非日常巡检）。
- **当前运行态**：验证环境处于**只读验收模式**（登记/重检/修复/审核禁用，仅查看与历史回查），任何"自动修复类"能力必须过 capability_gates 只读门控。

### 1.3 重合度、能力缺口与痛点

**重合度**：① 和 ③ 都在回答"K线齐不齐"，口径不同（实际记录 vs stale 判定 + 自然日近似），三套统计（①③以及 `/universe/stats`）未共用服务，数字互相对不上时无法解释（`/universe/stats` 旧口径曾把 5554/5555 四舍五入显示为 100%，本轮已修为两位小数但旧接口仍在）。

**能力缺口（实测坐实，不是猜测）**：

| 缺口 | 实测证据 |
|---|---|
| **只记不补**：覆盖率台账只记"确认点"，无任何缺口检测调度；backfill/range-repair/field-repair/gap-repair 全部手动 | `sync_coverage.py:1-6`、`scheduled_tasks.py:141-330` 仅三条日更 |
| **静默停更**：空帧标 `is_synced=1`、empty 计入成功、熔断标的（sync_failed≥5，实测 41 个）被跳过且无任何面板提示 | `universe_sync.py:699-704,775-780`、`market_data_sync_task.py:201-203`；**1713 个标的自 10-19 起静默停更且全部标"已同步"**，上证指数 000001 停更 2.5 个月 |
| **发现靠人工**：看板没有"停更标的数/熔断数"指标，没有趋势，1713 事件是人工比对每日行数才发现的 | `universe_health.py` 返回结构中无 stale/停更聚合 |
| **覆盖率数字无法下钻**：缺失样本只展示 2 条"零K线"标的，不展示"停更 6 天"这类最常见缺口 | `UniverseHealthDashboard.tsx:93-104` |
| **回测侧不可见**：daily_bars（回测读的旧存储）2026 年 75% 行 volume 单位污染，回测提交前无任何数据就绪检查 | 排查文档 §5.1 |

**痛点定性**：性能（看板全量聚合 2300 万行，客户端超时已放宽 60s，尚可接受）、口径（三套并存是最大痛点）、易用性（数字不能直达缺失明细，修复入口分散在三个页面）、可维护性（统计逻辑散在 4 个 service）。

### 1.4 价值定级与处置建议

| 功能 | 价值 | 理由 | 处置建议 |
|---|---|---|---|
| ① 行情统计看板（新口径） | **高** | 行情完整性直接决定评分/回测可信度；实测 24.2% 标的停更；本轮口径修复后已是全项目最可信的覆盖率视图 | **独立保留**，升级为覆盖率治理主入口（本报告 P0/P1 围绕它展开） |
| ② 外部字段覆盖 + 缺口修复 | **中高** | 已具备唯一的"缺口→修复"闭环，但只覆盖 valuation/financial/capital_flow 三个数据集 | 独立保留；把闭环模式复用给行情（见 P1-5） |
| ④ sync_coverage 台账 | **中高** | 原子记账设计严谨（与源写入同事务、不隐式补数），但缺"缺口视图"，当前对用户不可见 | 保留，补缺口视图（P1-6） |
| ③ 系统数据健康 + DataDiagnosticPanel | **低-中** | 与 ① 重复回答同一问题且口径更粗糙（自然日×5/7）；单标的诊断+修复入口有独立价值 | **合并进数据检查**：后端收敛复用 `read_universe_quality` 口径，保留单标的修复入口，逐步淘汰自然日近似 |
| `/universe/stats` 旧口径 | 低 | is_synced 标记口径已被证明失真（SLY 标已同步 0 行） | 保留字段兼容，前端已切新口径；旧四舍五入展示**精简下线** |
| 因子覆盖率 / 组合巡检覆盖率 | — | 不同域，口径独立成立 | 不动 |

**基础结论**：覆盖率功能方向上价值为高，但目前形态是"只看的统计"而不是"能治的治理"——价值被"只记不补、发现靠人工"打了对折。本次改造的主轴不是加新页面，而是**补上"缺口检测→可见→可修"的后半段**。

## 2. 务实优化（P0/P1/P2，均可低成本落地，不破坏现有口径）

### P0（止血：让"已同步"不再说谎）

| 编号 | 维度 | 优化项 | 做法 | 口径保护 |
|---|---|---|---|---|
| P0-1 | 数据计算 | 空帧不再标已同步 | `universe_sync.py:699-704` 空帧改置 `is_synced=2`（空结果待复核）；`market_data_sync_task.py:201-203` empty 单独计数，不再计入 ok_count | 新增枚举值而非改语义；检查全部 `is_synced` 消费方做兼容；看板读实际记录，天然不受影响 |
| P0-2 | 监控告警 | 看板暴露"停更/熔断"两个红字指标 | `read_universe_quality` 增补：最后K线 < 最近完整交易日的标的数、`sync_failed>=5` 熔断中标的数（纯 COUNT 聚合，兼容 MySQL 5.7），UniverseHealthDashboard 顶部红字展示 | 只新增聚合字段，不改动现有四项概览与分市场口径 |

| 编号 | 维度 | 优化项 | 做法 | 口径保护 |

## 3. 业界视角价值发散（**全部为创意提案，非本次需求**）

### 3.2 中期迭代（下次立项候选）

| **⑧ 分层口径体系**：覆盖率指标分层注册（原始数据层/因子层/组合校验层），层间关系显式化（因子覆盖率↓可能因行情层缺口） | 数据中台分层 metrics；DAMA 元数据血缘裁剪版 | 现在因子 readiness 报"coverage_zero"时不告诉你是不是行情层缺数导致的——分层后可归因 | P2-2 统一 coverage service | 中-高 | 抽象过度风险：先保证两层（行情→因子）打通再谈体系 |

### 3.3 长期架构规划（仅储备，不承诺）

| 创意 | 业界同类做法 | 业务价值 | 落地前提 | 预估成本 | 风险 |

### 3.4 明确不引入的创意（与本项目架构/规模冲突）

| 创意 | 不引入理由 |
|---|---|
| 工单责任人分派 + 邮件/IM 推送 | 单人自用平台，无用户体系、无收件人；站内横幅 + 待办列表已覆盖场景 |
| 重型数据目录/元数据平台（DataHub/Collibra 类） | 单库单服务规模，元数据管理成本远超收益；健康分创意（⑤）已覆盖其 20% 核心价值 |
| 实时流式覆盖率监控（Kafka/Flink 栈） | 数据链路是日更批处理，实时监控与现有调度模型冲突，且 MySQL 5.7 单机撑不起流式栈 |
| 自动改写/自动删除存量数据 | 违反项目"只读保护、不可变基线"的验收原则；一切存量修复必须经人工确认的定向 range-repair（P0-3 是前提） |
| LLM 覆盖率问答助手 | 与现有 AI 助手域重叠但增益极小——覆盖率问题本质是"数字+下钻"，不需要自然语言层 |

## 4. 方案汇总与建议

### 4.1 本次迭代推荐（按序执行）

1. **P0-1 空帧不标已同步** —— 根治"静默停更"的源头，本轮全部痛点的起点；
2. **P0-2 停更/熔断红字指标** + **P0-4 一键修复** —— 让已发生的问题可见、可修；
3. **P0-3 range-repair symbol 过滤** —— 为存量修复铺路，也是排查文档 P0.1 的前置；
4. **P1-1 交易日历对账任务（先只产缺口清单，自动回补默认关）** —— 本次迭代的价值主轴：覆盖率从"只记"变"对账"；
5. **P1-5 缺口告警横幅** + **P2-3 每日快照表（最小版：只存不算）** —— 为下一次迭代的趋势/门禁攒数据。

以上合计约 6 项，全部复用现有基建（trade_calendar、async_tasks、capability_gates、看板横幅模式），无新表除快照表外不超过一张。

### 4.2 产品路线储备（高价值点子，按建议优先级）

1. **④ 覆盖率门禁**（保护回测可信度，痛点最实）→ 2. **⑥ 缺口修复任务闭环**（把 P1-1 的缺口清单变成处置流）→ 3. **⑤ 数据资产健康分**（等趋势数据攒够 1 个月）→ 4. **⑦ 规则阈值配置化**（与门禁绑定）→ 5. **⑧⑨ 分层与统一引擎**（口径收敛 P2-2 完成后再评估）。

### 4.3 红线提醒（本次改造中不动的）

- 原有统计口径字段全部保留：`/universe/stats` 旧字段、`is_synced` 语义兼容（新增枚举不改旧值）、看板四项概览与分市场口径不变；
- 所有行情主键/标的键/日期/OHLC/量额/来源/时间戳字段不动；统计一律列查询+聚合，不改 ORM 实体、不提交业务事务（沿用本轮验收模式）；
- 新增统计 SQL 全部兼容 MySQL 5.7（无窗口函数/NULLS LAST，环比在写入时算好）；
- 只读验收模式下：缺口检测可跑（只读），一切修复动作（自动 backfill、门禁豁免、任务核销）必须过 capability_gates 门控或保持禁用。
