## 0. 本版编写口径（请先看这里）

本计划按 **「全量范围 + 紧迫度分级」** 编写：

- **P0（急 / 必做）**：不做就无法验证核心假设，或无法交付。占本次开发范围。
- **P1（不急 / 可延后）**：延后有代价但不阻塞，**每一项都标注明确的触发条件**——到点自动进入排期，不是无限期搁置。
- **P2（不急 / 二期）**：明确不在本次开发范围，只做数据与接口预留。

对应地，本文件第 1 章给全量范围总表（含不急项），第 3 章给 P0 的阶段计划，第 7 章是**「不急的开发」专章**（列出每一项的延后理由、代价、触发条件）。这样无论你想看"现在先做什么"还是"哪些可以先放着"，都能直接定位。

**与前两份文档的最大差异**：本计划**不采用"按层交付"**（M1a 地基 → M1b 闭环 → M2 算法 → M3 收尾），改为**「垂直切片优先 + 反馈门禁前置」**，并把人力从 12 人收敛到 4+3。差异清单见第 9 章。

## 1. 计划总纲

### 1.1 交付目标（什么算成功）

本项目的成功标准**不是"功能做完"，而是这三条同时成立**：

| # | 成功判据 | 验证方式 |
|---|---------|---------|
| S1 | 系统能**自主挖出**显著优于人工模板的因子 | W3 末 GO/NO-GO 门禁（第 4 章） |
| S2 | 挖出的因子**不是噪音**（OOS 不崩） | ≥5 个因子 `decay_ratio ≥ 0.5` 且 test 段 ICIR > 0 |
| S3 | 全过程**可复现、无泄漏** | 固定种子重跑一致；泄漏哨兵单测全程绿 |

> **S1 是真正的分水岭。** 如果系统只是"把 25 个经典模板跑了一遍"，那不需要 12 周开发，1 天写个脚本就够。项目的全部价值在于"进化搜索带来了增量"。

### 1.2 三条铁律

| # | 铁律 | 说明 |
|---|------|------|
| 铁律一 | **垂直切片优先** | 先打通一根能通水的最细管子，第 3 周就打开水龙头看有没有水，再决定要不要修大管子。**绝不先建 3 周地基再看结果。** |
| 铁律二 | **泄漏哨兵先写先绿** | 切分泄漏是唯一"写错了全盘皆输"的模块。哨兵单测在 W0 就写，之后所有人写的代码都必须让它保持绿。 |
| 铁律三 | **反馈前置** | 任何一个"需要 3 周才能验证"的假设，都要想办法拆成"3 天能验证"的版本。 |

### 1.4 三条铁律对应的组织纪律

- **不在 PH1 碰 DSL / 候选池 / AI / F1**。PH1 只证明一件事：进化搜索能不能带来增量。
- **任何"顺手也做了"的冲动都要拒绝**。PH1 的代码允许"丑"，允许用写死的标的列表，允许结果页只有一个表格。
- **探针与哨兵进 P0**。它们看起来是"非功能需求"，但它们是后面所有决策的依据，不能延后。

## 2. 人力与角色（4 + 3）

### 2.1 为什么是 4 人不是 12 人

关键路径是 **串行的**：`数据地基 → 泄漏防线 → 最小闭环 → 门禁`。往串行链条上加人不会缩短工期，只会增加沟通成本和接口冲突。前一份 WBS 的 12 人是**"要人用的资源规划"**（向上要预算用），本计划是**"实际怎么干"**。

| 阶段 | 主力 | 弹性 | 说明 |
|------|------|------|------|
| PH0 | 3 | 0 | TL + 后端 A + 后端 B |
| PH1 | 4 | 1（QA） | 前端这时只做最简结果页 |
| PH2 | 4 | 1（QA） | 前端全量投入 |
| PH3 | 4 | 2（算法 + QA） | 算法弹性到岗 |
| PH4 | 4 | 3（前端 + QA） | 前端加到 2 人做打磨 |

### 2.2 角色与归属

| 角色 | 人数 | 负责范围 | 关键约束 |
|------|------|---------|---------|
| **TL（我）** | 1 | 架构裁决、**泄漏哨兵**、DSL 扩展、评估切分接入、门禁主持、灰度开关 | 泄漏防线**不外包**——这是唯一"写错了全盘皆输"的模块 |
| **后端 A** | 1 | 进化引擎（主循环/选择/繁殖/观测）、去重、G2 缓存、性能探针 | 关键路径，禁止被拉去做杂活 |
| **后端 B** | 1 | 候选池域、双锁与任务编排、向导草稿与字段校验、接口层、中间数据清理 | |
| **前端** | 1→2 | 全部前端（PH1 最简版 → PH2-4 完整版） | PH1 按"丑但能用"标准，不允许提前做视觉打磨 |
| 弹性·算法 | +1（PH3） | A1 赛道竞争、D3 多样性、C1 自适应 | 只在 PH3 出现 |
| 弹性·前端 | +1（PH4） | 结果页打磨、证据抽屉、图表库 | |
| 弹性·QA | +1（PH1 起） | 单测、集成、并发穿透、端到端 | **从第一个切片就开始测**，不是等交付 |

### 2.3 协作纪律

| 项 | 规则 |
|----|------|
| 接口冻结 | 每个阶段**第 1 天**冻结该阶段的接口（`contracts.py` + Schema + TS 类型），冻结后只能加可选字段 |
| 开发隔离 | 冻结后用 stub / mock / 合成数据并行开发，**不互相等待** |
| 冲突高危文件 | `factor_compiler.py` / `contracts.py` / `Settings.tsx` / `client.ts` / `requirements.txt` 单一 codeowner，禁止并行编辑 |
| 每日站会 | 15 分钟。任一任务被卡 >1 天直接上报 TL |
| 每阶段末 | 演示 + 出口条件评审，不达标不进入下一阶段 |

## 3. 阶段计划

### PH0 · 开工条件（W0，3~5 天）

| 项 | 内容 |
|---|---|
| **目标** | 把"能不能跑"从风险变成事实 |

| **明确不做** | 不做 DSL、不做候选池、不做任何 UI、不做 AI 接入 |
| **交付物** | 镜像完成的 DuckDB 区间 + watermark；字段目录变更；**泄漏哨兵测试文件**；压测基线报告 |
| **出口条件** | 日频有效调仓点 ≥252、周频 ≥104、月频 ≥36；泄漏哨兵全绿；`import scipy` 在干净环境成功 |

> **为什么哨兵要在 PH0 就写**：PH1 的 GA 主循环会把"适应度只用 train"这件事写进业务逻辑里。如果哨兵晚写，PH1 的代码已经跑出结果了，再发现泄漏就要重跑、重调参、重新判断门禁——代价是几周的返工。

### PH1 · 垂直切片 + GO/NO-GO 门禁（W1~W3）

| 项 | 内容 |
|---|---|
| **目标** | 打通一根最细的可运行闭环，**第 3 周末拿到"能不能挖出东西"的答案** |

> **不允许"丑"的地方**：切分与哨兵、双锁的并发正确性、`total_trials` 的累加、checkpoint 的可恢复性。

## 4. GO/NO-GO 门禁（W3 末，本计划最重要的一个节点）

### 4.1 判据（三条全部满足才算 GO）

| # | 判据 | 阈值 | 数据来源 | 为什么是这个值 |
|---|------|------|---------|--------------|
| ① | 朴素 GA 20 代（种群 100）**最优 ICIR**（train 段） | **≥ 0.2** | `factor_mining_generations.best_icir` | 0.2 是"可能有信号"的最低线。低于 0.2 说明搜索空间或数据有问题，加算法机制救不回来 |
| ② | 最终验证 Top50 中满足 `decay_ratio ≥ 0.5` **且** test 段 ICIR > 0 的因子数 | **≥ 5 个** | 最终验证结果 | 只有 1~2 个可能是运气；≥5 个说明搜索有系统性效果 |
| ③ | **显著优于 baseline**：GA 最优因子的 test ICIR 相对"25 模板裸跑最优"的表现 | **绝对差 ≥ 0.05**，**或** GA 有 **≥2 个**因子进入 baseline **前 10%** | baseline 对照报告 + GA 产出 | 绝对差 0.05 是"肉眼可见"的增量下限；排名视角是对分布敏感场景的兜底 |

> **为什么必须加判据③**：没有 baseline，"GA 挖出 ICIR 0.4"这个数字毫无意义——因为 25 个模板裸跑可能本来就有 0.4。判据③把"进化到底有没有贡献"这个问题变成一个可算的数字。

### 4.2 baseline 基准怎么做（1 人日）

| 步骤 | 内容 |
|------|------|
| 1 | 用 25 个系统模板的参数网格展开（约 60~80 个具体公式） |
| 2 | **不做任何进化**，直接走单因子评估流程（短样本 train 段 + 最终 test 段） |
| 3 | 产出：每个公式的 train ICIR / test ICIR / 覆盖率 / 换手率 / `decay_ratio` |
| 4 | 汇总成《模板裸跑 baseline 报告》，落库为一张对照表（后续分级的"相关性"维度也能复用） |
| 5 | 报告给出：最优 train ICIR、最优 test ICIR、`decay_ratio ≥ 0.5` 的比例、覆盖率分布 |

> 这 1 人日是**整个项目里性价比最高的一天**。它同时服务三件事：门禁判据③、质量分级的"与已有因子相关性"维度、以及后续判断"新增算子/字段有没有带来增量"。

### 4.3 判定流程

```text
W3 末（建议周五）
  ├── 后端 A：出具 GA 运行报告（代数 / 最优 ICIR / 多样性 / Top50 明细）
  ├── TL：出具 baseline 对照报告 + 泄漏哨兵状态
  ├── QA：出具双锁并发测试 + 复现性测试结论
  ├── 全员 2 小时评审会，逐条判定判据① ② ③
  └── 结论二选一：
        GO    → 进入 PH2，按原计划加宽
        NO-GO → 进入归因流程（4.4），暂停 PH2 启动
```

### 4.4 NO-GO 的应对（关键：禁止无底洞投入）

**先归因，再决策。** 归因限定在 1 周内，分三类：

| 归因类别 | 典型信号 | 修法 | 时限 |
|---------|---------|------|------|
| **数据问题** | 有效调仓点刚过门槛、字段覆盖率低、标签生成异常、停牌/退市处理不当 | 扩镜像区间、补字段、修 `target_engine` 输入 | 1 周内可修 |
| **搜索空间问题** | 种群集中在少数结构、算子/字段过少、复杂度上限太低 | 扩 DSL 算子、扩字段范围、提高种群与代数 | 1 周内可修 |
| **评估口径问题** | 切分边界不合理、IC 计算与手工对不上、purge/embargo 过度剔除 | 修评估口径（注意：这是最容易掩盖问题的类别，必须与手工对拍） | 1 周内可修 |

**1 周内无法归因，或归因后修法需要 >2 周 → 暂停项目，向决策层汇报**，同时保留已有产物（镜像数据、DSL 扩展、泄漏哨兵、baseline 都有独立价值，不会白做）。

> 明确写这条，是为了避免"跑不通就一直调参"的常见失败模式。**门禁的价值在于它允许我们说"不"。**
