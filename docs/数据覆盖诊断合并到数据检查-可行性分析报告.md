# 【数据覆盖率】合并到「数据管理 → 数据检查」可行性分析与代码审查

> 审查范围：设置页「数据覆盖诊断」（用户所称“数据覆盖率”）与「数据管理 → 数据检查」的前端、接口、服务、SQL、数据表、权限、触发与告警逻辑。
> 审查方式：静态代码审查 + 页面实测 + 数据模型对照。本次只做分析与方案，不改代码。
> 审查日期：2026-10-25

## 0. 结论摘要

**结论：✅ 可完美合并，但必须是“入口与布局合并 + 原组件原接口复用”，不能顺手统一统计口径。**

- 「数据覆盖诊断」是单标的、按 1月/1季/1年/3年 统计 `daily_bars` 与 `scores` 的即时诊断；「数据检查」是字段级外部数据覆盖、源表完整性、股票状态资料检查。两者**数据域不同、统计粒度不同、结果不可互相替代**，因此不存在需强行合并的重复计算。
- 覆盖率诊断只有一个 GET 接口、没有缓存表、没有预计算任务、没有定时任务、没有导出、没有告警联动、没有写事务；把前端组件搬到「数据检查」不会改变任何查询结果。
- 真正需要改造的是**导航、命名和测试**，不是数据层；后端可以零改动。
- 最大风险不是“合不了”，而是合并过程中有人把覆盖率改成基于交易日历/去重评分批次的口径，导致数字与现在不一致。**这属于红线，必须禁止。**

**三条不可破坏的红线**
1. 不重算：继续使用 `/api/v1/system/data-health/symbols/{symbol_id}` 现有 SQL 与 Python 口径（含 UTC 取日、5/7 估算、评分行数计数）。
2. 不混表：不把单标的 K 线/评分覆盖率写入 `data_quality_snapshots`，否则会污染现有字段级检查。
3. 不共用刷新：`数据检查` 的“重新检查本地数据”仍只做外部字段快照采集，不能顺带跑单标的诊断。

**推荐落点**：在「数据检查」内部增加二级视图切换（默认「字段与来源检查」，第二视图「逐标的覆盖诊断」），原组件与接口直接复用；不建议把它塞进现有长页面的最下方，也不建议保留独立二级菜单。

## 1. 功能现状梳理

### 1.1 先校准：系统里至少有三类“覆盖率”

| 名称 | 入口 | 统计对象 | 粒度 | 数据源 |
|---|---|---|---|---|
| 数据覆盖诊断（本次对象） | 设置 → 数据覆盖诊断 | 当前业务标的的 K 线、评分 | 单标的 × 1月/1季/1年/3年 | MySQL `daily_bars`、`scores` |
| 数据检查 → 外部字段覆盖 | 数据管理 → 数据检查 | 估值、财报、龙虎榜、人气榜、资金流、ETF 字段 | 字段（全市场汇总） | 因子仓库 FormulaCatalog + `data_quality_snapshots` |
| 行情数据 → 数据健康度 | 数据管理 → 行情数据 | 全市场基础标的“是否有行情” | 市场/板块汇总 | `universe_symbols`、`universe_daily_bars` |

此外「今日决策」的数据健康卡展示的是“当前启用业务标的的独立行情副本”汇总，和本次的单标的诊断同属业务副本域，但粒度不同。合并时必须避免把这三类“覆盖率”混成一个指标。

#### 1.2.4 计算逻辑（必须冻结）

后端实现见 [system.py](file:///d:/ai_project/dataAanlystNew/app/api/routes/system.py#L352-L471)。

| 指标 | 公式/规则 |
|---|---|
| 今天 | `_now().date()`，即 **UTC 当天**，不是上海时间 |
| 周期 | `today-30`、`today-90`、`today-365`、`today-1095` 至 `today`（自然日区间） |
| 总K线 | `COUNT(daily_bars.id) WHERE symbol_id=?` |
| 最早/最新K线 | `MIN/MAX(daily_bars.trade_date)` |
| 距今天数 | 以 UTC 今天减日期，最小为 0 |
| 期望K线数 | 若最早K线晚于周期起点，则用“今天−最早K线”的自然日数；否则用“今天−周期起点”的自然日数；再 `int(days × 5 / 7)`，最后 `max(1, …)` |
| K线覆盖率 | `round(min(100, bar_count / expected_bars × 100), 1)` |
| 总评分 | `COUNT(scores.id) WHERE symbol_id=?`，**按行计数，不按交易日去重** |
| 最新评分 | `MAX(scores.trade_date)` |
| 评分覆盖率 | `round(score_count / bar_count × 100, 1)`，`bar_count=0` 时为 0；**无 100% 上限** |
| K线过期 | 最新K线 `< 今天−7天` |
| K线低覆盖 | 任一周期 `coverage_pct < 50` |
| 评分缺失 | `total_scores=0` 且 `total_bars>0` |
| 评分低覆盖 | 任一周期 `score_coverage_pct < 60` 且该周期 `bar_count>0` |
| 修复建议 | 无K线→初始化；过期→补最近7天；评分缺失/低覆盖→重算评分 |

页面截图 `561390` 的 `0/21、0/64、0/260、0/782` 正是 `30/90/365/1095 × 5/7` 取整的结果；同时“总评分 1、总K线 0、评分覆盖率 0%”说明评分存在但 K 线为 0 时，评分覆盖率分母为 0，仍显示 0%。

## 2. 代码与底层逻辑审查结果

### 2.1 底层数据源、统计口径是否一致

**不一致，而且是物理隔离的两个数据域。**

| 维度 | 数据覆盖诊断 | 数据检查 |
|---|---|---|
| 标的表 | `symbols`（业务标的） | `universe_symbols`（全市场基础库）/ 外部源表 |
| K线表 | `daily_bars`（业务独立行情副本） | `universe_daily_bars`（基础库行情） |
| 评分 | `scores` | 不检查评分 |
| 字段覆盖 | 不检查 | 因子仓库目录 + `data_quality_snapshots` |
| 日期基准 | UTC 今天 + 自然日 5/7 估算 | 上海时间 + `trade_calendar` 已验证交易日 |
| 统计粒度 | 单标的 × 周期 | 字段 × 全市场 / 源表 × 截止日 |

`UniverseSymbol` 与 `UniverseDailyBar` 的模型注释明确写着“与业务表 symbols 物理隔离”“不与 symbols.id 产生外键关系”，见 [universe.py](file:///d:/ai_project/dataAanlystNew/app/models/universe.py#L11-L86)。因此同一只 ETF 在“数据健康度”（universe）与“数据覆盖诊断”（business copy）里出现不同数字是正常的，不是数据错误。

**审查结论**：
- 两者没有重复统计，合并后不会出现同一指标两套数字互相打架（前提是分开展示）。
- 两者不能共用同一个“覆盖率”列或同一张汇总表；粒度不同。
- “数据检查”目前完全不检查 `daily_bars` 和 `scores`，因此新增单标的诊断是**补充能力**，不是替换现有能力。

### 2.2 缓存、预计算、定时任务

| 项 | 数据覆盖诊断 | 数据检查 |
|---|---|---|
| 缓存表 | 无 | `data_quality_snapshots`（字段级不可变快照） |
| 预计算 | 无，实时 SQL | 因子仓库目录（Parquet）+ 快照表 |
| 定时任务 | 无 | 无专门的“质量快照定时任务”；快照由外部数据同步、尾盘导入、手动刷新触发 |
| 迁移需求 | 无 | 无（本次不新增/不改表） |

**结论**：合并不需要迁移数据、不需要停任务、不需要补历史；唯一要避免的是把诊断结果写进 `data_quality_snapshots`。

### 2.3 前端审查

**可复用性：高。**
- `DataDiagnosticPanel` 只依赖 `api`、`AppContext`、`i18n`、Ant Design 和全局 CSS 类（`metric-label`、`item-subline` 在全局样式中），没有 Settings 内部状态耦合；唯一外部能力是 `onOpenHistoryInit` 回调。
- 组件自带请求竞态保护、加载态、错误提示、空态，搬迁不会丢能力。
- 组件没有导出、权限、任务轮询、定时刷新逻辑，搬迁面很小。

**需要处理的问题：**
1. **命名冲突**：`DataCenter` 内部已有一个函数叫 `CoverageDiagnostics`（外部字段覆盖），新面板叫 `DataDiagnosticPanel`（数据覆盖诊断），页面 Tab key 又叫 `coverage`。三者都含“ Coverage/覆盖”，维护时极易混淆。
2. **交互范式不一致**：数据检查的区块用内联 `Alert` + 重试按钮；诊断面板用 `message.error` 顶层提示，没有内联重试。合并后要么保留现状（能力不丢），要么统一为内联错误（属于 UI 改进，需另测）。
3. **无错误边界**：项目没有 React ErrorBoundary；`DataDiagnosticPanel` 直接解引用 `data.summary.total_bars`、`data.coverage[period]`。如果接口返回缺字段，当前只影响独立页面；搬进「数据检查」后可能让整个数据检查 Tab 白屏。
4. **类型是 `any`**：`api.getSymbolDataHealth` 返回 `any`，本地 `DiagnosticData` 只在编译期生效，无运行时校验。
5. **国际化不完整**：问题文案与修复建议由后端硬编码中文；英文界面仍显示中文。现状如此，搬迁不改变，但会被更多用户看到。
6. **标的搜索失败被静默吞掉**：`loadSymbols` 的 `catch` 为空，搜索接口失败时用户只看到选项不变，没有提示。
7. **每次选择新标的先清空旧结果**：请求失败后旧数据不会保留，只弹错误提示。现状如此。

### 2.4 后端审查

| 审查点 | 结果 |
|---|---|
| 接口职责 | 路由函数直接做 SQL + 规则计算，无独立 service、无 response_model、无 schema |
| 入参 | 只有路径参数 `symbol_id`，无筛选/分页/日期参数 |
| 返回结构 | 裸 dict；字段固定；无版本号 |
| 鉴权 | 无用户/角色鉴权；与全项目一致 |
| 事务 | 只读 SELECT，无写事务 |
| 校验 | 仅校验标的是否存在（404） |
| 硬编码 | 4 个周期天数、7 天过期阈值、50%/60% 阈值、5/7 折算、问题文案、建议文案全部硬编码 |
| 性能 | 单标的约 9 条索引聚合；无大表全扫；单次请求开销可控 |
| 并发 | 无写入，无锁；前端有竞态保护 |
| 可测试性 | 无后端测试；无 golden 输出 |

**代码风险（单独高亮）**

> **代码风险（高）· 口径漂移**
> 当前“今天”使用 **UTC 当天**（`_now().date()`），而数据检查的源表完整性使用 **Asia/Shanghai** 与 `trade_calendar`。若合并时顺手改为上海时间或真实交易日历，`expected_bars`、`coverage_pct`、`latest_age_days`、过期判断都会变化，直接违反“查询结果和原来完全一致”。

> **代码风险（高）· 评分覆盖率可能大于 100%**
> `score_count` 统计的是 `scores` 行数，而唯一约束包含 `calc_batch_id`；同一天多个评分批次会产生多行。分母却是 `bar_count`。因此同一周期可能显示 >100% 的评分覆盖率。若为了“看起来合理”去重，结果会与现在不一致。合并必须保留原口径，或把“修复评分覆盖率”作为独立需求另行评审。

> **代码风险（高）· 期望K线是近似值**
> `expected_bars` 用自然日 × 5/7 估算，未使用 `trade_calendar`；短周期取整和“最早K线晚于周期起点”的分支会让新上市标的的分母变小。合并后不要把它与“数据健康度”的真实交易日判断混为一谈。

> **代码风险（中）· 评分存在但K线为0时，评分覆盖率固定为0%**
> 截图中的 `总评分 1 / 总K线 0 / 评分覆盖率 0%` 就是该逻辑。它不是显示错误，而是分母为 0 的既有口径。若合并时“修复”为按评分日期数计算，同样会造成结果偏差。

> **代码风险（中）· 无响应校验 + 无错误边界**
> 接口字段缺失时，`data.summary.total_bars.toLocaleString()` 会抛异常。独立页面只坏一页；嵌入数据检查后可能坏整个 Tab。建议在搬迁时只增加运行时兜底（缺字段→错误提示），不改任何有效响应的数值。

> **代码风险（中）· 命名冲突**
> `CoverageDiagnostics`（现有字段覆盖函数）与新面板“数据覆盖诊断”仅差几个字，且 Tab key 为 `coverage`。不改名会在后续维护中造成“到底改的是哪一个覆盖率”的误改风险。

### 2.5 数据层审查

- 「数据覆盖诊断」**没有独立存储、没有落表、没有缓存**；每次请求实时计算。
- 现有的 `data_quality_snapshots` 是**字段级**外部数据质量证据（`dataset`、`field`、`readiness`、`nonnull_rows` 等），语义与“单标的 × 周期 K线/评分覆盖率”不同。把后者写入该表会：
  - 污染 `GET /external-data/quality-snapshots` 返回的字段列表；
  - 让“数据检查”的字段覆盖表出现非字段记录；
  - 破坏历史趋势查询。
- 因此：**不需要迁移，也不应该新增写入。**

## 4. 可行性结论

### 4.1 判定：✅ 可完美合并

**成立方式：入口/布局合并，组件与接口原样复用。**

判定依据：
1. 诊断面板是自包含组件，外部依赖只有 `onOpenHistoryInit` 回调；搬移不改变查询条件、指标、计算与展示。
2. 后端接口只读、无状态、无缓存、无任务、无写事务；前端换位置不会改变返回结果。
3. 数据检查是增量式区块组合；新增一个独立视图不会改动现有 4 个区块的查询与接口。
4. 两边没有共享表、共享预计算、共享任务或共享刷新链路，因此不存在“合并后互相污染”的数据耦合。
5. 合并后原能力可 1:1 保留：搜索、刷新、概览、四周期、评分覆盖、问题、建议、三种修复跳转、默认活跃标的、竞态保护。

### 4.2 “完美”的成立前提（不可破坏）

1. **接口 URL、入参、返回字段、SQL、Python 计算全部不动。**
2. **不把诊断结果写入 `data_quality_snapshots` 或任何现有表。**
3. **不把“重新检查本地数据”扩展成同时跑单标的诊断。**
4. **必须把 `onOpenHistoryInit` 回调从 Settings 传进新位置**，否则三个修复按钮会消失。
5. **必须保留旧入口的深链等价路径**：旧 `settings_active_section=diagnostic`、初始化补数页的“数据覆盖诊断”链接都要落到新视图。
6. **必须保留 `AppContext.activeSymbolId` 默认标的与请求竞态保护。**

### 4.3 什么情况下结论会降级

| 如果产品要求 | 结论 | 原因 |
|---|---|---|
| 只换入口/布局，原组件复用 | ✅ 可完美合并 | 结果逐字段一致 |
| 把诊断并入现有字段覆盖表，做统一“覆盖率”列 | ❌ 不适合合并 | 粒度、数据源、口径都不同，必须重写统计并改变结果 |
| 统一改用 `trade_calendar` 计算期望K线 | ⚠️ 可合并但口径变更 | 数字会变，不满足“结果完全一致” |
| 评分覆盖率改为按交易日去重 | ⚠️ 口径变更 | 修复了 >100% 的问题，但与现在不一致 |
| 要求合并后没有独立入口、也不接受多一次点击 | ⚠️ 有体验成本 | 能力保留，但发现路径变长，需要快捷入口或引导 |

> **结论边界**：本次推荐的是“展示层合并”，不是“统计模型合并”。只要坚持这一点，就是完美合并；一旦要求统一计算，就不再满足用户给定的“完美合并”定义。

| 测试 mock 缺失 | 中 | 新面板在 DataCenter 测试里调用未 mock 的 API，出现未处理 Promise | 默认视图不挂载诊断；新增 API mock；只在切换视图时断言 |
| 页面变长 | 中 | 不采用二级视图而直接追加区块，会让现有长页面更难用 | 采用二级视图，默认保持字段检查 |
| 性能 | 低 | 单标的 9 条聚合，开销可控 | 不在主 Tab 挂载时自动请求诊断；切换视图再加载 |
| 国际化 | 低 | 英文界面出现中文问题/建议 | 现状问题；可后续按 issue type 前端翻译，不改数值 |
| Toast 错误无重试 | 低 | 读取失败只有顶部提示 | 可在搬迁时补内联重试，属于 UI 改进 |
| 用户习惯 | 中 | 原来 1 次点击变 3 次 | 过渡期快捷入口；或在“数据健康度”加“查看逐标的覆盖”按钮 |

### 6.1 上线与回滚

- **上线**：纯前端改动；后端零改动；无数据库迁移；无任务变更。可随前端版本发布。
- **灰度/过渡**：保留侧边栏“数据覆盖诊断”作为快捷入口，点击落到合并视图；确认无回归后再移除。
- **回滚**：回退前端构建即可。后端、数据表、任务均未改变；`data_quality_snapshots` 不受影响。唯一残留是新 localStorage 键（旧版本会忽略），用户重新点击原入口即可。
- **监控**：上线后重点看数据检查 Tab 的前端错误、单标的诊断接口耗时、旧深链能否到达。

## 7. 回归测试重点

### 7.1 数据覆盖诊断全部场景

1. 未选择标的：显示空态，不发诊断请求。
2. 有活跃标的：进入后自动加载该标的。
3. 0 K线、0 评分：只有“没有任何K线数据”，建议初始化。
4. 0 K线但有评分：总评分 >0、评分覆盖率 0%、仍提示缺K线（当前截图场景）。
5. 有K线、0 评分：提示“有K线但没有任何评分数据”，建议重算评分。
6. K线最新日期早于今天 7 天：过期问题。
7. 任一周期覆盖率 <50%：对应周期的低覆盖问题，数量与周期一致。
8. 任一周期评分覆盖率 <60%：评分低覆盖问题。
9. 新上市标的：期望K线从最早K线起算，不因上市前日期被判低覆盖。
10. 同一天多个评分批次：评分条数按行累计，覆盖率可能 >100%；结果必须与合并前一致。
11. 周期边界：30/90/365/1095 天与 `expected_bars` 取整（21/64/260/782）一致。
12. 切换标的时旧请求晚到：旧结果不得覆盖新标的。
13. 搜索关键词：选项追加、去重、可选中。
14. 刷新按钮：重新请求同一标的，结果一致。
15. 404 标的：显示错误，不白屏。
16. 修复按钮：补K线 / 补评分 / 两者，跳转“初始化补数”且 `symbolId`、`repairMode` 正确。
17. 默认活跃标的：进入页面时自动选中。
18. 英文本地化：标签正常；后端中文问题文案现状保留。

### 7.2 数据检查全部场景

1. 5 个主 Tab 数量与顺序不变；默认行情数据。
2. 数据检查 Tab 持久化与恢复。
3. 历史股票状态下载：组合范围、日期、任务进度、失败原因、重试、只读模式禁用。
4. 股票状态导入：覆盖率、模板下载、CSV 选择/预览/确认、错误提示。
5. 源表关键字段完整性：默认日期、自定义截止日、交易日历警告、空表不判完整。
6. 外部字段覆盖：初始读取、部分失败仍显示已有数据、重试、空态。
7. 质量快照：最近检查时间、最近失败原因弹窗、趋势弹窗、关闭后不被晚到请求重新打开。
8. 手动“重新检查本地数据”：只采集快照，不触发单标的诊断。
9. 只读验收模式：写按钮禁用，读按钮可用。
10. `backtestRepair` 上下文仍能带入股票状态下载范围。
11. 新增二级视图切换：默认字段视图；切到逐标的后诊断组件加载；切回不丢现有字段数据。

### 7.3 导航与深链

1. 旧 `settings_active_section=diagnostic` 启动 → 数据管理 + 数据检查 + 逐标的视图。
2. 初始化补数失败列表点“数据覆盖诊断” → 正确带入标的并切视图。
