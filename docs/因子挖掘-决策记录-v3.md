## 二、Q6 双锁设计（用户补充，完整记录）

### 锁定义

| 锁 | 作用范围 | 冲突行为 |
|---|---------|---------|
| `mining_domain` | `task_type='factor_mining'` 的任务 | **域内唯一**，判定范围 `(queued, running)`；已有则**直接拒绝**（不排队） |
| `duckdb_write` | 所有会写 DuckDB 的任务（挖掘、因子流水线等） | **互斥**，被占则**进入排队队列** |

### 提交流程

1. 提交挖掘任务 → 先查 `mining_domain` 锁：有 `queued/running` → **直接拒绝**「已有挖掘任务进行中」
2. 再查 `duckdb_write` 锁：空闲 → 立即执行；被占 → 进入排队队列，前端提示「当前 XX 任务正在执行（预计剩余 X 分钟），已为你排队」
3. 写任务完成 / 失败 / 取消 → 释放写锁 → **自动拉起队首任务**
4. **锁超时兜底**：默认 **30 分钟**（可配置），心跳无更新则自动释放防死锁

### 心跳

- 默认 **30 分钟**，可配置（与现有 `async_tasks.STALE_RUNNING_DEADLINE` 对齐）
- 更新点：**每代结束** + **最终验证每完成 10 个因子**
- 锁异常释放时通过消息通知用户

### 前端交互

- Step4 提交时检查锁状态，资源确认框显示「当前无其他写任务，可立即开始」或「当前 XX 任务执行中，本任务将排队（前面还有 N 个）」
- Step5 运行页显示排队状态（第几位 / 预计等待时间 / 取消排队按钮）
- ETA 为**规则估算**（数据量 × 候选数），UI 必须标注「估算」

### 实现要点

- 队列消费者复用现有 `async_tasks` 状态机 + 锁释放时主动拉起队首，**不引入新调度器**
- ETA 首期无历史任务数据，只能规则估算

## 三、由审核报告确定、无需再决策的技术项（我直接定）

| 项 | 处理 |
|---|------|
| API 路径 | `/api/f1/...` → `/api/v1/factor-experience/...`，tag `factor-experience` |
| 字段注册 | 注册已存在的 `dividend_yield` / `total_market_cap` / `circulating_market_cap`（零采集成本）；`gross_margin` / `asset_turnover` 需新采集，放 M2 |
| `prev_close` 虚注册 | 撤销注册，ATR 改用 `ref(close, 1)` 实现 |
| 算子方言 | 模板公式 `std`→`stddev`、`llv/hhv`→`lowest/highest`、`turnover`→`turnover_rate`；`delta` 口径见下 |
| `delta` 口径 | 价格动量类用现有 `pct_change`（等价）；财报差分需明确 `n` 是报告期数还是交易日数 |
| test 段迁移 | `factor_evaluation_runs` 加 `test_start_date` / `test_end_date` 两个 nullable 列；历史仅 5 条，留 NULL |
| 快照标识对接 | 新建 `training_candidate_pool_snapshots`，`factor_evaluation_runs.universe_snapshot_id` 保持兼容（可指向新快照 ID） |
| 依赖 | 新增 `psutil`（G1，M3 才需要）、`openpyxl`（Excel 导入） |
| AI 异步 | `llm_client` 同步，需 `asyncio.to_thread` 包装 |
| AST 树编辑距离 | M1 用简化结构相似度，M2 再上树编辑距离 |
