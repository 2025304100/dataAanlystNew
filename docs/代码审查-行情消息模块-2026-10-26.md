## 4. P1 问题详情与整改建议

### R01：真实来源异常被吞，全源失败告警没有可靠输入

- 位置：[market_events.py:392](D:/ai_project/dataAanlystNew/app/services/market_events.py:392)、[scheduled_tasks.py:875](D:/ai_project/dataAanlystNew/app/services/scheduled_tasks.py:875)。
- 触发：六个来源在重试后全部抛异常。
- 实际：`_fetch_from_ak` 仅记 debug 日志并返回空列表；外层采集函数接不到异常，`errors=[]`，采集账目仍为 `done`。调度的“全源失败”分支不满足。后续连续空采可能告警，但不能代替首轮全源失败识别，且在默认每日排程下可能延后一轮。
- 取证：补丁仅作用于最低层 `call_akshare_with_retry`，六源均失败后得到 `collected=0/errors=[]/status=done`。没有在高层 fetcher 打桩绕过实际吞异常分支。
- 整改：来源适配层抛出带来源名的异常，或返回包含 `status/items/error` 的结构；区分成功空数据、全重复、部分失败、全部失败。调度按来源状态判定，手动采集也显示失败来源，账目明确记录 `failed/partial/done`。
- 验收：六源失败首轮能产生失败账目及有效告警；单源失败不触发“全源失败”；健康全重复不被标为断供。关联用例：SP-COL-02～06、SP-OBS-01～04。

### R02：清理保护在不同入口不一致

- 位置：[market_event.py:76](D:/ai_project/dataAanlystNew/app/schemas/market_event.py:76)、[scheduled_tasks.py:615](D:/ai_project/dataAanlystNew/app/services/scheduled_tasks.py:615)、[market_events.py:623](D:/ai_project/dataAanlystNew/app/services/market_events.py:623)。
- 触发：通过清理 API 提交 `{"keep_days":7}`。
- 实际：Schema 接受 7；相同参数被调度拒绝；服务层直接使用传入值，8 天前发布且已过期、自动、未引用的行会被永久删除。
- 影响：绕过既有调度的最低保留约束；与“90 天回看窗口内完整”的文字承诺不一致。文档自身同时出现 API 下限 7、调度下限 30 和窗口 90，需统一业务契约。
- 整改：由服务层实施统一最小保留期，Schema、调度、UI 共用同一常量。若产品保留“90 天内完整”承诺，下限应为 90；若允许更短窗口，应明确修订承诺，并给破坏性覆盖设置独立授权或专用运维入口。增加预估删除数量/时间范围与可恢复备份流程。
- 验收：API、调度、服务直调对同一参数得到一致结果；不允许通用参数绕过既定最低保护。关联：SP-CLN-03、04、07。

### R03：90 天硬删除与 365 天真实热点窗口冲突

- 位置：[market_events.py:610](D:/ai_project/dataAanlystNew/app/services/market_events.py:610)、[market_events.py:699](D:/ai_project/dataAanlystNew/app/services/market_events.py:699)。
- 触发：库中存在 120 天前的自动、已过期、未引用消息；先查一年热点，再执行默认清理，再查一年热点。
- 实际：清理前该板块统计 1 条，清理删除 1 行，之后一年热点为空。长期正常运行后，自动消息的 365 天统计只剩近 90 天及受保护的残留行，且残留会使样本偏向手工/被引用事件。
- 整改：为最长 365 天统计保留所需原始数据或归档并联合查询；也可持久化足以重建各窗口的日聚合。若只支持 90 天历史，应移除/改名一年入口并明确历史覆盖起点。仅把接口 `days` 设为 365 不能满足完整历史统计。
- 验收：执行多轮清理后，365 天统计仍符合明确的历史契约；采样 ID 与归档数据可追溯。关联：SP-CLN-08、SP-HOT-02、09。

### R04：新增自动采集后，去重仍存在检查与写入竞态

- 位置：[market_events.py:560](D:/ai_project/dataAanlystNew/app/services/market_events.py:560)、[market_events.py:573](D:/ai_project/dataAanlystNew/app/services/market_events.py:573)、[market_event.py:38](D:/ai_project/dataAanlystNew/app/models/market_event.py:38)。
- 触发：手动与定时采集同时读取同标题的 hash，均在另一方提交前判断不存在。
- 实际：`seen_hashes` 只在单次调用内有效；数据库索引非唯一，两次插入均可提交。隔离探针在“首请求读完空集合、尚未写入”时执行第二会话采集，最后同标题有两行。
- 影响：热点计数、采集新增数量及后续 AI 事件材料出现重复；前端按钮 loading 无法互斥调度、另一客户端或另一服务进程。
- 整改：若必须保留存量重复标题，采用跨进程采集互斥锁，或建立唯一 hash 的独立去重登记表并在事务中竞争占位。若可治理存量，先去重再加唯一约束并处理冲突。仅使用进程内锁或把 IN 查询分块不能解决跨进程竞态。
- 验收：手动/定时、双客户端、双进程同标题交错均只新增一次；失败释放锁；旧重复数据按已确认规则兼容。关联：SP-DED-04、05。

### R05：等级外置词表实际上不会覆盖内置等级词

- 位置：[market_events.py:89](D:/ai_project/dataAanlystNew/app/services/market_events.py:89)、[market_events.py:194](D:/ai_project/dataAanlystNew/app/services/market_events.py:194)。
- 触发：配置 `{"importance_level":{"5":["审查专属关键字甲"]}}`，采集只命中该词的消息。
- 实际：合并写入 `target[str(name)]`；分类循环读取整数 `5..2`。JSON 键始终为字符串，新增词不参与分类；探针返回等级 2，而非 5。已有测试只覆盖 scope 配置，没有覆盖等级配置。
- 影响：运营调词显示部署成功但不会生效；本应升为重大消息的事件可能无法进入 importance≥4 的 AI 上下文。
- 整改：分别验证三个配置分区；等级键转为允许的整数，scope/sentiment 验证枚举。配置结构错误给出可观测警告并整体回退，避免静默忽略。
- 验收：每个合法等级键的替换/新增/删除都真实生效；错误结构不会导致采集崩溃。关联：SP-TAG-02、03、04。

### R06：热点数据虽独立，热点界面仍依赖列表是否有数据

- 位置：[MarketNews.tsx:576](D:/ai_project/dataAanlystNew/frontend/src/components/MarketNews.tsx:576)、[MarketNews.tsx:596](D:/ai_project/dataAanlystNew/frontend/src/components/MarketNews.tsx:596)。

### R07：异步响应乱序可使界面展示旧筛选/旧窗口数据

- 位置：[MarketNews.tsx:270](D:/ai_project/dataAanlystNew/frontend/src/components/MarketNews.tsx:270)、[MarketNews.tsx:316](D:/ai_project/dataAanlystNew/frontend/src/components/MarketNews.tsx:316)。
