## 四、PT-DEF-6 · manual/confirm 成员被自动成交（资金路径回归 · 已修复 B 方案）

### 现象（探针实测）
构造含单个 confirm/manual 成员的组合 + 已应用快照，调用 `execute_member_source`：
- confirm 模式 → 生成 **filled 买单**（旧契约：待确认，不创建 SimOrder）
- manual 模式 → 生成 **filled 买单**（旧契约：只提示信号，不下单）
- 快照 `member_snapshot_json` 带不带 `execution_mode` 结果相同

### 证据链
1. **文档不变量**（多份、明确）：
   - `opportunity-center-...final-plan.md` L667-669 / L960 / L1552-1562：manual 只提示信号不下单；confirm 只生成待确认计划；**自动交易只遍历 execution_mode=auto 成员**
   - `组合策略因子模型与回测全链路贯通开发方案.md` L400：`execution_mode=auto` 是自动执行授权，不满足时「只能提示或等待确认，**不能自动下单**」
   - 同文件 L1163 将「自动交易与手动操作冲突」列为需 execution_mode 缓解的风险
2. **旧实现仍正确但已脱离主路径**：`get_buy_candidates`（L438 跳过非 auto）、`get_signal_candidates`（L528 只处理 manual/confirm）仍存在，但 `execute_member_source` 迁移后不再调用它们。
3. **新路径无 mode 感知**：`execute_member_source` → `_execute_snapshot_order_plans` → `default_engine.evaluate`。`default_engine = DecisionEngine()`（无参构造，L3276）→ `build_universe = _stub_universe_builder`（L480 默认兜底），该 stub 把快照全部成员当 universe、`ineligible=[]`、**不过滤 execution_mode**。L462-463 注释确认 stub「真实实现随 WP0-3b/0-4a/0-5a 逐步替换」——universe builder 至今未替换。
4. **快照含全 mode**：`_build_member_snapshot`（`factor_usage_service.py` L112-123）把所有有效成员（含 execution_mode 字段）写入快照，不过滤 manual/confirm。
5. **上游无补偿门**：`save_and_apply` 不筛 mode；`dual_run` 只 gate source/snapshot/readiness；`get_auto_trade_readiness` 只用 auto 成员算 eligible，但**不因存在 manual/confirm 成员而阻断执行**。

### 净效果
含 manual/confirm 成员的组合一旦 `save_and_apply`，下次自动模拟交易会把这些成员的买单**自动成交**，违反文档安全不变量。当前 ~18 个 auto_trade 失败测试是唯一绊到该回归的警报线——**不是"腐烂"，是"报警"**。

### 修复（已实施 B 方案 · 2026-09-26）
判定为**回归**，采纳根治方案 B：用真实 `_real_universe_builder` 替换 `_stub_universe_builder`，在 universe/eligibility 阶段按 execution_mode + run_type 过滤。

**核心改动**（`app/services/decision_engine.py`）：
1. `UniverseBuilder` Protocol 签名扩展 `run_type` 参数（原 `(db, snap, cutoff_utc)` 不含 run_type，无法区分回测/实盘）。
2. `evaluate` 调用点透传 `run_type`（L777）。
3. 新增 `_real_universe_builder`，`default_engine` 默认改用它（原 `_stub_universe_builder` 保留供 G2 直接引用）。
4. 适配注入自定义 builder 的测试签名（test_stage3_allocator_clamp ×6、test_wp_stage1_order_plan ×1）。

**run_type 隔离矩阵**（default_engine 为全局单例，四入口共用）：

| run_type | 语义 | universe 过滤 |
|---|---|---|
| `auto_simulation` | 实盘自动交易（唯一真实成交 SimOrder） | **仅纳入 auto**，manual/confirm → ineligible |
| `backtest` | 回测 | 全量（C-03 用 `auto_authorized_flag` 白名单） |

**向后兼容**：member dict 缺失/空 execution_mode（仅测试 seed 与迁移前历史快照；生产快照 `_to_row` 必写该列，NOT NULL default manual）→ 视为 eligible；明确 manual/confirm 及脏值 → fail-safe ineligible。

**层3 信号路径（选项 X，已实现）**：manual/confirm 的“信号提示/待确认”输出已在 `_execute_snapshot_order_plans` 末尾恢复——从快照 members 识别 manual/confirm，复用 `_get_latest_signal` + `_BUY_ACTIONS` 口径生成 signal_decisions（含 execution_mode）与 executed_orders（confirm→pending_confirmation、manual→signal_only，均无 order_id/不建 SimOrder）。至此文档三态不变量（manual 提示、confirm 待确认、auto 成交）完整实现。

### 七.6 PT-DEF-8（已拍板并修）：7 要素结构化错误在路由层退化为 409+字符串

- **证据链**：`app/api/routes/factor_pipeline.py` L32-39——`except FactorPipelineBindingError → HTTPException(422, detail=exc.to_dict())`（7 要素 dict），`except ValueError → HTTPException(409, detail=str(exc))`。而门禁实际抛的是 `factor_structured_error(...)` → `FactorSevenError`，且 `class FactorSevenError(ValueError)`（`app/schemas/errors.py`）→ **被 `except ValueError` 抢走**，所以下游拿到 `409 + "[PIPELINE_NO_FACTOR_SET] 中文文案"`，`error_code`/`fix_link`/`retryable` 全部丢失。
- **与同族缺陷对照**：PIPELINE_* 7 个码已在 `errors.py` registry 注册（L283-324），所以不会落入 PT-DEF-5 那种 `UNKNOWN_ERROR` 文案反转；本缺陷是“降级为裸字符串”，不是“未知错误”。
- **不一致点**：`pipeline_task.py` L389 与 `FactorSevenError` docstring 均自称“转 HTTP 400”，路由的 `FactorPipelineBindingError` 分支写的是 422，stage3 契约测试期望 422，现实际行为是 409 —— 三方不一致，需拍板。
- **可选方案（已选 A）**：A（✅已采纳）路由显式 `except FactorSevenError → HTTPException(422, exc.to_dict())` 并置于 `ValueError` 分支之前：与现有绑定错部分支和 stage3 测试契约一致；代价：流水线参数错从 409 变 422（对前端可见）；B：保留 409、重写测试为 409+字符串：最省力，但 7 要素契约在 HTTP 层依旧丢；C：只活页不改。
- **落地（2026-09-27）**：`app/api/routes/factor_pipeline.py` 新增 `except FactorSevenError` 分支（422 + `to_dict()`，置于 `except ValueError` 之前，并就地写明“FactorSevenError 是 ValueError 子类，不前置就会被抢走”）；`FactorPipelineBindingError` 与原 `ValueError`（disabled 路径→409）行为不变，`test_blackbox_factor_settings.py::test_disabled_factor_pipeline_returns_409_without_creating_task` 仍适用。
- **同步的测试契约**（`test_stage3_factor_binding_contract.py`）：① `train_factor_model(payload, db_session)` → `train_factor_model(payload, None, db_session)`（第二位参是 `request: Request`，`_actor_from_context` 对 None 安全）；② 5 例 expected_code 改用生产真实码（`PIPELINE_NO_FACTOR_SET`/`_FACTOR_SET_NOT_FOUND`/`_NOT_FROZEN`/`_NOT_READY`）——旧字面量 `FACTOR_SET_*` 从未在代码里出现过，并新增“detail 必须是 dict”的守护断言；③ 训练路由断言从大小写敏感的 `"frozen" in str(detail)` 改为 `error_code` + 中文“未冻结”+ 大小写不敏感兼顾。
- **残留不一致（待后续统一）**：同为 7 要素错，`factor_models.py` 训练路由转 400（`_factor_seven_to_http`/`_factor_status_to_http`）、`pipeline_task.py` L389 与 `FactorSevenError` docstring 自称“转 HTTP 400”，而流水线路由按本次拍板转 422。三个入口语义应按同一原则收敛（参数/语义校验失败=422，资源冲突=409），属跨域 API 契约调整，本轮不动。
- **验证**：`test_stage3_factor_binding_contract.py` 19/19 全绿（原 6 红）；`test_factor_pipeline_gates_task9.py` 服务层契约未受影响；三文件合跑 45 passed / 2 failed，2 例均为 `test_whitebox_factor_pipeline_state.py` 存量红（在 HEAD 基线里同样红，与本改动无关）。

### 七.9 PT-DEF-9（新发现·已修）：告警事件从未写入 WP-MSG.1 去重三列，且 flush 错误被吞

### 十四.1 为什么新建表而不抄因子域配置表

本仓没有通用 settings 表，最接近的 `factor_system_config.extra_json` 属**因子域**（docstring 自陈 “feature readiness settings”）。把发现中心的设置塞进去，就是本报告反复治理的“跨域耦合 / 同一事实多处记录”那一类（PT-DEF-13 同族）。所以新建 `app_settings`（rev 064）：主键即业务键、值统一 JSON、`updated_by` 留痕“谁关的”；以后各域设置都走它，新增一个开关只是登记表里加一行。

### 十四.2 落地形状

- **后端单一真相**：`app/services/app_settings.py::APP_SETTING_REGISTRY` 登记每个开关的
  `type / default / env_var / section / label_zh / description_zh`。前端与发现中心都不再
  自己拼清单：`discovery_data_prep.AUTO_DATA_PREP_ENV` 现在是登记表常量的**别名**，
  彻底消除“改了登记表忘改用例/文案”的隐契约。
- **生效优先级：表 > 环境变量 > 默认值**。保留 env 通道是为了运维级强制关闭
  （整环境禁外网、CI 不碰行情源）；表里没行等于“用户没改过”，所以 rev 064 **不 seed 任何行**，
  对现有行为零影响，回滚就是干净的 `DROP TABLE`。
- **读路径永不抛错**：表未建/连接异常时退回 env → 默认值（只留 warning）。这是 §七.9
  （告警写库把调用方事务打翻）同族的教训：读一个开关不应该打翻主链路。
- **写侧只接受登记过的键**：`PUT /settings/app/{key}` 对未登记键返 400
  `UNKNOWN_SETTING_KEY`，类型不符返 422 `SETTING_VALUE_INVALID`（两个码已登记进
  `ERROR_CODE_LIBRARY`，且 `detail` 传 dict 带 `error_code`，遵循 PT-DEF-8 结论）。
- **发现中心接线**：`auto_data_prep_enabled(db)` 接上调用方的 Session，快扫读到的是
  “本次请求那张库”的设置（跟 PT-DEF-15 同一个教训）。
- **前端零维护**：新增分区「系统设置」（`AppSettingsSection.tsx`）直接渲染 `GET /settings/app`；
  以后后端加一个键，页面自动出现。它额外显示**当前来源**（已在本页保存 / 由环境变量决定 /
  默认值），避免“页面上改了但没效果”这种说不清的回显陷阱；保存失败时**重新 GET 回读真相**，
  不把未存成功的乐观更新留在界面上。

### 十五.1 `test_blackbox_api_mgmt.py` 第 4 节：“不显式设 Content-Type，复刻前端行为”

这个前提本身就是错的，而且造成两种假结果：

| 类型 | 现象 | 后果 |
|---|---|---|
| 正向用例（3 条） | PUT 拿不到 200 → `pytest.skip("确认 Content-Type bug 存在")` | “配置保存是否真生效”**从来没被验证过** |

用三种发法对活后端实测（只回写当前值，不改配置）：

```
A 无 Content-Type        → 422
B text/plain（浏览器默认） → 422     ← 关键：浏览器正是发这个
C application/json        → 200
```

而前端 `updateAkshareApiConfig` 恰好是 `body: JSON.stringify(...)` 且**没设 Content-Type**
→ 按浏览器规则就是 B → **用户在界面上保存 akshare 接口配置一直失败（PT-DEF-17）**。
黑盒用例把这个现象记成“确认 bug 存在”却 skip 掉，所以没人修。

- 产品（前端）：`api/client.ts` 的 `requestJson` 在**统一入口**补齐：只要 body 是字符串且调用方
  没显式传 Content-Type，就设 `application/json`（全文件 110 处 `body:` 调用里只有一部分写了头，
  逐处补会漏；显式传了的优先不覆盖）。现在该节 8 条用例全部走标准 JSON：
  正向改成真断言 200 + 读回生效（并用 finally 恢复原值），负向改成真校 404/400，
  区间类额外断言“被拒的值不得落库”；另留一条用例显式记录“无 Content-Type 会被 422”，
  一旦后端改为宽容接受 text/plain，用例会提醒两边口径变了。

## 十七、11 条僵尸 xfail 清零（组合回测域，2026-09-28）

### 十八.1 PT-DEF-24：交易日历 Adapter 在 SQLite 上永远判“不可用”（已修）

链路：`no_snapshot` 用例走到"无 ready 快照 → 自动起后台 data_prep"这条 fire-and-forget 分支

## 二十三、PT-DEF-25：预检阻断被显示成 UNKNOWN_ERROR + 裸 JSON（新发现，含 300 天阈值评估）

触发：进入/操作「回测中心」，近 1 年窗口的组合回测被预检阻断时，弹窗主文案是
「UNKNOWN_ERROR / 未知错误 / 🚫 不可重试」，正文糊着一大段原始 JSON。

**原始响应（活后端实测，`POST /backtest/portfolio/run`，窗口 2025-09-29→2026-09-28）**：

```
status=400
error_code      = PRECHECK_BLOCKED          ← 顶层其实是对的，且已登记在 ERROR_CODE_LIBRARY
user_message    = 回测预检未通过，本次回测被阻断
next_actions    = []                        ← 空
extras.blocking_reasons[0]
  code          = INSUFFICIENT_TRADE_DAYS
  title_zh      = 回测区间交易日不足（阻断）
  detail_zh     = 当前可用交易日 261 天，低于最低要求 300 天…
  evidence      = {actual_usable:261, minimum_required:300, gap_days:39}
  fix_link      = {tab:"portfolio-backtest", label_zh:"调整回测区间参数"}
technical_details.error_message = "{'error_code': 'PRECHECK_BLOCKED', 'title_zh': …"  ← Python dict 的 repr 字符串
```

拆开是三个独立问题：

| # | 问题 | 位置 | 影响 |
|---|---|---|---|
| 25a | 后端信封其实是对的，**前端没读顶层 `error_code`/`user_message`**，反而把 `extras`（或 technical_details 里的 dict repr）当正文显示，主文案回退成 UNKNOWN_ERROR | 前端错误卡 | 用户看到"未知错误 + 一堆 JSON"，看不到"缺口 39 天、请扩大区间" |
| 25b | `technical_details.error_message` 把**整个 Python dict 的 repr**塞进技术细节（含内部 correlation_id、结构） | `_build_structured_error` 的组装处 | 违反本项目"错误信息脱敏"口径；长度不可控 |
| 25c | `blocking_reasons[].fix_link` 明明带着可跳转的 `tab + label_zh`，却没映射成 `next_actions`（实测为空） | 预检 → 信封转换 | 7 要素信封的"下一步动作"字段形同虚设，用户没有被引导去调区间 |

**300 天阈值的评估（你要求一起看）**：`minimum_trade_days` 现在**三处各写一份 300**
（路由 `backtest.py:1225` 硬编码、前端 `PortfolioBacktestCenter.tsx:480` 常量、
schema `bfg_precheck.py:84/133` 默认值）—— 三处漂移风险本身就是一类隐患。
实质问题：**300 个交易日 ≈ 1.2 个自然年**，而回测中心的快捷区间里**有「近1年」**，
A 股近 1 年只有 261 个交易日 → **点「近1年」必被阻断**，等于给了一个必然失败的预设。

建议（改动前等你定数值，因为这是回测可用性口径）：
- 阈值下调到 **240 交易日**（≈ 1 自然年，保住"近1年"可用），或按请求区间自适应
  `min(300, 0.8 × 区间内应有交易日)`；
- 三处收敛成单一来源（schema 默认值，或按既有 `app_settings` 机制做成可调项），
  前端只展示不再自带常量；
- 无论选哪个值，25a/25b/25c 都该修：它们不改变判定结果，只把"为什么被挡、下一步做什么"
  如实呈现。

## 二十八、PT-DEF-18 收口：探测改「提交任务 + 心跳轮询」，取消"猜超时秒数"（2026-09-29，用户拍板）

### 二十八.0 为什么不选"把一个常数改大"

待决项原本是：后端 `_PROBE_TIMEOUT_SECONDS=50` / 前端 `timeoutMs=30000` / 测试押 55s 三边不一致。
我提的两个选项（前端提到 60s，或后端压到 30s）**都被否决**，理由由用户指出且成立：
只要还是"一个同步请求等上游"，就永远需要有人猜一个数；上游哪天变慢，这个数立刻又错。
**正解是取消"必须猜一个数"这件事本身** —— 于是改成任务化 + 心跳轮询。

### 二十八.1 后端

- `POST /external-data/apis/{key}/probe` → **202 返回 `{task_id, api_key, status, reused}`**，不再等上游；
- `GET /external-data/apis/probe/{task_id}` → 状态、`stage/percent/message`、`heartbeat_at`、
  `seconds_since_heartbeat`、`heartbeat_stale`、终态时带 `result`；轮询走控制平面池（NullPool）；
- worker 复用现成 `create_async_task` / `_start_worker` / `_set_task`（含 PT-DEF-15 库归属守卫、
  `is_worker_stop_requested` 优雅停机、心跳过旧由框架巡查升级为 `interrupted`）；
- 真实调用仍交给 `_PROBE_EXECUTOR`，保住"最多 8 个并发探测"的上限；worker 只做**分段等待 + 刷心跳**；
- 两个新常量语义明确分开：`_PROBE_HEARTBEAT_SECONDS=5`（多久报一次平安）与
  `_PROBE_HARD_LIMIT_SECONDS=300`（防线程外泄的安全网，**不是** UX 时限）；
- 同 key 并发重复点击复用同一任务（进程内登记；终态后不劫持，"重探"一定真重探）；
- 顺手修掉两个我自己写出的真 bug（都是实现错，不是测试错）：
  ① 心跳是 aware、`_probe_now()` 是 naive，相减 `TypeError` 会让**轮询接口 500**、界面永远转圈
  → 加 `_as_naive_utc()` 归一；
  ② 轮询读的是 `AsyncTaskRead` 视图，它只暴露已解析的 `result` 字段，我按原始列名读
  `result_json` → **永远 None**（表现是"探测完成却没结果"）。

### 二十八.2 前端

`probeAkshareApi` 删除，改为 `submitApiProbe` + `getApiProbeTask`（两者都是快接口，15s 只是网络保护）。
`AkshareApiManager.probeOne` 保持签名不变（单个/批量共用同一接缝），内部变成"提交 → 轮询到终态"：
800ms 起、每轮 +400ms、封顶 3s；行内按钮显示「探测中 Ns」；
`heartbeat_stale` 时**明确报错并停止轮询**（绝不无声转圈）；探测失败/提交失败都显式提示。

### 二十八.3 顺带消灭的"押时长"守护

`test_blackbox_api_mgmt.py` 与 `test_blackbox_stability_guard.py` 里 4 条基于
`elapsed < 30/55/180` 的用例（其中 3 条挂着 `xfail_dev_hardware`，即在 CI 里**永远预期失败＝没测**）
换成语义断言：提交即时（<2s，它本就不该等上游）、任务必能收束（终态或心跳可疑）、
探测在后台跑时 `/discovery/tasks` 仍 5s 内响应、连续提交不退化。
`PROBE_BUDGET_SECONDS` 常量删除，`TIMEOUT` 从 62 回落 30（不再有"读超时须大于产品探测预算"这件事）。

### 二十八.4 又修掉一处测试隔离缺口

`tests/conftest.py` 的 `db_session` 逐用例改绑主库，却**没失效控制平面缓存**

### 二十九.2 做了什么

1. **`.gitignore` 规则化**：10,237 行 → 约 130 行，全部为目录/后缀/形状规则，不再逐文件列举。
2. **一次性产物出库**：`git rm` 共 **73 个**已跟踪的过程性文件（66 + 6 个 `_tr*.py` + 1 个

   - 第 12 道：`.gitignore` 条目数上限、禁止 `.venv/` 下逐文件条目、必须整目录忽略 `.venv/`，

### 二十九.3 过程中我自己写坏又被守护抓到的两处

1. **未锚定的形状规则会吞源码**：我一开始写了不带 `/` 的 `scan_*.py`、`check_*.py`、
   `fix_*.py`，于是 `scripts/scan_business_databases.py`、`scripts/scan_expected_failure_stale.py`
   这几个**正式工具**一起被匹配。与新守护的 `tracked ∩ ignored` 断言撞上后暴露
   （109 个命中），随后全部改为 `/` 锚定到仓库根。这正是 §十一.7 那起事故的同类。
2. **`git check-ignore --stdin` 在本机行为异常**：不带尾换行只返**最后一行**，
   带了尾换行反而**全不返**。我因此两次得出"根目录几乎没有文件被忽略"的错误结论
   （与 `git status` 只报 2 条未跟踪直接矛盾）。最终改用与守护测试同一口径的
   `git ls-files --others --ignored --exclude-standard`，数字立刻对上（447）。
   教训：口径冲突时先怀疑自己的工具，不要拿它当事实。
3. **压缩不是一步到位的**：第一版规则写完后，`git status` 立即冒出 **10 个漏网文件**
   （`.tmp-run-worker6.py`、`cleanup_tasks.py`、`debug_discovery_button*.py`、
   `blackbox/whitebox-*.xml`、`_pt_a_funds_blackbox.py` 等）—— 老黑名单逐条盖住的东西，
   形状比我推断的更杂；补完形状后又因 `/factor-*.xml` 误伤一个已跟踪转储文件。
   两轮都靠 `tracked ∩ ignored` 与 `git status` 这两个**外部口径**兜住，而不是靠我自己
   相信规则写全了 —— 这也正是第 12 道守护存在的意义。
