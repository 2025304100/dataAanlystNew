## 四、PT-DEF-6 · manual/confirm 成员被自动成交（资金路径回归 · 已修复 B 方案）

### 现象（探针实测）
构造含单个 confirm/manual 成员的组合 + 已应用快照，调用 `execute_member_source`：
- confirm 模式 → 生成 **filled 买单**（旧契约：待确认，不创建 SimOrder）
- manual 模式 → 生成 **filled 买单**（旧契约：只提示信号，不下单）
- 快照 `member_snapshot_json` 带不带 `execution_mode` 结果相同

### 证据链
1. **文档不变量**（多份、明确）：
   - `opportunity-center-...final-plan.md` L667-669 / L960 / L1552-1562：manual 只提示信号不下单；confirm 只生成待确认计划；**自动交易只遍历 execution_mode=auto 成员**
   - `组合策略因子模型与回测全链路贯通开发方案.md` L400：`execution_mode=auto` 是自动执行授权，不满足时「只能提示或等待确认，**不能自动下单**」
   - 同文件 L1163 将「自动交易与手动操作冲突」列为需 execution_mode 缓解的风险
2. **旧实现仍正确但已脱离主路径**：`get_buy_candidates`（L438 跳过非 auto）、`get_signal_candidates`（L528 只处理 manual/confirm）仍存在，但 `execute_member_source` 迁移后不再调用它们。
3. **新路径无 mode 感知**：`execute_member_source` → `_execute_snapshot_order_plans` → `default_engine.evaluate`。`default_engine = DecisionEngine()`（无参构造，L3276）→ `build_universe = _stub_universe_builder`（L480 默认兜底），该 stub 把快照全部成员当 universe、`ineligible=[]`、**不过滤 execution_mode**。L462-463 注释确认 stub「真实实现随 WP0-3b/0-4a/0-5a 逐步替换」——universe builder 至今未替换。
4. **快照含全 mode**：`_build_member_snapshot`（`factor_usage_service.py` L112-123）把所有有效成员（含 execution_mode 字段）写入快照，不过滤 manual/confirm。
5. **上游无补偿门**：`save_and_apply` 不筛 mode；`dual_run` 只 gate source/snapshot/readiness；`get_auto_trade_readiness` 只用 auto 成员算 eligible，但**不因存在 manual/confirm 成员而阻断执行**。

### 净效果
含 manual/confirm 成员的组合一旦 `save_and_apply`，下次自动模拟交易会把这些成员的买单**自动成交**，违反文档安全不变量。当前 ~18 个 auto_trade 失败测试是唯一绊到该回归的警报线——**不是"腐烂"，是"报警"**。

### 修复（已实施 B 方案 · 2026-09-26）
判定为**回归**，采纳根治方案 B：用真实 `_real_universe_builder` 替换 `_stub_universe_builder`，在 universe/eligibility 阶段按 execution_mode + run_type 过滤。

**核心改动**（`app/services/decision_engine.py`）：
1. `UniverseBuilder` Protocol 签名扩展 `run_type` 参数（原 `(db, snap, cutoff_utc)` 不含 run_type，无法区分回测/实盘）。
2. `evaluate` 调用点透传 `run_type`（L777）。
3. 新增 `_real_universe_builder`，`default_engine` 默认改用它（原 `_stub_universe_builder` 保留供 G2 直接引用）。
4. 适配注入自定义 builder 的测试签名（test_stage3_allocator_clamp ×6、test_wp_stage1_order_plan ×1）。

**run_type 隔离矩阵**（default_engine 为全局单例，四入口共用）：

| run_type | 语义 | universe 过滤 |
|---|---|---|
| `auto_simulation` | 实盘自动交易（唯一真实成交 SimOrder） | **仅纳入 auto**，manual/confirm → ineligible |
| `backtest` | 回测 | 全量（C-03 用 `auto_authorized_flag` 白名单） |

**向后兼容**：member dict 缺失/空 execution_mode（仅测试 seed 与迁移前历史快照；生产快照 `_to_row` 必写该列，NOT NULL default manual）→ 视为 eligible；明确 manual/confirm 及脏值 → fail-safe ineligible。

**层3 信号路径（选项 X，已实现）**：manual/confirm 的“信号提示/待确认”输出已在 `_execute_snapshot_order_plans` 末尾恢复——从快照 members 识别 manual/confirm，复用 `_get_latest_signal` + `_BUY_ACTIONS` 口径生成 signal_decisions（含 execution_mode）与 executed_orders（confirm→pending_confirmation、manual→signal_only，均无 order_id/不建 SimOrder）。至此文档三态不变量（manual 提示、confirm 待确认、auto 成交）完整实现。

  而 `db_session.get_bind().url` 与 `get_session_local()` 的 URL **完全一致**（排除了“写错库”）。`run_fast_scan` 按 `generated_at DESC` 取最新 ready 快照 → 取到那个空快照（id=1）而不是 helper 准备的 07-19 快照（id=2），于是 `cache_hit=True`、`coarse_match_count=0`。
- **根因**：上一个用例触发的 `Thread-N (_run)` 异步 worker 是 daemon、**跨用例存活**，并且它写库用的是 `get_session_local()` 的**进程全局 session** —— 而 `db_session` 夹具每个用例重绑一次 engine，于是那个线程把数据写进了“它执行那一刻恰好当前”的别人库。外网调用（实测报过 hot-rank 与龙虎榜两个端点）是同一批后台任务发的，属伴生症状而不是第一因。
- **修复**：
  1. `tests/conftest.py::_isolate_worker_stop_event` 升级为“停工位清理（全局）+ 残留 worker 线程回收（opt-in）”两层；
  2. 新增 marker `reap_workers`（已写入 `pytest.ini`，否则 `--strict-markers` 报错），只在 `test_whitebox_discovery_fast_scan.py` 上启用；

### 十四.1 为什么新建表而不抄因子域配置表

本仓没有通用 settings 表，最接近的 `factor_system_config.extra_json` 属**因子域**（docstring 自陈 “feature readiness settings”）。把发现中心的设置塞进去，就是本报告反复治理的“跨域耦合 / 同一事实多处记录”那一类（PT-DEF-13 同族）。所以新建 `app_settings`（rev 064）：主键即业务键、值统一 JSON、`updated_by` 留痕“谁关的”；以后各域设置都走它，新增一个开关只是登记表里加一行。

### 十四.2 落地形状

- **后端单一真相**：`app/services/app_settings.py::APP_SETTING_REGISTRY` 登记每个开关的
  `type / default / env_var / section / label_zh / description_zh`。前端与发现中心都不再
