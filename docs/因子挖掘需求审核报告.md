## 0. 一句话结论

三份文档的质量在**算法设计层面非常高**（遗传算法、NSGA-II、自适应调度、去重机制的设计深度超出一般需求文档），但在**与现有底座的对接、交付排期自洽性、工程量评估**三处存在系统性断裂。

最致命的问题不是"能不能做"，而是 **§7 分阶段交付表（P0 枚举范式、P3 才上遗传算法）与 §5.1"本期实现遗传算法范式"、以及验收标准第 11~15 条（全是遗传算法/F2/F1/G1+G2 的验收）互相矛盾** —— 按 P0+P1 交付的话，首期根本无法通过自己写的验收标准。

**建议：先花 1~2 天做一次需求定稿会，砍掉或延后 F1 独立模块 + F2，把首期收敛为"单种群遗传算法 + 结果页最小闭环"，再排期。**

## 3. 阻断项（Blocker）—— 不解决不能开工

### B1. 交付排期与验收标准自相矛盾（最严重）

- §7 分阶段交付：**P0 = 模板+参数网格（枚举范式）**，**P3 = 遗传算法适配器（逐代 IC 曲线、收敛提示、提前停止）**，并明确"首期（P0+P1）不做逐代进化曲线、收敛判定、提前停止"。
- 但 §2.1 / §5.1 明确："**本期实现遗传算法范式**……不再使用模板+参数网格一次性枚举的范式"。
- 而 §6 验收标准第 11~15 条，全部是**遗传算法、选择机制、繁殖自适应、F2、F1、G1+G2** 的验收。

**后果**：按 P0+P1 交付 → 验收 11~15 全部不通过；按遗传算法交付 → P0/P1 的交付物描述作废。
**建议**：删除 §7 旧表，重排为「GA 核心 → 选择机制 → 自适应 → 性能 → F1/F2」的增量顺序。

### B2. "训练"术语污染，范围边界不清

- 文件名叫《因子挖掘**训练**向导》，Step 2 叫"时间与目标"，全文充斥"训练任务/训练锁/训练快照/训练候选池"。
- 但 §2.1 明确："**因子挖掘……不是因子模型训练**"；§4.2 又写"不包含 Ridge 训练、评分生成或模型激活"。
- §4.2 的阶段展示（数据准备→公式计算→目标生成→单因子评估→去重确认）与 §2.1 的链路（……→冻结 FactorSet→训练 FactorModelRun→影子/激活）**直接打架**。

**后果**：开发和验收会各自理解成不同范围。
**建议**：全文"训练"改为"挖掘/实验"；文件名改为《因子挖掘实验向导》；明确"本模块止步于候选因子产出 + 加入 draft FactorSet，模型训练归因子模型页"。

### B3. 全局单任务锁定义冲突，且与定时调度打架

- §2.6："**全系统**训练任务最多保留一个 `queued`/`running` 任务"。
- §8.2："同一**因子仓库**同一时间只允许一个挖掘任务进入 `running`"——紧接着又说"系统全局最多保留一个训练任务"。
- 现实：项目已有 `scheduled_tasks` 的 **11 类定时任务**（行情同步 18:00、估值同步 19:00、因子流水线、自动交易等）在并发跑。

**问题**：如果挖掘任务占"全局唯一锁"，18:00 的行情增量同步和 19:00 的估值同步会不会被挡？文档没说。
**建议**：改为「**挖掘任务域内唯一**（`task_type='factor_mining'` 维度加唯一约束）+ 全局并发上限 N」，不要做全局唯一。这与现有 `async_tasks` 的多任务模型才兼容。

### B4. G2 缓存方案与现有 DuckDB 单写约束冲突

- 文档 3.13.1：`CREATE TEMP TABLE subexpr_cache` 在 DuckDB；G1 多进程并行计算；"DuckDB 单连接写入利用自带锁"。
- 现实：`app/services/factors/store.py` 明确 DuckDB **多读者单写者**，写入靠 `warehouse_locks` 串行化。多进程同时写一个 DuckDB 文件会崩，不是"利用自带锁"能解决的。
- 另外文档同时要求"断点续跑时持久化到磁盘 `{run_id}_cache_{generation}.duckdb`" —— 等于每个任务多开一个 DuckDB 文件，与主仓库锁是两套体系。

**建议**：子进程**纯内存计算**（不碰任何 DuckDB 文件），结果经共享内存/序列化回传主进程，由主进程统一写；缓存放主进程内存或独立临时文件，不复用业务 DuckDB 仓库。

### B5. `psutil` 不在依赖里（已核验）

文档 3.13.2 的 `determine_workers()` 用了 `psutil.cpu_count()` / `psutil.virtual_memory()`，但 `requirements.txt` **没有 psutil**。
**建议**：新增 `psutil`，或改用标准库 `os.cpu_count()` + 简化内存判断，避免为一个功能引入新依赖。

### B6. Windows 多进程性能风险被低估

- 项目是 Windows 优先（`.venv`、`scripts/*.ps1`、`.bat`）。Windows **没有 `fork`**，multiprocessing 用 `spawn`：每个子进程要重新 import 整个 app（pandas / numpy / akshare / sklearn），**单进程启动开销可达数秒**。
- 文档承诺"进程池复用"能缓解，但"端到端 20~25 分钟"的目标在 Windows + spawn 下非常激进，且 `multiprocessing.shared_memory` 在 Windows 上有 resource_tracker 泄漏的已知坑。

**建议**：先做**单进程串行基线压测**（100 个体 × 1 年样本 × 500 股），拿到真实数字再决定是否上 G1。文档自己的性能数字（每代 5 分钟 / 50 秒 / 25~35 秒三套）没有任何压测支撑。

### B7. API 路径不符合现有规范

文档定义 `/api/f1/experience`、`/api/f1/overview` 等，但项目统一前缀是 **`/api/v1`**，且路由命名用 kebab-case（`factor-sets`、`portfolio-governance`）。
**建议**：改为 `/api/v1/factor-experience/...`，tag 用 `factor-experience`。

### B8. 数据就绪结论已过期

§2.4 的"当前数据就绪结论"落款 **2026-09-06**（仓库 `degraded`、行情截至 2026-09-04、217 万行），今天是 **09-15**，已过 9 天。首期范围（只用价量+换手、估值/财报逐步开放）**建立在这个快照上**。
**建议**：开工前重新跑一次仓库健康检查，刷新数据能力矩阵再定首期字段范围。

## 5. 需求缺口（文档没写，但 PM 必须定）

1. **前瞻验证 / 过拟合防线** —— 见 R1，最高优先级缺口。
2. **AI 成本上限** —— 只在 §6.8.5 提了"成本超预算限制每代 1 次"，但**没有预算数值、没有全局月度上限、没有费用展示**。
3. **失败可诊断性** —— 进化任务失败后，用户怎么区分"数据问题"还是"参数问题"？`fix_action` 只覆盖字段校验阶段，进化阶段失败无引导。
4. **F1 模块归属** —— F1 放因子域内（`app/services/factors/`）会触发 conftest 的**因子域导入门禁**；独立放又需要新 tag。目录归属与防腐边界必须明确。
5. **结果写入压力** —— 2000 候选 × 每代 4 指标 + generations 汇总，7 天保留期。SQLite 单文件批量写入策略未提（批量 insert / 事务边界）。
6. **结果复现验证入口** —— 文档强调"固定种子可复现"，但**没有"重跑比对"功能**，用户无法验证可复现性。
7. **容量与配额** —— 单个挖掘任务的磁盘/内存上限、候选数上限、并发上限，只有"资源确认弹窗"的估算，没有硬配额。

**我的砍项建议**：**F1 历史经验库建议整体延后到 P4 甚至下一版。** 理由：
- 它是"独立模块"，但**没有挖掘主链路它就没有输入**（经验来源 100% 依赖挖掘产出），放在一起做等于先建仓库再造货；
- 它的 4 个 Tab（概览/列表/导入导出/清理）+ 共享库 + 插件式格式转换，是整套需求里**工程量最大、用户价值最滞后**的部分；
- 首期没有历史积累，"加权衰减/场景匹配/成功率"这些设计跑不起来。

**F2 也建议延后**：它依赖 C1/D1/D3 全部就位才能触发，且依赖 F1 的读接口（若 F1 延后，F2 的"相关经验"输入是空的）。

# 附录 A：裁剪决策的依据（为什么砍 F1 / F2 / G1+G2）

## A.1 我用的 7 个裁剪维度

不是凭感觉砍，每条建议都过这 7 个维度：

| # | 维度 | 判断标准 |
|---|------|----------|
| 1 | **依赖前置性** | 是否存在"上游没做完，本模块就是空转"的硬依赖 |
| 2 | **冷启动门槛** | 上线首日有没有数据/样本可供其运转 |
| 3 | **价值兑现时序** | 用户第几次使用才能感知到价值 |
| 4 | **工程量 / 价值比** | 投入产出比，是否有更便宜的替代方案 |
| 5 | **关键路径** | 砍掉它，主链路还能不能跑通 |
| 6 | **可独立验收性** | 能否单独上线、单独回归 |
| 7 | **返工代价** | 做错了推翻重来的成本 |

## A.2 F1 历史经验库：7 个维度全绿（都指向"延后"）

| 维度 | 结论 |
|------|------|
| 依赖前置性 | ❌ **100% 依赖挖掘产出**。唯一写接口（接口1）的触发条件是"因子全量验证有效 **且人工确认入库**"，即必须走完 5.4 生命周期 `candidate → testing`。P1 未完成前，F1 零输入。 |
| 冷启动门槛 | ❌ 上线首日库是空的。文档设计的"加权衰减 / 场景匹配打分 / 成功率 / use_count / success_count"**全部依赖历史积累**，空库下这些算法无输入、无法验证是否正确。 |
| 价值兑现时序 | ❌ 首次挖掘时 F1 完全无作用；需用户跑 N 轮并人工确认入库若干因子后才开始产生价值，是**最滞后的价值点**。 |
| 工程量/价值比 | ❌ 4 张表 + 4 个 Tab（概览 5 张图表 / 列表含详情弹窗 / 导入导出含异步执行+报告 / 清理含季度定时+消息通知）+ 共享库文件锁 + 插件式格式转换（识别器+转换器+字段映射表+算子映射表）+ 参数泛化 + 场景匹配 + 加权随机抽取 + 参数实例化。**是整套需求里工程量最大、价值最滞后的模块。** |
| 关键路径 | ✅ 砍掉不影响主链路（初始种群靠经典+AI+随机三来源已能跑） |
| 可独立验收性 | ✅ 独立模块，随时可补 |
| 返工代价 | ✅ 接口已定义（存/取两个），后补不污染现有代码 |

**结论：典型"先建仓库再造货"。放在首期等于用一个空转的复杂模块拖慢主链路交付。**

## A.3 F2 AI 引导变异：跟着延后（不是因为它不好，是因为它被三重依赖锁死）

1. **依赖 F1 读接口**：场景 B 明确"F2 调用 F1 查询相关经验 Top5 作为 AI 输入"。F1 延后 → `related_experiences` 恒空 → F2 的"历史经验参考"这个卖点直接失效，只剩纯 LLM 建议。
2. **依赖 C1/D1/D3 全部就位**：触发条件是 `stall≥2`、`health<0.5`、每 3 代定期 —— 这三个信号分别来自 D1 和 D3，而 D3 又依赖 A1 的类型均衡度。等于 **F2 是整条信号链的末端**，任何一个上游没做完它都无法触发。
3. **效果反馈闭环增加 C1 耦合面**：B1 分别统计 AI/随机平均 ICIR → 回喂 C1 动态调整比例。这是在"九机制职责分离"之外**又开了一条调参回路**，与文档自己强调的"C1 是唯一调参者、禁止两个机制同时写同一参数"有张力，容易破坏设计纯净性。
4. **AI 调用是同步的**（`llm_client.py` 全 `def` 无 `async`），在进化循环里要包 `asyncio.to_thread`，且初始种群 AI 生成是批量阻塞调用。
5. **成本不可控**：文档只在异常处理里提了"成本超预算限制每代 1 次"，**没有预算数值、没有月度上限、没有费用展示**。

**结论：F2 不是独立功能，是"锦上添花层"。它应该在 GA 主链路稳定跑通、F1 有货之后再上。**

## A.4 G1+G2：不是砍，是"先压测再决定"

反对盲做的理由：

1. **不知道瓶颈在哪**。没有任何压测基线。100 个体 × 1 年 × 500 股的真实耗时未知——瓶颈可能在数据加载、可能在 IC 计算、可能在 AST 求值，三者的优化手段完全不同。**没压测就并行化，可能优化了只占 10% 耗时的部分。**
2. **项目从未用过 ProcessPool**（已核验）：`discovery_tasks.py` / `universe_sync.py` / `task_state_machine.py` 全部是 `ThreadPoolExecutor`，且用途是给 akshare 加超时兜底（I/O 密集），**与 CPU 密集的因子计算是完全不同的场景，无可复用先例**。
3. **Windows 无 fork**：spawn 下每子进程重新 import pandas/numpy/akshare/sklearn，启动开销数秒级；`multiprocessing.shared_memory` 在 Windows 有 resource_tracker 泄漏的已知坑。
4. **撞 DuckDB 单写约束**（见 B4）。
5. **正确性兜底本身就是工作量**：抽样校验、NaN/Inf 检查、心跳重试、串行复现模式、缓存版本管理——这些不是为了"快"，是为了"不错"，占 G1+G2 工作量的相当比例。
6. **文档自己的性能数字三处打架**（每代 5 分钟 / 50 秒 / 25~35 秒；端到端 2 小时 / 55 分钟 / 20~25 分钟），说明这些是估算而非实测。

**建议顺序**：先交付**正确的串行版本** → 压测出真实数字与瓶颈画像 → 再决定是上 G1（并行）、G2（缓存）还是只做其中一项，甚至都不做（如果串行已够快）。

## C.1 DSL 扩展需要什么数据

### ① 截面算子 rank / zscore —— **数据已具备，卡点是工程 + 一个标记**

| 需要的 | 现状 | 结论 |
|--------|------|------|
| 横截面宽度 | 中位数 5,426 只/日 | ✅ 充足（需求只要 500） |
| 截面分组键 | `raw_daily_bars.trade_date` | ✅ 有 |
| 因子值面板（symbol × date） | `factor_values` 1.41 亿行 | ✅ 有现成结构可参考 |
| **停牌 / 退市 / 上市状态标记** | ❌ **无显式 status 列**，现靠"当日无记录"隐含表达 | ⚠️ **缺口**：rank 时无法区分"停牌"与"已退市"，会把停牌股算进截面或误剔除 |
| 行业标签（若做行业中性化） | `symbols.industry` 当前值，**无历史版本** | ⚠️ 仅能用于静态筛选 |

**结论：rank 算子不需要补任何行情数据**，只需补"交易状态标记"这一项元数据。这是三项前置里**数据成本最低**的。

### ② delta —— **不需要新数据，但口径必须先定死**

- 纯时序运算，`close` 列 ✅ 数据有。
- **关键口径分歧**：
  - 若意为"过去 N 日涨跌幅" → 现有 `pct_change(close, n)` **已完全等价**，不必新增算子，改模板写法即可。
  - 若意为"差分"（如 `roe_ttm[t] - roe_ttm[t-4]`）→ 财报是**按 `report_period` 的非等间隔序列**，`delta(n)` 的 `n` 究竟是"第 n 个报告期"还是"第 n 个交易日"？**这个不定，质量类 4 个模板无法实现。**

### ③ atr —— **可以零数据成本实现**

- ATR 需要 `prev_close`，但 **`raw_daily_bars` 没有 `prev_close` 列**。
- 两个方案：
  - **方案 A（推荐，零数据成本）**：用现有 `ref(close, 1)` 实现 → `atr = mean(max(high-low, abs(high-ref(close,1)), abs(low-ref(close,1))), n)`
  - **方案 B**：补 `prev_close` 列 → 需回灌 217 万行历史数据
- **顺带发现**：DSL 的 `FIELD_CATALOG` 里**已注册 `prev_close`，但日线表根本没有这一列** —— 这是一个"虚注册"字段，要么补数据、要么撤销注册，否则公式能编译但执行必报错。

### ④ 字段注册 —— **关键发现：估值数据是现成的，白扔了**

| 字段 | 原始表是否有 | 数据覆盖 | 行动 | 成本 |
|------|-------------|---------|------|------|
| `dividend_yield` 股息率 | ✅ `raw_valuation_snapshots` | 2018~2026，5,549 标的，**308 万行** | **直接注册** | 零 |
| `total_market_cap` 总市值 | ✅ 同上 | 同上 | **直接注册** | 零 |
| `circulating_market_cap` 流通市值 | ✅ 同上 | 同上 | **直接注册** | 零 |
| `pe_ttm` / `pb` | ✅ 已注册 | 同上 | 已有 | — |
| `roe_ttm` | ✅ 已注册 | **仅 2,209 标的**（日线 5,561）→ 覆盖率约 40% | 已有，但覆盖不足 | — |
| `gross_margin` 毛利率 | ❌ 财报表无此列 | 无 | **必须新采集 + 回灌** | 高 |
| `asset_turnover` 资产周转率 | ❌ 无此列 | 无 | **必须新采集 + 回灌** | 高 |
| `main_net_inflow` 主力资金 | ✅ 已注册 | **仅 320 标的 / 3 个月** | 首期禁用 | — |

**财报表实际列**：`symbol, report_period, announcement_date, report_type, roe_ttm, net_profit, revenue, net_profit_yoy, revenue_yoy` —— 确认**没有 gross_margin、没有 asset_turnover**。

**重要结论**：估值类 4 个模板"全挂"是**纯粹的 DSL 问题，不是数据问题**。估值数据（308 万行 / 5,549 标的 / 8 年）非常充分，只是 `dividend_yield` / `total_market_cap` / `circulating_market_cap` 三个字段没注册、加上缺 `rank`。
→ **注册这 3 个字段 + 加 rank 算子 = 零采集成本激活估值类因子，是三项前置里性价比最高的动作。**

## C.2 test 段 + 迁移需要什么数据

### 迁移本身：影响面极小，可以直接做

- 迁移基线（alembic head）：`2026_09_03_0052_wps_0023_050_factor_model_members`（共 52 个版本）
- `factor_evaluation_runs` **仅 5 条**历史记录 → 加 `test_start_date` / `test_end_date` 两个 nullable 列，历史留 NULL 即可
- 现有 5 条记录的区间示例：`train 2025-01-13~2025-12-31 / validation 2026-01-12~2026-05-07` —— **起点正是日线数据起点，说明历史评估已把现有数据用满**

### ⚠️ 真正的卡点：日线只有 1.65 年，撑不起需求的样本量门槛

`raw_daily_bars` 覆盖 **2025-01-13 ~ 2026-09-07 ≈ 400 个交易日**。对照需求 §4/§2.6 的最小样本量硬门槛：

| 调仓频率 | 需求最小有效调仓点 | 实际可得（400 交易日） | 结论 |
|---------|------------------|---------------------|------|
| 日频 | 252 | ~400 | ✅ 勉强够 |
| 周频 | 104 | ~80 | ❌ **不达标** |
| 月频 | 36 | ~19 | ❌ **严重不达标** |

**连锁反应**：
- 需求"每代短样本评估 1 年" → 1 年 / 1.65 年 = **吃掉 60% 的数据**，三段切分后每段只剩半年多
- 需求"最终全量验证 3~5 年" → **完全没有数据支撑**
- 需求"生产建议周频≥156 点、月频≥60 点" → 差距更大

**→ 这是三项前置里唯一必须真正补数据的一项，且是硬门槛。**

### ✅ 更正：数据其实早就有了，是"没镜像进因子仓库"，不是"没有数据"

初次审计我判断"需要跑历史同步重新采集"，这个结论**不完整**。进一步追查后更正如下：

| 层 | 表 | 实测覆盖 | 行数 | 标的 |
|---|-----|---------|------|------|
| **MySQL 基础数据层** | `universe_daily_bars` | **2016-07-12 ~ 2026-09-07（10 年）** | **11,538,502** | 7,270 |
| MySQL 业务表 | `daily_bars` | 2025-06-05 ~ 2026-08-27 | 1,420,232 | 5,969 |
| **DuckDB 因子仓库** | `raw_daily_bars` | **2025-01-13 ~ 2026-09-07** | 2,172,766 | 5,561 |

**MySQL 按年分布（完整无缺口）**：

| 年 | 2016 | 2017 | 2018 | 2019 | 2020 | 2021 | 2022 | 2023 | 2024 | 2025 | 2026 |
|---|---|---|---|---|---|---|---|---|---|---|---|
| 行数(万) | 24 | 70 | 77 | 84 | 91 | 109 | 129 | 142 | 151 | 161 | 117 |
| 标的数 | 2827 | 3289 | 3399 | 3602 | 4004 | 5072 | 5631 | 6100 | 6362 | 6907 | 7270 |

**根因（`bar_mirror.py` 实测）**：

- 镜像模块**本来就支持 universe 源**：`UNIVERSE_SOURCE_KEY = "sql.universe_daily_bars"`，且 `_mirror_universe_bars(start_date, end_date)` **支持指定任意区间**。
- DuckDB 里 98.9% 的行来自 universe 源（`source_origin='universe_daily_bars'` 有 2,148,863 行），说明**链路是通的**。
- 但 `warehouse_watermarks` 显示镜像任务的 key 形如 `sql.universe_daily_bars|2025-01-12|2026-07-17` —— **start_date 最早只到 2025-01-12**，从未要求同步 2016~2024 的历史。
- 辅证：`universe_sync.py` 的 `DEFAULT_HISTORY_DAYS = 365`（注释"默认 365"），`main.py` 的自动初始化也传 `history_days=365`。

**结论：不是缺数据，是"镜像范围只给了约 1 年"。**

**修复方案（成本远低于重新采集）**：
- 直接调用 `_mirror_universe_bars(start_date=..., end_date=2026-09-07)` 做一次**本地 MySQL → DuckDB 的历史镜像**，纯本地 I/O，**不受 AkShare 限流影响**。
- 建议区间：`2021-01-01` 起（5 年，标的数 5,072~7,270，截面充足）；若要最长历史可全量 `2016-07-12` 起（注意 2016~2018 标的仅 2.8k~3.4k，覆盖率偏低）。
- 容量预估：`raw_daily_bars` 从 217 万行 → 约 1,154 万行（5 年约 700 万行）；当前 DuckDB 文件 6.2 GB 主要由 `factor_values`（1.41 亿行）占用，磁盘剩余 169 GB，**空间充足**。
- 注意：镜像内容仅 OHLCV + `turnover_rate`，**仍然没有 `prev_close`** → ATR 依旧要用 `ref(close,1)` 方案。

## D.1 已实现（✅ 实测确认）

### ① 时间切分：三段 + purge + embargo

`factor_evaluator.TimeSplit`（L221-233）：

```python
train_start / train_end
validation_start / validation_end
test_start / test_end        # ✅ 有 test 段
purge_days: int = 5          # 训练-验证隔离期
embargo_days: int = 5        # 验证-测试禁运期
target_horizon: int = 5      # 目标 horizon
```

`build_time_split()`（L236-316）关键逻辑：

| 机制 | 实现 |
|------|------|
| 比例切分 | `train_ratio=0.6` / `validation_ratio=0.2` |
| **purge 隔离** | `val_start_idx = train_end_idx + purge_days` |
| **embargo 禁运** | `test_start_idx = val_end_idx + embargo_days` |
| **tail_loss 扣除** | `usable_n = n - target_horizon`（前向收益 shift 后尾部 horizon 天无标签，已扣除） |
| **硬失败诊断** | 样本不足抛 `insufficient_dates`，含 `actual / derived_min_total / splits[raw] / splits[effective] / tail_loss` 全量诊断 + 修复建议 |

### ② 特征-目标对齐：不预测过去

`align_factor_with_target()`（L331-400）文档串明确安全约束：

> - 特征日 t 的因子值**只能对齐 t+horizon 的目标收益（不预测过去）**
> - 事件因子只对齐事件日样本
> - 移除 NaN 对（特征或目标缺失）

### ③ 目标标签：T+1 开盘 → T+5 收盘（专业防前视）

`target_engine.calculate_targets()`（L151-211）：

> """Persist **T+1 open to T+5 close** labels without skipping suspensions."""

| 设计 | 防前视作用 |
|------|-----------|
| `signal_date`（T） | 因子值可得日 |
| **`entry_date`（T+1）用开盘价** | **不用 T 日收盘价成交**——避免"T 日收盘后信号用 T 日收盘价建仓"的经典前视 |
| `exit_date`（T+5）用收盘价 | 明确持有期 |
| `target_value = exit_close / entry_open - 1.0` | 实际可成交收益 |
| `limit_threshold = 0.095` 涨跌停过滤 | 涨跌停无法成交的样本标记 `is_tradable=False` + `invalid_reason` |
| "without skipping suspensions" | 停牌日不跳过，真实反映可执行性 |

标签持久化在 `factor_targets`（DuckDB **2,637 万行**），评估主路径读预生成面板；`wp5_eval_task._fallback_shift_pct()` 是兜底路径（`factor_values.shift(-horizon).pct_change(horizon)`）。
