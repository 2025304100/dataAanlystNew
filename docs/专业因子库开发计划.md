## 0. 执行结论

开发按“数据底座 + 三次功能发布”推进，不一次性重写现有因子流水线：

1. R0 先解决数据库迁移基线、DuckDB 锁、数据新鲜度和错误乱码，不在不稳定底座上叠加专业因子库；
2. 冻结现有 8 个系统因子和 manual 行为，建立可对账基线；
3. R1 只建设“设置和管理因子”，首批可执行模板限定为当前数据可支撑的日线技术类因子；
4. R2 对不同数据类别分别准入；估值、资金流、尾盘代理覆盖未达标前不得进入正式评估；
5. 评估通过后仍需至少 20 个有效交易日 Shadow；
6. R3 才让通过审批的 Active 因子进入新的 FactorSet 和新 Ridge 模型；
7. AI 始终只生成结构化草案，不具备激活、切换模型或绕过评估权限；
8. 任何阶段失败都优先回退 manual 和旧因子读取路径，不改写历史 Score。

预计工作量：

| 交付范围 | 工作量 | 单人参考周期 | 双人参考周期 |
|---|---:|---:|---:|
| R0 当前数据底座与迁移护栏 | 7～12 人日 | 1.5～2.5 周 | 1～1.5 周 |
| R1 因子库管理 MVP | 18～25 人日 | 4～5 周 | 2.5～3.5 周 |
| R2 数据分层、评估、去重与 Shadow | 15～24 人日 | 3～5 周 | 2～3 周 |
| R3 FactorSet、Ridge 与发布门禁 | 7～10 人日 | 1.5～2 周 | 1～1.5 周 |
| 合计开发工作 | 47～71 人日 | 10～14.5 周 | 6.5～9 周 |

Shadow 至少 20 个交易日是独立的日历观察期，可以与 R3 的非生产接线开发并行，但不能被压缩或用历史回填冒充。

## 1. 范围与实施约束

### 1.1 本期必须交付

- 因子草稿、版本、来源、生命周期和引用关系；
- 安全公式编译、静态校验、多日期预览和错误解释；
- 因子库列表、详情、编辑器和审计记录；
- 数值自定义指标提交为候选因子；
- AI 结构化 FactorDraft，用户确认后才可保存；
- 不可变评估运行、IC/ICIR、单调性、覆盖、成本和扰动；
- 相关性、聚类、残差 IC 和 Shadow 每日观察；
- FactorSet 冻结、新 Ridge 模型接线及 manual 回退；
- 迁移、双读对账、回滚演练和完整验收报告。

### 1.2 本期明确不做

- 不做遗传编程、强化学习或无约束表达式生成；
- 不让 AI 自动发布 Active；
- 不引入 ClickHouse、Airflow、Prefect 或分布式训练；
- 不改变 3～15 个交易日的中短期决策边界；
- 不做分钟级、高频或自动下单扩展；
- 不为提高通过率而降低数据、时间安全或模型门禁；
- 不将缺失值统一填 0；
- 不在回测和训练时访问外网。

### 1.3 开发前提

- 仓库 Alembic 唯一 head 为 wps_0023_020_api_deprecation_logs，但活动 MySQL 尚无可确认的 alembic_version 基线；
- 新迁移预留 revision 为 wps_0023_021_factor_library_lifecycle；
- 现有 8 个系统因子继续作为内置种子和灾备定义；
- 现有 FactorVersion ID、模型运行、权重快照和历史 Score 不重编号；
- 前端继续使用当前 React、TypeScript、Ant Design 和 i18n 体系；
- 后端继续使用 FastAPI、SQLAlchemy、现有异步任务状态机和 DuckDB 单写锁；
- 默认运行模式继续是 manual，新功能由独立开关逐步开放。
- 首批科学评估只使用通过完整交易日检查的日线技术类因子；
- 基本面、资金流、热度、龙虎榜和尾盘因子按实际数据类别独立准入，不共用连续因子覆盖门槛。

### 2A.4 完整交易日规则

- 不使用 MAX(trade_date) 直接决定评估截止日；
- 以 universe_symbols 中 active stock 范围和过去 20 个完整交易日中位数作为基准；
- 当日标的数低于基准的 90% 时标记 incomplete，不进入截面评估；
- 当前现场应回退到至少 2026-07-24，而不是使用只有 150/218 个标的的 2026-07-29；
- EvaluationRun 必须保存 selected_trade_date、observed_symbols、expected_symbols、completeness_ratio 和 fallback_reason；
- 数据补齐后允许重新评估，但不能覆盖原运行。

### 2A.5 数据补齐边界

- 估值：当前来源只有极少快照，短期只能从补齐后的日期开始积累；没有历史 point-in-time 数据时，不做伪历史 IC；
- 财报：必须按 announcement_date 使用，先覆盖 300～500 个高流动性训练池，再扩全市场；
- 主力资金：表为空时不运行 main_inflow_5d_ratio；先验证接口可用性、复权口径、限流和至少 60 日连续性；
- 龙虎榜：只在事件样本内评估，不把非事件日填 0；
- 热度：当前快照适合解释/候选增强，不承诺历史连续性；
- 尾盘代理：当前无分钟数据，维持 blocked；本期不为了该因子引入大规模分钟库；
- 宏观：作为 regime 条件使用，不按股票横截面覆盖率评估。

### 2A.6 R0 退出条件

- [ ] 活动 MySQL schema 与 ORM/Alembic 差异有报告且可回滚；
- [ ] 0021 迁移不会在未审计库上盲目 upgrade；

- [ ] turnover_z20 能在冻结的完整交易日上重复计算；

## 16. 风险与项目控制

| 风险 | 触发信号 | 处理 |
|---|---|---|
| 最新日期是假完整数据 | 最新两日只有 150/218 个标的 | 完整交易日门禁，评估自动回退并记录原因 |
| 数据源根本无历史 | 估值 6、资金流/尾盘为 0 | 因子标 blocked，不伪造回填、不启动评估 |
| 活动 MySQL 无 revision 基线 | 未发现 alembic_version | 先 schema fingerprint 和备份，再决定 stamp/upgrade |
| 迁移破坏历史引用 | ID、版本或 Score 数量变化 | 立即停止切换，恢复备份并修复迁移 |
| 新旧状态并存产生歧义 | status、is_active、lifecycle_status 不一致 | 明确新字段唯一事实来源，旧字段只单向兼容 |
| 前端重复请求 | 同一操作产生两个创建/评估任务 | 按钮 loading、防抖、AbortController 和后端幂等键共同处理 |
| 公式能力超出计算引擎 | AI/用户公式通过但无法执行 | 编译器能力声明与预览共用同一执行路径 |
| 评估时间泄漏 | 历史时点读到未来公告或版本 | 阻断发布，补充 point-in-time 测试 |
| 事件因子误用连续门禁 | 覆盖低但事件样本有效 | factor_type 分类门禁，单独统计事件日 |
| DuckDB 锁冲突 | 7 月 29 日最近两次流水线已失败 | 锁诊断、跨进程单飞、心跳、临时批次和原子提交 |
| 中文任务信息乱码 | MySQL 历史失败 message 不可读 | error_code 为事实来源，UTF-8 存储和前端本地化 |
| Shadow 观察不足 | 为赶排期申请提前 Active | 后端硬性 20 个有效交易日门禁 |
| 新因子破坏旧模型 | 旧模型重放结果变化 | 冻结 FactorSet，历史只读固定版本 |
| AI 权限膨胀 | AI 工具出现 transition/activate | 权限测试阻断合并和发布 |

每周检查一次范围：只要任务不能直接服务于“设置、管理、评估、Shadow、FactorSet、回退”之一，就移出当前版本。

## 17. 项目完成定义

项目完成不是页面可打开或接口返回 200，而是同时满足：

- [ ] 用户能安全设置、预览、版本化和管理因子；
- [ ] 每个因子先证明当前数据 readiness，blocked 因子不能进入 testing；
- [ ] 最新完整交易日判定不会把残缺横截面当成全市场；
- [ ] AI 只降低草案门槛，不改变生产权限；
- [ ] 因子通过样本外、扰动、相关性和 Shadow 证据后才能 Active；
- [ ] 所有生产评分引用冻结 FactorSet 和确切 FactorVersion；
- [ ] 新版本、新因子和新模型不改变历史结果；
- [ ] 重复请求、取消、超时、重启和锁冲突都有明确终态；
- [ ] 当前 0 覆盖因子保持阻断，直到真实数据补齐，而不是通过填 0 获得假样本；
- [ ] 现有 8 个系统因子及 manual 闭环无回归；
- [ ] 中文界面、接口、迁移、测试、审计和回滚全部通过验收；
- [ ] 正式验收报告明确记录仍未解决的数据覆盖和模型风险。

满足以上条件后，才考虑 Phase 6 的模板网格、受控表达式树或其他自动挖掘能力。
