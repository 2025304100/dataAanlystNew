## 1. 需求约束与架构裁决

### 1.1 用户三条背景约束的落地映射

| 用户约束 | 落地方式 | 一致性 |
|---------|---------|--------|
| ① 因子挖掘与「因子中心」「因子模型」**同属一体** | 不新建 App 顶级 Tab；挖掘作为**设置内的独立一栏**（§9.1），物理代码落在 `app/services/factors/mining/`（与因子中心同域同包），数据全部落现有库，`factor_evaluation_runs` / `factor_versions` / `factor_sets` 直接复用 | ✅ |
| ② 在系统设置中**新增一栏**，菜单入口命名「**因子挖掘**」 | `Settings.tsx` 左侧导航新增一栏，section 值 `factor-mining`，文案 key `factorMiningTabTitle` = 「因子挖掘」；同时新增「因子基础配置」一栏承载模板与经验库 | ✅ |
| ③ **相对独立但与前述两者关联**，底层数据依赖当前项目，**扩展而非重构** | 依赖方向单向：挖掘 → 因子中心（复用编译/评估/注册/生命周期）→ FactorSet → 因子模型。挖掘**不被**任何模块反向依赖；因子模型反向禁止调用挖掘。既有文件只加函数/分支/目录项，**不改既有签名**（§4.4 红线 B5） | ✅ |

### 1.2 需要裁决的文档冲突（架构师裁决）

| # | 冲突点 | 输入文档说法 | 裁决 | 理由 |
|---|--------|-------------|------|------|
| D1 | 菜单位置 | 开发文档 §6："挖掘入口在「设置→因子中心」的评估实验室区域，**不新增顶级菜单**"；用户约束："系统设置中新增一栏" | **设置左侧导航新增一栏「因子挖掘」**；因子中心页签区保留一个跳转按钮。 | "顶级菜单"指 `App.tsx` 的一级 Tab（decision/portfolio/opportunity/…），Settings 内的一栏不属于顶级菜单。两者不冲突，且满足用户明确要求。 |
| D2 | 候选池表前缀 | 需求 §3.8 用 `training_candidate_pools`；开发文档 §3.0.1 同名 | **保留 `training_candidate_pool*` 前缀不改名**，但归属挖掘域独占读写。 | 改名会与需求、Prompt 变量、AI 输出命名联动，收益低于成本。 |
| D3 | F1 代码目录 | 开发文档列 F1 在「设置→因子基础配置」 | 目录放 `app/services/factors/experience/`，与 `mining/` **并列**，不放进 `mining/` | 红线 C5 要求物理隔离，目录并列可让静态扫描规则（禁 mining 出现 F1 model 引用）保持简单。 |
| D4 | **purge/embargo 语义** | 需求 §3.2 / 开发 §3.16：`purge_days=5`、`embargo_days=5` | **在 `all_dates` = 有效调仓点的前提下，必须换算为调仓点计数**：`purge_points = max(1, ceil(target_horizon_days / rebalance_interval_trading_days))` | `build_time_split` 把该参数当作传入序列的索引间隔（`val_start_idx = train_end_idx + purge_days`）。若传 5，月频即"隔离 5 期 = 5 个月"，与"避免持有期标签跨界（T+5）"的本意完全不符。 |
| D5 | **样本量口径** | 需求 §2.1 表格给出月频 val 12 / test 12；§4.1 给出"镜像 10 年月频 test 24" | **按归一化后实算重写口径表**（§7.2.3）：月频 5 年 val 11 / test 6；10 年月频 val 23 / test 18。需求 §4.1 的 `≥24` 门槛**无法达成**，见 §12.2 待决 Q3。 | 需求表格按 `n×ratio` 计算，未扣除 purge/embargo 消耗。以代码实测为准并回填。 |
| D6 | **错误契约** | 开发文档 §4 / v1.0 §3.5：`error_code/title_zh/detail_zh/related_id/impact/fix_action{...}/retryable` | 采用现行代码契约：`FactorSevenError.to_7field()` → `error_code / title_zh / detail_zh / correlation_id / impact / fix_link / retryable`，扩展字段入 `extras`（`fix_action` 结构化对象放 `extras.fix_action`） | `fix_action` 在代码中不存在；`app/schemas/errors.py` 是唯一既有错误协议实现，不应平行造第二套。 |
| D7 | 新增依赖时点 | 开发文档 §2.2 要求 `psutil`/`openpyxl`/`scipy` | `scipy`、`openpyxl` **M1a 立即写入** `requirements.txt`；`psutil` 在 M3 决定 G1 时再写入 | `scipy` 已装（1.18.0，sklearn 传递依赖）但未声明；`psutil` 未安装且仅 G1 需要。按里程碑引入避免污染依赖。 |
| D8 | 路由文件数量 | 开发文档 2 个路由文件（`factor_mining.py` / `factor_experience.py`） | **拆为 4 个**：`factor_mining.py`（批次/候选/评估/锁）、`factor_mining_wizard.py`（草稿/校验/模板/清理）、`mining_candidate_pool.py`（候选池）、`factor_experience.py`（F1） | 单文件预计 >1200 行，拆分利于并行开发与 codeowner 划分。 |

### 3.2 进程与并发模型

```text
uvicorn 单进程（现状）
├── FastAPI 事件循环（API 请求）
├── async_tasks worker 线程池（ThreadPoolExecutor，现状）
│    ├── task_type='factor_pipeline'          （既有，写 DuckDB）
│    ├── task_type='factor_mining'            ★新增，持 mining_domain + duckdb_write
│    ├── task_type='factor_mining_validation' ★新增，独立类型，**不持 mining_domain**
│    ├── task_type='data_mirror'              ★新增，持 duckdb_write
│    └── task_type='factor_grade_review'      ★新增，scheduled_tasks 触发
└── 主进程内存（G2 子表达式缓存，任务生命周期内有效，**不落盘**）
```

- **不做多进程并行**（G1 归 M3，由探针数据决定）；M1/M2 全串行；进程内 `ThreadPoolExecutor` 仅用于 AI 4 路并发。
- 写 DuckDB 双层防护：业务锁 `task_locks.duckdb_write`（跨任务）+ 进程文件锁 `warehouse_locks.acquire_warehouse_lock`（跨进程）。
- **`create_async_task` 只写 DB 记录，不启动线程** —— `task_runner.py` 在创建后必须显式调用 `async_tasks._start_worker(task_id, worker_func)`。（V8）

### 7.1 双任务锁

| 锁 | 范围 | 冲突行为 | 实现要点 |
|----|------|---------|---------|
| `mining_domain` | `task_type='factor_mining'`，判定 `(queued, running)` | **直接拒绝**（不排队），返回当前任务 ID/状态/代数 | `INSERT INTO task_locks` 靠 `lock_key` 唯一约束原子获取；冲突时读 `owner_task_id` 拼拒绝体 |
| `duckdb_write` | 所有写 DuckDB 的任务 | **排队**，返回位次 + 估算等待 | 冲突时追加到 `queue_json`；释放时 `trigger_queue=True` 主动拉起队首 |

- **心跳** 默认 1800s（可配），更新点 = 每代结束 + 最终验证每完成 10 个因子。超时由 `expire_stale_locks` 释放并通知。
- **队列消费者**：复用 `async_tasks` 状态机 + 锁释放时主动触发，**不引入新调度器**。
- **字段校验任务不占 `mining_domain`**，但同一 `draft_id + config_hash` 活动任务唯一。

### 7.2 三段切分接入与 purge/embargo 单位归一化（★v2.0 核心修正）

#### 7.2.1 问题陈述

`build_time_split` 的实现（`factor_evaluator.py:266-273`）把 `purge_days`/`embargo_days` 当作**传入 `all_dates` 序列的索引间隔**：

```python
train_end_idx  = max(0, min(n - 1, int(n * train_ratio)))
val_end_idx    = max(train_end_idx, min(n - 1, int(n * (train_ratio + validation_ratio))))
val_start_idx  = min(n - 1, train_end_idx + int(purge_days))      # ← 索引偏移
test_start_idx = min(n - 1, val_end_idx   + int(embargo_days))    # ← 索引偏移
```

而挖掘传入的 `all_dates` 是**有效调仓点**（非交易日）。因此：

- 日频：1 个调仓点 = 1 个交易日 → `5` 语义正确
- 周频：1 个调仓点 = 5 个交易日 → `5` 变成"隔离 5 周（25 个交易日）"
- 月频：1 个调仓点 = 约 21 个交易日 → `5` 变成"隔离 5 个月（105 个交易日）"

**后果**：月频/周频的 val 与 test 段被 purge/embargo 吃光，且与"避免持有期标签（T+5）跨界"的本意完全不符。

**第二个问题**：`min_validation_days` 默认 50 推出 `derived_min_total = max(20, ceil((50 + purge + embargo) / validation_ratio))`。

实测（本机复算 `factor_evaluator.py:259-263` 口径）：

| 频率 | n | purge/embargo | `derived_min_total` | `hard_fail` |
|------|---|---------------|--------------------|------------|
| daily 5y | 1,215 | 5 / 5 | **300** | False ✅ |
| weekly 5y | 243 | **1 / 1**（已归一化） | **260** | **True** ❌ |
| monthly 5y | 60 | **1 / 1**（已归一化） | **260** | **True** ❌ |
| monthly 10y | 120 | **1 / 1** | **260** | **True** ❌ |

> **关键结论**：**即使先做了 §7.2.2 的单位归一化，只要仍依赖默认 `min_validation_days=50`，周频与月频依然全部 `hard_fail`。**
> 两个问题必须**同时修**（C11 + C12），只修单位归一化不足以让周/月频跑通。周频 243 点需要 `derived_min_total ≤ 243`，即 `min_validation_days ≤ 0.2×243 − 2 = 46.6`，故 `SPLIT_MINIMUMS["weekly"]` 取 `min_val=20` 留足余量。

#### 7.2.2 归一化规则（C11/C12）

```python
# 调仓频率 → 每期含交易日数
REBALANCE_INTERVAL_DAYS = {"daily": 1, "weekly": 5, "monthly": 21}

def normalize_purge_points(*, target_horizon_days: int, frequency: str) -> int:
    """把「日」为单位的隔离期换算为「调仓点」计数，最少 1 期。"""
    interval = REBALANCE_INTERVAL_DAYS[frequency]
    return max(1, math.ceil(target_horizon_days / interval))

# 频率标定的样本量地板（与需求 §3.2 最小样本量硬门槛对齐）
SPLIT_MINIMUMS = {
    # frequency: (min_total_points, min_val_points, min_test_points)
    "daily":   (252, 100, 50),
    "weekly":  (104,  20, 10),
    "monthly": ( 36,   6,  3),
}
```

**换算结果表**

| 频率 | `purge_points` | `embargo_points` | 相对旧写的语义变化 |
|------|---------------|------------------|------------------|
| daily | 5 | 5 | 不变 |
| weekly | **1** | **1** | 从"5 周"修正为"1 周"（覆盖 T+5 持有期） |
| monthly | **1** | **1** | 从"5 个月"修正为"1 个月"（覆盖 T+5 持有期） |

> 换算依据：持有期为 T+1 买入 → T+5 卖出，即约 5 个交易日。要阻止标签跨段越界，只需在边界处丢弃 `ceil(5 / 每期交易日数)` 个调仓点。周频与月频各丢 1 期即足够。

#### 7.2.3 样本量口径重算（**取代需求 §2.1 / §4.1 的乐观值**）

以 `train_ratio=0.6, validation_ratio=0.2, purge_points/embargo_points` 如上、`tail_loss = target_horizon = 5` 实算：

| 频率 | 总点数 n | purge/embargo | train | val | test | 频率地板 | 结论 |
|------|---------|--------------|-------|-----|------|---------|------|
| daily（5 年） | 1,215 | 5 / 5 | 729 | 238 | 233 | 252 ✅ | 健康 |
| weekly（5 年） | 243 | 1 / 1 | 145 | 48 | 43 | 104 ✅ | 健康（**修正后**） |
| monthly（5 年） | 60 | 1 / 1 | 36 | **11** | **6** | 36 ✅（压线） | 统计降级（见 §7.9.4） |
| monthly（10 年镜像） | ~120 | 1 / 1 | 72 | **23** | **18** | — | 仍**达不到需求 §4.1 的「test ≥24」** |

> **对需求文档的勘误**：需求 §2.1 表格给出月频 `val 12 / test 12`，是按 `n × ratio` 直算、未扣 purge/embargo 的结果；实算为 **val 11 / test 6**。需求 §4.1 声称"镜像 10 年月频 test 约 24 点"，实算约 **18 点**，因此 `≥24` 的 S/A 通道**在现有切分参数下不可达**。→ 见 §12.2 待决 Q3。
>
> **月频降级仍然是合理的**：test 6~18 点均远不足以做 Bootstrap/置换（需求 §2.1 逻辑缺口 1 的结论不变），故"月频不做 Bootstrap/置换、最高评 B 级"的规则**继续成立**，只是门槛数值需要重定。

### 7.3 G2 子表达式缓存与抽样校验

```text
AST 遍历提取子表达式（含叶子字段引用）
  → key = sha256(算子类型 + 参数 + 字段唯一 ID + 数据快照版本 + schema_version + hash_algorithm_version)
  → 向量化批量计算（numpy/DuckDB，float32 存储，不逐股票循环）
  → 主进程内存缓存（**不写 DuckDB**，规避单写锁）
  → 组装时递归查缓存（单测断言 compute_node 调用次数为 0）
```

| 风险 | 措施 |
|------|------|
| 哈希碰撞/语义不等价 | SHA-256 强哈希（**禁用 Python 内置 `hash`，有随机化种子**）；每代抽 5 个因子对比，差异 >1e-6 **报警 + 废弃重算 + 落库** |
| 缓存污染 | 每个子表达式算完检查 NaN/Inf/空值比例，异常不写入并标 `failed`；记录带 `status`（valid/failed/computing） |
| 版本不兼容 | 缓存带 `schema_version` + `hash_algorithm_version`，不匹配自动废弃 |
| 范围混用 | 预筛阶段与全量验证阶段**分别建缓存** |

**抽样校验结果必须落库**：每代写 `cache_validation_passed`(0/1) 与 `cache_validation_max_diff`，为 0 时前端进化曲线标记该代并提示"缓存校验未通过，已重算"。

|------|------|---------|
| A1 赛道竞争 | 决定"在哪个因子类型池里选" | 6 类归类优先级 `quality > valuation > volatility > volume_price > reversal > trend`；配额「保底 60% + 动态 40%」；`weak_category_generations=3`；`cross_category_crossover_ratio=0.2` |
| B1 多目标 NSGA-II | 决定"用什么标准判优劣" | 目标池固定（ICIR↑/覆盖率↑/换手率↓/复杂度↓ + 可选 `oos_stability`、`monotonicity`）；启用 3~5；`dominates(a,b)`；rank + CD；边界 CD=∞；比较「rank 升 → 同 rank 比 CD 降」 |
| B2 锦标赛 | 决定"用什么动作选出父代" | `k=3`（2~7）；可重复抽中；精英不参与 |
| 偏好档位 | **只作用于结果排序与前沿高亮** | `balanced/stable/aggressive/simple`；**不进入进化计算** |

> 与已有因子相关性（<0.95）**不进帕累托**，作为硬门禁单独卡（避免目标过多导致分层失效）。

### 7.8 繁殖自适应（M2）—— 九机制单向信号流

```text
评估(每代指标)
  → D3 产 health（类型均衡度 + 基因型 + 表现型三层合成）+ D1 产 stall / convergence_delta（只观测）
  → 选择阶段：A1 定配额 → B1 定标准 → B2 选父代（独立运作，不依赖 C1）
  → C1 读【health + stall + 代数】→ 输出 strategy(g)（唯一调参者）
  → C2 变异 / C3 交叉 / D2 注入（严格按 strategy 执行）+ 校验补位
  → D1 判断：C1 已自救且连续 3 代无进步 → 早停
```

**安全护栏（写死，规则不得突破）**：变异率 `[0.40, 0.80]`、交叉率 `[0.10, 0.50]`、注入率 `[0.05, 0.20]`，三率和归一为 1；滞回 `hysteresis_generations=2`；单步 `max_step=0.10`；精英永不参与变异/交叉/注入。

**分期**：M1 用朴素选择（按 ICIR 排序）+ 固定三率；M2 换完整机制。

### 7.9 统计层 8 方法

| 方法 | 实现 | 依赖 | 输出 |
|------|------|------|------|
| t 检验 | `scipy.stats.ttest_1samp(ic_series, 0)` | scipy | `p_value` |
| Bonferroni | **自研** `p_adj = min(p × n, 1.0)` | numpy | `p_adj`、是否 <0.001 |
| FDR (BH) | **自研** `_bh_adjust()`：p 升序 → `p×n/rank` → 自后向前单调化 | numpy | `q_value`、是否 <0.1 |
| Bootstrap | numpy 有放回重采样 1000 次 → ICIR 2.5%/97.5% 分位 | numpy | `ci_lower`/`ci_upper` |
| 置换检验 | 随机打乱因子值 1000 次重算 ICIR → 经验分布 | numpy | `perm_p_value` |
| Deflated Sharpe | `total_trials` + IC 分布偏度/峰度校正 | scipy | `dsr_icir` |
| 衰减率 | `test_ICIR / train_ICIR` | — | `decay_ratio`（<0.5 疑似过拟合） |
| Walk-Forward | 3~4 滚动窗口，每窗口内再切 train/val/test；**只做方向一致性计数** | — | `{windows, same_direction, per_window_icir}` |

**存储约定**：写 `factor_evaluation_runs.metrics_json.stats`（**不新建表**，避免与评估链路分叉）。若后续字段膨胀影响查询性能再考虑拆表。

**实现路径唯一**：Bonferroni/FDR 不做双路径开关，避免两条实现结果不一致。

#### 7.9.4 月频降级（口径按 §7.2.3 修正）

月频 test 点数为 **6（5 年）/ 18（10 年镜像）**：

| 项 | 处理 |
|---|---|
| Bootstrap / 置换检验 | **不做**（样本不足），仅报告 t 检验参考值，`stats.degraded = true` |
| 质量分级 | **最高 B 级** |
| 切分 | 不切第 4 段 holdout |
| 前端 | Step2 蓝色引导 + 结果页黄色提示 + 证据抽屉中 Bootstrap/置换两行**灰掉并标注"样本不足，未计算"** |
| **门槛数值** | `≥24` 改为**按实测可达值重定**（建议 `≥12`），见 §12.2 Q3 |

### 7.10 质量分级（M2）

```python
def grade(metrics: dict, thresholds: dict | None = None) -> tuple[str, str]:
    """纯函数：8 维度指标 → (等级, 理由)。阈值可注入，默认读设置页配置。"""
```

- **8 维度**：统计显著性、经济显著性（ICIR/分层收益）、稳定性、覆盖率、换手率、复杂度、与已有因子相关性、OOS 表现。
- **五级阈值「每一级全部满足才定级」**：S / A / B / C / D（默认值见需求 §6.8，可在设置页调整）。
- **硬约束**：`decay_ratio < 0.5` → 不得 B 级以上；月频任务 → 最高 B 级。
- **季度重评**：复用 `scheduled_tasks`（新增 `factor_grade_review`），每季首日；B 级连续 2 季稳定 → 升 A；S/A 连续 2 季下滑（ICIR 降幅 >30% 或 OOS 反转）→ 降级 + 移出 FactorSet + 高优先级通知；`grade_manual_adjusted=1` 不被自动覆盖。
- **与 F1 联动**：D 级因子结构写入 F1 且 `is_negative_sample=1`，抽取时自动规避（F1 内部过滤，挖掘无感知）。

## 10. 非功能设计

### 10.1 性能与容量

| 项 | 设计 |
|----|------|
| 性能目标 | **以压测为准**。v2.0 之前的"6000 因子/5 分钟""12 代/1 小时""每代 2 分钟/端到端 55 分钟"**均无实测支撑，全部作废，不作为验收硬指标** |
| M0 | 先出**串行基线压测报告** |
| M1/M2 | 通过探针持续采集真实数据 |
| M3 | 据此决定 G1 并行哪一段（或明确不做） |
| 向量化 | 一律按日期/股票池分片向量化，**不以 Python 逐股票循环作为正式实现** |
| 大表读取 | 快照成员一次性载入内存分析表，避免逐行查主库 |
| 缓存 | G2 主进程内存，任务结束释放；预筛与全量验证分别建缓存 |
| 前端长任务 | 5s 轮询 + 页面离开不中断；单请求默认 `timeoutMs=20000`（`client.ts:196`），挖掘类接口需显式放宽 |

### 10.2 并发与一致性

| 关注点 | 设计 |
|--------|------|
| 双锁原子性 | 数据库事务 + `lock_key` 唯一约束；**前端禁用按钮不能代替服务端锁** |
| DuckDB 写 | 业务锁 `task_locks.duckdb_write` + 进程文件锁 `warehouse_locks` 双层 |
| 任务幂等 | 配置哈希 + 输入快照 + 任务 ID；复用 `idempotency_record` |
| 任务启动 | `create_async_task` 只写 DB，**必须显式 `_start_worker`**（V8） |
| 取消/失败 | 保留 checkpoint，直到用户放弃或保留期到期（7 天） |
| 引用保护 | 清理前经 `factor_registry.get_factor_references(db, factor_id, version_id)` 检查；被模型/评分/回测/审计引用的数据不可自动删除 |

### 10.3 可复现性

固定 `random_seed`（默认 42）+ `config_hash` + `template_id/template_version/rule_hash` + `data_cutoff_at` + `candidate_pool_snapshot_id` + 缓存 `schema_version`/`hash_algorithm_version`，保证同配置重跑结果一致（G1 若实施，容差 <1e-6，并提供串行严格复现模式）。

**另需固定**：`purge_points`/`embargo_points`/`SPLIT_MINIMUMS` 版本 —— 切分参数若变更，历史任务重跑会得到不同样本区间。建议写入 `split_config_json` 并带 `split_algorithm_version`。

### 10.4 可观测性

| 维度 | 落点 |
|------|------|
| 任务进度 | `async_tasks.stage` + `update_progress`（`MAX_PROGRESS_STEP=30` 防跳跃）；前端 5s 轮询 |
| 代数级 | `factor_mining_generations`（指标 + 三率 + 探针 + 缓存校验） |
| 阶段耗时 | 探针 6 项 |
| 缓存健康 | `probe_g2_hit_rate` + `cache_validation_passed` |
| 日志 | 按代分组、级别筛选、ERROR 可展开堆栈 |
| 通知 | `event_emitter.emit_task_complete`：完成/失败/锁异常释放/季度重评摘要 |

### 10.5 安全与审计

| 项 | 设计 |
|----|------|
| 公式执行 | 一律走 AST 白名单 + 复杂度上限；**`indicator_ast_sandbox.ALLOWED_FUNCS` 与 `factor_compiler.FUNCTION_CATALOG` 必须双向同步**（新增算子只加一处会导致沙箱拒绝） |
| SQL 注入 | 全部 ORM 参数绑定；候选池规则编译输出**结构化条件对象**，禁止字符串拼接 SQL |
| XSS | 公式/经济逻辑/模板名展示一律转义；前端不得 `dangerouslySetInnerHTML` |
| 密钥 | AI API Key 走既有 profile/密钥存储；**禁止硬编码** |
| 审计 | 候选池成员批量删除、FactorSet 成员移出（季度降级）、人工调整等级、清理临时数据、10 年区间的 S/A 二次确认，全部写审计 |
| 越权 | 人工调整等级限本人/admin；跨域只依赖 DTO |
| PIT | 财报/估值强制 `announcement_date <= trade_date`；稀疏字段**禁止填零或最新快照回填** |
| 文件上传 | Excel/CSV 导入限 `openpyxl` 解析、限大小、限扩展名；解析失败逐行报错不整体崩 |

### 10.6 回滚与降级

| 场景 | 动作 |
|------|------|
| 挖掘功能异常 | 关闭写开关 `FACTOR_MINING_WRITE_ENABLED`；保留历史审计与结果；评分运行退回 `manual`；**不删除数据** |
| AI 不可用 | 名额全部回退受约束随机，进化不中断 |
| G2 缓存校验失败 | 报警 + 废弃该代缓存重算 + 前端标红；不阻断任务 |
| 统计层异常 | `stats` 置空并标 `degraded`，结果页不展示校正 ICIR，不阻断 |
| DuckDB 写锁死锁 | 心跳超时（30 分钟）自动释放 + 通知 |
| 镜像失败 | 不阻断挖掘上线（需求 §2.4：ROE 补齐失败不阻断），但月频 S/A 通道被引导至镜像页 |
| **切分参数不达标** | 由 `MINING_SAMPLE_INSUFFICIENT` 阻断并给出频率化建议（扩大时间范围 / 降低调仓频率 / 先镜像） |

#### D-D 撤销说明（T06 执行时实测推翻原前提）

**原裁决的前提是错的。** D-D 写的是「`app/services/factors/` 内**无任何派生实现**」——该结论来自一次
**被截断的搜索结果**（`Grep` 当时带了 `head_limit`，`factor_executor.py` 的命中行落在截断之外），
属于「从截断结果推断不存在」的方法错误，不是代码事实。

**物证一：派生实现就在执行器的 SELECT 投影里**

```python
# app/services/factors/factor_executor.py:674-685
@staticmethod
def _select_field_expressions(table_name: str, table_fields: list[str]) -> list[str]:
    """Return safe SQL projections, including virtual warehouse fields."""
    for field_name in table_fields:
        if table_name == "raw_daily_bars" and field_name == "prev_close":
            expressions.append(
                "LAG(close) OVER (PARTITION BY symbol ORDER BY trade_date) AS prev_close"
            )
```

两个取数点都走这条投影（`factor_executor.py:891`、`:1352`）。

**物证二：真实数仓端到端实测（2026-09-16）**

| symbol | trade_date | close | prev_close |
|---|---|---|---|
| 000001 | 2026-07-21 | 10.84 | **10.98** |
| 000001 | 2026-07-22 | 10.98 | **10.84** |
| 000001 | 2026-07-23 | 11.08 | **10.98** |
| 000001 | 2026-07-24 | 11.10 | **11.08** |
| 600519 | 2026-07-24 | 1297.41 | **1292.01** |

与上一交易日收盘价逐条相等，且与 `close.groupby(symbol).shift(1)` 完全一致。

**物证三：既有绿灯测试**

`tests/test_whitebox_factor_executor.py::TestFactorExecutorPreview::test_preview_derives_prev_close_without_physical_column`
（seed 2026-07-23 close=10 / 2026-07-24 close=11，断言 2026-07-24 的 `prev_close == 10.0`）**当前通过**。
另有 `tests/factors/test_preflight_api.py` 断言 `prev_close` 不在 `missing_fields`、
且 `derived_fields["prev_close"] == ["close"]`，亦为绿灯。

**若执行原 D-D 会造成什么**

① 打破 2 个既有绿灯测试；② 移除一项**正在正常工作**的能力；
③ 打破 DSL 用例书 DSL-001（`close / prev_close - 1`）；④ 破坏前端 `AiChatDrawer` 的字段词表。

**保留该结论的方法论教训**（已写入排期手册 R17 与项目 `MEMORY.md`）：
**永远不要用「被截断的搜索结果」证明某个东西不存在。** 判断「不存在」必须用无上限的搜索，
或直接用代码/数据做正向验证。
