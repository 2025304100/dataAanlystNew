## 二、缺陷清单（按严重度）

### P1（功能正确性/数据完整性）

**DEF-1 切分预算不校验三段比例之和**（设计 §4：train+val+test=100%）
- `POST /factor-mining/split-budget` 传 `train_ratio=0.6, validation_ratio=0.6`（和>100%）→ 200，`test_points=0`，无任何告警字段。
- 根因：`SplitBudgetRequest` 仅有单字段 `gt=0, lt=1`，无 validator 联合校验。用户把 test 段"算没了"仍显示 available=true。

**DEF-2 提交挖掘不校验候选池快照存在性**（设计 §7 最终校验清单）
- 伪造 `candidate_pool_snapshot_id="snap-not-exist-000"` → **201 创建 run 并真实开跑**，持续心跳占用 `mining_domain`+`duckdb_write` 双锁 7 分钟，期间所有正常提交 409，需手工取消。
- 违反"最终校验检查快照存在性/锁定态"红线；恶意/失误输入即可锁死功能入口。

**DEF-3 中断(pause)后无法继续：锁释放缺失**（设计 §8.3.5 中断-断点恢复）
- 专项复现（`_bb23_j2_repro.py`）：running 中 pause → 240 秒内 18 次 resume 全部 409，`miningDomain.busy` 始终 true 且心跳常新；对照 cancel 约 45s 释放。
- 根因（代码印证）：`task_runner.py` 中 `should_stop()` 只在 stage_runner **调用前后**检查，GA 进化循环内部无逐代取消检查点 → pause 停不住 worker；而 `stall_watchdog.release_orphan_locks` 只回收**终态**批次的锁，paused 非终态不在其职责内。心跳泵持续刷新使 `expire_stale_locks`（30min）也永不触发。
- 用户视角：点"中断"再点"继续"＝功能报废，只能放弃本批次从头再挖，checkpoint 机制形同虚设。
- **UI 层补测（09-24 第二轮，`_bb24_ui_ops_step5.py`）**：从 Step5 看板真实点击「继续」，后端 409 被前端吞掉——**无任何 toast/内联提示**，页面零反馈停在 paused（静默失败，比 API 层更严重）；且步骤条仍显示「进化执行与结果 进行中」，不反映 paused 态。对照：「提前停止」交互良好（二次确认弹窗→converged→锁正常释放）。

### P2（可用性/性能/数据卫生）

**DEF-4 Step1 预览与预设接口冷启动 15~90s，且期间 UI 反馈误导**（设计 §3.2"底部实时更新命中数量"）
- 实测：`filter-presets` 冷启动约 36~60s；`preview` 单次 15~24s（重复同参数不缓存，一次观察到 90s 并伴随连接重置 10054）。
- 前端在 presets 返回前显示**「暂无可用预设」空态**（实际接口仍在计算）；preview 返回前统计区完全空白，无 loading/无骨架/无"计算中约需 N 秒"提示。两组 e2e 脚本的固定等待（1.2s/20s）全部因此失败——用户同样会认为"功能坏了"。
- 关联面：后端 `compute_split_budget_preview` 在 DuckDB 被占用时抛 IOException→500（DEF-8），未按 §4/§5"数仓不可用→available=False 降级"精神兜底。

**DEF-5 候选池/草稿无法删除，同名垃圾池累积**
- 前端"生成挖掘物料"固定 `name:"因子挖掘候选池"`，不查重、不复用 → 库内已累积 **50+ 个同名池**（含历次自动化测试与 UI 反复点击）。
- 后端无 `DELETE /candidate-pools/{id}`、无 `DELETE /drafts/{id}`（405），PUT 归档也未验证通路。设计文档承诺的池生命周期管理缺失，长期使用必然污染池列表。

**DEF-6 错误信封中文一致性破口**
- `GET /factor-mining/candidates/{id}/grade/evidence` 不存在候选 → 404 `user_message="Not found"`（英文泛化、extras=null），与全域 FactorSevenError 中文信封不一致。`GET /runs/{id}/task` 同样命中英文 404（09-24 补测再确认）。
- 候选池 4xx 的可读原因（如"命中 0 只，请放宽区间"）埋在 `technical_details.error_message` 字符串化 JSON 里，顶层 `user_message` 只有泛化"输入参数有误"——前端若只读顶层将丢失关键指引。

**DEF-9（P1，09-24 补测发现）run 成功后结果页永不可达，最终验证链路断点**
- 提交 `finalize_top_k=3` 的 20×2 代 run（`a9a1cd1a`），后端自然收敛至 `succeeded`；但：
  - 候选 `factor_version_id` 全部为 null → **test 段最终验证（finalize_run）未执行/未回填**（代码上 `final_top_k>0` 应执行，`current_generation=1` 即停，疑似提前收敛分支绕过或静默失败）；
  - UI 直达该 succeeded run（`?run=`）：步骤条仍显示「进行中」、仍提供「中断/提前停止」按钮（已终止态不应可操作）；页面停在进化跟踪视图，**研究声明/等级列/证据抽屉的结果页（FactorMiningResult）从未出现**，仅有「候选因子（结果预览）」+「跳转因子模型页」；
  - 因无带等级的候选，证据抽屉/人工调级/季度重评 UI 链路全部无法验证（E2~E7 阻塞）。设计 §8.4「结果页=挖掘价值兑现的最后一公里」在真实环境不可达。
- 建议开发白盒排查：`_run_real_stages` 提前收敛（stopped_reason=converged）路径是否跳过 finalize；finalize_run 异常是否被吞。

## 四、优化改造建议

### 功能层面
1. **补齐提交前校验闭环**（修 DEF-1/2）：`SplitBudgetRequest` 加 model_validator（train+val≤100−最小 test 预算）；`create run` 前校验快照存在、已锁定、属于当前候选池，并返回 `split_budget` 预览（当前 201 响应 split_budget=null）。
2. **进化循环逐代取消检查点**（修 DEF-3）：GA 每代结束调用 `ctx.should_stop()`；pause 语义定义为"跑完当前代→停 worker→释放锁→保留 checkpoint"；resume 在锁未释放窗口内提供 202 排队语义或明确"等待释放（约 N 秒）"提示。
3. **预览/预设服务端缓存**（修 DEF-4）：全市场分位阈值按 `as_of_date` 日级物化（DuckDB 结果表或进程 TTL 缓存），preview 按 `rule_hash` 缓存命中统计；冷启动目标 <2s，编辑期 p95 <500ms 才能兑现"实时"。
4. **池生命周期**（修 DEF-5）：提供池归档/删除端点（成员解除关联、快照级联失效校验）；前端生成物料时若存在同名同 rule_hash 的池则复用并提示，杜绝垃圾池。
5. 数仓降级统一（修 DEF-8）：DuckDB IOException → `available=False + reason_zh="数据仓库忙，稍后重试"`，禁止 500。
6. F1 经验库当前近乎空态：run 成功收官时自动沉淀条目（公式/参数/评级/理由），否则"经验库"名不副实。
7. filter_config 阈值单位（元 vs 亿）在 API 契约与 UI 输入间不透明，建议字段目录内返回 `unit_zh/scale`，服务端做合理性告警（避免用户输入 80 想表达 80 亿实际按元比较）。

### 前端交互层面
1. **慢接口三态反馈**（修 DEF-4 观感）：presets/preview 加载中显示骨架 + "正在按全市场计算分位（约 X 秒）"；失败显示"加载失败·重试"而非"暂无可用预设"；preview 未返回时保留上一次结果并置灰"待更新"。
2. 预设点击后明确生效反馈：现有 B2 已应用/自定义 Tag 机制好，但「全市场」类空条件预设点击后无任何状态变化，建议也触发 preview 并点亮 applied。
3. Step5 控制按钮与锁联动：resume 遇 409 时禁用按钮 + 倒计时"等待上一次任务释放锁"，而不是反复弹"已有挖掘任务进行中"。
4. 向导 Step 间跳转（step-jump）在已锁定/已提交态给防误提示；批次列表增加状态筛选与"我的最新批次"快捷回到（LAST_RUN_KEY 已有，入口可见性不足）。
5. 错误弹窗统一消费信封的 `fix_link`（后端已回 `/settings/factor-mining?step=1`）做成"跳转到问题步骤"按钮，形成"报错→定位→修复"闭环。
6. 候选池成员表格支持按"为什么被排除"逐行 tooltip（by_rule 数据已有，UI 仅汇总展示）。

### 前端样式效果层面
1. Step1 底部统计条：命中率做成进度条 + 阈值刻度（<50 红 / 接近下限橙 / 达标绿），当前纯文本数字扫读效率低。
2. 锁定横幅、阻断区、404 页统一一套"原因 + 影响 + 下一步"三段式卡片样式（信封字段齐全，只差样式规范）；文案全部走 i18n，清除英文残留（DEF-6 场景前端兜底 `user_message` 为英文时映射中文）。
3. 看板弹窗（PoolAnalysisModal）图表配色与主站暗色主题对齐，空数据图表给占位插画而非空白轴。
4. 预设左栏 Tabs `tabPosition="left"` 在窄容器下按钮组换行错乱，建议断点降为顶部 Tabs；`mining-filter-sep` 区间输入在 1366px 下有挤压，InputNumber 宽度改 flex 自适应。
5. 清理 Console（DEF-7）：列表补 key、message 换 `App.useApp()`——顺带避免生产噪音影响排障。

**DEF-12（P1）停滞看门狗误杀正常大 run，且僵尸 worker 继续吃内存**
- 复现：提交默认量级 100×20 run（`c61cb96a`）→ 5~6 分钟后 `status=failed, error_code=STALLED`，候选 0 条。
- 根因：`stall_watchdog.STALL_THRESHOLD_SECONDS=600` 以 `run.updated_at` 为唯一推进信号，但**代内评估全程不刷新 updated_at**（只在每代末提交）；100 个体首代实测需 >10 分钟 → 正常任务必被误杀。**前端默认参数就是 100×20，即默认配置几乎必死**（小池/小种群测试不易触发，故历史未暴露）。
- 叠加伤害：watchdog 只改库+放锁，**不停 worker**——run 已 failed 后评估线程仍在跑，后端 WS 从 2.3GB→3.3GB→4.3GB 持续攀升（最终可能 OOM）；同代还存在 MySQL OperationalError 重试（gen=0 持久化拖慢，加剧无推进窗口）。
- 修复建议：① 代内评估每 N 个体 touch 一次 run.updated_at（或看门狗改判 `lock.heartbeat_at`新鲜度+worker 存活双信号）；② 阈值随种群规模缩放（如 max(600, pop×8s)）；③ reap 时同步 `cancel_async_task` 停 worker。
