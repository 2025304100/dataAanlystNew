## 2. 变更与接口行为

| 文件 | 变更及目的 |
|---|---|
| [outbox.py](D:/ai_project/dataAanlystNew/app/services/notifications/outbox.py) | `mark_sending`仅将指定ID、status=pending、重试时间已到的记录原子更新为sending；仅受影响行数为1的调用方获得发送资格。提交后强制读取最新ORM对象，避免旧缓存/RR快照影响 |

| [webhook.py](D:/ai_project/dataAanlystNew/app/services/notifications/webhook.py) | 经Dispatcher投递时自动发送`Idempotency-Key`请求头；仍保持原JSON结构和配置契约，接收端需按该键去重 |
| [隔离运行器](D:/ai_project/dataAanlystNew/scripts/verify_market_news_acceptance.py) | 新增`--stage delivery`，只创建全新专用schema并执行MySQL发送专项；`--stage all`现在同时包含迁移、发送专项和页面E2E |

没有新增数据列或迁移revision，唯一head仍为`wps_0024_091_market_compat`。使用MySQL 5.7可执行的UPDATE，不使用SKIP LOCKED、窗口函数或MySQL 8特性。

幂等键规则：

- 同一Outbox经适配器内部重试、发送器重启或手工重试，键不变。
- 不同Outbox或渠道使用不同键，即使正文相同也不会误合并。
- 原payload自带同名保留字段不能覆盖发送器生成的键；哈希不暴露原始事件键或库名。
- 默认Webhook正文不增加字段；自定义JSON模板需要时可引用`{_notification_idempotency_key}`。直接调用适配器而未提供Outbox上下文的测试发送，不宣称自动具有业务幂等身份。

## 3. 先失败、再修复的过程

采用tdd流程，在已讨论的发送器轮询和HTTP收件边界验证，未mock业务发送逻辑。

| 阶段 | 实际结果 |
|---|---|
| 并发复现（red） | 两个独立Python进程连接同一SQLite测试库；让两个真实SELECT都观察到pending后放行；本机收件端实际收到2次请求，预期1次，测试失败 |
| 原子领取修复（green） | 相同复现条件仅收到1次请求；两个`run_once`返回值排序为[0,1]，测试通过 |
| 响应丢失复现（red） | 本机收件端先接受请求再断开连接；任务失败后在新进程手工重试；两次请求都未携带键，测试失败 |
| 稳定键修复（green） | 两次请求携带同一非空键；本机收件端保留键并仅产生1次处理，测试通过 |
| 扩展与关联回归 | SQLite专项9项通过；277项关联测试通过；真实MySQL2项通过 |

MySQL h26首轮为1过1失败：并发测试通过，重试协调端错误地沿用工作进程运行前的REPEATABLE-READ快照。将测试协调端结束旧事务，以模拟真实手工重试HTTP请求的新事务边界后，在全新i27专用schema复验2项通过；没有为通过测试而修改业务事务隔离级别。

## 5. 部署、回退及剩余风险

1. **全部发送实例必须升级**：新旧发送器混跑时，旧版仍可能无条件标记sending并发送。不能仅升级一个节点就承诺并发防重生效。回退代码也会恢复这项风险；本轮未重启或升级用户现有服务。
2. **接收端必须支持幂等**：需要持久化Idempotency-Key，将去重判断与业务处理保持一致，并对重复请求返回已有结果。键的保留期必须覆盖实际自动/手工重试跨度。忽略或提前过期该键的接收端仍可能重复处理；本机支持不等于第三方已经支持。
3. **sending中崩溃**：当前不自动抢回sending，防止旧工作进程仍在发送时被另一个进程再次投递。异常退出留下的sending需核实处理，当前手工retry接口只接受failed/dead_letter。若后续需要自动恢复，应另行设计租约、所有权与续租，不能简单定时改回pending。
4. **幂等身份要稳定**：同一Outbox表示同一业务消息；要发送修改后的新业务内容，应创建新任务。更换数据库命名空间、重建/修改任务身份或超出接收端去重保留期，不承诺仍沿用旧去重身份。
5. **规则性再提醒保留**：不同渠道各发一次、不同日期键再次告警是当前业务规则。按日键仍使用UTC日期，即北京时间08:00切换；本轮未改变日期边界，也未加入新闻语义去重。
6. **外部边界延续**：百度两源Cookie失败、历史时间质量、正式部署后冒烟和容量验证仍按0091报告列为未完成；第三方送达由用户明确选择另行安排。

本轮不新增schema变更。专用测试库及失败尝试h26保留供复核；工作进程和本机收件端均已结束，未建立常驻服务或调度。代码、测试、证据与文档尚未提交Git。
