## 1. 技术边界

```text
React Settings/FactorCenter
        ↓ 业务 Facade / DTO
FastAPI 因子路由、评估路由、scoring facade
        ↓
Factor services（registry/compiler/evaluation/lifecycle/pipeline/mining）
        ↓
SQLite/MySQL 元数据 + DuckDB 因子值仓库
```

禁止前端解析 `hyperparameters_json`、权重内部格式或调用内部路由；禁止回测、组合、交易直接访问因子域 ORM/Session/DuckDB。跨域只依赖公开 DTO/Facade。

**新增边界**：挖掘模块**不执行**模型训练/激活，结果页跳转因子模型页并携带 `factor_set_id`/`data_cutoff_at`/`candidate_pool_snapshot_id`/`rebalance_frequency`。

## 2. 复用与新增文件边界

### 2.0 已确认运行约束

- 候选池有效标的硬下限为 **50**，由后端校验，前端不能降低。
- **双任务锁**（替代原全局单任务锁）：
  - `mining_domain`：`task_type='factor_mining'` **域内唯一**，判定 `(queued, running)`，已有则**直接拒绝**（不排队）
  - `duckdb_write`：所有写 DuckDB 的任务**互斥**，被占则**排队**；完成/失败/取消释放并自动拉起队首
  - 心跳默认 **30 分钟**可配置；更新点：每代结束 + 最终验证每完成 10 个因子
- 字段完整性校验是独立异步任务，**不占用 mining_domain 锁**；同一草稿、同一配置哈希只能存在一个活动校验任务，可按分片续跑。
- 完成任务的未引用中间数据默认保留 **7 天**，提供经引用保护检查的手动清理接口。

> **为何不引 `statsmodels`**：Bonferroni 极简（`p_adj = min(p × n, 1.0)`），Benjamini-Hochberg FDR 自实现约 15 行（p 升序 → `p×n/rank` → 自后向前单调化）。两者均纯 numpy 可完成且可单测，引入 statsmodels 会连带 patsy 等依赖，为一个多重校正函数不划算。**实现路径保持唯一**（不做双路径开关，避免两条实现结果不一致）。

## 3. 数据模型

### 3.0 数据能力门禁

创建挖掘/评估任务前，服务必须读取 `formula-catalog`、readiness 和数据源路线状态，按字段能力拒绝不成立的组合：

| 字段 | 状态 | 处理 |
|------|------|------|
| 连续日线行情、换手率 | 覆盖 99.7% | ✅ 首期主力 |
| `pe_ttm`/`pb` | 已注册 | ✅ |
| `dividend_yield`/`total_market_cap`/`circulating_market_cap` | 数据已存在未注册 | **M1 注册（零采集）** |
| `roe_ttm` | 覆盖 2,209 标的 | ⚠️ 标注覆盖偏低 |
| 财报净利润/营收/同比 | 需公告日映射 | 映射后开放 |
| 龙虎榜/热度/ETF 快照 | event/snapshot | 仅事件模式评估 |
| `proxy_score` | blocked | ❌ 禁用 |
| `gross_margin`/`asset_turnover` | 数据不存在 | M2 采集 |
| `prev_close` | **虚注册**（表无此列） | **撤销注册** |

禁止把稀疏字段填零或以最新快照回填历史。财报回填复用现有 `financial` 外部数据任务，先写业务表再 mirror 到 `raw_financial_reports`；回填后执行 PIT 泄漏、报告期连续性、公告日有效性、覆盖率检查，未通过不提高 readiness。

### 3.0.1 候选池隔离模型

候选池不写回 `symbols`、行情或财报主表：

- `training_candidate_pools`：候选池定义、`source_type`（`import`/`filter`）、规则 JSON/导入批次、状态、版本、审计
- `training_candidate_pool_members`：`pool_id`、`symbol_id`、纳入校验摘要、`included_at`、软删除；`(pool_id, symbol_id)` 唯一约束
- `training_candidate_pool_snapshots`：冻结成员、规则哈希、数据截止日、统计摘要；**新增** `analysis_json`（市值分布/行业分布/风格暴露/市场环境/数据质量/因子类型建议）、`analysis_status`（`not_analyzed`/`analyzing`/`analyzed`/`reset`）、`analyzed_at`、`is_locked`（锁定筛选/导入）

导入服务只接收模板字段，通过 `symbol` 匹配主数据；名称/市场不回写主表。`source_type` 创建后不可切换。成员批量删除只做关联软删除并写审计。

首期固定 A 股（`sh/sz/bj/cn`），不接收 `region`；非 A 股返回结构化拒绝。区间预设由服务端 `GET /candidate-pool-filter-presets?as_of_date=&markets=` 基于 A 股样本返回实际边界/样本量/分位数/数据版本，创建快照时展开固化到 `filter_config_json`。

**行业**：首期仅读 `symbols.industry` 当前标签，快照记录 `industry_value`/`industry_source`/`industry_observed_at`，**严禁用于历史 PIT 或中性化**。历史行业能力需新增 `security_industry_classifications`（含 `effective_from`/`effective_to`/`announced_at`）→ **二期**。

训练表必须保存 `candidate_pool_snapshot_id`（不能只存 `pool_id`）；同一候选池多次挖掘各生成独立快照。

### 3.1 `factor_mining_runs`

字段：`id`、`status`、`draft_id`、`template_id`、`template_version`、`rule_hash`、`candidate_pool_snapshot_id`、`data_cutoff_at`、`start_date`、`end_date`、`rebalance_frequency`、`risk_monitor_frequency`、`risk_exit_config_json`、`target_horizon`、`split_method`、`split_config_json`、`purge_points`、`embargo_points`、`filter_config_json`、`evolution_params_json`、`random_seed`、`current_generation`、`max_generation`、`converged`、**`total_trials`**、`created_by`、`created_at`、`updated_at`、`error_code`。

**`total_trials`（v3.3 新增）**：一次挖掘任务中**累计评估过的候选因子总数**（初始种群 + 各代新生成个体，约 2,000），由挖掘主循环累加。**Deflated Sharpe 校正的输入**（见 §3.17.1），也是"多重检验次数"的唯一事实来源。统计层未启用时（M1）仍持续累加，不增加额外开销。

**`evolution_params_json` 包含**：种群大小、最大代数、选择比例、精英保留数、变异率、交叉率、随机注入率、收敛阈值、每代评估样本长度、最终验证 Top 数、复杂度上限；初始种群两层结构（经典底座：`classic_enabled`/`classic_cap`/`classic_categories`/`classic_coverage_strategy`；探索层：`ai_random_ratio`、`redundancy_factor`）。

**选择机制配置**（M2，`track_competition`/`multi_objective`/`tournament`）：赛道竞争 `base_guarantee_ratio=0.6`、`weak_category_generations=3`、`cross_category_crossover_ratio=0.2`；多目标 `preference`（balanced 默认，只影响展示）、`objectives` 数组（启用数 3~5，方向只读）；锦标赛 `k=3`（2~7）。

**繁殖自适应配置**（M2，`adaptive_reproduction`）：`adaptive_enabled=true`、`sensitivity`（conservative/balanced/aggressive）；基线三率 0.6/0.3/0.1；安全区间 mutation[0.40,0.80]、crossover[0.10,0.50]、random[0.05,0.20]，三率和归一为 1；`hysteresis_generations=2`、`max_step=0.10`；`mutation_ops_enabled{param/op/field/struct}`。

**AI 生成配置**（`ai_generation_config`）：约束盒子（最大公式长度 3~8、嵌套深度 1~3、字段引用数 1~4、窗口期范围、算子子集、字段子集、创新程度、类型严格度、禁止结构）；预设 conservative/balanced/aggressive。

**状态**：`queued/running/paused/cancel_requested/validating/succeeded/failed/cancelled/converged`。`paused` 保留 checkpoint 与已进化结果、释放资源，可 resume。

### 3.7 初始种群三来源实现逻辑

**两层结构**

1. **经典底座**：按启用类别过滤模板 → 参数网格展开 → AST/字段/复杂度校验 → 来源内去重 → 按覆盖策略（均衡：每类 `floor(cap/类数)`，余数按优先级补；优先级：统一排序取 Top）分配名额 → 锁定，`operation=enumerated`，`generation=0`
2. **探索层**：剩余名额 = 种群大小 − 经典实际入库数

**AI 生成（M1）**

- **批量调用**：10 次调用 × 每次 8~12 个骨架 ≈ 80~120 个；去重后保留约 57 个
- **并发**：4 路 `ThreadPoolExecutor` + `asyncio.to_thread`（`llm_client` 为同步 def）
- **超时**：单次 30 秒；**AI 环节总超时 5 分钟**

**受约束随机生成**：字段分类 + 算子类型签名 + 类型匹配 + 复杂度上限（算子 ≤4、嵌套 ≤2、字段引用 ≤3）；实时哈希拦截、同 AST 结构最多 3 个变体、分层采样保结构分散。

### 3.13 性能优化

#### G2 子表达式缓存（M1 必做）

流程：AST 遍历提取子表达式 → **SHA-256 强哈希去重**（算子+参数+字段 ID+数据快照版本；**禁用 Python 内置 hash，其有随机化种子**）→ 向量化批量计算 → **主进程内存缓存**（**不写 DuckDB，规避单写锁**）→ 组装时递归查缓存（断言 `compute_node` 调用次数为 0）。

- 正确性兜底：每代随机抽 5 个因子，缓存结果与直接全量计算对比，差异 >1e-6 报警并废弃缓存重算
- NaN/Inf 检查：异常不写入缓存，标记 `failed`；缓存记录带 `status`（valid/failed/computing）
- 缓存带 `schema_version` + `hash_algorithm_version`，不匹配自动废弃
- 预筛阶段与全量验证阶段分别建缓存，不混用
- 每代统计 `probe_subexpr_total`/`probe_subexpr_unique`/`probe_g2_hit_rate` 落库
- **抽样校验结果必须落库（v3.3 补充）**：每代抽样 5 个因子的对比结果写入 `generations.cache_validation_passed`（0/1）与 `cache_validation_max_diff`（最大差异值）。**校验不通过时该代结果不可信**，前端进化曲线需标记该代、并提示"缓存校验未通过，已重算"。缺少这两个字段则无法回溯"哪一代的缓存出过问题"。

#### 性能探针（M1 必埋）

见 §3.2.2 探针字段。M3 依据 M1/M2 探针数据定位瓶颈后再决定 G1 并行哪一段。

#### G1 多进程并行（M3，压测后决定）

候选方案：子表达式级并行 + 因子级并行；进程数 `min(6, cpu-2)` 并按内存自适应（<2GB 串行 / <4GB 2 / <8GB 4）；进程池复用；主进程汇总写入（子进程不写共享存储）；贪心负载均衡。

**已识别风险**：项目无 ProcessPool 先例（全 `ThreadPoolExecutor`，且用于 akshare I/O 超时兜底）；Windows 无 `fork`，spawn 每子进程重 import pandas/numpy/akshare；`multiprocessing.shared_memory` 在 Windows 有 resource_tracker 泄漏坑。

### 3.14 DSL 扩展实现（M1 必做）

**背景**：现有 `rank`/`zscore` 仅为后处理配置项（`apply_postprocess(values: pd.Series, ...)` 作用于最终因子值），无法表达 `cs_rank(A) - cs_rank(B)`；白名单无 delta/atr。

**实现步骤**

1. `FUNCTION_CATALOG` 新增算子注册（`factor_compiler.py`）
2. `indicator_ast_sandbox.ALLOWED_FUNCS` 同步放开（现仅 9 个：abs/min/max/round/sum/len/log/sqrt/exp）
3. `factor_executor` 增加按 `trade_date` 分组的截面求值分支
4. AST 节点**标注计算方向**（`timeseries` / `cross_section`），嵌套时**从内到外逐层计算**
5. 字段目录注册 `dividend_yield`/`total_market_cap`/`circulating_market_cap`
6. 方言归一：`std`→`stddev`、`llv/hhv`→`lowest/highest`、`turnover`→`turnover_rate`
7. **撤销 `prev_close` 虚注册**（`raw_daily_bars` 无此列）

**新增算子**

| 算子 | 类别 | 语义 |
|------|------|------|
| `cs_rank` / `cs_zscore` / `cs_demean` / `cs_scale` / `cs_quantile` / `cs_winsorize` | 截面 | 见需求 §6.0 |
| `ts_delta_bars(x, n)` | 时序 | **行情**字段 N 个交易日差分 |
| `ts_delta_periods(x, n)` | 时序 | **财报**字段 N 个报告期差分 |
| `ts_atr(x, n)` | 时序 | 平均真实波幅，**内部用 `ref(close, 1)` 取 prev_close**（无需补数据） |

> `ts_delta` 拆为两个算子的原因：行情与财报采样频率不同（交易日 vs 报告期），共用会让 AST 隐式解释 n，极易算错质量类模板。

**验收**：`cs_rank(A) - cs_rank(B)` 可正确表达且与后处理 rank 语义可区分；25 个模板可编译 ≥90%。

### 3.17 统计层实现（M2）

服务：`app/services/factors/mining/statistical_tests.py`

#### 3.17.1 八个方法

| 方法 | 实现 | 依赖 | 输入 | 输出 |
|------|------|------|------|------|
| **t 检验** | `scipy.stats.ttest_1samp(ic_series, 0)` | scipy | IC 时间序列 | `p_value` |
| **Bonferroni** | **自研**：`p_adj = min(p × n, 1.0)` | numpy | Top50 的 p 值数组 | `p_adj`、是否 < 0.001 |
| **FDR (BH)** | **自研** `_bh_adjust()`：p 升序 → `p×n/rank` → 自后向前单调化 | numpy | Top50 的 p 值数组 | `q_value`、是否 < 0.1 |
| **Bootstrap** | numpy 有放回重采样 1,000 次，取 ICIR 的 2.5%/97.5% 分位 | numpy | IC + IC 标准差序列 | `ci_lower` / `ci_upper` |
| **置换检验** | 随机打乱因子值 1,000 次重算 ICIR，取经验分布 | numpy | 因子面板 + 收益面板 | `perm_p_value` |
| **Deflated Sharpe** | 记录 `total_trials`，按 DSR 公式校正（含试验次数、偏度、峰度） | scipy（偏度峰度） | ICIR、`total_trials`、IC 分布 | `dsr_icir` |
| **衰减率** | `test_ICIR / train_ICIR` | — | train/test 两段 ICIR | `decay_ratio`；<0.5 标记疑似过拟合 |
| **Walk-Forward** | 见 3.17.3 | — | 全区间 | 窗口数、各窗口 ICIR、同向窗口数 |

`total_trials` 定义：**一次挖掘任务中累计评估过的候选因子总数**（初始种群 + 各代新生成个体，约 2,000），由挖掘主循环累计并写入 `factor_mining_runs.total_trials`。

```json
    "perm_p_value": 0.002,
    "total_trials": 1987, "dsr_icir": 0.31,
    "decay_ratio": 0.67,
    "walk_forward": {"windows": 4, "same_direction": 4, "per_window_icir": [0.41,0.38,0.52,0.29]}

```

> 若后续统计字段膨胀到影响 `metrics_json` 查询性能，再考虑拆 `factor_stat_tests` 表；**M2 先用 JSON 约定**，避免过度设计。

#### 3.17.3 Walk-Forward 实现

- **窗口划分**：全区间按时间顺序切 3~4 个滚动窗口，每个窗口内部再切 train/val/test
- **滚动方式**：窗口起点按 `总长度 / 窗口数` 步长前移，**相邻窗口 train 段重叠约 1.5 年**
- **方向一致性判定**：统计各窗口 test 段 ICIR 符号，**≥3/4 窗口同向**判定为方向一致
- **聚合口径**：**只做方向一致性计数，不做跨窗口均值/合并检验** —— 重叠窗口非独立样本，合并会高估显著性
- 结果页展示：`windows / same_direction / per_window_icir`，并标注"窗口滚动重叠，仅作方向一致性观察，不作独立统计检验"
- 镜像 10 年时可加第 4 段 holdout（月频则不做，见 §3.16）

#### 3.17.4 月频降级

月频 test 仅 12 点（自由度 11）：**跳过 Bootstrap 与置换**，仅计算 t 检验参考值并标记 `stats.degraded = true`；质量分级最高 B 级。

### 3.18 质量分级实现（M2）

服务：`app/services/factors/mining/factor_grading.py`

#### 3.18.1 数据模型变更

`factor_versions` 新增字段：

| 字段 | 类型 | 说明 |
|------|------|------|
| `quality_grade` | str(2) | S / A / B / C / D |
| `grade_updated_at` | DateTime | 最近评定时间 |
| `grade_metrics_json` | Text(JSON) | 评定时 8 维度指标快照 |
| `grade_manual_adjusted` | int(0/1) | 是否被人工调整（人工调整后不再自动覆盖） |

新增 `factor_grade_history` 表：

| 字段 | 说明 |
|------|------|
| `id` / `factor_version_id` | 主键 / 外键 |
| `grade` | 本次级别 |
| `previous_grade` | 上次级别 |
| `metrics_json` | 8 维度指标快照 |
| `trigger` | `initial` / `quarterly` / `manual` / `downgrade_auto` |
| `reason` | 升降级理由文本 |
| `created_at` | 时间 |

#### 3.18.2 核心函数

```python
def grade(metrics: dict, thresholds: dict | None = None) -> tuple[str, str]:
    """纯函数：8 维度指标 → (等级, 理由)。阈值可注入，默认读配置。"""
```

- **纯函数、无副作用**，便于单测覆盖五级边界
- 阈值来自设置页配置（默认见需求 §6.8 五级表），**每一级要求全部满足才定级**
- 返回理由文本用于 `factor_grade_history.reason` 与前端 tooltip

**8 维度**：统计显著性、经济显著性（ICIR/分层收益）、稳定性、覆盖率、换手率、复杂度、与已有因子相关性、OOS 表现。

**硬约束**：`decay_ratio < 0.5` → **不得评 B 级以上**；月频任务 → **最高 B 级**。

#### 3.18.3 季度重评调度

**落点**：复用现有 `scheduled_tasks`（新增任务类型 `factor_grade_review`，与既有定时任务同机制；`task_type` 为字符串字段，新增类型无需改枚举），**不新建调度器**。

- 频率：每季度首日触发
- 流程：扫描所有 `quality_grade ∈ {S,A,B,C}` 且非 `grade_manual_adjusted` 的因子版本 → 重算 8 维度 → `grade()` 重评 → 写 `factor_grade_history`
- **升降级规则**：
  - B 级**连续 2 季稳定** → 升 A
  - S/A 级**连续 2 季下滑**（ICIR 降幅 >30% 或 OOS 反转）→ **降级并移出 FactorSet**
- 移出 FactorSet 调用现有 `/scoring/factorsets/{id}` 成员管理接口，并写审计
- 完成通过通知 Outbox 推送摘要（升级 N 个、降级 M 个、移出 K 个）

#### 3.18.4 与 F1 联动

**D 级因子结构写入 F1 且 `is_negative_sample = 1`**，抽取时自动规避（F1 内部过滤，挖掘无感知）。

## 5. 任务执行与性能

1. 生成、字段校验、评估均进入现有异步任务中心；请求接口只创建任务，不同步执行长计算。字段校验与挖掘任务使用不同任务类型与锁。
2. DuckDB 只读连接可并行；写入使用现有单写锁和批次提交。**G2 缓存在主进程内存，不走 DuckDB**。
3. 先实现按日期/股票池分片的向量化计算；不以 Python 逐股票循环作为正式实现。
4. **性能目标以压测为准**。原 v2.0「6000 因子/5 分钟、12 代/1 小时」及「每代 2 分钟、端到端 55 分钟」等数字**均无实测支撑，且不作为验收硬指标**。M0 阶段先出串行基线压测报告；M1/M2 通过 §3.2.2 探针持续采集真实数据；M3 据此决定 G1。
5. 任务重试必须幂等（配置哈希 + 输入快照 + 任务 ID）；每代写 checkpoint；取消与失败保留 checkpoint 直到用户放弃或保留期到期。
6. **AI 环节**：4 路并发、单次 30 秒、总超时 5 分钟、成本上限 ¥10/500k token；超限回退随机。
