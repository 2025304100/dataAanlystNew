## 2. 任务清单

### T0 导航目标存在性核对（不改代码，约 0.5h）

- 产出：一份「action target 白名单」，每个目标标注「已确认存在 / P0 降级方案」。
- 逐项核对（设计 §10）：
  1. 设置→数据中心行情同步（`settings-data-center`，预期存在，核对高亮锚点）。
  2. 因子输入重算入口（SCORE_STALE/MARKET_DATA_STALE 的次选落点）。
  3. 定时任务管理入口（SCHEDULE_DISABLED 用）——**若无独立路由，P0 降级**：动作为「none + 文案指引」，不登记悬空跳转。
  4. 组合编辑（改账户类型，ACCOUNT_NOT_SIMULATED 用）——核对选择器下拉是否已有「编辑组合」；**无则 P0 降级为文案**。
  5. 自动交易来源模式控件位置（SOURCE_MODE_INVALID/LEGACY_SCAN）——核对是否在治理运行保障面板；P0 subtab 目标先记为 `governance`，不深入子面板。
- 验收点：白名单中每个 `redirect/subtab` 目标都能在当前前端找到对应路由/回调；找不到的一律走降级，**不允许登记任何未验证 target**（从根上杜绝「指引指向空气」）。

### T1 后端：ReadinessIssue 契约扩展 + 修复注册表

- 文件：`app/services/auto_trade_readiness.py`
- 改动：
  1. `ReadinessIssue` 增三个带默认值字段：`severity: str = "blocker"`、`title: str | None = None`、`fix_link: dict | None = None`。
  2. 新增模块级 `READINESS_FIX_REGISTRY: dict[str, dict]`，登记 §0 的 13 个真实 code，每条含 `title/action_type/target`，外加一个**可选** `display_severity`（仅用于展示降级，见下）；跨页类填 target，组合内类 target 留空由前端绑定。title ≤12 字、impact 一句话，文案集中在注册表，不再散落。
  3. 提供两个工厂 `_blocker(code, message, detail=None)` 与 `_warning(code, message, detail=None)`：基础 severity 由「进入哪个列表」天然决定（blockers→blocker，warnings→warning），工厂从注册表补 title/fix_link。这样同一 code `SCHEDULE_DISABLED` 在 for_schedule 进 blockers 即 blocker、否则进 warnings 即 warning，不会误判。14 个构造点全部改走这两个工厂。
  4. `NO_BUY_SIGNALS_TODAY` 的 info 降级不在 readiness 层做（它在 readiness 语义里仍是 warning），由 T2 聚合层按注册表 `display_severity=info` 覆写。
  5. `readiness_to_dict` 的 asdict 兜底分支补齐新字段。
- 不做：不改任何判定条件、ready 计算、for_schedule 语义。
- 交付物：可运行的注册表 + 工厂；旧 `/auto-trade/readiness` 响应仅新增字段。
- 验收点：
  - 遍历 `BLOCKER_*`/`WARNING_*` 常量的守护测试通过：每个真实 code 在注册表有登记且字段合法。
  - 旧接口现有测试全绿，响应新增字段不破坏旧消费方（前端旧字段仍在）。
  - 断言 `SCHEDULE_DISABLED` 随 for_schedule 在 blockers/warnings 两列表分别得到 blocker/warning；`NO_BUY_SIGNALS_TODAY` 在 readiness 层保持 warning（info 降级由 T2 验证）。

### T2 后端：行动项聚合服务（只读）

- 新增：`app/services/portfolio_action_items.py`
- 改动：
  1. 入参 `(db, portfolio_id, for_schedule=True)`，调用 `get_auto_trade_readiness` + 现有状态机取数（与 `/portfolios/{id}/status` 同一取数路径，避免新写状态判定）+ `evaluate_g7_operational_status`。
  2. 基础 severity 由来源列表决定（blockers 列表→blocker，warnings 列表→warning），再套用注册表可选 `display_severity` 覆写（`NO_BUY_SIGNALS_TODAY`→info）；HG1 `current_state` 按设计 §3.4-C 映射产出 0/1 条；G7 P0 仅把 `operational_blockers` 文本包成 severity=info 的透传项（无动作，标题「灰度运行条件待确认」），不做结构化。
  3. 去重：readiness `MARKET_DATA_STALE` 与 HG1 `DATA_INCOMPLETE_PAUSED`/`SCORE_STALE` 同属「数据新鲜度族」，合并为一条，保留最高 severity，source 折叠记录两源。
  4. 排序：blocker→warning→info；输出 `summary{blockers,warnings,info,ready}` 与 `generated_at`。
  5. 纯只读：函数内禁止出现状态转移/写库调用（评审与测试共同把关）。
- 交付物：`build_portfolio_action_items(...) -> dict`。
- 验收点（pytest，mock 三源）：
  - READY 且无 issue → items 为空、summary.blockers=0。
  - 数据过期 + DATA_INCOMPLETE_PAUSED 并存 → 仅 1 条合并项、severity=blocker。
  - RECONCILIATION_BLOCKED → 产出 1 条 blocker 且带对账 guided 标记。
  - G7 文本项 → info 透传、不含可点击 action。
  - 未知 HG1 状态 → 通用兜底项、不抛异常。

## 3. 端到端验收场景（UAC）

**场景 A：行情/评分过期**
1. 构造候选新鲜度全不过 → 顶栏显示「自动接管 · 1 项待处理」（红）。
2. 点开抽屉 → 见 1 张 blocker 卡「行情数据过期」+ 一句影响 + 按钮「去同步行情」；数据维度灯红；页面无英文 code、无长段说明文。
3. 点按钮直达设置数据中心；返回后轮询/手动「重新检测」，数据恢复后卡片移除、pill 变绿「运行中」。

**场景 B：对账差异阻塞**
1. 构造对账非零 → HG1 徽章「对账差异阻塞」，pill 计数含该项。
2. 点徽章直达抽屉对账卡；三步引导：重新对账→看差异→确认。
3. 确认成功自动重检 → 对账卡消失、HG1 徽章按后端规则恢复；全过程不离开当前页。

**反例回归**：开关关闭时 pill 为灰「已关闭」；无候选时点动作为打开「添加候选」弹窗，而 `allow_new_buys=false` 时该入口仍被门禁禁用；非模拟账户抽屉不报错。
