## 4. MySQL 0090升级与回滚证据

真实执行链：空库→完整迁移至0089→插入5条历史行→0090→重复upgrade→写入2条当前自动/手工标签消息→downgrade0089→重新upgrade0090。

| 验证项 | 实际断言 |
|---|---|
| 新列 | sector_tag_source为可空VARCHAR(16)，继承utf8mb4排序规则；迁移后历史来源均NULL |
| 原数据 | 5条历史消息全部保留，包括重复标题、中文/emoji、NULL/空/自定义/已停用板块、hash与原时间；除新列外逐字段比较一致 |
| 新写入 | 当前ORM在严格模式下可写auto/manual来源，未编造event_type/event_date，退役字段为NULL |
| 幂等 | 再次upgrade不重复加列，不重写标签 |
| 回滚 | 7条升级前后消息均保留，来源列删除，revision回到0089；其余字段与回滚前逐字段相同 |
| 再升级/重启连接 | 恢复0090，来源均视为legacy；原标签仍保留，可显式切回auto |
| 跨进程锁 | 一进程持有MySQL命名锁，业务commit后另一进程仍返回busy；释放后可取得 |
| RR旧快照 | 真实REPEATABLE-READ会话先看到不存在，另一个会话入库后旧会话仍看不到；采集服务重置旧快照后正确跳过，最终同标题仅1条 |

**回滚边界**：0090的downgrade删除来源列，**保留退役列nullable兼容修复**。恢复旧NOT NULL会拒绝升级后合法NULL行，也会再次阻断旧版ORM写入，因而不恢复。它是保留证据的功能回退，不宣称逐字节还原全部旧DDL。

## 8. 发布注意与剩余风险
