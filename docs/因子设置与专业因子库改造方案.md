| 项目 | 内容 |
|---|---|
| 文档版本 | V1.0 |
| 编制日期 | 2026-07-31 |
| 适用项目 | Personal Quant Workbench / dataAanlystNew |

## 0. 执行结论

用户对“AI 自动设置因子”的担忧成立。

AI 能降低公式编写门槛，但它无法单独保证：

- 公式具有经济含义；
- 数据在历史时点真实可见；
- 参数不是针对单段行情过拟合；
- 新因子不与已有因子高度同质；
- 样本外表现、交易成本和衰减速度稳定；
- 修改后的因子不会影响当前已运行的扫描、模型和交易计划。

因此，本次改造不应继续强化“AI 直接创建并启用因子”，而应建立以下产品定位：

> 用户负责定义意图、检查结果和批准状态迁移；AI 负责生成草案、解释公式、补充测试建议和分析失败原因；系统负责确定性计算、版本冻结、统计评估、风险门禁和回滚。

目标闭环：

    人工创建 / 模板创建 / AI 辅助草案
        -> 静态校验与数据依赖检查
        -> 候选因子
        -> 历史评估与压力测试
        -> 相关性去重与增量价值验证
        -> 影子运行
        -> 人工批准启用
        -> 持续监控、降权、隔离或归档

本次改造的第一优先级不是实现遗传编程或强化学习挖掘，而是先补齐“因子可设置、可管理、可验证、可追溯、可回退”的底座。自动挖掘只能建立在该底座之上。

## 1. 参考 PDF 的核心思想

PDF 提出了四层治理架构：

1. 自动挖掘与算子引擎；
2. 多维筛查与压力测试；
3. 正交化与结构去重；
4. 因子生命周期与动态模型。

其中最值得当前项目优先吸收的，不是“自动生成更多因子”，而是以下三点。

### 1.1 状态隔离

因子必须经过 Candidate、Testing、Shadow、Active、Deprecated 等状态，未经验证不得直接上线。

### 1.2 多维评估

不能只看一次回测收益或单个 IC。至少需要参数扰动、风格/行业中性化、分位数组合单调性、Walk-Forward 样本外验证和交易成本后的结果。

### 1.3 去同质化

新因子与成熟因子相关性过高时，应触发预警；需要通过相关性矩阵、聚类或残差化验证其独立增量价值。

### 1.4 不应直接照搬的部分

结合当前项目和个人工作台定位，以下内容不应在第一期照搬：

- 不立即建设遗传编程、表达式树搜索或深度强化学习；
- 不引入 ClickHouse、Prefect 或 Airflow；
- 不自动把 Shadow 因子转为 Active；
- 不对所有稀疏事件因子统一使用“缺失率小于 5%”标准；
- 不把 PCA 或正交化后的抽象主成分直接暴露为用户主因子；
- 不在数据覆盖仍不足时通过降低门禁制造“可用模型”。

当前主要瓶颈仍是数据覆盖、样本构造、因子定义硬编码和治理缺失，而不是候选因子数量不足。

## 2. 当前项目能力盘点

### 2.1 已具备的能力

| 能力 | 当前实现 | 可复用结论 |
|---|---|---|
| 因子稳定字典 | factors | 可作为因子主实体继续扩展 |
| 因子版本 | factor_versions | 已有公式、参数、方向、数据源映射和版本号 |
| 因子值仓库 | DuckDB factor_values | 可继续承载批量股票日因子值 |
| 因子计算 | factor_engine.py | 已有截面 MAD 去极值、Z-Score 和覆盖率 |
| 模型运行 | factor_model_runs | 已保存训练区间、指标、特征版本和状态 |
| 权重快照 | factor_weight_snapshots | 已固定模型与因子版本、系数和 IC |
| 运行模式 | manual / shadow / ridge | 已具备模式切换与回退 |
| 激活审计 | factor_model_audit_logs | 已记录模型激活和回退 |
| 流水线 | 因子流水线异步任务 | 已有进度、取消、历史和 ETA |
| 自定义公式 | custom_indicators | 已有编辑、预览、版本、回滚和作用域 |
| 公式安全 | Python AST 允许列表 | 已限制函数、变量和语法节点 |
| AI 辅助 | AI 公式助手、指标草稿 | 已有公式生成和草稿确认基础 |
| 解释链 | 单股因子解释接口 | 已展示动态模型贡献和数据截止时间 |

### 2.2 关键缺口

| 问题 | 当前表现 | 风险 |
|---|---|---|
| 因子定义硬编码 | 8 个因子来自 FACTOR_DEFINITIONS | 用户无法新增、修改或停用正式因子 |
| 计算逻辑硬编码 | SQL 直接生成固定列 | 数据库中的公式版本不能真正驱动计算 |
| 模型特征硬编码 | FEATURE_CODES 在代码加载时固定 | 因子启停和版本变化不能动态形成训练集 |
| 因子 API 只读 | 只有列表和版本查询 | 没有草稿、发布、测试、回滚等操作 |
| 缺少因子级状态机 | status 只有简单字符串 | 无法隔离候选、测试、影子和正式状态 |
| 缺少评估实体 | 指标主要附着在模型运行 | 无法独立比较一个因子的多次测试结果 |
| 缺少压力测试 | 无参数扰动和区间稳定性报告 | 容易将单点参数过拟合因子上线 |
| 缺少去重治理 | 无相关性矩阵、聚类和残差增量 | 因子库会逐步同质化 |
| 自定义指标与因子割裂 | 指标只用于筛选和回测 | 数值指标不能按治理流程晋升为模型因子 |
| AI 权限边界不够清晰 | AI 可建议指标草稿 | 容易让用户误解为 AI 已验证有效性 |
| Active 监控不足 | 缺少因子级 IC 衰减和拥挤度状态 | 已启用因子失效后不能及时隔离 |

### 2.3 必须保留的安全边界

- 模型候选不得自动激活；
- manual 必须始终可用；
- 训练和回测只读取本地时点可见数据；
- 财报继续按公告日期生效；
- 稀疏事件因子不强行填 0；
- 任务失败不得覆盖上一批有效 Score；
- DuckDB 保持单写和可回滚；
- 所有扫描、回测和交易计划继续固定评分模式、模型版本和数据截止时间。

## 3. 产品定位与信息架构

### 3.1 将“因子模型”升级为“因子中心”

设置页现有“因子模型”建议改名为“因子中心”，内部划分为六个页签：

| 页签 | 主要职责 |
|---|---|
| 总览 | 仓库健康、因子状态分布、最新评估、活动模型、风险提示 |
| 因子库 | 搜索、筛选、查看系统、用户、AI 辅助因子及生命周期 |
| 因子编辑器 | 定义公式、参数、数据依赖、方向、缺失策略和说明 |
| 评估实验室 | 运行单因子评估、压力测试、相关性和分层收益分析 |
| 影子与模型 | Shadow 观察、模型训练、激活、回退和权重对比 |
| 审计记录 | 因子版本、状态迁移、审批、失败和回滚历史 |

现有 FactorModelSettings.tsx 继续承载“影子与模型”，不要把所有管理能力继续堆在同一个页面。

### 3.2 自定义指标与正式因子的边界

现有自定义指标不应被直接改名为因子。建议明确分为：

| 类型 | 用途 | 是否进入因子仓库 | 是否进入 Ridge |
|---|---|---:|---:|
| 布尔指标 | 筛选、提醒、买卖条件 | 否 | 否 |
| 数值研究指标 | 预览、回测、观察 | 可选 | 否 |
| 候选因子 | 已提交因子治理流程 | 是 | 否 |
| Shadow 因子 | 已通过离线评估，在线观察 | 是 | 仅影子模型 |
| Active 因子 | 已人工批准 | 是 | 可进入正式模型 |

在自定义指标页面增加“提交为候选因子”命令，仅允许 value_type=number 的指标提交。提交后复制形成独立的 Factor/FactorVersion，不与原指标共享可变记录。

## 4. AI 的正确角色

### 4.1 AI 可以做什么

- 根据自然语言生成因子草案；
- 推荐公式模板和可调参数；
- 输出经济或行为逻辑假设；
- 声明所需数据字段和数据源；
- 解释公式每一部分的含义；
- 建议方向、频率和缺失策略；
- 生成参数扰动范围；
- 分析评估失败原因；
- 对比两个版本的公式变化；
- 根据已有评估报告建议下一轮实验。

### 4.2 AI 不可以做什么

- 不得直接创建 Active 因子；
- 不得绕过 AST 和数据依赖校验；
- 不得伪造 IC、ICIR、收益或覆盖率；
- 不得直接修改正在使用的 FactorVersion；
- 不得自动激活模型或切换 ridge；
- 不得把接口失败当成真实数值 0；
- 不得替用户确认经济逻辑；
- 不得在训练或回测过程中临时访问外部数据；
- 不得删除因子历史、评估和审计记录。

### 4.3 AI 草案必须结构化

AI 返回的草案不能只有公式字符串，至少包含：

| 字段 | 示例 |
|---|---|
| name | 20 日量价趋势强度 |
| code_suggestion | price_volume_trend_20 |
| thesis | 趋势上涨同时成交活跃度增强，可能代表持续资金推动 |
| formula | pct_change(close, 20) * volume_ratio(20) |
| direction | higher_better |
| category | technical |
| frequency | daily |
| parameters | window=20，扰动值 16/18/22/24 |
| data_dependencies | daily_bar.close、daily_bar.volume |
| missing_policy | exclude |
| expected_risks | 小盘暴露、高换手、单边行情依赖 |
| test_plan | 参数扰动、中性化、5 分组单调性、Walk-Forward |

系统必须独立验证该结构，不信任 AI 声称的“已通过”结论。

## 5. 因子生命周期状态机

### 5.1 状态定义

在 PDF 五态基础上增加 Draft 和 Quarantined：

| 状态 | 含义 | 是否计算全量值 | 是否可入模 |
|---|---|---:|---:|
| draft | 编辑中，尚未提交 | 否 | 否 |
| candidate | 语法和依赖已通过 | 小样本或指定范围 | 否 |
| testing | 正在或已完成历史评估 | 评估范围 | 否 |
| shadow | 离线门禁通过，在线观察 | 是 | 仅 shadow |
| active | 人工批准的正式因子 | 是 | 是 |
| quarantined | 数据异常或显著失效，临时隔离 | 可停止 | 否 |
| deprecated | 淘汰归档，只读保留 | 否 | 否 |
| rejected | 本版本未通过准入 | 否 | 否 |

### 5.2 允许的状态迁移

    Draft
      -> Candidate
      -> Testing
         -> Rejected -> 新版本 Draft
         -> Shadow
            -> Active
            -> Quarantined
      Active -> Quarantined
      Quarantined -> Shadow 或 Deprecated
      Active -> Deprecated

### 5.3 状态迁移规则

- 修改公式、参数、数据依赖、方向或缺失策略必须创建新版本；
- 旧版本继续保持原状态和历史引用；
- 新版本从 draft 重新开始，不继承旧版本测试结论；
- Shadow 和 Active 必须绑定不可变 factor_version_id；
- 自动化只能把因子置为 quarantined，不能自动从 shadow 升级为 active；
- Active 因子被隔离时，模型运行继续使用上一份有效模型或回退 manual；
- 每次状态变化都记录 actor、reason、evidence_run_id 和时间。

## 6. 因子定义与公式体系

### 6.1 复用 AST，但拆成两层 DSL

现有自定义指标 AST 可作为表达式安全基础，但正式因子需要增加两层能力。

原始表达式层定义单个股票在单个时点的原始值，例如：

    pct_change(close, 20) * volume_ratio(20)
    sum(main_net_inflow, 5) / sum(amount, 5)
    1 / pe_ttm
    roe_ttm - lag_same_period(roe_ttm, 1y)

截面处理层定义：

- MAD 去极值及参数；
- Z-Score 或 Rank 标准化；
- 行业、市值、Beta 中性化；
- higher_better、lower_better 或 nonlinear 方向；
- 排除、截面中位数、事件缺失等策略。

不要把行业中性化、去极值和缺失填充隐式藏在公式字符串里，否则版本难以比较和审计。

### 6.2 公式编译流程

    公式文本
      -> AST 语法校验
      -> 函数与字段允许列表
      -> 参数类型和范围校验
      -> 数据依赖解析
      -> 最大回看窗口计算
      -> 复杂度评分
      -> 规范化 AST/JSON
      -> 内容哈希
      -> DuckDB SQL 或受控向量算子执行计划

### 6.3 复杂度限制

- AST 最大深度默认 4；
- 函数调用数量默认不超过 12；
- 单因子最大回看窗口默认 250 个交易日；
- 禁止任意 Python、属性访问、下标执行、文件和网络访问；
- 禁止递归和动态函数名；
- 禁止未来引用和负数 lag；
- 超出限制可保存 draft，但不能提交 candidate。

### 6.4 计算引擎策略

第一期不建设通用 Python 动态执行器：

1. 现有 8 个系统因子继续使用受测的专用计算器；
2. 新增注册式算子目录，将公式编译到受控向量函数或 DuckDB SQL；
3. 未被编译器支持的 AI 公式明确标记“当前无法执行”，不得使用 eval；
4. 每个 FactorVersion 保存 compiler_version 和 execution_plan_hash；
5. 相同数据批次、版本和参数必须得到相同结果。

### 7.4 新增评估与治理表

- factor_evaluation_slices：按时间、行业、市值、市场状态保存分段指标；

- factor_correlation_edges：版本间相关性、IC 相关性、残差 IC；
- factor_shadow_daily_metrics：每日 IC、覆盖率、换手、分层收益和衰减；

### 7.5 不可变性要求

- 已被评估或模型引用的 FactorVersion 禁止原地更新；
- FactorEvaluationRun 禁止覆盖；
- 模型必须引用 FactorSet，而不是运行时查询所有 active 因子；
- 回测、扫描和解释必须能追溯到 FactorSet 和各 FactorVersion；
- 删除操作只允许软归档，不物理删除历史引用。

## 8. 因子评估与压力测试

### 8.1 评估流水线

    静态校验
      -> 数据覆盖预检
      -> 冻结股票池和数据截止时间
      -> 原始值计算
      -> 去极值/中性化/标准化
      -> 目标收益对齐
      -> Walk-Forward 样本外评估
      -> 参数扰动
      -> 分组单调性
      -> 成本与换手
      -> 分市场状态稳定性
      -> 相关性与增量价值
      -> 门禁结论

### 8.2 必须计算的指标

| 维度 | 指标 |
|---|---|
| 数据 | 覆盖率、缺失率、异常率、最新日期、可用股票和交易日 |
| 预测 | 日截面 Rank IC 均值、中位数、ICIR、正 IC 日期比例 |
| 分层 | 5/10 分组收益、单调性得分、Top-Bottom 收益 |
| 风险 | 最大回撤、波动率、尾部损失、行业/市值/Beta 暴露 |
| 交易 | 换手率、含成本收益、容量提示 |
| 稳定 | 滚动 IC、分年份、分市场状态、参数扰动稳定性 |
| 独立性 | 值相关、IC 相关、收益序列相关、残差 IC |
| 可解释 | 方向一致性、极值依赖、经济逻辑检查结果 |

### 8.3 参数扰动标准

对时间窗口参数默认测试 -20%、-10%、基准、+10%、+20%，至少满足：

- 邻近参数的 IC 符号大体一致；
- 基准参数不是唯一显著尖峰；
- 扰动后的中位 IC 不低于基准的 60%；
- 至少 3 个相邻参数通过最小有效门禁；
- 若 IC 出现断崖式下跌，版本直接 rejected。

阈值应配置化，评估报告必须展示完整曲线，不能只保存 passed。

### 8.4 分类门禁

PDF 的“缺失率小于 5%”不适合所有因子：

| 类型 | 覆盖门禁 |
|---|---|
| continuous 核心因子 | 正式候选覆盖率不低于 70% |
| event 稀疏因子 | 评估事件样本数、事件覆盖和事件后收益 |
| regime 宏观因子 | 评估时间覆盖和状态区分，不要求截面差异 |

### 8.5 分级门禁建议

Candidate 到 Testing：

- 语法和依赖校验通过；
- 无未来引用；
- 复杂度在限制内；
- 小样本计算无 NaN/Inf 异常扩散；
- 数据源在当前环境存在。

Testing 到 Shadow：

- 验证交易日不少于 50；
- 连续因子有效样本不少于 10,000；
- 平均 Rank IC 大于 0；
- ICIR 大于 0.15；
- 正 IC 日期比例不低于 55%；
- 扣成本 Top-Bottom 收益为正；
- 参数扰动没有断崖；
- 与 Active 因子最大相关性低于 0.7，或残差 IC 显著为正；
- 无明确时点穿越。

Shadow 到 Active：

- 影子观察至少 20 个交易日；
- 影子覆盖率和离线评估一致；
- 近 20 日 IC 未显著反转；
- 数据延迟和失败率在可接受范围；
- 与当前模型组合相比有可解释增量；
- 完成一次回退演练；
- 必须人工审批。

以上为初始研究阈值，最终应根据本地真实样本校准，但不得因为失败而临时降低单次运行门禁。

## 9. 相关性、聚类与正交化

### 9.1 先做可解释去重

第一期优先实现：

1. 因子值 Spearman 相关矩阵；
2. 日 Rank IC 序列相关矩阵；
3. 分层多空收益序列相关矩阵；
4. 层次聚类；
5. 每个聚类展示 ICIR、覆盖率、换手和稳定性；
6. 同一簇默认只推荐一个代表因子进入 FactorSet。

### 9.2 残差增量验证

当新因子与 Active 因子相关性超过 0.7 时：

- 用现有 Active 因子解释新因子；
- 对残差进行相同的 IC 和分层评估；
- 保存 residual_ic、residual_icir 和增量分层收益；
- 残差无效则 rejected；
- 残差有效时可进入 Shadow，但报告标明同质化风险。

### 9.3 PCA 的使用边界

PCA 只用于研究诊断、聚类辅助和共线性分析，不直接替代用户可理解的因子名称。正式模型仍保存原始 FactorVersion 和有符号权重。

## 10. Active 因子的持续监控

### 10.1 每日监控

- 最新数据日期；
- 覆盖率、异常率和填充率；
- 当日 Rank IC；
- 5/20/60 日滚动 IC 和 ICIR；
- 分组收益和换手；
- 行业、市值和 Beta 暴露；
- 与其他 Active 因子相关性；
- 计算耗时和失败率。

### 10.2 自动隔离条件

满足任一硬条件时可以自动转 quarantined，但不得自动删除：

- 数据截止时间连续 3 个交易日落后；
- 连续计算失败超过阈值；
- 覆盖率降至准入门槛的一半以下；
- 发现未来数据泄漏或数据源映射错误；
- 输出出现大规模 Inf/NaN；
- 因子定义对应的数据源契约失效。

表现衰减类条件只报警和建议降权，不直接自动下线：

- 近 60 日 IC 均值接近 0；
- IC 符号持续反转；
- 成本后收益为负；
- 拥挤度或同质化显著上升。

### 10.3 回退策略

- 因子隔离后不重写历史模型；
- 新模型训练自动排除 quarantined 因子；
- 当前 ridge 模型若依赖被隔离因子，先停止生成新 ridge Score；
- 优先回退上一有效 FactorSet；
- 无有效 FactorSet 时回退 manual；
- 保留 DuckDB 数据、评估、模型和审计。

## 13. 流水线与模型改造

### 13.1 因子计算

将 FACTOR_DEFINITIONS 从唯一事实源改为“系统种子 + 数据库注册表”：

- 系统因子仍由代码提供专用执行器；
- 数据库保存统一定义和版本；
- 用户因子通过编译器生成执行计划；
- 计算任务按 FactorSet 读取版本；
- 任务启动时冻结 FactorSet，不在运行中感知新修改。

### 13.2 Ridge 特征选择

移除模块加载时静态 FEATURE_CODES，改为：

1. 读取本次训练绑定的 FactorSet；
2. 排除非 shadow/active、quarantined 和数据未就绪版本；
3. 记录每个特征的准入或排除原因；
4. 保存实际特征清单、版本和缺失策略；
5. 不再因为一个覆盖为 0 的因子把所有样本 dropna 为 0；
6. 仍禁止把覆盖为 0 的因子填成 0；
7. 训练后新模型保持 validated/rejected，不自动激活。

### 13.3 模型门禁增强

当前模型门禁增加：

- Purged Walk-Forward；
- 验证期日截面 IC 均值和 ICIR；
- 扣成本分层收益；
- 特征系数稳定性；
- 新旧模型权重漂移；
- 因子集中度和同簇暴露；
- FactorSet 健康状态；
- 数据截止时间一致性。

### 13.4 调度

继续使用现有 SQL 定时任务和 FastAPI 生命周期调度器：

| 任务 | 建议频率 |
|---|---|
| 因子健康刷新 | 每日数据同步后 |
| Active/Shadow 因子增量计算 | 每个交易日 |
| Shadow 指标汇总 | 每个交易日 |
| 相关性和聚类刷新 | 每周 |
| 模型训练 | 每周，readiness 达标后 |
| 因子衰减报告 | 每周 |

不为每个因子创建独立系统任务。

## 14. 实施阶段

### Phase 0：基线冻结与契约确认，2 天

- 固定当前 8 个系统因子、版本和运行结果；
- 为现有公式、因子覆盖和 Ridge 建立回归快照；
- 明确 custom indicator 与 factor 的迁移边界；
- 补齐当前 DuckDB 锁、任务取消和训练样本问题的基线记录。

验收：manual 和现有流水线结果可重复，改造前后有对账基准。

### Phase 1：因子元数据与状态机，4-5 天

- 扩展 Factor/FactorVersion；
- 新增状态迁移和审计表；
- 实现草稿、候选、隔离、归档 API；
- 系统 8 因子幂等迁移为 active；
- 禁止直接修改已引用版本。

验收：可创建草稿、提交候选、生成新版本和回滚，无法绕过迁移门禁直接 Active。

### Phase 2：因子编辑器与编译器，5-7 天

- 复用 AST 白名单；
- 建立原始表达式 + 后处理配置；
- 注册式函数和数据字段目录；
- 实现多日期预览和执行计划；
- 实现数值自定义指标提交候选；
- AI 输出改为结构化草案。

验收：至少 3 个用户自定义数值因子可确定性计算，非法公式和未来引用被阻止。

### Phase 3：评估实验室，7-10 天

- FactorEvaluationRun；
- Rank IC、ICIR、分组单调性和成本收益；
- 参数扰动；
- 时间分段和市场状态稳定性；
- 评估任务、取消、历史和报告；
- Testing 到 Shadow 门禁。

验收：同一版本同一数据快照结果可重复；任一硬门禁失败不能进入 Shadow。

### Phase 4：去重与影子观察，5-7 天

- 相关性矩阵；
- 层次聚类；
- 残差 IC；
- Shadow 每日观测；
- 衰减和异常告警；
- Shadow 到 Active 人工审批。

验收：高度同质因子能被识别；Shadow 至少连续保存 20 日观测后才允许提交 Active。

### Phase 5：动态 FactorSet 与模型接线，5-7 天

- 动态特征清单；
- FactorSet 冻结；
- Ridge 样本构造按版本和缺失策略执行；
- 模型门禁升级；
- 扫描、回测、解释固定 FactorSet；
- 隔离和 manual 回退。

验收：新增 Active 因子能进入新模型但不改变旧模型；回退后现有决策链恢复 manual。

### Phase 6：自动挖掘扩展，后续可选

只有 Phase 1-5 稳定后再考虑：

- 模板参数网格生成；
- 受控表达式树组合；
- 遗传编程；
- LightGBM 作为非线性候选研究；
- 自动生成候选批次。

所有自动生成结果仍从 draft/candidate 开始，不拥有更高权限。

## 17. 验收标准

### 17.1 因子设置

- 用户可以手工创建数值因子草稿；
- 可以选择模板并修改参数；
- AI 可以生成草案，但不能直接发布；
- 公式、依赖、方向、缺失策略和后处理都可见；
- 预览能解释原值、数据来源和缺失原因。

### 17.2 因子管理

- 因子列表能按状态、来源和类别筛选；
- 任何公式变化都生成新版本；
- 已被引用版本不可修改和删除；
- 状态迁移具有原因和操作者；
- 能看到被哪些模型、回测和扫描引用。

### 17.3 科学评估

- 评估包含样本外 Rank IC、ICIR、单调性、参数扰动和成本；
- 连续、事件和宏观因子使用不同覆盖口径；
- 高相关因子触发去重分析；
- 评估结果可重复且固定数据截止时间；
- 失败因子不能进入 Shadow。

### 17.4 上线安全

- Shadow 不能影响当前正式评分；
- Active 必须人工批准；
- 新因子只进入新 FactorSet 和新模型；
- 任一异常不会改写历史 Score；
- 可以回退上一 FactorSet 或 manual；
- 回退后扫描、交易计划和解释仍可用。

### 17.5 AI 边界

- AI 不拥有状态迁移权限；
- AI 输出必须经过结构化校验；
- AI 生成内容保存来源和哈希；
- AI 不提供伪造评估指标；
- AI 不读取或输出 API Key；
- AI 不在回测和训练期间访问外网。

## 18. 主要风险与应对

| 风险 | 应对 |
|---|---|
| 通用公式执行导致安全问题 | AST 白名单 + 编译执行计划，禁止 eval |
| 因子数量膨胀 | 生命周期、聚类、归档和 FactorSet 准入 |
| 数据覆盖不足 | readiness 预检和分类门禁，不用填 0 伪造样本 |
| 事件因子被错误判为低覆盖 | 单独的 event 评估口径 |
| 参数网格造成计算爆炸 | 限制参数数目、组合数和评估范围 |
| DuckDB 锁冲突 | 复用单写锁，评估读取冻结批次 |
| AI 生成不可执行公式 | 结构化草案 + 编译器能力声明 |
| 新因子破坏现有模型 | FactorSet 冻结，新版本只影响新模型 |
| 自动下线误伤 | 性能衰减只告警，数据硬错误才自动隔离 |
| 前端功能过重 | 分页签建设，第一期只交付库、编辑和状态机 |

## 21. 兼容迁移与上线步骤

### 21.1 上线前基线

上线前导出并保存以下只读快照：

- factors、factor_versions、factor_model_runs、factor_weight_snapshots、factor_runtime_state；
- 当前 active_model_run_id、weight_mode、warehouse_path 和 feature_enabled；
- 当前 8 个系统因子代码：ep_ttm、negative_pb、roe_yoy_growth、main_inflow_5d_ratio、lhb_institution_net_ratio、turnover_z20、hot_rank_attention、tail_accumulation_proxy；
- 最近一个成功计算批次的行数、日期范围、FactorVersion 映射和 Score 样本；
- Alembic 当前 revision 及数据库备份文件。

迁移脚本不得在 upgrade 中重新编号已有 Factor.id 或 FactorVersion.id，也不得删除现有 FactorValue、Score、模型运行和权重快照。

### 21.2 历史数据回填

1. 为已有 8 个系统因子回填 origin=system、lifecycle_status=active；factor_type 必须按 definitions.py 的显式迁移映射填写，事件/状态类因子不能被一律标成 continuous；
2. 复用已有 FactorVersion；若个别因子没有版本，只追加 version=1，不改 Factor.id；
3. 由已有 formula_expr、params_json、source_mapping_json 生成 content_hash；
4. 对无法可靠推断的字段使用明确 unknown/legacy 值，并记录 migration_note，禁止猜测；
5. 将 Factor.latest_version_id 指向现有 is_latest=1 的唯一版本，发现多个 latest 时迁移失败并要求修复；
6. 创建初始 FactorSet legacy-system-v1，成员固定为迁移时的 8 个版本；
7. 迁移事务不改变现有 FactorRuntimeState.weight_mode 和 active_model_run_id；新因子中心首次开放时通过独立功能开关默认 manual，不在 schema migration 中自动切换运行模式；
8. 为回填动作写入 migration 类型审计，actor=system_migration。

### 21.3 双读验证和切换

上线采用“先写新表、双读比对、最后切读”的顺序：

1. 先部署数据库结构和只读 API，不显示创建/迁移按钮；
2. 运行内置 definitions 与数据库 registry 对账，代码、方向、版本、依赖必须一致；
3. 对同一 data_cutoff_at 用旧路径和 legacy-system-v1 各计算一次；
4. 比较覆盖行数、缺失标记、归一化值、Quality/Timing Score 和解释引用；
5. 关键数值在约定浮点容差内一致后，开放因子中心的草稿和候选功能；
6. 第一阶段继续以 manual 为默认运行模式，FactorSet/Ridge 接线通过第二批验收后再单独开关；
7. Shadow/Active 权限开关最后开放，且必须保留 local_user 人工确认。

### 21.4 回滚步骤

任一关键比对失败时：

1. 关闭因子中心写开关和评估调度，不删除已写审计；
2. 调用现有 runtime 回退能力切到 manual，并清空新决策使用的 active_model_run_id；
3. 读取路径退回 app/services/factors/definitions.py 和现有 factor_engine 兼容路径；
4. 保留新增表供排障；只有在确认没有新业务写入时才执行 Alembic downgrade；
5. 恢复数据库前先校验备份 revision、文件哈希和最近 Score 数量；
6. 回滚后执行现有 factor settings、factor engine、factor runtime、ridge model、scoring bridge 和主流程测试。

数据库结构回滚不是首选恢复手段。生产故障优先通过功能开关、manual 和旧读取路径恢复服务，避免因 downgrade 丢失草稿、评估和审计证据。

## 22. Definition of Done

以下条件必须全部满足，任务才可以从“开发完成”进入“验收完成”。

### 22.1 功能完成

- 用户能在中文界面创建、编辑、校验和预览数值因子草稿；
- 用户能提交 candidate，看到 testing 结果，并按门禁进入 Shadow；
- 任何状态迁移均通过专用命令接口，普通更新接口不能改变 lifecycle_status；
- 版本创建、对比、引用查看和基于旧版本创建新草稿均可用；
- 数值自定义指标可以提升，boolean 指标明确拒绝；
- AI 只生成待确认草案，页面刷新前后不会出现隐式保存或自动激活；
- manual、shadow、ridge 三种既有运行模式行为无回归。

### 22.2 数据与科学性

- 每次评估固定 factor_version_id、FactorSet、universe、target、data_cutoff_at、时间切分和成本模型；
- 测试集严格晚于训练/选择区间，财报字段按 announcement_date 可见；
- 连续、事件、宏观/状态因子使用各自覆盖口径；
- IC/ICIR、分组单调性、覆盖、换手、成本后表现和参数扰动都有可追溯明细；
- 同输入重复运行得到相同内容哈希和容差内一致结果；
- DuckDB 写入失败不覆盖上一个成功批次。

### 22.3 AI 与权限安全

- AI API 无状态迁移、FactorSet 激活、模型激活和运行模式修改权限；
- AI 输出在入库前通过 Pydantic、AST、依赖和复杂度校验；
- API Key 不进入 FactorDraft、日志、审计或前端错误详情；
- 未经 local_user 明确确认，candidate/testing/shadow 均不能成为 Active；
- 高风险写接口有 actor、reason、幂等键和冲突响应。

### 22.4 兼容与回归

- 现有 8 个系统因子的 ID、版本引用和历史 Score 不变；
- legacy-system-v1 与旧计算路径在约定容差内一致；
- 新 Active 因子不会改变旧 FactorSet、旧模型产物和历史解释；
- 迁移在空库、历史 SQLite 测试库及目标部署数据库上通过；
- Alembic 保持单 head，upgrade 可重复检查，downgrade 路径经过测试；
- tests 中现有 factor_*、custom_indicator、async_task、scoring 和主流程回归通过；
- 前端 TypeScript、Vitest 和因子库 E2E 通过。

### 22.5 运行稳定性

- 长评估可取消、可重跑，并有明确终态；重复请求不会启动两个同参数运行；
- 评估任务超时、进程重启或 DuckDB 锁冲突后不会永久停在 running；
- Shadow 每日任务具有幂等键，同一因子版本和交易日只生成一份观测；
- 数据硬错误会隔离新批次，性能衰减只告警并等待人工决策；
- manual 回退在故障演练中能恢复扫描、评分解释和交易计划。

### 22.6 可审计与交付物

- 因子定义、版本、评估、状态迁移、FactorSet、模型运行和 Score 可沿 ID 完整追溯；
- 审计记录包含 actor、时间、原因、前后状态、对象版本和请求关联 ID；
- API OpenAPI 契约、状态机说明、错误码、迁移手册和回滚手册同步更新；
- 验收报告包含测试命令、环境、数据库 revision、通过/失败数量和遗留风险；
- 产品负责人确认第一批只开放草稿、候选和管理能力，不把自动挖掘或自动 Active 混入 MVP。

## 23. 最终建议

本项目下一步应优先建设“专业因子库管理”，而不是继续扩大“AI 自动设置因子”的权限。

最适合当前环境的路径：

1. 保留现有 8 个系统因子和 manual 稳定闭环；
2. 将现有自定义公式编辑器升级为可复用的因子草稿编辑能力；
3. 用数据库注册表替代因子和模型特征硬编码；
4. 先完成生命周期、版本和评估记录；
5. 再建设参数扰动、单调性、相关性和 Shadow；
6. 最后才开放受控的自动候选生成。

产品最终提供两个层次的体验：

- 低门槛：用模板或 AI 快速形成一个可读、可编辑的因子草稿；
- 高可信：任何进入决策链的因子都必须有数据证据、稳定性报告、版本记录、影子观察和人工批准。

这能同时解决用户提出的两个目标：既保留 AI 降低使用门槛的价值，又把稳定性和不确定性控制交给可验证、可审计的系统工程流程。
