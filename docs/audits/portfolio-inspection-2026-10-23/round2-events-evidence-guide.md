# 第二轮补齐：来源事件、补证关联与步骤引导

核查日期：2026-10-23。范围仍为「组合交易 → 检查与对账」及其必要服务，不重做全局导航。本记录以两份源文档与最终 v10 为基线；原型中的示例标的、模型、报告号不作为真实环境材料。

## 1. 本轮可落地的三个闭环

| 闭环 | 当前实现 | 仍需区分的边界 |
|---|---|---|
| 来源变化 → 持久事件 → 日期需求 → 核对 | 应用内 SQLAlchemy ORM/Core 来源写入与事件同连接、同事务保存；核对作业消费，真实日历决定日期。晚到材料重新打开受影响日期及后续日期，保留原报告和旧历史事实 | 这是当前应用写入路径的覆盖，不是对外部直写数据库、跨库服务或未接入生产环境的 CDC 保证 |
| 实际来源 → 补证申请 → 本人关联审核 → 重检 | 新增可核验原订单候选、限定批量申请、逐笔批准/拒绝、不可改写的原申请及决定；只读核对使用审核有效且来源仍匹配的关联 | 当前启用适配器是保留确切计划键的原自动订单。无锚点记录、人工活动最终结案和外部备份导入仍不能直接认定为真实自动执行 |
| 当前证据 → 步骤状态 → 子流程返回 → 最终确认 | 服务端给出每步状态、指纹、任务、原因及完成证明；最终确认冻结完整步骤快照，事务内重新读取；错误保留理由 | 真实所有者/审核角色模型尚未接通；通用旧确认入口契约和全系统状态统一不因本向导完成而视作全部完成 |

普通对账仍必须重检，例外恢复默认关闭。双跑仍以旧/新引擎链为主，模型作为独立输入。本轮没有改变这两个已确认决策。

## 2. 来源事件的覆盖与事务保证

实现入口：`app/services/portfolio_reconciliation_events.py`，在 `app/db/session.py` 为应用引擎注册；持久化模型在 `app/models/portfolio_inspection_workflow.py`。

| 来源 | 已覆盖的变化 | 避免的误判 |
|---|---|---|
| `cash_ledger` | 新增、更正、删除，含资金、余额及归属引用 | 不以接管开关判断是否核对账户 |
| `sim_orders` | 委托、实际成交字段、状态/审核终态、归属及执行关联变化 | 不只在成功订单后触发 |
| `sim_trades` | 成交数量、价格、金额、费用及原订单变化 | 晚到成交不继续沿用旧通过报告 |
| `positions` | 数量、成本及归属变化 | 普通行情估值刷新不反复制造账户来源事件 |
| `decision_runs` / `decision_evidence` / `decision_order_plans` | 正式自动运行完成、失败、取消、中断及对应计划/决策证据变化 | 研究/回测不伪装成账户自动执行；失去正式资格的旧来源变更仍留事件 |
| `async_tasks` | 组合执行、恢复、数据修复的状态、取消和结果，含全局自动交易任务的实际组合范围 | Core 批量状态更新也留事件；心跳/纯进度不重复登记 |
| `inspection_evidence_decisions` | 批准原执行关联 | 批准与事件同事务；拒绝不生成虚假的已关联事实 |

移除原来的三处“执行提交后再尽力请求核对”回调。来源回滚时事件回滚；事件存储写失败时来源事务也回滚，即使 Core 调用方尝试继续提交也不会留下半次成功。已有活动覆盖范围却未部署事件存储时拒绝相关写入，不能静默丢事件。

消费过程采用组合根锁在前的顺序，按账户分配处理额度，避免某个等待材料的账户独占一批。无有效覆盖的遗留事件保留，建立独立核验且本人接受的账户基线时，将已纳入快照的事件标记为 `covered_by_baseline`，不把它们写成历史通过。可信日历缺失时保留 `waiting_calendar`，不猜星期一至星期五。

晚到来源会增加日期工作单的 `requested_evidence_version`，回退受影响的连续覆盖指针，原不可变报告保留。`account_source_pending` 在事件已消费后仍保持，只有相应需求版本实际核对完成才清除，防止“事件消费完了但账实尚未重检”提前放行新买入。风险退出保留独立入口。

人工重检使用相同的核对任务，返回真实任务 ID；即使五分钟计划尚未启用也可派发。派发失败返回“需求已保存、待重试”，不声称核对成功。作业抽屉保留逐日进度、待消费事件、原任务失败原因及配置计划入口；不会被新的提示覆盖真实失败结果。

## 3. 补证关联的有效范围

实现入口：`app/services/portfolio_inspection_supplement.py`；接口位于现有 inspection workflow 路由；界面在同一个抽屉的 `InspectionEvidencePanel.tsx` 中。

1. 服务端查找同组合、同决策交易日的实际运行、决策明细和确切订单计划。订单必须保留原计划键，且自动执行模式、证券、方向、数量和实际执行日期吻合。用户不能任填一个来源 ID。
2. 同一交易日按实际原订单整合展示，选择范围后预览批量申请。每对象保存原来源快照与指纹；同一批中任何来源冲突整批回滚。已登记对象移至申请区，后续候选继续可处理，不把首批 100 条变成无法越过的入口。
3. 申请不直接参与对账。本人填写理由、确认范围后批准或拒绝；审核重新校验来源指纹及基线/代次，并保留实际操作者。重复请求返回原记录，不生成重复审批。
4. 批准仅追加核对关联，不改 `SimOrder.decision_evidence_id`、原运行、成交或资金行。新来源事件与审核同事务保存；关联通过后仍需重跑原日核对。
5. 每次读取关联和每次核对都重新核验原来源。来源变化或覆盖代次变化后，旧申请/决定仍保留，但不继续作为有效关联。
6. 对账报告指纹与来源清单包含有效的关联决定；处理记录保留原运行、订单、决策、对象、交易日和整批引用，审批通过与实际核对结果分开显示。

未找到可验证候选时，明确列出要求并提供历史材料入口；确实不可恢复仍走“历史缺口 → 当前账户独立核验 → 本人接受新覆盖范围”。没有自动改账、假造 DecisionRun 或为过去补订单。

## 4. 步骤引导与最终审核

实现入口：`portfolio_inspection_runtime.py`、`portfolio_inspection_guide.py` 与现有 `PortfolioInspectionWorkbench.tsx`。

- 步骤状态为 `INCOMPLETE / RUNNING / NEEDS_RECHECK / PASSED / NOT_APPLICABLE / UNAVAILABLE`，正常等待另有 `WAITING`。状态来自实际检查、当前任务和持久需求；访问步骤不算通过。
- 四步独立可切换，同一时间只展开当前完整内容。前置工作未结束、未知或待重检时，最终确认不可提交。
- 有效报告的引用、版本、检查快照、目标日与已保留追赶日报告一起进入完成证明。最终审核显示拟恢复能力与保留限制；向导新接口要求当前快照指纹、审核动作、本人理由和幂等键。
- 最终写入在组合根锁下重读全部证明。报告、数据、绑定、代次、任务或当前条件变化返回结构化冲突；保留用户理由，不默认替用户接受新材料。
- 补证原运行/计划/订单、成交、资金、当前代次和已有审核决定均使用提交时的当前读取，避免重复读事务或 ORM 缓存沿用旧来源；最终向导也重读当前状态和持久日期工作单。新增保留旧成交对象、Core 更改来源后的冲突用例。
- 同抽屉子流程有返回第 N 步入口；返回重新读取条件。批量选择、筛选、原任务和审核草稿保留，切换组合隔离引用。
- 前往设置/策略后提供“返回检查与对账并重检”。短期草稿包括步骤、筛选、选择、任务引用、理由及已查看证明；它不保存可复用授权。历史交易日进入补证后刷新仍保留原日。
- 已通过依据更新时，相关步骤显示需重检；重新核实后才继续。首日新覆盖范围使用独立启用审核，旧期保持未知。
- 抽屉在宽屏和窄屏使用同一结构，修复宽屏缩为手机尺寸时的宽度动画裁切。补证确认窗的焦点和 Escape 返回单独验收。
