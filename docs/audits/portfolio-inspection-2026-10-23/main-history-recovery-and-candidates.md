核查日期：2026-10-23（北京时间）。对象：本机 MySQL `gpfx` / 组合 `main` / `portfolio_id=1`。

## 1. 结果

1. 找到了导致历史状态难以解释的真实缺陷：自动交易调度跨日复用同一任务 ID，worker 又允许进入旧终态任务，任务的起止时间及结果被后续运行覆盖。仅凭调度记录的 `done` 不能证明目标日实际执行成功。
2. 完整 MySQL 备份及本地 SQLite 检查后，没有找到可以补回的目标日正式决策链。**实际恢复原运行/明细/计划/订单行：0。** 没有将当前数据、回放或备注充作历史执行。
3. 补齐了可核验的调度与原任务来源上下文，并在真实库重新核对 13 个待处理交易日，形成审计 3745–3757。13 日均为 `EVIDENCE_INCOMPLETE`，可关联补证候选均为 0；报告和版本均能立即定位至历史记录。
4. main 保持 `RECONCILIATION_BLOCKED`，旧核验标记保持 2026-09-28。当前现金 434,752.27 元核验一致，但这不证明任何旧日的期初/期末快照完整。
5. 正式模型资格检查的当前可用结果为 **0 个**。现有模型与策略只能按缺口分别列为研究参考或配置草案，详见[模型与策略待确认清单](main-model-strategy-candidates.md)。

证据包为 [main-history-evidence/](main-history-evidence/evidence-manifest.json)，75 个文件约 1.65 MB，清单记录各文件 SHA-256。完整数据库备份未复制进该证据包，也未执行其中的 SQL。

这说明旧任务的当前起止时间不能还原每次调度当时的结果。当前保留的 main 分项是“行情或评分数据已过期，当前组合候选均未通过新鲜度检查”；它是该任务**当前保留的分项结果**，不能追认成每个旧交易日的结果。

缺陷及前向修复独立记录在[自动交易调度热修记录](main-auto-dispatch-hotfix.md)，不作为 G5 双跑验收完成证明：

- 自动执行任务的去重负载加入真实北京时间 `dispatch_date`；同日同设置去重，后日不会复用前日终态。该字段是派发日期，不能伪装历史决策日。
- 已完成、失败、取消或锁定的任务不能重新进入 worker。
- 新增只读 `execution_dispatch_history` 来源：只沿实际 `ScheduledTaskRun.task_id` 与原任务负载/分项结果限定组合，不用当前计划配置或名称推断历史归属。
- `CONTEXT_ONLY` 与真实订单、成交、流水分别展示并进入报告指纹；`proves_execution=false`，不会消除 `DECISION_RUN_NOT_FOUND`。
- 区分“早期创建任务被复用”与“确知原终态早于本次调度”。当前任务结束时间被覆盖时，仅报告前者，保留未知。

**没有在真实库派发任何自动交易任务验证该热修。** 验证使用隔离测试；本地实际服务继续只运行核对计划 16。
