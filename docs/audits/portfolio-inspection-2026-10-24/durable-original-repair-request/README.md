# 原修复请求跨刷新、关页及标签页恢复（2026-10-24）

本轮把已有客户端幂等键的数据修复提交与失败项重试，改为发送前持久登记、重新进入只读精确找回。后台任务生成、幂等、校验、放行及执行规则均未改。

## 修复内容

- 原先结果不明的冻结请求只在内存ref中，刷新/关页即丢失。本轮先将组合、原请求键、冻结范围、父任务及可核验任务标识写入同源localStorage并读回核验，成功后才允许POST。保存失败时不发送。
- 不保存勾选、confirmed、审核理由、交易权限或放行决定。恢复不会打开已勾选确认，不自动提交或重放。
- 原任务标识按照现有后端的确定性规则从组合和原幂等键核验，使用已有精确任务GET，不根据名称、日期、最近任务或历史第一页猜测。初次修复和重试使用同一任务标识规则。
- 刷新、关闭后重新进入、新标签页及同一浏览器配置重开后，优先精确读取保留的原任务，包括已完成及不在最近第一页的任务。已有会话里的旧taskId/自动挑选最近活动任务不能覆盖精确恢复的原任务。
- 404只表示当前没有查到，503/网络错误表示尚无法核实：保留原键和范围，暂停另起请求，提供重新读取入口。未决记录没有自动过期删除逻辑。
- 只有原请求确实查不到且记录仍未决时，才提供“核对原请求并重试”，恢复原限定范围并要求重新勾选；继续用原请求键，由原后台规则验证/返回原任务。已知存在的同键任务只GET，不再次POST。明确的计划过期/快照变化等后台拒绝保留为拒绝状态，允许重新预览当前计划。
- Web Locks覆盖同组合的持久登记和提交，防止同源多标签页同时产生两个新键；其他页看到未决记录即暂停另起提交。锁随关闭页面自动释放，持久原记录不会随锁消失。
- 当前未决记录查明后保留最近已知任务关联。允许新一批之前，会再GET核实上一任务已终结，不只信本地状态。服务端仍负责完整任务历史。
- 检查页新增“查看原请求与任务”直接入口，进入原有独立数据修复工作区；历史/浏览位置与返回机制沿用现有设计。
- 本地记录损坏、丢失或存储/锁能力不可用时，明确停止新提交，既有服务端任务历史仍可只读查看。记录只在同浏览器配置、同源站点共享；清空网站数据、不同域名/端口或不同设备不具有同一份日志，不能假设自动恢复。

## 范围与接口依赖

精确恢复覆盖已有客户端幂等标识的“数据修复提交”和“失败项重试”。自动对账来源重检旧接口没有客户端请求键，且提交会推进需求版本；本轮未修改该后台契约。它继续通过已有持久工作单/作业只读回查，刷新和恢复不自动重提，但不能把“最新任务”冒认为一次丢失回执的精确对应任务。若要为该旧接口也提供按一次提交精确关联，需要服务端请求关联信息，作为独立接口依赖保留。

本日志不是新的任务队列，不调度修复，不接受账户基线、不放行交易，也不把本地保存当作后台已接收的证明。

## 验收方式

实际main及安全只读后端作为基础，浏览器固定加载最终dist。来源修复计划、任务列表、POST接收及响应丢失均在浏览器隔离模拟，唯一POST未转发后端。原任务ID按实际后端规则在浏览器模拟端独立计算。

使用独立Chrome持久配置，不接触用户Chrome配置。实际执行了关闭来源标签、刷新接收页、新标签页打开，以及关闭隔离浏览器进程后用同一配置重开。配置及浏览器临时文件在本次tmp目录，冻结证据不包含配置本体。

## 最终结果

浏览器6条场景通过：

1. 请求发送前已保存原键，另一标签看到相同键；真实Web Locks检查发送中锁不可获取。
2. 关闭发起页后锁释放，但刷新接收页仍保存原键，精确GET的404不清除原记录、不重提。
3. 精确GET返回受控503时继续保留原请求，阻止新键，并有只读重试入口。
4. 恢复后精确找回已完成原任务，最近任务第一页刻意只有其他任务，未误关联。
5. 新标签重新进入找回同一任务，不恢复勾选、不开新请求。
6. 隔离浏览器完整关闭、同一配置重开后仍找回原键与原任务，期间没有重放POST。

模拟提交总数始终1次；实际HTTP错误、浏览器异常及非预期写请求0；受控404/503单列为注入故障。

最终18个前端测试文件191项通过（76.47秒），生产构建通过（33.38秒）。另外2项Python标准库契约测试，从实际后端源文件提取任务标识表达式和哈希函数进行隔离求值，与前端固定向量一致；未导入app、未启动服务或访问数据库。git diff --check通过。
