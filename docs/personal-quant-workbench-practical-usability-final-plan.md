# 个人量化工作台实用性与易用性改良最终方案

> 文档状态：可实施基线  
> 适用项目：`dataAanlystNew` 个人量化研究与交易决策工作台  
> 目标用户：不熟悉量化模型、数据库和接口的普通投资者，同时兼容专业用户  
> 核心原则：保留现有能力，通过简单模式、统一状态和自动化编排降低使用门槛，不推倒重做

## 1. 最终结论

当前项目已经具备“数据、因子、打分、机会、交易计划、模拟执行、回测、任务调度、通知、复盘”的主要能力，问题不再是功能数量不足，而是功能之间缺少一条普通用户可以理解并每天重复使用的主线。

本次改良应将产品收敛为一个个人决策助手：

```text
更新数据 -> 判断今天是否可决策 -> 选择机会 -> 查看交易计划
        -> 记录实际执行 -> 跟踪持仓 -> 复盘结果
```

产品同时提供两种界面：

- 简单模式：新用户默认，只展示“今日、机会、资产与执行、复盘、设置”五个入口。
- 专家模式：保留当前完整功能、因子模型、调度、回测、宏观、新闻和高级参数。

已有用户升级后继续使用专家模式，避免突然改变操作习惯；系统在设置中提供简单模式预览和一键切换。新用户默认进入简单模式。

## 2. 当前项目与环境事实

### 2.1 已有能力

当前项目已有或基本具备：

- 今日决策与数据健康概览。
- 股票/ETF 观察池、机会扫描与排序。
- `Quality Score`（标的质量）和 `Timing Score`（交易时机）双评分。
- 资金、情绪、基本面、宏观等因子计算与因子模型。
- 组合、持仓、风险规则、交易计划和模拟交易。
- 事件驱动回测及 VectorBT 专用回测能力。
- 新闻、宏观信息、预警和通知。
- 运行流水、定时任务、手动执行、取消任务和历史记录。
- 数据备份、接口设置、复盘日志等管理能力。

因此，本方案不重新实现这些模块，而是增加统一入口、默认值、状态解释、失败恢复和新手引导。

### 2.2 当前运行快照

本方案编写时的检查结果显示：

- 系统健康评分约为 `84`，整体可运行但存在数据时效问题。
- 当前跟踪约 `7` 个标的，约 `85.7%` 存在行情过期提示。
- 因子仓库可访问，但因子健康状态为 `degraded`。
- 因子模型当前采用 `manual` 权重模式。
- 当前存在约 `9` 个定时任务，其中约 `6` 个启用。
- 组合数据中存在多个默认组合的歧义，需要由唯一 `active_portfolio_id` 解决。

以上属于检查时快照，会随数据库和任务运行变化。产品不应依赖这些固定数字，而应实时计算并解释状态。

### 2.3 当前环境边界

- 以 Windows 本地使用为主，同时兼容 Linux 部署。
- 后端为 Python/FastAPI，前端为 React，数据以本地数据库为核心。
- AkShare 免费接口会遇到限流、字段变化和空数据，必须保留缓存、重试、随机休眠和降级机制。
- 普通用户不应接触 DuckDB、SQL、Ridge、Z-Score、crontab 或 API 参数。
- 回测和模型训练只读取本地数据，不应在计算过程中重复访问外网。

## 3. 产品定位

### 3.1 一句话定位

每天用十分钟完成“数据更新、机会筛选、仓位判断、执行记录和复盘”的个人量化决策工作台。

### 3.2 不做什么

- 不承诺预测必然正确或保证收益。
- 不做毫秒级高频、Level-2 逐笔或日内 T+0 系统。
- 不让普通用户自行拼接大量因子、脚本和调度依赖。
- 不把健康分、模型分数直接等同为买卖命令。
- 不因数据异常自动开仓或扩大仓位。

### 3.3 用户分层

| 用户 | 主要需求 | 默认体验 |
| --- | --- | --- |
| 新手 | 今天能不能用、看什么、买多少、风险在哪 | 简单模式 + 推荐预设 |
| 有经验个人用户 | 自定义观察池、风险规则、策略和回测 | 简单模式或专家模式 |
| 研究型用户 | 因子诊断、权重训练、数据仓库和任务编排 | 专家模式 |

## 4. 设计原则

1. 先回答“现在是否可决策”，再展示机会。
2. 先展示结论、原因和动作，再展示模型细节。
3. 默认值必须安全、可解释、可恢复。
4. 一次操作只要求用户做一个明确决定。
5. 失败时告诉用户影响范围和恢复动作，而不只显示技术报错。
6. 所有推荐都必须保留数据日期、模型版本、参数版本和生成流水号。
7. 自动化负责准备数据和建议，不代替用户确认真实交易。
8. 简单模式隐藏复杂度，但不能删掉追溯能力。

## 5. 简单模式与专家模式

### 5.1 简单模式

简单模式只保留五个一级入口：

1. 今日
2. 机会
3. 资产与执行
4. 复盘
5. 设置

宏观、新闻、因子解释、任务流水和数据健康作为相应页面的二级详情，不占用一级导航。

### 5.2 专家模式

专家模式保留当前所有导航和能力，包括因子工程、模型训练、回测实验、任务管理、宏观、新闻、接口和高级系统设置。

### 5.3 切换规则

- 新安装：默认简单模式。
- 已有安装：继续专家模式，并提示可以体验简单模式。
- 切换只影响导航和信息密度，不改变数据、模型、组合和任务。
- 简单模式中的“查看技术详情”可临时打开专家详情，不强制永久切换。

## 7. 首次使用引导

首次启动使用六步向导，整个过程不出现数据库、接口函数和模型术语。

### 7.1 引导步骤

1. 环境检查：检查后端、数据库、数据源和任务执行器。
2. 选择或创建当前组合：确保全局只有一个活动组合。
3. 设置计划投入资金：区分总资产、策略资金和单次最大风险。
4. 选择风险预设：稳健、均衡、积极。
5. 添加 `5–20` 个关注标的，支持股票和 ETF 搜索。
6. 选择自动更新方式并执行首次数据准备。

### 7.2 风险预设

| 项目 | 稳健 | 均衡（推荐） | 积极 |
| --- | ---: | ---: | ---: |
| 最大总仓位 | 50% | 70% | 85% |
| 单标的上限 | 10% | 15% | 20% |
| 单次计划风险 | 0.5% | 1.0% | 1.5% |
| 同行业集中度 | 20% | 30% | 40% |
| 最低计划盈亏比 | 2.0 | 1.8 | 1.5 |

参数只是产品默认值，用户确认后保存。界面必须解释“单次计划风险”是止损触发时可接受的最大损失，不是买入金额。

### 7.3 首次数据准备

系统自动完成：

- 同步标的基础信息与交易日历。
- 同步观察池行情和必要的因子原始数据。
- 计算 Quality Score 与 Timing Score。
- 执行一次机会扫描。
- 生成当天摘要。

任务结束后显示“可以开始使用”或明确列出仍受限的能力。

## 8. “今日”页面改良

“今日”是简单模式默认首页，只回答五个问题：

1. 今天的数据准备好了吗？
2. 当前持仓是否有需要处理的风险？
3. 今天有哪些值得进一步查看的机会？
4. 组合还允许投入多少资金？
5. 下一步该做什么？

### 8.1 页面顺序

1. 决策状态条。
2. 当前持仓风险和待处理事项。
3. 今日前三个机会。
4. 资金与仓位概览。
5. 市场、宏观和新闻摘要。
6. 最近一次更新与运行流水。

持仓风险优先于新机会，避免在已有止损或集中度问题时继续引导开仓。

### 8.2 今日机会卡片

每张卡片固定展示：

- 标的名称、代码、市场和数据日期。
- Quality Score、Timing Score 及其可信度。
- 一句话入选原因。
- 建议动作：观察、等待回撤、可制定计划、持有、减仓关注。
- 建议买入区间、失效位、目标位和建议仓位上限。
- 主要风险及导致推荐失效的条件。
- “查看解释”和“生成计划”按钮。

不直接显示“强烈买入”之类无法体现条件的绝对表达。

## 9. “机会”页面改良

### 9.1 默认筛选

普通用户默认只看：

- 当前活动组合允许交易的市场和品种。
- 数据状态为可用的标的。
- 流动性满足最低要求的标的。
- 未触发 ST、退市、高波动或集中度限制的标的。
- 评分和时机达到预设门槛的标的。

### 9.2 排序逻辑

列表默认使用可解释的综合优先级，不只按单一模型分数：

```text
机会优先级
= 质量分 × 质量权重
+ 时机分 × 时机权重
+ 资金与情绪确认
- 数据不确定性惩罚
- 组合约束惩罚
- 事件风险惩罚
```

实际计算公式和权重必须版本化。普通页面展示贡献项，专家页面展示完整公式。

### 9.3 从机会到交易计划

用户选择标的后，系统根据活动组合自动填入：

- 计划方向和适用周期。
- 触发条件与买入区间。
- 失效位/止损位。
- 第一、第二目标位。
- 按资金和最大风险计算的建议股数/份额。
- 计划占总资金比例。
- 预计盈亏比和主要风险。

用户确认后才创建待执行计划；创建计划不等于实际成交。

## 10. “资产与执行”整合

将组合、持仓、交易计划、模拟交易和风险约束整合为一个连续流程。

### 10.1 唯一活动组合

新增用户偏好 `active_portfolio_id`：

- 系统任意时刻只有一个活动组合。
- 所有首页仓位、机会过滤、计划计算和复盘默认使用该组合。
- 数据库已有多个 `is_default=true` 时，在迁移阶段选择最近使用的一个，并要求用户确认。
- 切换活动组合必须在页面顶部明显提示。

### 10.2 计划状态

统一状态流：

```text
草稿 -> 待执行 -> 部分成交 -> 已成交 -> 已退出
              └-> 已取消
草稿/待执行 -> 已失效
```

每次状态变化记录时间、价格、数量、备注和来源。

### 10.3 普通用户执行方式

- 项目只生成和记录计划，不默认连接真实券商自动下单。
- 用户在线下完成交易后点击“记录成交”。
- 系统根据成交价、数量和费用更新虚拟账本与持仓。
- 计划价格与实际成交偏差过大时要求确认。
- 卖出后进入复盘队列。

## 11. 复盘中心

复盘不只展示收益曲线，而要回答“建议是否有效、执行是否遵守计划、下次如何调整”。

### 11.1 单笔复盘

- 当时的数据日期和市场状态。
- 评分、模型版本、参数版本及入选原因。
- 原计划与实际成交的差异。
- 最大有利/不利波动。
- 退出原因：止损、止盈、信号失效、人工判断或时间退出。
- 用户备注和标签。

### 11.2 周报/月报

- 总收益、最大回撤、胜率、盈亏比和资金利用率。
- 按市场、品种、策略、评分区间和持有周期分组。
- 计划遵守率和追涨、超仓、未止损等行为偏差。
- Quality Score 和 Timing Score 的分层表现。
- 数据不可用或任务失败对结果的影响。
- 三条可执行改进建议。

### 11.3 模型复盘

模型表现只作为辅助：

- 样本数量不足时不输出确定性结论。
- 明确区分样本内与样本外。
- 避免只按收益选择模型，至少同时观察回撤、稳定性和换手成本。
- 保留每次模型启用和停用的版本轨迹。

## 12. 设置中心简化

当前设置项较多，简单模式分为五组：

### 12.1 我的偏好

- 简单/专家模式。
- 当前活动组合。
- 默认市场和语言。
- 首页面板密度。

### 12.2 资金与风险

- 计划资金。
- 风险预设。
- 总仓位、单标的、行业集中度和单笔风险上限。
- 是否允许高风险标的。

### 12.3 数据与自动更新

- 自动化配置档。
- 下次运行时间。
- 最近运行结果。
- “立即更新”和“查看详情”。

### 12.4 通知

- WxPusher 或当前可用通知渠道。
- 通知测试。
- 只发送重要事项/发送每日摘要。
- 安静时段。

### 12.5 高级设置

接口、因子权重、模型训练、任务定义、备份恢复和诊断日志全部放入高级设置，并显示风险提示。

## 13. 统一“决策就绪状态”

新增后端聚合服务 `decision_readiness.py`，将散落的健康状态统一为：

- `ready`：数据、评分和组合规则足以支持今天的决策。
- `limited`：部分因子或信息缺失，可以查看和管理持仓，但新机会应谨慎。
- `blocked`：关键行情过期、数据库不可用或核心计算失败，禁止生成新的开仓建议。

### 13.1 聚合输入

- 系统和数据库健康。
- 交易日历及当前市场日期。
- 观察池行情覆盖率和新鲜度。
- Quality Score / Timing Score 是否完成。
- 因子数据覆盖率和因子健康。
- 活动组合与风险规则是否完整。
- 必需任务的最后成功时间。

### 13.2 返回结构

```json
{
  "status": "limited",
  "as_of": "2026-07-18T16:35:00+08:00",
  "headline": "可以管理现有持仓，新机会建议等待数据更新",
  "can_open_position": false,
  "can_manage_positions": true,
  "reasons": [
    {
      "code": "MARKET_DATA_STALE",
      "level": "blocking",
      "message": "6 个关注标的行情不是最近交易日",
      "action": "refresh_market_data"
    }
  ],
  "last_successful_pipeline_at": "2026-07-17T16:42:10+08:00"
}
```

### 13.3 关键规则

- 行情过期：阻止生成新开仓计划，但仍显示已有持仓和风控建议。
- 因子 `degraded`：继续使用可用因子或人工权重，显著标记可信度下降。
- Ridge 模型未就绪：保持 `manual`，不能悄悄切换模型。
- 非交易日：显示“市场休市，数据已更新至最近交易日”，不误报为数据故障。
- 所有阻断都提供一键恢复动作。

## 14. 一键每日更新

新增 `daily_orchestrator.py`，把多个任务编排为普通用户理解的“每日更新”。

### 14.1 默认流水线

```text
运行前检查
-> 同步交易日历与标的信息
-> 同步观察池行情
-> 同步轻量因子数据
-> 计算四类因子
-> 计算 Quality/Timing Score
-> 执行机会扫描
-> 更新组合风险
-> 生成每日摘要
-> 发送可选通知
```

### 14.2 自动化配置档

| 配置档 | 内容 | 适合用户 |
| --- | --- | --- |
| 手动 | 用户点击后运行 | 不希望后台任务的用户 |
| 每日推荐 | 每个交易日盘后自动更新必要数据、评分和摘要 | 普通用户默认 |
| 研究增强 | 增加深度因子、全市场扫描和回测准备 | 专家用户 |

滚动 Ridge 训练暂不加入普通用户默认配置。只有样本量、标签、数据覆盖和回测验证均通过就绪检查后，专家用户才能启用。

### 14.3 运行和取消

- 同一流水线只允许一个活动实例。
- 支持取消，但每个步骤必须响应取消令牌并释放数据库连接。
- 任务进程、DuckDB 连接和文件句柄必须放入 `try/finally`。
- 取消完成后执行只读连接探测，确认数据库已解锁。
- 强制终止作为最后手段，并标记为“非正常结束，需要健康检查”。
- 进度条按已完成工作单元推进，不使用无法解释的固定百分比。

### 14.4 调度入口

同一套后端任务定义同时服务于：

- 设置页定时任务管理。
- 页面手动执行。
- Windows 任务计划程序。
- Linux crontab。

用户能够查看所有任务、启停、编辑时间、手动执行、取消运行、查看历史和失败原因。操作系统调度只是触发器，业务逻辑不得复制到多个脚本。

## 15. 错误、空状态与恢复

所有错误展示四个要素：

1. 发生了什么。
2. 影响哪些功能。
3. 用户是否需要处理。
4. 可以点击什么恢复。

### 15.1 示例

| 技术状态 | 普通用户文案 | 恢复动作 |
| --- | --- | --- |
| HTTP 429 | 免费数据源暂时限制访问，本次更新未完成 | 稍后重试 / 使用缓存 |
| 因子字段缺失 | 部分资金因子缺失，综合评分可信度降低 | 查看缺失项 / 重新同步 |
| DuckDB 锁 | 上次任务尚未完全释放数据文件 | 检查任务 / 安全释放 |
| 无扫描结果 | 当前条件下没有满足风险规则的机会 | 查看过滤原因 / 调整观察池 |
| 无活动组合 | 尚未选择用于计算仓位的组合 | 选择组合 |
| 非交易日 | 市场休市，数据已更新到最近交易日 | 无需处理 |

### 15.2 防御性规则

- API 返回空列表时页面展示解释型空状态，不抛白屏。
- 后端字段新增或缺失时前端提供兼容默认值并记录诊断信息。
- 截面标准差使用安全下限，避免除以零。
- 短期缺失因子可使用最多五日移动值降级，但必须标记来源和日期。
- 关键行情和价格不得用静默前值填充后假装是最新数据。

## 16. 普通语言术语

| 专业术语 | 简单模式显示 |
| --- | --- |
| Factor warehouse degraded | 部分评分依据缺失，可信度下降 |

## 17. 安全默认值

- 新计划默认需要用户确认，不自动真实交易。
- 数据不是最近交易日时禁止生成新开仓建议。
- 超过总仓位、单标的上限或行业集中度时禁止确认计划。
- 缺少止损/失效条件时不能进入待执行状态。
- 预期盈亏比低于组合规则时显示阻断原因。
- 模型切换、权重修改和风险上限提高需要二次确认。
- 删除计划、清空记录和恢复备份均要求明确确认。
- 系统不得把回测收益作为未来收益承诺。

## 25. 优势与代价

### 25.1 主要优势

- 最大化复用现有功能，改造成本可控。
- 普通用户只需要理解自己的资金、风险和计划。
- 数据异常和任务问题在做出决策前被显性化。
- 简单模式与专家模式共用数据和业务服务，不形成两个产品。
- 自动化、任务历史和版本追溯使系统可长期使用。
- 保留 Quality Score 与 Timing Score 的分工，避免单一综合分掩盖交易时机。

### 25.2 必须接受的代价

- 聚合状态和简单页面会增加一层后端编排与前端适配。
- 为了安全，数据过期或组合规则不完整时会减少可执行建议。
- 免费数据源无法提供稳定的 Level-2、高频和完整历史退市样本。
- 自动复盘需要积累足够的计划与成交数据，早期结论会较弱。
- 同时维护简单/专家两种信息密度，需要持续做回归测试。

这些代价符合个人工具的目标：宁可少给一个机会，也不要在数据不可信时给出看似精确的建议。

## 27. 外部数据透明度与长耗时同步专项优化

### 27.1 当前问题诊断

“设置 → 外部数据”当前可以完成手工同步，但还不适合作为普通用户长期使用的日常入口，原因包括：

- 卡片只说明同步内容，没有显示数据截至日期、最近成功时间、覆盖率和来源状态。
- 点击后使用同步阻塞请求，运行期间只有按钮 loading，用户不知道目标数量、当前标的和剩余时间。
- 同步结果主要依赖临时消息和单个结果 Alert，刷新页面后缺乏历史可见性。
- 页面共用一个“自选股/持仓/全部”范围，但不同数据实际支持的资产和范围不同，用户难以预测按钮会处理多少数据。
- “同步成功”只代表接口调用和入库成功，不代表每个字段都是当天数据。
- ETF 市价、基金净值、份额和规模可能来自不同接口、不同发布日期，不能只用一个笼统日期表示实时性。
- 财报数据天然按报告期与公告日更新，日常重复同步全部历史既慢，也不会产生新的有效信息。

当前实现还存在两个明确的效率问题：

1. ETF 指标同步按每只 ETF 循环执行；循环内会重复请求 ETF 全市场现货与全市场每日数据，再单独请求该 ETF 的历史净值。全市场接口本应每批只拉取一次。
2. 财报同步每次为每只股票获取全部可用历史，并对全部记录执行 UPSERT；未区分“首次回填”“日常增量”和“强制重建”。

### 27.2 页面透明度改造

每张数据卡片增加固定的状态区域，不再只有描述和按钮。

```text
同步 ETF 指标                         [部分过期]
数据范围：自选股中的 4 只 A 股 ETF
最新市价：2026-07-17 15:00
最新净值：2026-07-17（基金公司公布）
覆盖情况：3/4 可用，1 只过期
最近同步：2026-07-18 07:32，耗时 8 秒
数据来源：AkShare / 东方财富公开数据
下次计划：今天 18:05

[更新过期的 1 只]  [查看明细]
```

卡片至少显示：

- 状态：可用、部分过期、已过期、未同步、同步中、失败。
- 目标标的数量和实际适用数量。
- 最新有效数据日期，而不只是抓取时间。
- 最近一次尝试时间与最近一次成功时间。
- 成功、缺失、过期、失败的标的数量。
- 数据来源和更新频率说明。
- 预计同步耗时或耗时范围。
- 下次定时运行时间。
- 永久可查看的最近结果和历史流水入口。

按钮文案根据状态变化：

- 全部最新：`已是最新`，次按钮提供“重新校验”。
- 部分过期：`更新过期的 2 只`。
- 首次使用：`准备最近数据`。
- 运行中：`已完成 3/8 · 可后台运行`。
- 失败：`重试失败的 1 只`。

### 27.3 数据日期必须分层展示

数据透明度不能只增加一个 `updated_at`。至少区分：

| 字段 | 含义 |
| --- | --- |
| `effective_date` | 该数值实际对应的交易日、报告期或公告日 |
| `provider_time` | 上游明确提供的时间；上游未提供时为空 |
| `fetched_at` | 本系统抓取完成时间 |
| `stored_at` | 本地成功提交时间 |
| `source` | 数据源与接口标识 |
| `freshness_status` | 按数据类型规则计算的可用、过期或未知 |

ETF 卡片需要按字段显示：

- 市价截至时间。
- 单位净值日期。
- 溢价/折价计算使用的市价与净值日期。
- 规模/份额公布日期。
- 是否由原始接口直接提供，还是由市价和净值计算。

当市价与净值不是同一日期时，溢价折价标记为“估算”或“不参与评分”，不能展示成当日精确值。

财报卡片需要显示：

- 最新报告期。
- 最新公告日期。
- 历史覆盖起止报告期。
- 已保存公告版本数。
- 有多少标的缺少最近应披露报告。

### 27.4 点击前预检

同步按钮不应直接启动潜在长任务。点击后先调用预检接口，弹出确认框：

```text
准备更新财报数据

范围：自选股中的 12 只 A 股
已是最新：8 只
需要检查：4 只
预计外部请求：4 次
预计耗时：20–45 秒
模式：智能增量
将写入：新增公告版本，不重写已有历史

[开始更新] [更改范围] [取消]
```

若选择“全部”，必须额外显示实际标的数量、预计请求数、预计时间和限流风险。超过安全阈值时，不允许通过同步 HTTP 请求直接运行，必须转为后台任务并分批执行。

### 27.5 ETF 指标优化方案

#### 默认策略：智能快照

普通用户点击 ETF 更新时只执行：

1. 找出当前范围内的 A 股 ETF。
2. 查询本地每只 ETF 的字段级有效日期。
3. 跳过仍在新鲜度范围内的标的。
4. 每批只调用一次全市场 ETF 现货接口。
5. 每批只调用一次全市场 ETF 每日指标接口。
6. 将结果转为 `code -> row` 映射，批量写入目标 ETF。
7. 只有目标 ETF 缺少净值，或全市场接口未覆盖时，才按单只基金调用历史净值接口兜底。

这能把主要请求量从近似 `2 × ETF 数量 + 单只历史请求` 降为 `2 个批量请求 + 少量缺失兜底请求`。

#### 三种模式

| 模式 | 行为 | 默认入口 |
| --- | --- | --- |
| 智能更新 | 只更新缺失或过期的最新快照 | 普通用户默认 |
| 校验当前范围 | 重新拉取批量快照并核对本地数据 | 卡片二级操作 |
| 历史回填 | 仅对明确选择的 ETF 回填限定时间段 | 专家设置 |

普通页面不提供“全市场逐只历史净值”按钮。

#### 新鲜度建议

- 盘中市价：标记为盘中快照，不宣称收盘有效。
- 盘后市价：最近交易日收盘后可视为最新。
- 单位净值：允许晚于市价公布，按净值自身日期判断。
- 规模和份额：按数据源公布周期判断，不要求每天变化。
- 新鲜度计算使用交易日历，不能简单使用七个自然日。

#### 数据库与缓存

- 为一次批量运行增加 run 级内存缓存，避免相同 AkShare 接口重复调用。
- 可选增加短期本地原始响应缓存，保存接口、抓取时间和内容摘要。
- `EtfIndicator` 增加字段级日期或单独的数据血缘明细表。
- 唯一键保持 `symbol_id + effective_date + source`，重复运行必须幂等。
- 只有字段发生变化时才更新业务记录，原始响应摘要用于审计。

### 27.6 财报历史优化方案

#### 将一个按钮拆成三种语义

| 模式 | 范围 | 用途 |
| --- | --- | --- |
| 更新最新财报 | 只检查可能出现新公告版本的标的 | 日常默认 |
| 首次准备近三年 | 最近 12 个季度或近三年 | 新用户/新加入标的 |
| 完整历史回填 | 用户明确选择的少量标的 | 研究用途 |

普通用户的按钮改为“更新最新财报”，不再默认表达成“同步财报历史”。

#### 日常增量规则

对每只标的保存财报同步水位：

- 最近成功检查时间。
- 最新报告期。
- 最新公告日期。
- 最新公告版本摘要。
- 历史覆盖起点。
- 上次失败类型和可重试时间。

运行时先判断：

1. 非财报披露窗口且最近已成功检查：直接跳过。
2. 持仓和自选股优先，默认最多 20 只。
3. 新加入且没有历史：准备近三年数据。
4. 已有历史：只比较本次响应中比本地水位更新的公告版本。
5. 没有新增版本时记录“已检查，无新财报”，不要把全部历史条数报告为新增。
6. 强制完整回填只能在专家模式中选择，并转为后台任务。

AkShare 的单股财务分析接口可能仍会返回该股票全部历史，无法完全减少单次响应体；但通过缩小同步范围、降低无效调用频率、只写入变化记录，可以显著降低总耗时和数据库负担。

#### 调度策略

- 默认周末运行一次自选股/持仓增量检查。
- 财报集中披露窗口可提高到每个交易日盘后检查。
- 普通自动化配置只检查持仓与自选股，不跑全市场逐股财报。
- 全市场最新财报优先评估市场级批量接口；详细公告版本只为进入候选、持仓或自选股的标的补齐。

### 27.7 从同步 HTTP 请求迁移为后台任务

ETF 和财报统一采用：

```text
预检 -> 创建任务 -> 立即返回 run_id -> 页面轮询/SSE 显示进度
     -> 分批抓取 -> 分批提交 -> 生成永久结果摘要
```

长任务返回：

```json
{
  run_id: external-sync-20260718-001,
  status: running,
  stage: fetch_financial_reports,
  processed: 7,
  total: 12,
  up_to_date: 5,
  created: 8,
  updated: 1,
  failed: 0,
  current_symbol: 600519.SH,
  started_at: 2026-07-18T08:20:00+08:00,
  heartbeat_at: 2026-07-18T08:20:31+08:00,
  estimated_remaining_seconds: 24
}
```

页面离开或刷新不影响任务；重新进入时自动恢复当前进度。任务支持取消，取消后必须释放数据库连接并保留已成功提交的批次。

### 27.8 建议 API

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| GET | `/api/v1/external-data/status` | 七类数据的覆盖率、新鲜度与最近流水 |
| POST | `/api/v1/external-data/preview` | 计算目标、跳过数、请求数和预计耗时 |
| POST | `/api/v1/external-data/runs` | 创建智能增量或历史回填任务 |
| GET | `/api/v1/external-data/runs/{run_id}` | 查询进度与结果 |
| POST | `/api/v1/external-data/runs/{run_id}/cancel` | 安全取消 |
| GET | `/api/v1/external-data/details/{data_type}` | 查看逐标的数据日期和错误 |

请求参数统一为：

```json
{
  data_type: financial_reports,
  scope: watchlist,
  mode: incremental,
  limit: 20,
  force: false
}
```

### 27.9 状态与结果口径

同步结果不能只返回 `success/skipped/failed`，需要明确：

- `target_count`：范围内适用标的数。
- `up_to_date_count`：预检发现无需访问外部接口的标的数。
- `checked_count`：实际访问或校验的标的数。
- `created_records`：真正新增记录数。
- `updated_records`：真正发生变化的记录数。
- `unchanged_records`：接口返回但与本地一致的记录数。
- `missing_count`：上游没有返回有效数据的标的数。
- `failed_count`：发生异常的标的数。
- `effective_date_min/max`：本批有效数据日期范围。

“跳过”需要细分为“已是最新、非适用资产、无上游数据、达到范围上限”，避免用户把跳过误认为失败。

### 27.10 落地顺序

#### 第一批：先解决不透明

- 增加外部数据状态聚合接口。
- 每张卡片展示有效日期、覆盖率、最近成功时间和来源。
- 点击前显示目标数量与预计耗时。
- 同步结果持久化并链接到任务历史。

#### 第二批：解决 ETF 重复请求

- 将两个全市场 ETF 接口提升为批次级请求。
- 增加批次缓存和代码映射。
- 只对缺失标的调用单只历史净值兜底。
- 使用交易日历计算新鲜度。

#### 第三批：解决财报全量重写

- 增加标的级财报同步水位。
- 默认改为“更新最新财报”。
- 首次准备限制为近三年，自选/持仓默认上限 20 只。
- 完整历史回填进入专家模式后台任务。

#### 第四批：统一后台运行体验

- 接入任务中心的进度、心跳、取消和历史机制。
- 页面刷新后恢复进度。
- 失败标的支持单独重试。
- 将卡片状态接入 `decision_readiness`。

### 27.11 验收标准

- 用户不点击按钮即可知道每类数据是否可用、截至哪一天、覆盖多少标的。
- 点击前能看到实际目标数和预计耗时。
- 自选股中多个 ETF 同步时，全市场 ETF 接口每批最多调用一次，而不是每只调用一次。
- 财报日常更新只写入新增或变化版本，不把历史总条数显示为新增数。
- 普通模式不会直接启动全市场逐股财报历史回填。
- 运行超过 3 秒的同步均进入任务中心并展示真实进度。
- 页面刷新、切换设置页后仍能看到运行状态和历史结果。
- 市价、净值、规模、报告期和公告日分别展示其有效日期。
- 任务失败或部分成功不会抹掉已存在的有效数据。
- 取消任务后数据库连接正常释放，失败项可以继续重试。

## 28. Definition of Done

本方案不是以“页面已经存在”作为完成，而是满足以下定义才算落地：

- 普通用户能独立完成每日决策闭环。
- 专家功能完整保留且原有数据不受影响。
- 系统能实时判断数据和模型是否足以支持决策。
- 推荐包含原因、风险、仓位、失效条件和追溯版本。
- 长任务具备真实进度、心跳、取消、历史和恢复。
- Windows 手动/定时任务与 Linux crontab 共用同一业务入口。
- 关键路径通过单元、契约、浏览器黑盒和回归测试。
- 文档、页面术语和错误信息均能被非技术用户理解。

完成以上条件后，项目将从“功能较多的量化工具集合”转变为“普通用户每天可以放心重复使用的个人量化决策工作台”。
