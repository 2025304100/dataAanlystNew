## 十、“mock 抄漏方法被 catch 吞掉”的结构性防线（用户采纳 A+B 后执行）

### 先说清楚这个坑为什么难发现

前端 85 个测试文件几乎每个都**自己手写一份局部 api mock**，要用几个写几个。
抄漏一个方法时，`api.xxx` 是 `undefined` → `TypeError: ... is not a function`，
而组件普遍 `try/catch + console.error` —— **这个异常变成一行日志就被吞了**。
结果是测试跑的是“取数失败的降级路径”，断言却全通过。851 全绿里根本看不出来。

本次是前端全量输出里偶然看到的一行
`[notifications] inbox fetch failed: api.getInboxNotifications is not a function` 把它逗出来的
（该方法在 `client.ts:2651` 与后端 `/notifications/inbox` 均存在）。

### B（构造性照妖镜，已装）

`frontend/src/test/setup.ts` 新增：拦截 `console.error/warn` 中包含 `is not a function`
的消息并收集，`afterEach` **直接判失败**（即使组件把它吞了也跑不掉）。
真在测“接口不可用”分支的用例，必须调 `__allowMissingApiMethod()` 显式声明 ——
把隐式绕过变成显式选择。

**实际抖出来的东西**（一次跑完全量）：`1 file / 2 tests` 失败，全部是同一个缺口
`getInboxNotifications` —— 定位到我自己写的 `WP9Cleanup.test.tsx`：它渲染带通知下拉的
壳组件，但 mock 里没声明这个方法。也就是说之前那两条用例验证的是通知拉失败时的降级，
而它们看上去在测“投顾 tab 移除与路由兼容”。

双向验证已完成：装守卫时红 2 条（报出确切缺失方法）→ 补上 mock 后转绿；
补后全量 **85 files / 851 passed**，`tsc -b` 干净。

### A（类型约束，已加一半，剩下的诚实说明）

`makeMockApi(overrides: Partial<typeof ApiClient.api>)`（type-only import，不把真 api 拉进
测试运行时）：把方法名**拼错**（如 `getPosistions`）从“运行时 undefined 静默降级”
变成**编译期报错**。

但要说清局限：**它不能保证 mock “方法齐全”**——jsdom 下组件到底调哪几个方法，
类型系统看不出来。真正兼顶这个的是 B。另：`makeMockApi` 仍然 **0 使用者**
（本轮没组迁 85 个测试去用它，那个改动量太大且容易撞用户在途文件）。

### 待观察
后续新测试如果 mock 缺方法，会直接红并提示修法；如果谁真需要测降级分支，
要写 `__allowMissingApiMethod()` —— 评审时看到这一行就该问“为什么在测降级”。
