## 一、交接结论

当前项目已完成阶段 0-3 的主要统一决策、PIT 和自动模拟实现，G0-G4 定向门禁及 G3 真实浏览器矩阵已通过；G5/G6/G7 的代码、接口和治理操作入口也已实现，但真实双跑、灰度和运维演练尚未达到全部验收 Definition of Done，不能在这些证据完成前扩大自动模拟交易范围。

本轮已完成 WP0-5 的统一订单计划接入、PIT/成员/基准门禁和自动模拟适配，并在存在不可变 `strategy_snapshot_id` 的组合回测中逐交易日持久化 `DecisionRun`/`DecisionEvidence`，回填 `BacktestTrade` 的买入/卖出证据 ID，并把 `decision_run_ids_json` 写入 `BacktestRun`。独立 `decision_order_plans` 账本、回测买卖计划价投影、G6 灰度启停和 G7 运维状态入口也已实现；当前剩余集中在 G5 真实十日双跑、G6 单组合灰度和 G7 运维演练。

建议先按“阻断问题清零 -> P0 真实贯通 -> G0-G4 验收 -> 双跑/灰度”的顺序推进。所有任务必须以测试产物、数据库核对和页面实际请求为完成依据。

## 三、当前阻断项与已知风险

### 1. 本地测试环境不完整

项目专用 `.venv` 已可导入第三方 Alembic（`from alembic.config import Config` 通过），阶段 1-3 定向回归不再使用缺少 Alembic 的旧解释器。Python Playwright 包已存在于仓库缓存 `.pip_packages`，但必须通过 `PYTHONPATH=.pip_packages` 暴露；Chromium 在当前受限沙箱中启动会报 `spawn EPERM`，这属于验收环境限制，不是业务用例失败。

处理要求：接手人继续固定使用 `.venv` 和锁定依赖；完整 G3 应在允许启动 Chromium 的验收环境执行。不要为规避该问题给本地 `alembic/` 增加 `__init__.py`，那会继续遮蔽第三方包。

### 2. 工作区不是干净状态

工作区有大量用户既有改动、新增文件、删除的旧 migration 和未跟踪文件。接手前必须：

1. 用 `git status --short` 和 `git diff --name-status` 导出快照。
2. 将本轮和已有工作按主题拆分提交或补丁包，至少分为 migration、DecisionEngine、回测/前端、测试/脚本四组。
3. 不执行 `git reset --hard`、不恢复或删除未确认的 migration/备份/数据库文件。
4. 在副本数据库上验证 Alembic `upgrade head`、应用启动和历史数据库升级；不能只使用 `Base.metadata.create_all()`。

### 3. 回测统一决策链的剩余风险

阶段 1-3 定向契约和跨入口测试已通过，当前主链已使用 `DecisionEngine -> DecisionOrderPlan -> simulation_matching_engine -> BacktestTrade`，但仍需在完整回归和故障注入中持续确认：

1. 新决策运行的订单计划已持久化到独立 `decision_order_plans` 表，并保留 `DecisionEvidence.versions_json` 作为历史兼容回退；旧历史运行不能猜测性回填。
2. 自动模拟保留 `place_sim_order` 账户记账兼容层；实时行情、资金不足顺延和跨入口待单状态仍需阶段 3 专项验证。
3. 同一快照/日期的 DecisionRun 复用、不同成本参数不复用成交、失败运行的状态降级和 savepoint 语义需继续通过故障注入测试确认。
4. 生产 PIT、数据质量 quarantine、基准缺口和成员有效区间已有 fail-closed 逻辑，但完整历史数据升级和多源切换仍需 G4 验收。

### 4. 旧白盒测试契约状态

`tests/test_whitebox_portfolio_backtest.py` 当前为 `30 passed, 8 xfailed`；8 个 xfail 已明确标注为废弃旧语义（旧 PIT/snapshot 输入、manual/confirm 阻断和 `only_auto` 筛选），使用 `--runxfail` 可复现为 8 个预期失败。`tests/test_whitebox_backtest_snapshot.py` 为 `16 passed`。后续不应简单移除 xfail；若产品重新要求旧语义，需先新增兼容契约和独立开关。

## 四、建议执行顺序和工作包

### 阶段 0：接手冻结与可重复环境（P0，0.5-1 人日）

目标：让后续结论可复现，避免在错误 Python、错误 migration 链和持续变化的数据上开发。

任务：

1. 建立项目专用 Python/Node 环境，补齐 Alembic、pytest、前端依赖；记录版本、安装命令、`where python`/`where pytest` 结果。
2. 运行 migration 链检查：新库 upgrade、现有库升级、降级兼容窗口和应用启动检查。
3. 固化测试数据：组合、成员快照、模型、Score、日线、指数日线、时间区和浏览器版本。
4. 给所有回测测试设置独立数据库；集成测试优先用 migration 创建，不依赖全局运行数据库。
5. 建立 CI 的最小门禁：backend lint/compile、G0、G1、G2、TypeScript build、前端单测。

完成标准：`alembic.config` 可导入；新库可 `upgrade head`；G0/G1 测试不再因环境 setup 报错；工作区改动来源可追溯。

### 阶段 1：回测真正接入统一决策（WP0-5 收尾，P0，3-5 人日）

目标：同一执行快照、同一交易日、同一数据输入下，回测的订单意图必须由 DecisionEngine 输出驱动，而不是在旧回测完成后再补写审计记录。

后端任务：

1. 定义稳定的中间订单契约，例如 `DecisionOrderPlan` 或 Evidence 中的唯一计划键，至少包含：`decision_run_id`、`evidence_id`、`symbol_id`、`signal_date`、`execution_date`、目标数量、方向、价格假设、原因码、拒绝/顺延轨迹。
2. 把 `run_backtest` 改为：逐日组装当日 PIT 行情/成员/持仓状态 -> 调用 DecisionEngine -> 用其 BUY/SELL/REJECTED/NO_ACTION 的订单计划撮合 -> 写 BacktestTrade/拒绝记录。旧规则函数仅作为 DecisionEngine adapter，不能双算。
3. 将 `price_data_by_symbol`、实际初始资金/可用现金、持仓、成本模型、滑点、最小手数、成交量和涨跌停约束传入统一链路；禁止 DecisionEngine 和撮合端分别计算不同的目标数量。
4. 去掉 evidence 与交易的“选择最早/最近历史证据”匹配。以 plan ID 或严格 `(symbol, action, signal_date, execution_date)` 一对一关联；同一证券反复交易必须有回归测试。
5. 明确交易时点：默认 T 日收盘产生信号、T+1 开盘成交；若研究模式允许 T_CLOSE，必须在运行、Evidence 和 UI 上明确降级标识，正式 PIT 不允许。
6. 明确失败事务：回测失败应保存 `BacktestRun=failed` 和可追溯错误；本次创建的 DecisionRun 状态一致为 FAILED/取消，不能留下看似成功但未归属的成交或证据。使用 savepoint 或专门失败审计事务，不要在通用异常分支无选择 `commit`。
7. 确定重复运行契约：相同 snapshot/date 是复用 DecisionRun，还是每个 BacktestRun 各有 DecisionRun；若复用，增加关联表或明确只读引用，并保证运行级成本参数差异不会误复用决策。

测试任务：

1. 单日 dry-run、单日回测、auto-simulation 的逐证券结果哈希相同。
2. 两次进出同一证券、部分成交、next-open 顺延、T-close 研究降级、最小手数拒绝、涨跌停/停牌、资金不足和卖出优先级。
3. DecisionRun/Evidence/Trade/拒绝记录的数量和外键双向核对。
4. 注入第 N 日 DecisionEngine 失败，验证无成交半写、状态一致、重试幂等。

完成标准：回测不再依赖后置猜测绑定；G2 能证明模型/快照 -> 决策 -> 订单/成交 -> 证据完整贯通；跨入口逐证券结果 hash 一致。

### 阶段 2：PIT、数据质量与基准正确性（WP0-6/WP0-9，P0，4-6 人日）

目标：正式回测没有未来函数，数据缺失不伪造结果，基准只影响相对指标。

任务：

1. 统一 Score 查询契约：精确 `factor_model_run_id`/FactorSet，`as_of_date <= data_cutoff_at`，`published_at <= data_cutoff_at`，处理同日修订并持久化所选 Score/数据版本。研究模式 legacy fallback 必须显式留痕，production 禁用。
2. 回测使用成员历史快照或有效区间；成员在生效前、退市、ST、停牌、主数据不完整时的处理写入 Evidence。禁止当前成员列表回填历史。
3. 编写防未来反例：向决策日后插入极端 Score、行情修订、财务修订，原区间订单、净值和证据完全不变；延长结束日不改变原结束日前结果；切换当前模型不改变旧快照重放。
4. 校验 T+1 时间语义；预热窗口只能计算指标，不能提前成交。
5. 基准以真实指数日 K 的共同起点归一化；缺失时 `BENCHMARK_INCOMPLETE/SOURCE_MISSING`，隐藏超额/信息比率等相对指标，不生成年化 5% 或任何填充曲线，也不影响组合成交。
6. 接入 LIGHT/MEDIUM/HEAVY 数据完整度、AkShare/Baostock 主备、源切换血缘、财报披露时间和 quarantine 规则；关键缺口 production fail-closed，研究模式风险标识。
7. **尾盘代理二期（当前预留，P1/P2）**：将候选池分钟数据采集做成系统任务，而不是把 CSV 准备责任长期交给用户。任务必须使用最近真实交易日（周末/节假日不请求空日期），尊重自选股/持仓/候选池范围，支持可配置分钟数据源（主源、备用源、人工 CSV 导入），并保存源、日期、候选快照和失败原因。只有满足每标的至少 180 根日内分钟、20 根尾盘分钟且最后时间不早于 14:59，才写入 `TailAccumulationSnapshot` 并镜像 `raw_tail_proxy`；不得用日线或前值填充。

完成标准：PIT 污染测试 100% 通过；Score/model/FactorSet 绑定完整率 100%；缺基准不改变订单；重度缺口不生成新买单。

尾盘代理二期验收项：

- 自动任务在非交易日自动定位最近交易日；
- 三种范围（候选池、自选股、持仓）逐项验证，不允许异步任务丢弃范围参数；
- 主/备分钟源切换、限流、熔断、断点继续和幂等写入均有审计；
- 完整会话、部分会话、停牌/空返回、供应商连接中断均有可解释结果；
- 真实分钟数据写入后，因子仓库、覆盖诊断和评分批次可追溯；在上述条件未满足前，`tail_accumulation_proxy` 继续保持 blocked。

### 阶段 3：仓位、因子模型和自动模拟交易统一（WP0-4/WP0-7，P0，4-7 人日）

目标：模型、因子、规则、仓位和自动交易不再存在独立解释路径。

任务：

1. 以 DecisionEngine allocator 取代 `auto_trade_member_source.py` 中固定或独立的仓位计算；核对 `_calculate_position_size` 不再返回固定 100。
2. 实现并测试总仓位、单票、行业、资产类型、阶段限制、现金下限、风险预算、手数、费用、滑点和成交量的顺序 clamp 明细；Evidence 保存每一层 before/after/trigger。
3. 打通 `FactorSet -> PIT 特征 -> FactorModelRun -> validated/active -> 精确 Score -> StrategyUsageBinding -> Snapshot`。新训练请求必须携带 `factor_set_id`；策略页只展示 active 且 readiness 合格的模型。
4. 自动模拟交易仅负责获取已应用快照、调用 DecisionEngine、把订单计划转换为模拟订单、写撮合/持仓/现金；不得自行筛选、打分或算仓位。
5. 为模型退役、Score 过期、模型切换、成员无 Score、读取旧 snapshot 等场景补 fail-closed 和审计测试。

完成标准：预检、回测、自动模拟在固定输入下的候选/动作/仓位/原因码一致；自动交易不产生固定 100 数量；任意 Score 可追溯到模型/因子版本。

### 阶段 4：前端与接口契约收尾（WP0-8/WP1-1，P0/P1，3-5 人日）

目标：页面只展示真实执行状态，用户可解释运行、交易和拒绝。

任务：

1. 清点策略页和回测中心每个可编辑控件，建立“组件字段 -> API -> schema -> snapshot/DecisionEngine 使用点”清单；无执行映射的控件删除或禁用。
2. 回测请求/响应完整回显 initial_capital、benchmark、price_type、commission、stamp tax、slippage、volume_limit、rebalance_frequency、pit_mode、snapshot/model/FactorSet/data snapshot。
3. 策略页只读展示模型的真实 FactorWeightSnapshot；区分 validated、global active、portfolio applied 三种状态；预检失败保留原绑定并定位首个阻断项。
4. 完成回测结果五个 Tab、服务端分页/排序/筛选、空态/阻断态/失败可重试、历史运行打开与快照只读信息。
5. 完整化 `DecisionEvidenceDrawer`：结论、规则比较、因子贡献、仓位 clamp、执行假设、版本、原始 JSON、上一/下一、复制 ID、Esc 关闭及焦点/滚动/分页保留；移动端全屏且不遮挡操作。
6. 对长文本、键盘可访问性、桌面/窄屏/移动端和国际化补测试。

完成标准：BT-UI-01~20 使用真实接口全部通过；浏览器不全量加载十年流水；抽屉关闭后状态不丢失；页面无法把数据阻断误显示为“无信号”。

### 阶段 5：可靠性、迁移和对账（WP1-2/WP1-4/WP1-5/WP1-6/WP1-7，P1，6-10 人日）

目标：任务可恢复、重复投递无副作用、数据和账户守恒、历史记录可解释。

任务：

1. 完成任务幂等键、锁、心跳、取消、断点恢复、correlation_id 和跨库 outbox；对同一任务三次投递、worker 重启、DB 暂不可用、DuckDB 锁冲突做故障注入。
2. 每日对账 DecisionEvidence、订单计划、成交、持仓、现金、费用；任一差异自动告警并暂停新买单，风险退出保留受控路径。
3. 建立旧策略/旧回测迁移报告：不可精确转换的字段必须 `needs_review` 或 `legacy/non_reproducible`，不填默认值；历史运行保持只读。
4. 建立 snapshot 不可变、保留、查询、恢复机制。恢复配置只能创建新绑定/新 snapshot，不能改写历史。
5. 完成外部数据熔断、备用源、脏数据隔离、官方修复批次、日常数据对账和审计事件。

完成标准：故障注入没有重复订单/半保存绑定；所有运行可按 correlation_id 串联；每日守恒对账为零或有自动阻断与可执行恢复动作。

### 阶段 6：验收流水线与上线（G0-G7，持续执行）

1. G0：migration、schema、枚举、错误码、hash、idempotency、版本引用的契约测试全部通过。
2. G1：门禁/PIT/条件树/仓位/成本/证据/分页单测；新增和修改逻辑覆盖率 >= 90%。
3. G2：以迁移后的真实数据库和任务运行模型完成从 FactorSet/模型到回测成交/证据的完整集成，并验证事务回滚。
4. G3：执行真实前后端 Playwright，BT-UI-01~20 100% 通过，保存桌面与移动截图、网络请求和接口响应摘要。
5. G4：执行数据源超时、主备切换、脏数据、财报 PIT、缺口、熔断、成员快照缺失等故障注入并保存审计产物。
6. G5：新旧链路影子双跑至少 10 个交易日，逐证券比较候选、动作、仓位、拒绝原因；全部差异有归因。
7. G6：指定组合灰度一个完整再平衡周期，对订单计划、成交、持仓、现金、证据逐日对账零差异，保留人工停止新买单能力。
8. G7：扩大目标组合，演练监控、告警、回滚和人工停止；获得产品、量化、测试、开发签署。

### 数据库核对 SQL

以下查询用于验收时从快照向决策、证据和成交反向核对（字段名以当前模型为准）：

```sql
-- 1. 快照 -> DecisionRun
SELECT s.id AS snapshot_id, dr.id AS decision_run_id,
       dr.status, dr.trade_date, dr.run_type
FROM strategy_execution_snapshots s
JOIN decision_runs dr ON dr.strategy_snapshot_id = s.id
WHERE s.id = :snapshot_id
ORDER BY dr.trade_date, dr.id;

-- 2. DecisionRun -> Evidence（每个计划必须有唯一证据）
SELECT dr.id AS decision_run_id, de.id AS evidence_id,
       de.symbol_id, de.action, de.trade_date,
       json_extract(de.versions_json, '$.order_plan_id') AS order_plan_id
FROM decision_runs dr
JOIN decision_evidence de ON de.decision_run_id = dr.id
WHERE dr.id = :decision_run_id
ORDER BY de.trade_date, de.symbol_id, de.id;

-- 3. 成交 -> 买入/卖出证据；结果不应出现 NULL 或孤儿外键
SELECT bt.id AS backtest_trade_id, bt.symbol_id,
       bt.decision_evidence_id AS entry_evidence_id,
       bt.exit_evidence_id,
       entry_ev.action AS entry_action,
       exit_ev.action AS exit_action
FROM backtest_trades bt
LEFT JOIN decision_evidence entry_ev ON entry_ev.id = bt.decision_evidence_id
LEFT JOIN decision_evidence exit_ev ON exit_ev.id = bt.exit_evidence_id
WHERE bt.run_id = :backtest_run_id;

-- 4. 孤儿证据/重复计划键
SELECT de.id AS evidence_id
FROM decision_evidence de
LEFT JOIN backtest_trades bt
  ON bt.decision_evidence_id = de.id OR bt.exit_evidence_id = de.id
WHERE de.decision_run_id = :decision_run_id
  AND de.action IN ('BUY', 'SELL')
  AND json_extract(de.versions_json, '$.order_plan_status') = 'FILLED'
  AND bt.id IS NULL;

SELECT json_extract(versions_json, '$.order_plan_id') AS order_plan_id,
       COUNT(*) AS evidence_count
FROM decision_evidence
WHERE decision_run_id = :decision_run_id
GROUP BY json_extract(versions_json, '$.order_plan_id')
HAVING order_plan_id IS NOT NULL AND COUNT(*) <> 1;
```

已知限制：旧历史运行仍可能只有 `DecisionEvidence.versions_json`，无法重建时必须标记为不可复现；新运行已使用独立 `decision_order_plans` 表。自动模拟已先调用统一 `match_order_plan()` 做市场规则判定，再保留既有 `place_sim_order` 作为账户记账兼容层。自动模拟的真实连续双跑、资金顺延和跨入口待单状态仍需在 G5/G6 实际演练中验证；回测侧部分成交拆单已补齐累计数量和同计划重试。
