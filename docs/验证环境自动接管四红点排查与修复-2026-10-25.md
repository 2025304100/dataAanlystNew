## 二、测试中发现的隐藏问题

按严重程度排序。**H1 已修复**，其余为遗留。

### H1（P0，已修复）MySQL 5.7 不支持窗口函数与 NULLS LAST
`fetch_latest_pit_scores` 的 `row_number() OVER (...) + nullslast()` 在 MySQL 5.7 上一执行即 1064。影响面不止本次红点：策略保存应用预检、决策引擎精确 PIT 取分、评分覆盖率估算都走这条路径。此前只跑 SQLite/8.0 语义时被掩盖，切到 5.7 后暴露。诊断时有个迷惑点：报错位置显示在 `(PARTITION BY` 而非 `NULLS`，容易被误判为其他问题；先修 nullslast 后依然 1064 才定位到 5.7 本身不支持窗口函数。

### H2（环境级）东财数据源被 IP 级封禁
`push2his.eastmoney.com` 对本机所有请求 `RemoteDisconnected`（akshare 直连、带 `_proxy_bypass`、换浏览器 UA 均失败，跨标的全部失败；而批量同步进程内的成功均为 uptodate 空转）。10-20~10-23 的行情回退链因此整体降级：东财(有换手率) → 新浪(有换手率) → **腾讯(无换手率字段)**。封禁疑似与高频批量同步有关，恢复时间不可控。

### H3（数据质量）新浪源对 600519 存在"股本变动日期重复"
`parse_sina_history_bundle` 对 `duplicate Sina outstanding_share date` 直接拒绝（严格解析器 fail-closed，设计正确）。后果：600519 的换手率在东财封禁期间**没有任何可用来源**。缺一个"单标的、单字段的数据缺口"可恢复处置路径（现有 `VerifiedBarCorrection` 需要不可变 provider 证据摘要，人工核验成本高）。

### H4（设计缝隙）换手率缺失的行永远无法被增量回补
增量同步起点 = `latest_bar.trade_date + 1`（universe_sync.py:657）。行已存在但 `turnover_rate` 为 NULL 时，增量同步视为"已最新"直接跳过；`range-repair` 端点可回补但**无法按标的过滤**（只有 scopes/sync_limit），对单标的修复要么全量跑要么取前 N。600519 的四天缺口因此无自动通道可补。

### H5（数据一致性）回退源可降级覆盖优质源数据
`_fetch_universe_history` 的多源回退成功即写入，`_upsert_universe_bars` 按行整体覆盖 `payload_fields`。实测：600519 10-19 原有东财源的换手率 0.32，一次腾讯回退源拉取将其覆盖为 NULL（本次排查中亲手复现）。"低质量回退源覆盖优质源字段"缺字段级保护。

### H6（稳定性）因子流水线大窗口 OOM 且带崩后端
window=250 全市场截面计算在 factors 阶段触发 DuckDB `OutOfMemoryException: Allocation failure`，连续两次复现；当时后端 uvicorn 进程一并退出，未完成的 async 任务被标记 interrupted。内存充足（22GB 空闲）时重跑小窗口成功——问题不在数据量本身，而在单次全窗口截面计算无分批/内存上限保护。

### H7（运维防呆）重启即换库
`dev_services.py start` 不读 `DATABASE_URL` 环境变量，按 `config/db_config.json` 连 **gpfx（开发库）**；验证环境必须手动带 `DATABASE_URL=…gpfx_validation` 启动。本次中途一次重启后 readiness 指纹（schedule_id 11→17）立刻暴露连错库，靠 schedule_id 才发现。两个库同名组合、同名任务，极易混淆。

### H8（存量脏数据）门禁生效前的演示模型快照长期顶在门禁上
旧快照（8-19 创建，"验证测试" offline_minimal 模型 + research 模式 + 失效 rule）一直挂到本次才被重新保存应用顶掉。binding_review 的 fail-closed 拦截是设计正常工作，但说明：门禁上线前的存量绑定没有迁移/清理机制，会在面板上以"策略绑定需要更新"的形式长期驻留。

### H9（成员准入）无评分标的可被加入自动模式成员
600519 在 10-24 被加入 auto 成员+候选时无任何评分覆盖校验（新模型评分发布于 10-25），加入即触发数据红色阻断。准入发生在数据可用性验证之前。

## 三、优化与改造意见

### 3.1 代码/守门（防回归）

1. **MySQL 5.7 兼容性进 CI**：新增方言编译断言测试（对关键查询 `str(stmt.compile(dialect=mysql.dialect()))` 断言不含 `OVER (`、`NULLS LAST`），或在 lint 层禁用 `nullslast/row_number().over`。若未来升级 MySQL 8 再放开。
2. **单标的定向回补通道**：`range-repair` 增加 `symbol_ids` 过滤参数；或增量同步对"近 N 日内 turnover_rate IS NULL 的行"做补偿性重拉。这是 600519 类缺口唯一能自动闭合的路。
3. **回退源字段级降级保护**：upsert 时对"低质量源缺失的字段"保留原值（如 MySQL `ON DUPLICATE KEY UPDATE turnover_rate = COALESCE(VALUES(turnover_rate), turnover_rate)`，但需配合 source 标签判断，避免永久卡住脏值）；至少做到"回退源不覆盖优质源已有的非空字段"。

### 3.2 流水线/稳定性

4. **因子截面计算内存保护**：factors 阶段按标的分批（如每批 1000）或给 DuckDB 显式 `memory_limit`；训练任务窗口建议自适应（默认 250，OOM 后自动降窗重试一次），并在任务错误信息里带 `window_days` 提示。
5. **流水线与 Web 进程隔离**：重型 async 任务（训练/镜像）跑在独立 worker 进程，避免 OOM 时把 API 一起带走（本次 uvicorn 直接退出、所有 inflight 任务 interrupted）。

### 3.3 运维/体验

6. **连库防呆**：`dev_services.py` 支持 `-Database validation|dev` 参数（拼好 DATABASE_URL 再拉起）；`/auto-trade/action-items` 响应里附 `database` 指纹，前端"自动接管"面板角落显示当前库名，杜绝连错库排查半天。
7. **覆盖启用时间门文案**：周日撞上 `COVERAGE_NOT_NEWER`（新起点必须晚于旧起点）× `CALENDAR_COVERAGE_INCOMPLETE`（起点必须是今天之后的下一交易日）双重拦截时，直接给用户一句"下一交易日 2026-10-26 收盘后可重新接受新基线"，而不是两条抽象错误码。
8. **成员准入校验前移**：添加 auto 成员/候选时检查该标的近 N 交易日评分覆盖（含换手率等因子输入可用性），不可用则警告或要求确认，避免"加入即红色阻断"。
9. **G7/G6 信息项瘦身**：`G6_GATE_NOT_READY` 单条 info 塞了 10+ 条 blocker 文案，建议按证据维度折叠分组，与四个红点的呈现粒度对齐。

### 3.4 数据源

10. **东财封禁治理**：批量同步对东财源加并发/频率上限与熔断（连续 N 次 RemoteDisconnected 即全局退避到新浪），降低触发 WAF 封禁的概率；封禁期间在数据健康面板显式标注"东财源不可用（疑似 IP 封禁），当前由新浪/腾讯回退"。
11. **600519 恢复路径**：东财解封后执行定向回补（依赖 3.1-2 的通道），重跑评分物化，再将成员 14 恢复 active、候选加回，黄色警告随之消除。
