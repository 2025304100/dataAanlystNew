# vectorbt + numba: root cause FOUND, and it is NOT a version problem -- do not add a
# numba pin here again, that route was measured and closed:
#   Symptom (CI): vectorbt 0.28.5 + numba 0.68.0 + numpy 2.5.4 raised, at runtime,
#     AttributeError: 'function' object has no attribute 'get_call_template'
#     inside numba's own type inference (get_call_type -> self.dispatcher....).
#   Falsified hypotheses (each measured):
#     - pin numba 0.67.0 (newest-oldest that still accepts numpy 2.5): same error.
#       numba <= 0.66 requires numpy < 2.5, which would force a project-wide numpy
#       downgrade -> not acceptable for one research engine.
#     - upgrade to vectorbt 1.0.0 (metadata pandas >=2.0,<3.0, OK for our 2.3.3):
#       same error. 1.1.x needs pandas >=3.0.3 (cross-major migration), out of scope.
#     - "our code misuses numba": app/ has zero numba usage (0 hits).
#   Real cause: VectorBTConfig.disable_numba defaults to True, but it sets
#   NUMBA_DISABLE_JIT via os.environ.setdefault at import time. If numba was already
#   imported, that call is a no-op -- so CI had been exercising the JIT-on path, which
#   is not what the product uses by default. Setting NUMBA_DISABLE_JIT=1 at CI job level
#   (before any import) makes the two whitebox vectorbt cases pass; they are back in the
#   blocking gate (verified on probe branch main_work_vbtjit, run f64b03c4).
# Still open: the CLI opt-in `scripts/backtest_vectorbt.py --enable-numba` (JIT on) is
# broken. It is kept visible by a non-blocking step in the whitebox job instead of being
# hidden. Removing that option, or fixing JIT, would delete that step.

# plotly must be pinned explicitly: it is a TRANSITIVE dependency of vectorbt, so
# an unpinned resolve floats it to the newest major.
# Real breakage seen in CI (whitebox shard 1, two vectorbt backtest cases): newer
# plotly removed `scattermapbox` from plotly.graph_objs.layout.template.Data, while
# vectorbt 0.28.5 still writes that field -> ValueError.
# Why it stayed invisible locally (two layers, worse than plain version drift):
#   1) plotly was not installed in the local venv at all;
#   2) the local venv did not even have vectorbt (despite this file pinning it),
#      so this plotting path had never executed locally -- local env != requirements.
# Only the upper bound is pinned here (<6); no exact lower bound, because locally
# I could not read vectorbt's own metadata to verify what it actually requires.
# Before moving to plotly 6.x, confirm vectorbt supports it. Real verification can
# only come from CI (or locally once vectorbt is installed).
plotly>=5,<6

# Playwright must be pinned to an EXACT version: it is bound 1:1 to the browser
# build it downloads.
# Real breakage seen: pinning only `pytest-playwright>=1.4.0` without pinning
# playwright itself let the venv resolve to 1.62.0 (wants browser build 1234) while
# this machine had build 1223 -- all 38 `-m e2e` cases died with
# "Executable doesn't exist" (see the walkthrough report, section 8).
# Why 1.60.0 rather than 1.62.0: 1.62 needs a fresh ~192MB browser download, which
# measurably kept dropping around 90% (server closed connection) on both the
# Microsoft CDN and the domestic mirror; 1.60.0 matches the already-installed build
# 1223 and only needs a 38MB wheel to run the chromium channel.
# Local and CI now use the same version and the same browser build, so behaviour is
# reproducible. When upgrading playwright, also run:
#   python -m playwright install chromium   (and confirm the download can complete)
#
# The old `pytest-playwright>=1.4.0` line was removed: the code never used it (the
# `page`/`browser` fixtures come from tests/e2e/conftest.py), and e2e passed 34
# cases locally without it installed. Keeping a never-used dependency only makes
# people assume e2e behaviour comes from it.
playwright==1.60.0
