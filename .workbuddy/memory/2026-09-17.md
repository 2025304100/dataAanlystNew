### 🚨 比并发穿透更严重的缺陷：超时回收会丢整个排队队列
原 `expire_stale_locks` 直接 DELETE 锁行，而排队队列存在锁行的 `queue_json` 里
→ 进程崩溃 + 心跳超时回收 = **排队任务永久静默卡死**（不需要并发就能触发，
一次崩溃即可）。已修：对 duckdb_write 走「删行+拉起队首」，并返回被拉起者供通知。
回归哨兵 `test_expire_promotes_queue_instead_of_dropping_it`。

### 并发穿透结果
- `mining_domain`：8 线程同时抢 → **恰好 1 成功**，7 个 MiningDomainBusy 且
  owner 指针全部指向真实持有者
- `duckdb_write`：6 线程 → 1 持有 + 5 排队，位次无重复、无任务丢失、可 drain 干净
- 释放与排队的读写竞态：终态一致、无重复无丢失

### 环境认知（新）
**SQLite 静默忽略 FOR UPDATE** → 测试环境与生产并发语义不同。
`acquire_write_slot` 的队列读改写在 SQLite 下会互相覆盖（生产 MySQL 靠行锁正确）。
修法：临界段补进程内 `_QUEUE_LOCK`。已写进 MEMORY §1.13 / 手册 R24。

### 🔧 订正：`inf` / `1e308` 都写不进 MySQL FLOAT（用户追问后的复核）

用户追问「啥情况」，我没复述结论而是去**真实库实测** —— 结果**发现自己第一版修正也是错的**。

#### 实测矩阵（MySQL 5.7.26；临时表 + 真实列各验一次，真实列用完回滚）
| 值 | MySQL `DOUBLE` | **MySQL `FLOAT`（= 本列真实列型）** | SQLite `REAL` |
|---|---|---|---|
| `float('inf')` | ❌ PyMySQL **客户端**抛 `ProgrammingError` | ❌ 同样 | ✅ |
| `1e308`（**我第一版哨兵**） | ✅ | **❌ DataError 1264 Out of range** | ✅ |
| `3e38`（**新哨兵**） | ✅ | ✅ | ✅ |
| `1e39` | ✅ | ❌ 1264 | ✅ |

#### 真实列端到端（ORM 写入 → 读回 → 清理，残留 0 行）
- `inf` → ❌ `ProgrammingError`
- `1e308` → ❌ `DataError 1264`
- `3e38` / `clamp(1e308)` / `clamp(inf)` → ✅ 读回 `3e+38`
- 完整探针链路三种情形全部落库成功：`passed=1 max_diff=0.0` /
  `passed=0 max_diff=0.001` / `passed=0 max_diff=3e+38`（不可比较）

#### 根因与修正
- 真实列型是 **`float` 单精度 ≈3.4e38**（SQLAlchemy `Float` 无 precision → MySQL `float`），
  不是 DOUBLE。**`Float` ≠ `Double`**。
- 哨兵 `1e308` → **`3e38`**；新增 `clamp_to_float_column` 作为写入前兜底。
- **SQLite 单测对这问题天然放行**（`REAL`=DOUBLE 且无范围检查）→
  「单测全绿」不能证明写入安全。

#### 沉淀
- 铁律 **R34**（范围类约束要按列型核对 + 真实库试探）；跑偏 **#69**；
  **R33 / 跑偏 #67 已订正**（原文教的 `1e308` 是错的）
- MEMORY **§1.25**（实测矩阵 + 三条结论）
- 测试 +8 用例（哨兵 ≤ 单精度上限、1e308 必被夹、inf/NaN 不上列、
  `test_reported_sqlite_does_not_enforce_range` 把「盲区」写成可执行断言）→ **57 passed**
