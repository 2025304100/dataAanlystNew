## 更正：日线数据不缺，是镜像范围问题（重要）

- **MySQL `universe_daily_bars`（基础数据隔离层）有 2016-07-12 ~ 2026-09-07 共 10 年、1154 万行、7270 标的**，按年分布完整（2016年24万行/2827标的 → 2025年161万行/6907标的）。
- MySQL 老表 `daily_bars` 仅 2025-06-05~2026-08-27、142 万行、5969 标的。
- DuckDB `raw_daily_bars` 仅 2025-01-13~2026-09-07、217 万行，其中 98.9%（214.9 万行）来自 `universe_daily_bars` 源，仅 2.4 万行来自老表。
- **根因**：`app/services/factors/bar_mirror.py` 本就支持 universe 源（`UNIVERSE_SOURCE_KEY="sql.universe_daily_bars"`）且 `_mirror_universe_bars(start_date, end_date)` 可指定任意区间；但 `warehouse_watermarks` 显示镜像起点最早只到 2025-01-12，从未同步 2016~2024。`universe_sync.DEFAULT_HISTORY_DAYS=365`，`main._auto_start_universe_init` 也只传 365 天。
- **修复**：本地 MySQL → DuckDB 历史镜像即可（纯本地 I/O，无需 AkShare 重采）。建议 2021-01-01 起取 5 年（标的 5072~7270）；全量则 2016-07-12 起（注意 2016~2018 仅 2827~3399 标的）。磁盘剩余 169GB 充足。
- 镜像内容仅 OHLCV + turnover_rate，**仍无 prev_close** → ATR 仍需用 `ref(close,1)`。
